# Plan review

This procedure governs main's orchestration. Analyst's role definition governs review criteria and its READY/REVISE report.

Resolve the active review mode from task/session choices, then the installed policy; default off. Explicit plan-review requests apply in either mode. In auto, review before material security-boundary changes, data migrations, irreversible operations or complex cross-module changes. Routine edits do not trigger review merely because several files change. Main decides whether a trigger applies, so in auto, before implementing work that plausibly matches one, state in the reply whether review is triggered, with a one-line reason; a skipped review is then a visible decision rather than a silent one.

1. Identify the logical plan and recover its prior call count, verdicts and blockers from the task and any active handoff. When neither the conversation nor an active handoff records a prior call, the count starts at zero. Establish the state before another automatic call only when the available evidence conflicts, for example a handoff mentions a review whose verdict or count is missing. Mode changes, new sessions, renamed plans, different reviewers/models or cosmetic splits do not reset the count or clear blockers.
2. Supply a stable plan with outcome, scope/exclusions, ownership, dependencies, acceptance checks and relevant rollback. Use analyst, under its installed native name, in fresh native context. If fresh context is unavailable, report the limitation and keep the required review blocked.
3. Allow at most two automatic calls total per logical plan, including failed or interrupted calls. Count each attempted review. Missing verdicts and protocol failures never imply READY.
4. On REVISE, disposition every material blocker as FIX, revising the plan, or REJECT with concrete evidence: a reproduction, a source citation or the requirement text, never preference. Send the second review the prior findings with each disposition and its closure or rejection evidence. It may uphold a rejection; an upheld blocker can be rejected again only with new evidence. Never resubmit an unchanged plan unless every remaining blocker carries rejection evidence. Style preferences and optional improvements are non-blocking.
5. With READY, continue work already authorized without another routine confirmation. READY grants no new authority. While required review remains unresolved, stop dependent implementation; gather evidence or continue independent authorized work.
6. After two calls without READY, stop automatic submission. Further review requires an explicit user request. Preserve plan identity, count, verdicts and unresolved blockers in the task and any existing active handoff; do not create a handoff solely for bookkeeping.

Once the reviewed plan is implemented, follow [outcome verification](outcome-verification.md) before reporting it complete. Follow cc-feather:auto-on or cc-feather:auto-off for mode changes. Turning review off does not erase an unresolved verdict or manufacture approval.
