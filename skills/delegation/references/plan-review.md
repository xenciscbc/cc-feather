# Plan review

This procedure governs main's orchestration. Analyst's role definition governs review criteria and its READY/REVISE report.

Resolve the active review mode in this order: a task/session choice, then project guidance, then user guidance. Project guidance that states automatic plan review is off in this project makes it off even while user-scope guidance states it is on. Otherwise the mode is auto while the delegation guidance states that automatic plan review is on, and off when it does not. Explicit plan-review requests apply in either mode.

In auto, plan-driven work gets the full review flow: plan review before implementation, then [code review](code-review.md), then [outcome verification](outcome-verification.md). A plan is an implementation basis with stated scope and acceptance criteria that the user agreed to: a plan file, spec, ticket, plan-mode plan, or a plan proposed in conversation and approved by the user. Telling main to implement a given plan or ticket is that agreement. A document without scope or acceptance is not yet a plan: complete it and confirm the completed version with the user before treating the work as plan-driven. A plan lists its claims, each an independently verifiable outcome with its own acceptance; a plan that lists none is one claim. Unplanned work that changes a security boundary, migrates data or performs an irreversible operation must not start without one: main writes the plan, gets it reviewed, then presents the reviewed plan and waits for the user's explicit approval before implementing. Main never approves such a plan itself. Other unplanned edits get no automatic review; the user requests review when wanted. Before implementing in auto, state in the reply whether the work is plan-driven and therefore reviewed, with a one-line reason; a skipped review is then a visible decision rather than a silent one.

1. Identify the logical plan and recover its prior call count, verdicts and blockers from this session's task. Counts are per session: a resumed session starts a new count, since resuming requires the user. If the in-session state is unknown, establish it before another automatic call. Within a session, mode changes, renamed plans, different reviewers/models or cosmetic splits do not reset the count or clear blockers. An unresolved verdict restricts a resumed session only when an active handoff records it; it then applies until a later review passes it or the user decides. Code review and outcome verification apply this step to their own per-claim counts.
2. Supply a stable plan with outcome, scope/exclusions, claims with their acceptance, ownership, dependencies and relevant rollback. Use analyst, under its installed native name, in fresh native context. If fresh context is unavailable, report the limitation and keep the required review blocked.
3. Allow at most two automatic calls total per logical plan, including failed or interrupted calls. Count each attempted review. Missing verdicts and protocol failures never imply READY.
4. On REVISE, disposition every material blocker as FIX, revising the plan, or REJECT with concrete evidence: a reproduction, a source citation or the requirement text, never preference. Send the second review the prior findings with each disposition and its closure or rejection evidence. It may uphold a rejection; an upheld blocker can be rejected again only with new evidence. Never resubmit an unchanged plan unless every remaining blocker carries rejection evidence. Style preferences and optional improvements are non-blocking.
5. With READY, continue work already authorized without another routine confirmation. READY grants no new authority. A revision that stays within the user's approved outcome, scope and acceptance needs no new approval; one that materially changes any of them needs the user's approval again. The same applies when implementation deviates from the plan: a material deviation stops dependent work for another review of the revised plan, within this plan's existing two-call count, and the user's approval. When no automatic call remains, report the deviation and keep dependent work stopped; another review then needs an explicit user request, as in step 6. While required review remains unresolved, stop dependent implementation; gather evidence or continue independent authorized work.
6. After two calls without READY, stop automatic submission. Further review requires an explicit user request. Preserve plan identity, count, verdicts and unresolved blockers in the task. When a handoff is active, record the unresolved verdict and what it blocks as plain text in the record; do not create a handoff solely for bookkeeping. Once the plan is resolved, because a later call passes it or the user decides, remove that note; deferred findings become separate work items or are listed in the completion report.

In auto, once the reviewed plan is implemented, follow [code review](code-review.md) and then [outcome verification](outcome-verification.md) before reporting it complete. In off, run code review or verification only on an explicit request; you may offer it. Follow [the toggle procedure](../../setup/references/auto-review.md) for mode changes. Turning review off does not erase an unresolved verdict or manufacture approval.
