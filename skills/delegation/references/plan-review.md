# Plan review

This procedure governs main's orchestration. Analyst's role definition governs review criteria and its READY/REVISE report. The state each review step keeps is named in [review state](review-state.md).

Resolve the active review mode in this order: a task/session choice, then project guidance, then user guidance. Project guidance that states automatic plan review is off in this project makes it off even while user-scope guidance states it is on. Otherwise the mode is auto while the delegation guidance states that automatic plan review is on, and off when it does not. Explicit plan-review requests apply in either mode. Explicit calls do not count toward the automatic budget below.

In auto, plan-driven work gets the full review flow: plan review before implementation, then [code review](code-review.md), then [outcome verification](outcome-verification.md). A plan is an implementation basis with stated scope and acceptance criteria that the user agreed to: a plan file, spec, ticket, plan-mode plan, or a plan proposed in conversation and approved by the user. Telling main to implement a given plan or ticket is that agreement. A document without scope or acceptance is not yet a plan: complete it and confirm the completed version with the user before treating the work as plan-driven. A plan lists its claims, each an independently verifiable outcome with its own acceptance; a plan that lists none is one claim. The plan is what the user names. A spec, or a set of its tickets, makes the spec with those tickets the plan: each unfinished ticket in the named scope is one claim, and its `Blocked by` lines are the dependencies. A single named ticket is the plan, with its spec supplied as context to plan review, code review and outcome verification. A ticket that belongs to no spec is its own plan. When every ticket in the named scope is finished, report that nothing is left to implement. The named-plan rule applies only when no plan in this session already covers the named work; otherwise that plan continues with no new plan review and keeps its count, verdicts and blockers, and a new plan that partly overlaps one inherits its unresolved verdicts and blockers for the overlapping tickets, and, where that plan had stopped, its count and stop for them as [review state](review-state.md) describes. In a resumed session, an unresolved verdict that an active handoff records for a spec's plan applies to that spec's tickets when they are named. Recognise a spec's tickets by an explicit link such as a `Spec:` line or parent reference, a shared feature directory, or the user naming them; ask when none or several plans match, and state the tickets used. Look first at the project's instructions, such as CLAUDE.md or AGENTS.md, and any file they point to, for where tickets live. Without such a note, search for them: a repository-wide content search can skip files that version control ignores, and often hidden directories too, so an empty result is not evidence that none exist; pass likely directories to the search explicitly, list them directly, or search with both ignored and hidden files included. If a spec's tickets still cannot be found, a spec that lists its own claims keeps that list without asking. Unless the spec lists its own claims, when it refers to its own tickets or claims that cannot be found, ask the user before plan review or implementation whether to point to them or treat the spec as one claim; a spec that refers to none is one claim without asking. A spec that lists claims and also has tickets must agree with all of them, finished or not; report a mismatch as a blocker for the user to settle. Main does not edit a spec or ticket to add claims. Where specs live and whether tickets are committed are the project's choice; use what this session has. Unplanned work that changes a security boundary, migrates data or performs an irreversible operation must not start without one: main writes the plan, gets it reviewed, then presents the reviewed plan and waits for the user's explicit approval before implementing. Main never approves such a plan itself. Other unplanned edits get no automatic review; the user requests review when wanted. Before implementing in auto, state in the reply whether the work is plan-driven and therefore reviewed, with a one-line reason; a skipped review is then a visible decision rather than a silent one.

1. Identify the logical plan and recover its current count, verdicts and blockers from this session's task. Counts are per session: a resumed session starts a new count, since resuming requires the user. If the in-session state is unknown and cannot be established, treat the step as stopped and ask the user, as [review state](review-state.md) describes; never assume a count of zero. Within a session, mode changes, renamed plans, different reviewers/models or cosmetic splits do not reset the count or clear blockers. An unresolved verdict restricts a resumed session only when an active handoff records it; it then applies until a later review passes it or the user decides. Code review and outcome verification apply this step to their own per-claim counts.
2. Supply a stable plan with outcome, scope/exclusions, claims with their acceptance, ownership, dependencies and relevant rollback. Use analyst, under its installed native name, in fresh native context. If fresh context is unavailable, report the limitation and keep the required review blocked.
3. Count consecutive automatic calls without a pass, per logical plan. Count each attempted review: failed, interrupted and protocol-failure calls count, and missing verdicts and protocol failures never imply READY. An automatic READY resets the count to zero; an explicit call's verdict does not change it. Two consecutive automatic calls without READY stop automatic submission (step 6).
4. On REVISE, disposition every material blocker as FIX, revising the plan, or REJECT with concrete evidence: a reproduction, a source citation or the requirement text, never preference. Send the next review the prior findings with each disposition and its closure or rejection evidence. It may uphold a rejection; an upheld blocker can be rejected again only with new evidence. Never resubmit an unchanged plan unless every remaining blocker carries rejection evidence. Style preferences and optional improvements are non-blocking.
5. With READY, continue work already authorized without another routine confirmation. READY grants no new authority. A revision that stays within the user's approved outcome, scope and acceptance needs no new approval; one that materially changes any of them needs the user's approval again. The same applies when implementation deviates from the plan: a material deviation stops dependent work for another review of the revised plan, counted from the reset of the last automatic READY, and the user's approval. When two consecutive automatic calls without READY have already stopped submission, report the deviation and keep dependent work stopped; another review then needs an explicit user request, as in step 6. While required review remains unresolved, stop dependent implementation; gather evidence or continue independent authorized work.
6. After two consecutive automatic calls without READY, stop automatic submission. Further review requires an explicit user request, and an explicit call is outside the count; an explicit READY clears the stop and lets work continue, as [review state](review-state.md) describes. Preserve plan identity, count, verdicts and unresolved blockers in the task. When a handoff is active, record the unresolved verdict and what it blocks as plain text in the record; do not create a handoff solely for bookkeeping. Once the plan is resolved, because a later call passes it or the user decides, remove that note; deferred findings become separate work items or are listed in the completion report.

In auto, once the reviewed plan is implemented, follow [code review](code-review.md) and then [outcome verification](outcome-verification.md) before reporting it complete. In off, run code review or verification only on an explicit request; you may offer it. Follow [the toggle procedure](../../setup/references/auto-review.md) for mode changes. Turning review off does not erase an unresolved verdict or manufacture approval.
