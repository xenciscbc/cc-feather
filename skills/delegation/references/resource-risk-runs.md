# Resource-risk runs

This reference governs main's side of running tests and probes within resource limits. The verifier, adversary, executor and security-executor definitions each carry the role's own floor; this reference states main's approval of a Resource-risk claim's Execution method, what main gives those roles, main's own floor and the Observed resource risk record. It adds to [review state](review-state.md)'s Execution and never replaces it: nothing here, an approved Execution method included, allows a run that Execution does not, lifts a restriction the user stated, or makes the Runner an isolated environment the user named. Before any decision or brief of this reference that depends on a rule review state owns, in off and in auto, main reads [review state](review-state.md) in full; review state's Reading it says when an earlier full read still serves.

## Execution method

Plan review marks a Resource-risk claim and proposes an Execution method for its risky part, as analyst's role definition states.

- **Approving it.** Before the first brief of a Resource-risk claim for a role that may execute code, and before main's own first run for it, main reviews the proposed Execution method and approves it, changes it, or asks the user. An approved Execution method names the experiment for the risky part, its bounds, the memory and time limits, that it runs inside the Runner, and the source of the budget.
- **The budget.** The budget comes, in order, from the user's own statement in this session, the Plan's execution conditions, the project's resource guidance, then the user's resource guidance; guidance may state a default budget. When the needed budget exceeds that default or no source states one, main asks the user. cc-feather states no numbers.
- **What it is bound to.** An approved Execution method is bound to its Claim, the Claim's recorded reading set, the experiment it describes, its budget and the budget's source. It stops being valid when the Claim's reading set changes, when the Plan gets a new plan review, or when its record is missing or does not match what it was recorded for; main then approves it again before the Claim's next run, asking the user where the budget's source requires it.
- **Where it is kept.** Main records each approval where an Observed resource risk is kept, as that section's Where it is kept states, and never writes it into the Claim's text.
- **Carrying the conditions.** A Claim's execution conditions are its approved Execution method and its Observed resource risks. Main carries them verbatim into every brief of a role that may execute code for the Claim: its implementation, outcome verification and Adversarial review, reopened calls and later sessions included. Main applies them to its own runs for the Claim, such as reruns, reproductions and the final check's rerun of its primary acceptance.
- **Conditions and Execution.** A review's run, and main's own run, needs both the Execution determination [review state](review-state.md)'s Execution describes and the Claim's execution conditions. For an implementation by executor or security-executor, which get no Execution determination, the execution conditions add limits to what the Assignment allows and add no Execution determination.
- **When the Runner refuses.** When the Runner refuses a run of a Resource-risk claim, the Claim stops for the user to decide: provide a tool that meets the Runner's contract, or accept that Claim's run without a hard limit in their own words. Main does not run the risky part another way meanwhile.
- **After an INCONCLUSIVE about the method.** When a role reports the approved Execution method insufficient or wrong, main either approves the role's proposed method, or another, and dispatches a new, fresh, normally counted call, asking the user where the new budget requires it; or keeps the method only together with new evidence or a changed condition that addresses the named gap. Without either, the Claim is reported unverified and the user decides. A call stopped by a limit closes as a completed call without a pass; a larger budget means a new call. A newly approved method is the changed prerequisite a call after INCONCLUSIVE needs: read the [outcome-verification procedure](outcome-verification.md)'s step 5, or for an Adversarial review the [Adversarial review procedure](adversarial-review.md)'s step 5, and follow it. Counting, the Stop threshold and what counts as a call are unchanged.

## The Runner

The Runner is cc-feather's launcher for one command with a memory limit for its whole process tree, a time limit and an output limit. Resolve it relative to this loaded skill: `scripts/runner.py`. When installed as a plugin, its path is `${CLAUDE_PLUGIN_ROOT}/skills/delegation/scripts/runner.py`; use the actual loaded skill directory if the variable is unavailable. It is invoked as `python -B <skill>/scripts/runner.py --memory-mib N --time-seconds S --output-bytes B --cwd DIR -- COMMAND ...`, with the target command as plain arguments after the separator; its usage text states every option. It prints one JSON result whose `outcome` is passed, target-failed, contained (with `limit_event` memory or time), refused (with `refusal_reason`) or evidence-missing, and it exits 0 only for passed.

- **In the brief.** When a brief is for a role that may execute code and the role may run part of its work inside the Runner, main gives in it the resolved Runner path and the memory, time and output limits to run with.
- **Its boundary.** Only processes inside the Runner's containment are limited. Work handed to an already running service, such as a daemon, a container runtime, WSL, a build server, a database or a remote service, and tools that execute code outside the shell, such as an MCP server, are outside it. Two runs started at the same time each check available memory on their own, so their total is not limited; that is a known limitation of this release. The Runner refuses to start when containment is not available, when an enclosing limit would make its own limits unreliable, or when available memory is below the memory limit.
- **Permissions.** A Runner invocation goes through the host's normal permission handling like any other command, and cc-feather adds no permission rule. Because the target command is plain text in the invocation, whatever decides the permission sees what will run. cc-feather advises against a permission rule that allows every Runner invocation, because such a rule allows any command through the Runner. A rule written for the target alone no longer matches once the target is wrapped in the Runner.

## Main's floor

The floor follows execution, not authorship: it covers a new or modified test or probe whoever wrote it. It binds main when main runs a test or probe a role returned and when main reproduces a failure a role reported.

- **What is unbounded.** A test or probe is an Unbounded probe when any part of it, the input generator, the code under test, a reference implementation or control, callbacks, measurement, output collection and descendant processes, has no established bound on total work or retained data, or when the peak memory and time that the bound allows do not fit the run's budget or, without one, the project's resource guidance. An unknown bound counts as none; a bounded input size, a bounded outer loop or a timeout alone is not a bound; a check the Plan lists that is changed counts as modified. Main does not run a test or probe it cannot judge against a budget: it takes the budget, and asks the user when no source states one, as Execution method's The budget states.
- **A returned probe.** Main runs a returned Unbounded probe only after redesigning it so that every part is bounded within the budget, or inside the Runner with the budget's limits. It never runs it as it is and never with a timeout alone: a timeout limits time, not memory.
- **A Resource-risk claim.** Main's own runs for a Resource-risk claim use the Runner, with the limits of its approved Execution method.
- **Judging the run.** Main never raises a limit and reruns. A run the Runner reports as contained, timed out or refused, or whose evidence is missing, is inconclusive evidence judged from the Runner's result, not from the target's exit code; a non-zero exit with no limit event is a failure, and results established independently of that run stand.

## Observed resource risk

- **Recording it.** When a role's report names a probe it returned or a run a limit stopped, or a run of main's own stops on a limit, main records an Observed resource risk on that Claim. It names the run and its test or probe, the reason, how it was handled (returned, redesigned, run within a budget, stopped by a limit), the budget and any peak the Runner observed. The record does not assume that plan review missed the risk: a probe invented during execution, or a run in off, had no plan review to miss it.
- **Where it is kept.** In auto, main keeps it in the Plan's dispatch record, as [review state](review-state.md)'s Dispatch record describes; in off, in the Active handoff when one exists, and otherwise in the session's state. It is never written into the Claim's text: writing it into the Plan or a ticket needs the user's agreement.
- **Telling the user.** Main tells the user about it in its next reply.
- **Carrying it.** It is one of the Claim's execution conditions, carried into every later brief of that Claim and applied to main's own runs for it as Execution method's Carrying the conditions states. It stays until the Plan ends.
- **At the end of the Plan.** Main lists every Observed resource risk of the Plan in the decision or completion report at the end of the Plan.
