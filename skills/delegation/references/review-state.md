# Review state

Plan review, code review, outcome verification and Adversarial review keep the same kind of state for each step. This file names it once; [plan review](plan-review.md), [code review](code-review.md), [outcome verification](outcome-verification.md) and [adversarial review](adversarial-review.md) state how their own step changes it. It also states, under Completion criteria, what a claim's reviews judge it against and where the findings that do not hold completion go.

| State | Meaning |
| --- | --- |
| Work identity | What the step judges: the logical plan for plan review, one claim for code review, for outcome verification and for Adversarial review, identified as in [plan review](plan-review.md). |
| Reviewed content | What a call actually judged: the plan text supplied, or the claim's change from its base revision and the acceptance checks supplied. For a claim the acceptance gate covers, that change is the commit named in the brief, judged with a clean workspace, as What a gated pass judged describes. |
| Call source | Automatic, when the call belongs to the automatic flow, including a call the user requests for a step the flow is due to run or, in a step whose stop was cleared, a later call that step needs; explicit, when the user asks for a step that has stopped or a review outside the flow. Explicit calls are outside the automatic budget. |
| Consecutive non-pass count | Automatic calls in a row that did not pass, including failed, interrupted and protocol-failure calls. A count that reaches the Stop threshold in effect stops the step. |
| Valid verdict | The last pass for the work, READY, APPROVED, CONFIRMED or, for a Security-critical claim's Adversarial review, HELD, while it stays valid as described under Validity and completion. |
| Blockers | Unresolved findings and verdicts, with what each one blocks. |

State lives in the current session's task. Counts are per session; an unresolved verdict reaches a resumed session only through an active handoff record. Each procedure's step 1 or step 3 says how to recover this state before another automatic call.

## Stop threshold

The Stop threshold, written K in formulas, is the number of consecutive automatic calls without a pass that stops a step: one integer from 2 to 10 that applies to plan review, code review, outcome verification and Adversarial review alike.

- **Resolution.** The Stop threshold in effect is, in order: the user's task choice, for that task; otherwise the user's session choice; otherwise the value the loaded project guidance states; otherwise the value the loaded user guidance states; otherwise 2. Main never raises or lowers the Stop threshold on its own; a task or session choice comes only from the user's own words in this conversation. A guidance value that is not an integer from 2 to 10 is not used: main takes the next source and reports the invalid value.
- **Unknown threshold.** When main cannot establish whether a task or session choice exists, for example after context compaction, it treats the Stop threshold as unknown, as Unknown state does for counts: affected steps are treated as stopped and main asks the user. A step whose count is below 2 is not affected, since no Stop threshold is lower.
- **Stating it.** Whenever a review decision comes up, main states the Stop threshold in effect and its source (task, session, project, user or default), as it does for the Review mode. A session choice does not cross sessions and is not written into a handoff; a resumed session resolves the Stop threshold again from its loaded guidance.
- **Changing it.** A change of the Stop threshold never changes a count; Next automatic call is applied with the new value at once. A stopped step whose count is now below the new value resumes automatically, because the change is the user's own act. A step whose count reaches or exceeds the new value stops at once, which means only that its next automatic call now needs the user's request under Next automatic call: a step an explicit pass had cleared stays cleared, and a call the user then requests is classified as Clearing a stop describes. Main lists the steps the change resumed or stopped in its reply.
- **Saved in this conversation.** A value the user saves in project or user scope in this conversation replaces any earlier task or session choice in this conversation, and the Stop threshold in effect is resolved again from the saved values in the order of Resolution, so this session uses what a new session would. A user value saved where the project states its own is reported as overridden by it. This is the reverse of the Review mode, whose saved change keeps a separate task or session override.
- **Not counted.** The security analysis before plan review is not a counted step, and the Stop threshold does not apply to it. The final check before landing or release, as Validity and completion's Final check describes, is not a counted step either.

## Transitions

- **Stop.** As many consecutive automatic calls without a pass as the Stop threshold in effect stop the step for that work; it waits for the user's explicit request.
- **Next automatic call.** A step's next automatic call for a work needs the user's explicit request exactly while that step's count for the work is at or above the Stop threshold in effect, and is made without one while it is below. This one rule decides it after an explicit pass that cleared a stop, for a reopened call, for a review after a material deviation, for the review of a fix and for work that inherits an overlapping plan's count and stop.
- **Clearing a stop.** An explicit call that passes clears the stop and leaves the count unchanged, and in auto the automatic flow continues to the next step. A later automatic call in the same step for the same work, such as a reopened review or the review of a fix, follows Next automatic call: while the count is at or above the Stop threshold in effect it needs the user's explicit request; that requested call is still an automatic call of the flow, so a pass resets the count and a non-pass stops the step again. An explicit HELD obtained before the claim's valid APPROVED and CONFIRMED does not clear a stop, since it does not count as the step's pass.
- **What an explicit call runs.** An explicit call runs only the requested step; what follows a stop it cleared is the automatic flow resuming, not part of the request. An explicit review or verification made before the automatic flow reached that step does not count as that step's pass. This rule on early explicit calls holds in off as well as in auto: in either mode, an explicit Adversarial review made before the claim's valid APPROVED and CONFIRMED does not count as the step's pass.
- **Classifying a request.** In auto, when the user asks for a review, the call is automatic if the flow is due to run that step for that work, and explicit if the step has stopped or the request is outside the flow. State the classification before dispatching. For implemented work whose plan has no plan-review state in this session, Implemented before plan review below comes first.
- **What counts as a call.** Every attempted call counts, including a generic retry after a temporary failure, and a stopped step is never dispatched again as a retry. A missing role or fresh context found before dispatch is a precondition failure, not a call.
- **Completed calls and coverage.** A completed call is one that returned a verdict for the content it judged; a call that failed, was interrupted, broke protocol or returned no verdict did not complete. Only a completed review establishes coverage. The exception is a call whose pass main does not use after its comparison of the workspace, as Serial within a working tree describes: it counts as a call without a pass, establishes no coverage and resets no count, and the next call for the claim reviews its full scope from its base revision. A second review, narrowed to the earlier findings and the fixes, and the range from the previously judged commit follow only when the previous call completed. The code review after an INCONCLUSIVE covers every gap that call named, even though that call completed: a narrowed follow-up never closes a gap it did not examine, and no APPROVED is given while a named gap is unexamined. After a call that did not complete, the next call reviews the claim's full scope from its base revision (for plan review, the whole plan), carrying any partial findings as evidence, not as coverage. Every attempted call still counts as under What counts as a call, and the budgets are unchanged.
- **Unknown state.** When the count, verdicts or blockers cannot be established in this session, for example after context compaction, which does not start a new session, treat the step as stopped and ask the user. State the current count with each review result.
- **Overlap.** Work that overlaps a stopped plan keeps that plan's count and stop, and its next automatic call follows Next automatic call, so it gains no new automatic calls while that count is at or above the Stop threshold in effect: an automatic READY of the widened plan does not clear the inherited stop for the overlapping work, while an explicit pass covering it does. The first review of the new plan receives the inherited findings with their dispositions. Independent new work is counted on its own, and counts of different plans are not added.

## Completion criteria

- **Completion conditions.** A claim's reviews judge it against these conditions: its acceptance as written is met; existing behaviour is not broken, shown by a failing test or a reproduction; it introduces no security problem and no data loss, as Security findings below describes; and it has no deviation from the plan. A Blocking finding is a finding that shows one of these conditions unmet; every other finding is a Non-blocking finding. The criteria apply in both review modes and to every user; there is no setting that changes them. Plan review checks a plan before these reviews, and the Adversarial review procedure and its BROKEN are unchanged.
- **Evidence for a regression.** A regression that is only inferred and is neither a security problem nor data loss does not block: such a regression blocks only when a failing test or a reproduction shows it. The existing behaviour a regression breaks, and any written rule or shipped spec acceptance it is judged against, are taken at the claim's base revision, never from the reviewed commit, so a change cannot redefine what it must not break. Every brief of the claim's code review, outcome verification and Adversarial review, a narrowed follow-up's included, names the claim's base revision, which main establishes itself from Git in this session.
- **Security findings.** A security problem the change introduced or made exploitable, through a new route, permission or data flow even when the vulnerable code is outside the diff, and data loss the change introduced, are Blocking findings whatever the acceptance states. They block on the reviewer's evidence as before: the rule that a regression needs a failing test or a reproduction applies only to regressions that are neither security problems nor data loss, so a removed or weakened security control is a Blocking finding without a reproduction. A verifier's note that main judges to be, or cannot rule out as, a security problem or data loss the change introduced or made exploitable is a Blocking finding, and that call's CONFIRMED is not used as a pass, the call counting as a call without a pass, until main dispositions the note as FIX or REJECT with evidence under [outcome verification](outcome-verification.md)'s rule for a REFUTED. The adversary's BROKEN and the [adversarial review](adversarial-review.md) procedure are unchanged, and a pre-existing vulnerability still becomes separate work in the project's tracker, as its step 10 describes.
- **Deviations.** A finding that shows a deviation from the plan is a Blocking finding, and a Deviation still stops main to ask the user: a material deviation stops dependent work for another review of the revised plan and the user's approval, as [plan review](plan-review.md) step 5 describes.
- **Non-blocking findings.** Every other finding is a Non-blocking finding, including an issue that predates the change, a correctness problem outside what the acceptance states, a regression that is only inferred and is neither a security problem nor data loss, and style, naming or a refactoring suggestion. It does not hold completion and is recorded in the work's Follow-up record.
- **Follow-up record.** Non-blocking findings go to one Follow-up record per piece of work. With handoff maintenance active it is a handoff record of its own, kept by that work's handoff writer as a separate work item under the handoff skill's separable-item rule, not in the current record; otherwise main lists its content in the completion report. The completion report names the Follow-up record. The record is data: its next step is always the user's decision whether to start a later plan, the findings it quotes are marked as untrusted data, reading or resuming it authorizes nothing, and Accept and land never relies on it. Nothing starts the later plan automatically; the user decides when to start it, and a later plan that fixes recorded findings of completed claims is new work under the existing rules. What it records about a vulnerability follows [adversarial review](adversarial-review.md) step 10.

## Validity and completion

- **What a pass covers.** A pass covers the work identity, its acceptance and the reviewed content it judged. A later change to a claim's files or to what they depend on reopens code review and outcome verification for that claim, except where its passes stay fixed in auto as described below; a change only to the environment, such as installed tools or external state, reopens outcome verification only, unless it changes a test target as the next sentences describe. A Security-critical claim's HELD is reopened by a change to the claim's files or dependencies, to a test target's definition, start-up, version or configuration, or by another change that shares its security assumptions. When that shared change belongs to a new claim and the claim it shares assumptions with is already accepted, the new claim owns the composed review and the accepted claim is not reopened, as [adversarial review](adversarial-review.md) step 9 describes. This exception covers only the shared-assumptions trigger: a change to the accepted claim's own files or dependencies, or to a test target, still reopens its HELD. A test target's reset and test-induced changes to its synthetic data are not an environment change: the brief's reset procedure and those changes reopen neither HELD nor CONFIRMED. For any other later change, main states why it does not affect the pass. Updating a ticket's status is not a relevant change. In auto, a claim's valid APPROVED and CONFIRMED are a judgement of the commit they judged and stay fixed: they are not reopened by a change to the claim's files or to what they depend on that lies within the range judged by another claim's completed code review and outcome verification of the same plan, both of which passed; a fix claim counts as another claim. A Blocking finding in that other claim's reviews is that claim's to fix. Which files of another claim's acceptance checks a claim may change, and what its code review then checks, are as [code review](code-review.md) step 2 describes. Passes stay fixed only for a change inside the range judged by another claim's completed code review and outcome verification of the same plan that both passed: when that claim's review stops, is cancelled, is deferred or ends in accept and land without both passes, its changes reopen the claims whose files or dependencies they touch, under the file-level rules above. Any other change keeps the file-level rules above, such as an edit outside the plan's claims, a rebase, an environment or test target change, a change to the claim's reading set, or a change whose claim ends without both passes. Fixed passes do not change what reopens a Security-critical claim's HELD. Fixed passes hold in auto only: in off, a later change to a claim's files or to what they depend on reopens its code review and outcome verification under the file-level rules above, whichever claim made it. When automatic review is turned off for a plan before the user's decision at the end of the plan, as Accept and land at the end of the plan describes, every fixed pass whose claim's files or dependencies another claim changed after it is reopened under the file-level rules above, and the cross-session rules of off apply from then on, as Resumed sessions describes. Fixed passes have limits this flow does not check: a later claim's reviewer reads only its own reading set and may not know an earlier claim's design intent, and a property of an earlier claim that no acceptance check the final check runs covers can be broken without the final check noticing. A plan's READY is reopened by a material deviation, as [plan review](plan-review.md) step 5 describes.
- **Reading set.** A claim's reading set is what its implementation and every review of it read: the text the claim is written in and the parts of a spec it cites, an Out of Scope line that limits what the claim may change included, and, only for a claim a spec lists, the spec's parts that state they hold for every claim; no other part of a spec is supplied, and the whole spec only when the spec itself is the claim, except for a ticket of a spec implemented or reviewed without a READY for its plan in this session, as described below. For a claim of a plan that is neither a spec nor tickets of a spec, such as a plan file, a plan-mode plan or a conversation plan with several claims, the text the claim is written in is the whole plan: the whole plan is supplied to the claim's implementation and every review of it, as before cc-feather 0.23.0, and main records and compares it, with any part of a spec the claim cites, as the claim's reading set, so a change to another claim's part of that plan is a change to the reading set. Citations are as [plan review](plan-review.md) defines them, and a `Spec:` line, a parent reference or a shared directory brings in no part of a spec. A Security-critical claim's security invariants and test targets are those written in the claim's own text, which for a claim of a plan that is neither a spec nor tickets of a spec is its own part of that plan, the parts it cites and, for a claim a spec or other plan lists, the parts stated to hold for every claim; a claim of such a plan takes no other claim's invariants or targets from the rest of that plan. When plan review returns READY, main records each claim's reading set, by content or by hash; when no READY was given for the claim in this session, as in off mode, after a waived plan review or for an explicit call, main records it at the claim's first dispatch in this session. When a ticket of a spec is implemented or reviewed without a READY for its plan in this session, as in off mode, after a waived plan review or for an explicit call, the checklist has not passed, so its implementation and every review of it read the whole spec as context, as before cc-feather 0.23.0, and main records and compares the ticket and the whole spec as its reading set, while its security invariants and test targets stay those named above. Before dispatching the claim's implementation or any of its reviews, main confirms that the reading set is unchanged, and the briefs use only the recorded reading set, except as [adversarial review](adversarial-review.md) step 2 adds for a claim that owns a composed review. In auto, a code review brief also carries another claim's acceptance where [code review](code-review.md) step 2 adds it for a claim that changes that claim's acceptance checks. The status and note main writes under Ticket status are not a change to the reading set. A change the user did not authorise is a material deviation, as [plan review](plan-review.md) step 5 describes; after a change the user authorises, main records the changed reading set before the claim's next dispatch.
- **Reopened calls.** A reopened call continues the step's count from where it stands, which is zero after an automatic pass and unchanged after an explicit pass that cleared a stop. It follows Next automatic call: a reopened automatic call needs the user's explicit request exactly while that count is at or above the Stop threshold in effect.
- **Commit and completion.** For a claim of plan-driven work in the automatic flow, and for any claim an active handoff records as unreviewed, unverified or pending acceptance, main lands the claim on the remote default branch (by pushing it there or merging it, directly or through a pull request), releases or tags it, reports it complete or sets its ticket to a done value only with a valid APPROVED and a valid CONFIRMED, and for a Security-critical claim a valid HELD as well, or with the user's accept-and-land decision for it. This is the acceptance gate. It covers the completion value for done work; a value for work that will not be done is set only on the user's recorded cancellation and never counts as acceptance. Landing a branch lands every claim on it, so it waits for every gated claim there. Landing and release that the acceptance gate covers also wait for the final check, as Final check below describes. A cancelled claim's commits that remain on a branch are listed as unaccepted, in the report and in any active handoff, until the user decides their disposition: reverted with a new commit, kept off the default branch, or accepted and landed; landing a branch that carries them waits for that decision. The default branch is the branch the `origin` remote's HEAD names, or the only remote's HEAD when there is no `origin`; with no remote, several remotes and no `origin`, or no HEAD, main asks. A protected or shared branch the user names counts as a default branch.
- **Commits before the passes.** Before its passes, main may commit a claim of plan-driven work in the automatic flow on any branch, push it to a branch main created for the current work and open a pull request whose description lists the claims still unaccepted, without the user's permission, and keeps that list current as claims pass or are accepted. Before pushing to a remote branch that already existed and that main did not create, it asks the user; in a resumed session main treats a branch as its own only when an active handoff records that main created it for this work, and otherwise asks. For a claim the gate covers only because an active handoff records it, main may make the local commit a gated call needs without asking, while pushes and pull requests follow off-mode behaviour, so main asks. Before dispatching a gated code review, outcome verification or Adversarial review, main ensures the claim's content is committed and the precondition of What a gated pass judged holds; when a commit is needed, the authority above permits it without asking, and an already suitable commit needs no new one. It never rewrites pushed history, so a fix is a new commit. On a default branch, main labels each commit made before its claim's passes (both passes, plus HELD for a Security-critical claim) unaccepted in its message when it creates it; the label records the commit's state then and stays in history. Commits on other branches carry no label. It pushes such commits to the remote default branch only after both passes, plus a valid HELD for a Security-critical claim, or the user's accept-and-land decision for their claim, or as a work-in-progress push the user explicitly allows, and while they stay unpushed it says a reclaimed environment would lose them. Off mode otherwise keeps its behaviour. Before each `git add`, commit or push this authority allows, main meets [repository safety](repository-safety.md)'s Before add, commit, tag or push.
- **Repository authority.** The authority under Commits before the passes covers committing, pushing and opening pull requests only. Opening a pull request is not permission to merge it, and a pass is a condition for landing or release, not a request to perform either: landing, merging, releasing and tagging need the user's authority for that operation. Every commit, tag and push, and every `git add` before a commit, also meets [repository safety](repository-safety.md)'s Before add, commit, tag or push, which adds a condition to this authority and grants none. An explicit user instruction not to commit or not to push overrides this authority within its scope; when it leaves a gated call without the commit it needs, main reports the claim blocked rather than reviewing an uncommitted workspace.
- **What a gated pass judged.** For a claim the acceptance gate covers, main dispatches a code review, outcome verification or Adversarial review only when the workspace equals the commit it names in the brief: HEAD is that commit, nothing the claim's files or acceptance checks depend on has an uncommitted or untracked change, and nothing changes the workspace during the call. An Adversarial review that can count as the step's pass also needs a valid APPROVED and a valid CONFIRMED at that same commit, so it follows them, as [adversarial review](adversarial-review.md) describes; an explicit one the user requests before them runs but does not count. The pass covers that commit, and a second review after a completed review receives the range from the previously judged commit to the new one, as Completed calls and coverage describes. A call for work the gate does not cover, such as an explicit review of unplanned edits or of work in off that no active handoff restricts, judges the workspace change from the base revision, except that an Adversarial review run through [the adversarial-review command](../../adversarial-review/SKILL.md) reviews the range that command defines, and main does not commit that work to review it.
- **Per-claim timing.** In auto, each claim of plan-driven work gets its code review and then its outcome verification once that claim is implemented and committed, not once the whole plan is implemented. This is the only review timing in auto: no setting or plan statement selects another. A plan with a single claim is unchanged. Implementation and reviews in one working tree stay serial as Serial within a working tree states, so a claim with no dependency still waits for a review call running in the same working tree. Which claim starts next follows Dependent claims.
- **Dependent claims.** In auto, a claim that lists another under `Blocked by`, or otherwise depends on it as its plan states, starts only after that claim has a valid APPROVED and a valid CONFIRMED. A claim with no such dependency does not wait for other claims' passes. Where a plan states no dependencies between its claims, main follows the plan's order and treats each claim as depending on those before it. When a claim's code review or outcome verification stops, its outcome verification cannot be resolved, it has a Deviation, or it would need accept and land, every claim that depends on it stops and main asks the user. The user may decide that named dependent claims proceed: main records it under User decisions as a deferral of the upstream claim whose scope names the dependent claims allowed to start, and only those start. The upstream claim stays a Pending-acceptance claim until its passes become valid or the user decides on it at the end of the plan, as Accept and land at the end of the plan describes.
- **Serial within a working tree.** Within one working tree, reviews and implementation are serial. While a code review, outcome verification or Adversarial review call runs, main does not change the working tree it judges, and nothing main started writes to it; implementation in that working tree waits until the call ends. This includes main's own handoff records inside the project, which main updates only between calls. Before dispatching a code review, outcome verification or Adversarial review call, main confirms that no Assignment or background process it started that may write the working tree is still running. At most one gated call that executes code runs in a working tree at a time. When main's comparison of the workspace after a call, under [repository safety](repository-safety.md)'s Main's preparation, finds a change to a file the claim depends on, its own files and what its acceptance checks depend on included, that call's pass is not used. Such a call counts as a call without a pass, establishes no coverage and resets no count, and the next call for the claim reviews its full scope from its base revision, as Completed calls and coverage describes. Main does not create a worktree for a review on its own. Work the user runs in separate worktrees may proceed in parallel, each worktree its own workspace and serial in itself. The worktree exception extends no trust: each worktree still gets [repository safety](repository-safety.md)'s preparation and checks. Shared test resources stay governed by each brief's target start and reset.
- **Final check.** Before landing or release, main runs the plan's overall acceptance checks, such as the full test suite, at the commit to be landed or tagged, within [repository safety](repository-safety.md)'s Execution rules. It is main's own run, not a review step: it is not a counted step and adds no verdict. It runs only when the workspace equals the commit to be landed or tagged, established as for a gated pass under What a gated pass judged, so an untracked or changed file cannot take part in it. It runs again whenever the commit to be landed changes, after a fix or any other commit. After it runs, main compares the workspace as after a review call, under [repository safety](repository-safety.md)'s Main's preparation; a change to a tracked file or a file the check depends on makes that run a failed run, with the change as its output. Landing and release that the acceptance gate covers wait until the final check passes at the commit to be landed; otherwise only an accept-and-land decision that states its actual state lets them proceed, as Accept and land at the end of the plan describes. When Execution does not allow it, it is recorded as not run, and main states that it has not run before landing and in any accept-and-land decision. Once it has failed at a commit, that commit's state is failed, and a later pass at the same commit lets landing proceed only through an accept-and-land decision that names the failure. Its state comes only from main's own run in this session at that commit, never passed from a record or an earlier session, and after a context compaction main runs it again. When main cannot establish from this session that the commit has not failed, it treats the commit as failed, and a decision states that state as "failed (presumed: not established as unfailed in this session)", with the reason and this session's outputs. A record can only make the state failed, never passed. A failure reopens the claims it affects under the existing rules, and its output goes with it to the reopened claims' reviews as evidence; landing and release wait for their passes again. A failure that cannot be attributed with evidence reopens every claim the check covers. For a landing or release the acceptance gate does not cover, main runs the final check when Execution allows, reports its state before landing, and waits for the user's instruction given after that report.
- **Existing handoff notes.** An active handoff's record that a claim is unreviewed, unverified or pending acceptance restricts it under the acceptance gate whatever its wording, such as "must not be committed"; main updates the wording at the next handoff maintenance.
- **Pending acceptance.** A gated claim stays gated after either single pass, and a Security-critical claim after both until it also has a valid HELD. When a pass resolves an active handoff's unreviewed or unverified note for a gated claim, main replaces it with a note that the claim is pending acceptance, naming what is still missing and that it must not be landed on the default branch, released or reported complete. When Adversarial review stops, or a BROKEN is unresolved, main records a pending-acceptance note naming the missing Adversarial review and its open findings whether or not an earlier note existed, as [adversarial review](adversarial-review.md) describes. An accept-and-land decision does not remove the note: main records the decision in it, turning an unreviewed or unverified note into a pending-acceptance note, and the note then counts as the record that keeps the claim under the gate until it is landed. Main removes the note only when the claim is landed, released or reported complete, or cancelled with its commits disposed of; a deferral keeps it and a waiver stays visible in it. When a relevant change ends an accept-and-land decision, the note returns to pending acceptance, naming what is missing. A resumed session that finds a pending-acceptance note keeps the claim under the gate and obtains passes from the current session, as passing verdicts do not cross sessions, unless the note records an accept-and-land decision that still holds or the claim's ticket is exempt as under Resumed sessions.
- **Postconditions.** An acceptance item that can exist only after an authorised operation, such as a release tag after its commit, is a postcondition: outcome verification covers the rest of the claim before the operation, and main checks and reports it after the operation. A postcondition that does not hold leaves the claim incomplete and its ticket unfinished, with the observed state noted.

## Ticket status and user decisions

- **Ticket status.** After a claim has passed (both passes, plus HELD for a Security-critical claim) and is committed, and any postcondition holds, main sets its ticket's status to the completion value the project's tracker convention defines for done work, with a note naming the version or commit; after an accept-and-land decision it does the same, and the note also names the decision and its remaining risk. Without a defined value, main reports which tickets it considers done and leaves their status alone. A ticket is finished when its status equals one of the completion values that convention defines, such as one for work that will not be done, or the user says it is done; without a defined value, main asks. Finished means not redone, not accepted: only a ticket set to a done value after valid passes or an accept-and-land decision counts as accepted for landing and release, and only while no relevant change has reopened its claim. A value for work that will not be done never counts as acceptance.
- **User decisions.** Where a procedure waits for the user to decide, main records the decision as one of re-review, deferral, cancellation, changed acceptance, waiver or accept and land, with its scope. Re-review is another call, classified as above. Deferral keeps the work, its blockers and any handoff note waiting. A deferral of a stopped upstream claim names in its scope the dependent claims allowed to start, as Dependent claims describes. Cancellation drops the work and its open findings from the plan without reverting changes already made; its commits left on a branch stay listed until the user decides their disposition, as under Commit and completion. Changed acceptance replaces the claim's acceptance and reopens its review and verification, and for a Security-critical claim its HELD as well, as under Validity and completion. A waiver accepts a named open finding or missing pass and names what it waives; a missing READY can be waived as Implemented before plan review describes. It stays visible with its remaining risk in the report and in any active handoff, and is never recorded as READY, APPROVED, CONFIRMED or HELD. A waiver does not complete a claim the acceptance gate covers: such a claim is landed on the default branch, released or reported complete only after a later pass or an accept-and-land decision. For a claim an active handoff recorded as unreviewed, unverified or pending acceptance, a waiver kept in that handoff counts as that record for the gate. Separately, a work-in-progress push the user allows may move a gated claim's commits to the default branch, labelled as under Commits before the passes; it satisfies neither release nor completion. Accept and land is the user's explicit acceptance of a named gated claim without one or both passes or, for a Security-critical claim, without a valid HELD. It may also name a gated claim whose passes are complete when the final check at the commit to be landed failed or was not run, and it then states the final check's state at that commit, as Final check describes. Main records its scope, the commit it accepts, the missing passes and the remaining risk; it stays visible in the report and in any active handoff, is never recorded as READY, APPROVED, CONFIRMED or HELD, and satisfies the acceptance gate for that claim as it stands. Main asks for it, and builds what it names, as Accept and land at the end of the plan describes. When it covers a missing HELD, main names for each commit it accepts the missing Adversarial review, the known vulnerabilities and the remaining risk. A later relevant change to the claim ends it, as for a pass. Unlike a pass, it is the user's decision, so one recorded in an active handoff still satisfies the gate in a resumed session while no relevant change has followed the commit it names. A user statement that work is done counts as acceptance only after main confirms it with the user and records it as accept and land; otherwise it means the work is not to be redone. Saying "continue" or turning auto off does not accept a known defect.
- **Accept and land at the end of the plan.** One accept-and-land decision may name several claims, including a gated claim whose passes are complete when the final check at the commit to be landed failed or was not run. For each claim it names, it states the commit it accepts, the missing passes, the known vulnerabilities and the remaining risk, and the decision states the final check's state at the commit to be landed: passed, failed with its output, or not run, as Final check describes. Main asks for the decision once, after every claim of the plan has finished its reviews and the final check has run or is recorded as not run, before landing or release; it does not ask after each claim. Until then a claim that needs the decision stays under the acceptance gate as it stands, and its ticket stays unfinished. Main asks earlier only when the user asks to land a claim earlier. Landing a claim before the end of the plan lands every claim on that branch, so main's list then covers every gated claim on the branch, and the decision states the final check's actual state at that commit; main runs it whenever Execution allows, and records it as not run only when Execution does not. Main builds the list from the review results it received in this session, not by reading a record in the working tree, such as a handoff, a ticket or the Follow-up record, and reports any difference between the list and such a record. Each missing pass names the step and the call that left it missing, or that the step has not run. Known vulnerabilities appear as the reporting role stated them, never merged or downgraded; what main writes of them in a public or possibly public record follows [adversarial review](adversarial-review.md) step 10. Where main cannot establish a claim's verdicts or missing passes in this session, for example after context compaction, Unknown state applies: main stops and asks the user. The user may confirm part of the list by whole claims, and the rest stays pending, under the acceptance gate as it stands; a claim is accepted only with everything listed for it. Saying "continue", silence or turning automatic review off is not a confirmation. The decision covers only what was listed: the claims, their commits, their missing passes and their known vulnerabilities, and main records it for each claim as User decisions describes. A Blocking finding or known vulnerability reported after the decision is not covered, and it holds landing until it is resolved or a new decision names it. The final-check part of the decision covers only the commit and the output it states. Accept and land never relies on the Follow-up record, as Follow-up record describes.

## Resumed sessions and plan changes

- **Resumed sessions.** Counts and passing verdicts do not cross sessions. In auto, a resumed session reviews an unfinished plan again before implementing it; in either mode it does not redo tickets that are finished. In either mode, an unresolved verdict that an active handoff records for a spec's plan restricts that spec's tickets when they are named, and one recorded for a ticket's plan still restricts that ticket when the whole spec is named; without an active handoff record, no restriction carries into a resumed session. Before a gated operation, a claim needs valid passes from this session, so a claim that passed in an earlier session is reviewed and verified again, and a Security-critical claim gets Adversarial review again, counted as usual. Only a claim whose ticket was set to a done value after valid passes or an accept-and-land decision, with no relevant change since, is exempt and counts as accepted for landing and release, as is a claim whose pending-acceptance note records an accept-and-land decision that still holds; any other finished ticket is only not redone. For a plan with an implemented claim, Implemented before plan review comes first.
- **Implemented before plan review.** In auto, when the user asks for review, or the flow reaches review, for a plan that is implemented in part or whole and has no plan-review state in this session (no automatic plan-review call and no recorded user decision on its plan review), main asks before any call. This covers work implemented in another session, outside Claude, or in this session while review was off. An explicit READY given before the flow reached plan review is not plan-review state; main names it. Main states the case, names any record it found of an earlier plan review, such as a handoff, ticket comment or validation entry, without treating it as a pass, and asks the user to choose:
  - plan review first: an automatic call of the flow covering the whole plan, with the implemented claims and their changes as context; a REVISE then follows [plan review](plan-review.md) steps 4 and 5, and changes needed in implemented claims are fixes that go through code review;
  - straight to code review: recorded as a waiver of the missing READY for the implemented claims, with its scope, visible in the report and in any active handoff.
  Main dispatches neither call until the user answers. A waiver of the missing READY does not waive security analysis: before code review of an implemented Security-critical claim, main runs its security analysis and dispositions the findings as [plan review](plan-review.md) describes, or the user explicitly waives them, and main records either, with its scope, in the report and in any active handoff. Security invariants added this way change the claim's acceptance and need the user's approval, as a material revision does. Claims of the plan not yet implemented still get plan review before they are implemented. A plan whose plan review ran in this session, including one that stopped, was cleared by an explicit READY or was decided by the user, follows the rules above, and main does not ask again. When plan-review state cannot be established, Unknown state applies, and work overlapping a stopped plan keeps the Overlap rule.
- **Claim changes.** When a REVISE blocker needs claims added, split or changed, main reports it and the user or the planning step decides. Main edits a spec or ticket for it only after the user authorises it, keeping a mapping from old claims to new ones and the unresolved blockers each carries. Main also updates a ticket's status when the user asks, such as setting a value for work that will not be done after a cancellation.
- **Deviation scope.** For a plan that is tickets of a spec, a single named ticket included, the review of the revised plan after a material deviation, as [plan review](plan-review.md) step 5 describes, covers the changed tickets and the tickets they block, and also every ticket that shares a file, a trust boundary or a security invariant with a changed ticket. It runs the spec checklist again only when the change touches the spec's stated outcome, scope, decisions or invariants; a change that stops the tickets covering the spec's outcome touches the spec's outcome, so the checklist, its coverage part included, runs again as [plan review](plan-review.md) describes. Every plan review over tickets of a spec, a narrowed one included, still checks that each of the spec's security invariants is cited by at least one of its tickets, as [plan review](plan-review.md) describes. When main judges that a change does not touch the spec's stated outcome, scope, decisions or invariants, it states why in the plan-review brief and in its report; the brief still supplies the spec, and analyst may require the checklist, which then runs before the revised plan can be READY. A change to a claim's recorded reading set that the user did not authorise is a material deviation, as Reading set describes, and that claim's ticket counts as a changed ticket. A deviation that adds or changes a security control or invariant reopens security analysis under its existing triggers, as [plan review](plan-review.md) describes, before the narrowed plan review, and that plan review also runs the checklist's citation part over all of the plan's tickets. The narrowing follows Completed calls and coverage: the review is narrowed only when the plan's previous plan-review call completed, and after a call that did not complete, the next call reviews the whole plan. The count, the Stop threshold and the user's approval of the revised plan are as [plan review](plan-review.md) step 5 describes.
- **Spec updates.** Once tickets are cut, they govern implementation. After an agreed change to the spec's stated outcome, scope, decisions or invariants, such as one a deviation or a claim change brings, main updates the spec with the user's authorisation, so that later checklist checks and other sessions read the agreed version. An agreed change to a spec part a claim cites, or to a part the spec states holds for every claim, reopens the READY, APPROVED, CONFIRMED and HELD of every claim that cites or reads it, as a change to its acceptance does under User decisions, and main records each such claim's changed reading set before its next dispatch, as Reading set describes.
- **Conversation plans.** In a new session, a plan-mode or conversation plan is identified only from its original text, an available record of it or a version the user confirms; main does not reconstruct it from memory.
