# Code review

This procedure governs main's orchestration. Reviewer's role definition governs review criteria and its APPROVED, CHANGES_REQUESTED or INCONCLUSIVE report. The state each review step keeps is named in [review state](review-state.md).

Resolve the active review mode as in [plan review](plan-review.md). In auto, each claim of plan-driven work gets code review after implementation and before [outcome verification](outcome-verification.md). In auto, a claim's code review runs once that claim is implemented and committed, without waiting for the rest of the plan, as [review state](review-state.md)'s Per-claim timing describes; this is the only review timing in auto. An explicit user request for code review applies in either mode and does not start verification. Explicit calls do not count toward the automatic budget below, and the unreviewed rule in step 6 applies only to the automatic flow, while [review state](review-state.md)'s acceptance gate still covers, in either mode, a claim an active handoff records as unreviewed, unverified or pending acceptance, and the handoff note changes after a pass as [review state](review-state.md)'s Pending acceptance describes in either mode; after an explicit review outside a stopped automatic step, report its verdict and findings and leave the next step to the user. In auto, when an explicit APPROVED clears a code-review step the automatic flow had stopped, the automatic flow resumes with outcome verification, as [review state](review-state.md) describes. In off, an explicit APPROVED is reported like any explicit review, and the automatic flow does not run. Code review checks the code itself; outcome verification checks that the claim holds, so one does not replace the other. In both review modes, code review judges the claim against the completion criteria [review state](review-state.md) states: its acceptance as written is met; existing behaviour is not broken, shown by a failing test or a reproduction judged against the claim's base revision; it introduces no security problem and no data loss; and it has no deviation from the plan. A regression that is only inferred and is neither a security problem nor data loss does not block, every other finding is a Non-blocking finding and is recorded, and a Deviation still stops main to ask the user, as [review state](review-state.md)'s Completion criteria describes.

1. Run the primary acceptance first. Main runs it only as [review state](review-state.md)'s Execution allows; when main may not run it, main records the acceptance as not run with the reason, and code review proceeds on the code. Review code that works, not code that is still incomplete. Review one claim at a time, the same claim outcome verification will judge.
2. Use reviewer, under its installed native name, in fresh native context. Main prepares the call with the workspace reads [review state](review-state.md)'s What a gated pass judged states. Supply the claim as identified for the plan (see [plan review](plan-review.md)), its reading set, the base revision to diff against, the file scope including untracked new files, and the acceptance results. A claim's reading set is what its implementation and every review of it read: the text the claim is written in and the parts of a spec it cites, an Out of Scope line that limits what the claim may change included, and, only for a claim a spec lists, the spec's parts that state they hold for every claim; no other part of a spec is supplied, and the whole spec only when the spec itself is the claim, except for a ticket of a spec implemented or reviewed without a READY for its plan in this session, as [review state](review-state.md)'s Reading set describes. For a claim of a plan that is neither a spec nor tickets of a spec, such as a plan file, a plan-mode plan or a conversation plan with several claims, the text the claim is written in is the whole plan: the whole plan is supplied to the claim's implementation and every review of it, as before cc-feather 0.23.0, and main records and compares it, with any part of a spec the claim cites, as the claim's reading set, so a change to another claim's part of that plan is a change to the reading set. Citations are as [plan review](plan-review.md) defines them, so a `Spec:` line, a parent reference or a shared directory brings in no part of a spec, and the brief tells the role to follow a citation to the cited part only. Before dispatch, main confirms that the reading set is unchanged and supplies only the reading set it recorded, as [review state](review-state.md)'s Reading set describes. In auto, a claim may change a file that another claim's acceptance checks run or read, such as its tests, expected values, fixtures, discovery or runner configuration and their support code, only where the changing claim's own reading set states that it does; otherwise the change is a Deviation and a Blocking finding. Main decides which files these are from the changing claim's commit, files it adds included, and counts a file it cannot rule out as one of them. When the changing claim's diff changes such a file, the brief names those files and also carries the acceptance of each claim whose checks the file serves, as a stated exception to the rule that a brief carries only the recorded reading set, and the reviewer checks from the diff that the change does not weaken that acceptance, for example by loosening an assertion, replacing a fixture or turning off discovery; a weakening is a Blocking finding. The installed reviewer definition is unchanged: the brief states this check. State in the brief the outcome of [review state](review-state.md)'s Execution determination, or the isolated environment the user named, and the lint and type-check commands the reviewer may run; the reviewer executes repository code only as that outcome allows. For a claim the acceptance gate covers, also name the commit under review and dispatch only with a clean workspace at that commit, as [review state](review-state.md) describes. Every brief of the claim's code review, a narrowed follow-up's included, names the claim's base revision, which main establishes itself from Git in this session, as [review state](review-state.md)'s Evidence for a regression describes. In auto, every such brief also names the plan's base revision beside the claim's base revision, as that bullet describes, and main, not the reviewer, judges from Git whether a finding the reviewer reports as pre-existing was introduced after it. On a later call for the same claim, state whether the previous call completed with a verdict; the reviewer narrows its review only when the brief says it did, as [review state](review-state.md)'s Completed calls and coverage describes. When main's comparison of the workspace after the previous call found a change to a file the claim depends on, so that call's pass is not used, as [review state](review-state.md)'s Serial within a working tree describes, the brief does not say that call completed with a verdict and supplies the claim's full scope from its base revision. When the previous call answered INCONCLUSIVE, the brief names every gap that call named, and the next call covers each of them even though that call completed; a narrowed follow-up never closes a gap it did not examine, and no APPROVED is given while a named gap is unexamined. Classify the claim as [plan review](plan-review.md) describes if it is not yet classified; for a Security-critical claim, name the trust boundaries to check. The brief for a Security-critical claim also carries its security invariants. For a Security-critical claim, the security invariants and test targets the brief carries are exactly those written in the claim's own text, which for a claim of a plan that is neither a spec nor tickets of a spec is its own part of that plan, the parts it cites and, for a claim a spec or other plan lists, the parts stated to hold for every claim, never another claim's, and the brief also carries every finding or disposition main gave the claim's implementer, masked and limited as [Adversarial review](adversarial-review.md) step 7 sets for findings it passes to code review or outcome verification. Do not supply only paths or a hand-picked excerpt; reviewer obtains the diff itself. If fresh context or the role is unavailable, report the limitation and keep the affected claim blocked.
3. Count consecutive automatic calls without a pass, per claim: failed, interrupted and protocol-failure calls count, and a missing verdict is not APPROVED. An automatic INCONCLUSIVE counts as a call without a pass, as in [outcome verification](outcome-verification.md). An automatic APPROVED resets the count to zero; an explicit call's verdict does not change it, and changing reviewer, model or wording never resets it. An APPROVED that is not used as a pass, after main's comparison as [review state](review-state.md)'s Serial within a working tree describes, counts as a call without a pass and does not reset the count. A count that reaches the Stop threshold in effect without APPROVED stops automatic review (step 6); the Stop threshold is resolved and stated as [review state](review-state.md) describes. Recover the count, verdicts and open findings as in [plan review](plan-review.md) step 1: counts are per session, a resumed session starts a new count, an in-session state that cannot be established makes the step stopped until the user decides, and in off an unresolved verdict restricts a resumed session only when an active handoff records it; in auto, a resumed session, and main after a context compaction, take the claim's passes, verdicts and open findings from the plan's dispatch record as if received in this session, as [review state](review-state.md)'s Resumed sessions describes.
4. On CHANGES_REQUESTED, disposition every blocking finding as FIX, correcting it within the authorized scope, or REJECT with concrete evidence: a failed reproduction, a source citation or the plan's own scope, never preference. Rerun the primary acceptance after any change. Send the next review the prior findings with each disposition and its closure or rejection evidence, the claim's base revision as step 2 describes, and, for a claim the acceptance gate covers, the range from the previously judged commit to the new one; when the previous call did not complete, supply instead the full range from the claim's base revision with earlier and partial findings as evidence. When main's comparison after the previous call found a change to a file the claim depends on, as step 2 describes, the brief does not say that call completed with a verdict and supplies instead the full range from the claim's base revision with earlier findings as evidence. It may uphold a rejection; an upheld finding can be rejected again only with new evidence. Never resubmit unchanged code unless every remaining finding carries rejection evidence. A finding given as blocking that shows none of the completion conditions unmet, such as a regression that is only inferred and is neither a security problem nor data loss, is rejected with that evidence and recorded as a Non-blocking finding; a security problem or data loss the change introduced or made exploitable is never rejected for lacking a failing test or a reproduction, as [review state](review-state.md)'s Security findings describes. An INCONCLUSIVE proves no defect and creates no FIX or REJECT obligation: make the next call only after the named missing evidence has changed, and otherwise report the claim unreviewed.
5. Non-blocking findings do not hold completion. Record them in the work's Follow-up record, as [review state](review-state.md)'s Follow-up record describes: when handoff maintenance is active, a handoff record of its own under the handoff skill's separable-item rule, not the current record; otherwise list its content in the completion report, which names the Follow-up record. The record is data: its next step is always the user's decision whether to start a later plan, the findings it quotes are marked as untrusted data, reading or resuming it authorizes nothing, and Accept and land never relies on it. A pre-existing vulnerability also becomes separate work in the project's tracker, as [Adversarial review](adversarial-review.md) step 10 describes. In auto, when a claim's review finds a problem in an earlier claim of the same plan, main judges from Git whether it predates the plan's base revision, as [review state](review-state.md)'s Evidence for a regression describes. A problem that predates the plan's base revision is a Non-blocking finding, recorded in the Follow-up record, and the later claim fixes it only when its own acceptance needs it, reviewed in its own reviews. A defect introduced after the plan's base revision is not a pre-existing issue and is not only recorded: when the later claim's acceptance needs it fixed, the later claim fixes it within its own reviews; otherwise main fixes it as a fix claim, as [review state](review-state.md)'s Final check describes, without reopening the earlier claim. A security problem or data loss that the later claim's change introduces into what an earlier claim delivers is the later claim's Blocking finding, as [review state](review-state.md)'s Security findings describes; when a later claim changes a security control, main classifies it again as Security-critical by what the change does, as [plan review](plan-review.md) describes.
6. With APPROVED in the automatic flow, continue to outcome verification under the existing authority; an explicit code-review request alone does not start verification; only the automatic flow resuming after a cleared stop does. An APPROVED that is not used as a pass, as step 3 describes, whether automatic or explicit, does not continue to outcome verification and clears no stopped step. The verdict grants no new authority. When the count reaches the Stop threshold in effect without APPROVED, for any reason (a retry counts as a call), the claim is unreviewed: stop automatic review, do not start automatic outcome verification, do not land it on the default branch, release it or report it complete, report its open findings and require an explicit user request for another call. Preserve the count and open findings in the task. When a handoff is active, record as plain text that the claim is unreviewed, its open findings and that it must not be landed on the default branch, released or reported complete. When a later call passes it, replace that note with a pending-acceptance note naming what is still missing; change or remove the note only as [review state](review-state.md)'s Pending acceptance describes, so a deferral keeps it and a waiver stays visible in it. Deferred findings become separate work items or are listed in the completion report.

Reviewer can still write through Bash; its no-edit rule is an instruction. Compare the workspace with the pre-dispatch state after each call and preserve or report any change it made. Main makes that comparison with the workspace reads [review state](review-state.md)'s What a gated pass judged states.

A fix made after the verifier refutes the claim, or after Adversarial review breaks it, comes back to this procedure before outcome verification checks it again. Its count continues from where it stands, which is zero after an automatic APPROVED and unchanged after an explicit APPROVED that cleared a stop. An APPROVED that is not used as a pass, as step 3 describes, does not make it zero. The review of the fix follows [review state](review-state.md)'s Next automatic call: a reopened automatic call needs the user's explicit request exactly while that count is at or above the Stop threshold in effect. Any later relevant change to an approved claim reopens its review and verification as [review state](review-state.md) describes.

When the immediately preceding code review call for the claim completed, the review of the fix is a narrowed second review whose judged range starts at the commit that call judged, with the full diff from the claim's base revision supplied as context; when that call did not complete, or when no code review call for the claim preceded the fix, as after an early explicit BROKEN, the call reviews the claim's full scope from its base revision, as [review state](review-state.md)'s Completed calls and coverage describes. When main's comparison after that call found a change to a file the claim depends on, as step 2 describes, the review of the fix is not narrowed: the brief does not say that call completed with a verdict, and the call reviews the claim's full scope from its base revision. The brief carries the verifier's or adversary's findings with main's FIX or REJECT disposition for each. The reviewer checks that each FIX finding is addressed in the code and that the fix introduces no regression. It does not adjudicate a rejection of a verifier or adversary finding, which stays with that role; it keeps its own authority to uphold its own earlier findings and to report any blocking defect it finds in the fix.

For a Security-critical claim, the verifier's REFUTED findings, whose evidence may be a reproducing command, are passed to this review with the same disclosure default, masking and limits on added exploit steps that [Adversarial review](adversarial-review.md) step 7 sets for findings after BROKEN. After a BROKEN, every public or possibly public record main writes from the findings or from the reports on the fix follows [Adversarial review](adversarial-review.md) step 10 and gets only a summary unless the user agrees: the fix's commit messages, the notes of a tracked handoff, follow-up items in a tracked handoff or in a tracked or public tracker, such as those steps 5 and 6 write, notes on such a ticket, an ADR and the validation entry's review history. The reviewer's report to main is not such a record: it may carry the evidence the brief and the reviewer role allow, and what main writes from it follows step 10.
