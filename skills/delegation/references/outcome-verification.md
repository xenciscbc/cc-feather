# Outcome verification

This procedure governs main's orchestration. Verifier's role definition governs how it checks a claim and reports CONFIRMED, REFUTED or INCONCLUSIVE. The state each review step keeps is named in [review state](review-state.md). Before any decision or brief of this procedure that depends on a rule review state owns, in off and in auto, main reads [review state](review-state.md) in full; review state's Reading it says when an earlier full read still serves; a scout or Explore lookup needs no such read.

Resolve the active review mode as in [plan review](plan-review.md). In auto, a claim gets outcome verification after its [code review](code-review.md), as [review state](review-state.md)'s Per-claim timing describes. For when a Security-critical claim's Adversarial review follows, read the [Adversarial review procedure](adversarial-review.md)'s step 1 and At the final commit and follow them. Whether a request runs outcome verification, in either mode, is as [review state](review-state.md)'s What an explicit call runs describes. Explicit calls are outside the count below. In auto, an explicit verification made before the automatic flow reached verification counts as [review state](review-state.md)'s What an explicit call runs describes. An explicit CONFIRMED clears a stopped verification step as [review state](review-state.md)'s Clearing a stop describes. Plan review checks the plan before work starts, code review checks the code, outcome verification checks the result and Adversarial review tries to break a Security-critical claim, so none replaces another. In both review modes, outcome verification judges the claim against [review state](review-state.md)'s Completion criteria.

1. Verify at the smallest integration boundary where the whole claim can be refuted, after main has run the primary acceptance itself. Main runs the primary acceptance only as [review state](review-state.md)'s Execution allows; when main may not run it, main records the acceptance as not run with the reason and still dispatches the verifier, whose brief says the acceptance was not run, so the verifier reports what needs execution INCONCLUSIVE and the call counts as for any INCONCLUSIVE. Tests and builds are evidence for the verifier, not a substitute for it. An acceptance item that exists only after an authorised operation, such as a tag after its commit, is a postcondition: verify the rest before the operation, and main checks and reports it after the operation.
2. Use verifier, under its installed native name, in fresh native context. Main prepares the call with the workspace reads [review state](review-state.md)'s What a gated pass judged states. Supply the exact claim as identified for the plan (see [plan review](plan-review.md)) with the claim's acceptance checks, its reading set, the relevant diff or paths and the commands main ran. Main supplies the recorded reading set as [review state](review-state.md)'s Reading set describes. Citations are as plan review defines them: read the [plan-review procedure](plan-review.md)'s definition of a citation and follow it, and the brief tells the role to follow a citation to the cited part only. State in the brief the outcome of [review state](review-state.md)'s Execution determination, or the isolated environment the user named; the verifier executes repository code only as that outcome allows. The brief for a Security-critical claim also carries its security invariants. For a Security-critical claim, the security invariants and test targets the brief carries are exactly the claim's own, never another claim's, as [review state](review-state.md)'s Reading set describes, and the brief also carries every finding or disposition main gave the claim's implementer, masked and limited as the Adversarial review procedure's step 7 sets for findings it passes to code review or outcome verification: read the [Adversarial review procedure](adversarial-review.md)'s step 7 and follow it. For a claim the acceptance gate covers, also name the base revision and the commit under verification, and dispatch as [review state](review-state.md)'s What a gated pass judged describes. Every brief of the claim's outcome verification, a recheck's included, names the claim's base revision, as [review state](review-state.md)'s Evidence for a regression describes. In auto, every such brief also names the plan's base revision beside the claim's base revision, as that bullet describes. On a later call for the same claim, state whether the previous call for the claim completed with a verdict, as [review state](review-state.md)'s Completed calls and coverage describes. If fresh context or the role is unavailable, report the limitation and keep completion of the affected claim blocked.
3. Count consecutive automatic calls without a pass, per claim, as [review state](review-state.md)'s Consecutive non-pass count and Transitions describe; a missing verdict or protocol failure is not CONFIRMED. A CONFIRMED that is not used as a pass, as step 7 describes or after main's comparison of the workspace, counts as [review state](review-state.md)'s Security findings and Serial within a working tree describe. Within a session the count runs across fixes and resets only on an automatic CONFIRMED. A count that reaches the Stop threshold in effect without CONFIRMED stops automatic verification (step 6), so, with K the Stop threshold, a claim refuted K times in a row stops after K − 1 automatically rechecked fixes. Whether the next automatic call, such as the recheck after a fix or a reopened verification, needs the user's explicit request follows [review state](review-state.md)'s Next automatic call. Recover the count, verdicts and open findings as [review state](review-state.md)'s Resumed sessions and Unknown state describe.
4. On REFUTED, reproduce the failure and disposition each finding as FIX, correcting it within the authorized scope, or REJECT with concrete evidence: a failed reproduction, a source citation or the claim's own scope, never preference. A fix goes to [code review](code-review.md) first, under that procedure's rule for the review of a fix, and returns to this recheck only once code review approves it; if that review stops without APPROVED, the claim is unreviewed under that procedure. When the previous verification call completed, use the next call to recheck the original failure plus a bounded regression check; after a verification call that did not complete, the next call verifies the claim's full acceptance rather than only the original failure. When main's comparison after the previous call found a change to a file the claim depends on, as [review state](review-state.md)'s Serial within a working tree describes, the brief does not say that call completed with a verdict and the next call verifies the claim's full acceptance from its base revision, not only the original failure. Send the next call each rejection with its evidence. The verifier may uphold a rejection; an upheld finding can be rejected again only with new evidence. Never resubmit unchanged work unless every remaining finding carries rejection evidence. A finding that shows none of the completion conditions unmet, such as a failure outside what the acceptance states that also occurs at the claim's base revision, is rejected with that evidence and recorded as a Non-blocking finding; a security problem or data loss the change introduced or made exploitable is judged as [review state](review-state.md)'s Security findings describes. A fix after BROKEN also comes to this procedure once code review approves it, with a brief that carries the adversary's findings as the Adversarial review procedure's step 7 describes: read the [Adversarial review procedure](adversarial-review.md)'s step 7 and follow it. After a BROKEN, every public or possibly public record main writes from the findings or from the verifier's report, such as those [code review](code-review.md) lists for the review of a fix, follows [Adversarial review](adversarial-review.md) step 10 and gets only a summary unless the user agrees; the verifier's report to main is not such a record.
5. On INCONCLUSIVE, use the next call only after the named missing evidence, prerequisite or environment has changed; otherwise report the claim unverified.
6. With CONFIRMED, continue to completion under the existing authority; for a Security-critical claim in the automatic flow, read the [Adversarial review procedure](adversarial-review.md)'s At the final commit and follow it. The verdict grants no new authority and main still accepts the whole task. When the count reaches the Stop threshold in effect without CONFIRMED, stop automatic verification, report the claim as unverified with the findings, do not land it on the default branch, release it or report it complete, and require an explicit user request for another call. Preserve the count and open findings in the task. When a handoff is active, record as plain text that the claim is unverified, its open findings and that it must not be landed on the default branch, released or reported complete. Change or remove that note only as [review state](review-state.md)'s Pending acceptance describes. Deferred findings become separate work items or are listed in the completion report. A CONFIRMED that is not used as a pass, as step 3 describes, continues neither to completion nor to Adversarial review.
7. Non-blocking findings do not hold completion. Record them in the work's Follow-up record, as [review state](review-state.md)'s Follow-up record describes. Judge a verifier's optional note as [review state](review-state.md)'s Security findings describes.

A verifier can still write through Bash; its no-edit rule is an instruction. Compare the workspace with the pre-dispatch state after each call and preserve or report any change it made. Main makes that comparison with the workspace reads [review state](review-state.md)'s What a gated pass judged states.
