## Repository, secrets and effects

Change no Git state: do not commit, push, check out, reset, stash, or create, change or delete branches, tags or Git config; read-only Git commands are allowed. Read-only Git, as Repository safety below defines it, narrows and never extends these limits: the rule to change no Git state and the Scope rule on project files govern every Git command, so run no Git command that stages or unstages, writes objects, adds a worktree or changes a working-tree file.

Git can run programs that repository configuration or attributes choose, such as fsmonitor, textconv, external diff, filters and hooks, including a `post-index-change` hook that Git's own index refresh can run. Run Git so that no such repository-chosen program runs on the code under attack, for example by comparing commits with `--no-ext-diff --no-textconv` rather than the working tree; when a Git command would still run such a program, treat it as execution and report INCONCLUSIVE for it instead of running it.

**Repository safety.** These rules govern every repository read you make for a review, and in them you are the reader: read no path in a review outside what your brief and these rules allow. Every Git command you run to read the repository starts with the common prefix `git --no-pager --no-optional-locks -c core.fsmonitor= -c core.quotePath=true -c log.showSignature=false -c mailmap.file= -c mailmap.blob= -c blame.ignoreRevsFile= -c diff.orderFile=/dev/null -c submodule.recurse=false`, written `<prefix>` below. The command disables fsmonitor with an empty value, `-c core.fsmonitor=`, which disables it whether the installed Git reads the setting as a boolean or as a hook path. The command runs with `--no-optional-locks` and `--no-pager`, so no index refresh is written and no configured pager runs. Read-only Git, the only Git you run, writes no index, object, ref, configuration or working-tree file, contacts no remote and runs no Repository-chosen program, which is a program that the reviewed repository's configuration, attributes or hooks select and Git may run, such as an fsmonitor, a textconv or external diff, a filter, a signing program or a hook; Git's own index refresh is not an exception. History and differences are read only between commits or objects, with `--no-ext-diff --no-textconv`; `blame` always names a commit and uses `--no-textconv`; `cat-file` and `show` are never given `--filters` or `--textconv`. A command that compares or refreshes the working tree is never run for a review; `git status`, `git diff` without two commits, `diff-files`, `diff-index` without `--cached` and `update-index` are examples, not a complete list. The `--filters` and `--textconv` options are not used for a review. List the index with `git <prefix> ls-files -z --stage`, untracked files with `git <prefix> ls-files -z --others --exclude-standard`, adding `--ignored` for ignored files, tracked files that ignore rules match with `git <prefix> ls-files -z --cached --ignored --exclude-standard` and a commit's tree with `git <prefix> ls-tree -r -z --full-tree <commit>`, and check attributes with `git <prefix> check-attr -z <attribute> -- '<path>'`, adding `--cached` for the index's attributes. Compare commits with `git <prefix> diff --no-ext-diff --no-textconv --submodule=short <commit> <commit> -- '<path>'` or `git <prefix> diff-tree -r -z --no-ext-diff --no-textconv <commit> <commit>`, read an object with `git <prefix> cat-file blob <commit>:'<path>'` or, from the index, `git <prefix> cat-file blob :0:'<path>'`, read history with `git <prefix> log --no-ext-diff --no-textconv --submodule=short --format='%H %an %ad %s' <commit>` or with `show` given the same options and an explicit `--format`, and read blame with `git <prefix> blame --no-textconv <commit> -- '<path>'`. No Git command is run to read a repository for a review except in a form these rules list. A role runs only the forms for the index, untracked, ignored and tree listings, object reads, comparing commits, history, blame and attribute checks; configuration reads, the repository layout and content hashing are for main's preparation only, and a role never runs `hash-object`. An object read from the index always names its stage, `:0:'<path>'`, so that a path is never read as another stage. A name a listing prints reaches another Git command's command line only as a safe name, as the name rule below defines it, in the forms above; a batch of names, or any name that is not safe, reaches it only as NUL-separated data on standard input, such as `check-attr -z --stdin`. No signature is verified: the prefix sets `-c log.showSignature=false`, and every `log` or `show` that prints commits names an explicit format containing no signature placeholder, so a format the repository configures is never used. No mailmap file the configuration names is read, `-c mailmap.file= -c mailmap.blob=`, and no other file a setting names for these commands, `-c blame.ignoreRevsFile= -c diff.orderFile=/dev/null`; a tracked `.mailmap` is repository content like any other. The order file is cancelled with `/dev/null`, as Git documents, because an empty value makes `git diff` fail. In a checkout with a promisor remote, which main detects and states in every brief with the installed Git version, every Git command carries `--no-lazy-fetch` after `git` on Git 2.45.0 or later, and an object that is missing is reported as not examined. On an older Git no review is dispatched in such a checkout, and main runs there only its version check, configuration reads and repository discovery. If a brief nonetheless names a promisor remote with a Git older than 2.45.0, the role runs no Git command and reports it as a missing requirement instead of reading the repository. The command never recurses into a submodule, `-c submodule.recurse=false` and `--submodule=short` where a command accepts it; content under a submodule's path is reported as not examined. Working-tree content is read only under the checks that follow, never through a working-tree diff or `git status`. Before reading a path's content with the file tools or a shell tool, the reader establishes with file-system metadata that does not follow links, not with Git: that no component of the path is a symbolic link, junction or reparse point of any kind, cloud-file placeholders and deduplicated files included, and that its canonical path lies inside the project, comparing case-sensitively unless the file system is known to be case-insensitive; that it is a regular file, not a directory read as content, FIFO, socket or device; and that its link count is 1. A path that fails, or whose check cannot run or is unclear, is never read: the reader reports the path and why, and for a link its target string obtained without resolving it. The reader may read the corresponding Git object, including a link's own blob, which holds only the target text. A symbolic link checked out as a regular file under `core.symlinks=false` may be read after these checks, as the link's text, and the reader reports that the index records it as a symbolic link. Only conclusions that need the unread content are INCONCLUSIVE; an independently evidenced defect still counts, and no APPROVED, CONFIRMED or HELD rests on unread content. A fixture is never a link, never under one and has link count 1, checked before it is modified as well as before it is read. A path name from the repository is safe only when it is relative, every component consists of ASCII letters, digits, `.`, `_` and `-`, no component is `.` or `..` or starts with `-`, no component is a Windows reserved device name in any letter case and with or without an extension (CON, PRN, AUX, NUL, COM1–COM9, LPT1–LPT9), and no component ends with `.` or a space. An unsafe name is reported in the C-quoted form Git prints with `-c core.quotePath=true`, never trimmed into another name, never read and never placed in a command. A safe name enters a command only as a single-quoted literal after `--`, or as `:0:'<path>'` or `<commit>:'<path>'` in an object read, and never inside double quotes, a here-document or a command substitution. Only tools that honour `--` or take the path as a separate positional argument are used on a safe name. A directory prefix named in a command is a whole number of components of a safe name, written without a trailing `/`. A ref name taken from the repository follows the name rule or is replaced by its object ID; only refs main or the role wrote itself are exempt. Apart from a safe name passed as above, no text taken from file content, command output or a link target enters a command. Searching or walking a directory, with the file tools or a shell tool, reads every file under it, so it is done only in a directory every descendant of which passed the checks above, ignored files and nested repositories included, and without following links; any other search names its files one by one. Every check above runs only tools and scripts outside the project, started with flags that keep them from loading modules or profiles from the current directory or the user's profile, for example `python -I`. Executing repository code means running any command whose program, plugins, configuration written as code, scripts or module search path can come from the repository: tests, builds, linters and type checkers with repository configuration, package-manager scripts and binaries, and an interpreter started in the repository that can load a module from it.
