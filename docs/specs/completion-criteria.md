# Only what a Claim's acceptance needs holds its completion

Label: `ready-for-agent`

Vocabulary follows [CONTEXT.md](../../CONTEXT.md), whose Recorded security defect and Follow-up record entries were added for this spec; its Blocking finding, Non-blocking finding, Adversarial review, Acceptance gate, Accept and land and Security-critical claim entries are amended as part of this work. It builds on [the claims-at-implementation spec](claims-at-implementation.md), released in 0.23.0. The decisions were settled in a grilling with the user on 2026-10-14 and are recorded in ADR 0013, written as part of this work, and in the handoff `review-schedule-per-claim`.

This spec replaces the per-Claim review schedule spec of 2026-10-13. On 2026-10-14 the user dropped its per-Claim review timing, Review schedules and Review groups, for the reasons ADR 0013 records, and kept its serial rule and final check, which are stated here.

This spec has no Claims table: implementing it makes it one Claim against the Acceptance below, and cutting it into tickets first makes each ticket a Claim.

## Problem Statement

Reviews hold completion for more than the Claim promised. A correctness bug or security problem anywhere in the change blocks code review, and any vulnerability the change introduced is BROKEN, whether or not the Claim's acceptance states it. Each such finding starts another fix and another review, and each fix can surface the next edge case: the 0.22.0 round looped on Adversarial edge cases of its security claims, and the 0.23.0 round was finished only by deferring findings by hand. Nothing in the product says which findings hold completion and which are recorded for later.

Two smaller gaps sit beside it. Nothing states that main leaves a working tree alone while a review of it runs, although a gated pass judges a workspace equal to the commit its brief names. And nothing runs the Plan's overall acceptance at the final commit before landing or release, so a dependency between Claims that main missed can still slip through.

## Solution

A Claim is complete when its acceptance as written is met, existing behaviour is not broken, and it has no Deviation. A finding holds completion only when it shows one of these unmet, and a broken existing behaviour needs a failing test or a reproduction. Everything else found along the way, including issues that predate the change and the change's own security defects outside what the acceptance states, is recorded in the work's Follow-up record for a later Plan. A Recorded security defect never passes silently: in auto, the Claim carrying it is landed or released only through an Accept and land decision that names it. A Security-critical claim whose acceptance states no security property has its Adversarial review deferred to that later Plan.

Within one working tree, reviews and implementation are serial: while a review call runs, main does not change that working tree. Main does not create worktrees for reviews on its own. Work the user already runs in separate worktrees proceeds in parallel, each worktree serial in itself.

Before landing or release, main runs the Plan's overall acceptance once at the final commit; a failure reopens the Claims it affects.

## Acceptance

1. **Completion criteria.** Plan review, the review procedures and review state state that a Claim's reviews judge it against three conditions: its acceptance as written is met; existing behaviour is not broken, shown by a failing test or a reproduction that a written rule or a shipped spec's acceptance no longer holds; and it has no Deviation from the Plan. A Blocking finding shows one of them unmet; inference alone does not block. Every other finding, including an issue that predates the change, a correctness or security problem outside what the acceptance states and a regression only inferred, is a Non-blocking finding and is recorded. A Deviation still stops main to ask the user, as today. The criteria apply in both Review modes and to every user; there is no setting.
2. **Reviewer role.** The installed reviewer definition states the Blocking and Non-blocking criteria of item 1, and lists a vulnerability the change introduced outside what the acceptance states under a separate Recorded security defects heading, which does not change an APPROVED. The installed verifier definition is unchanged.
3. **Recorded security defects.** In auto, a gated Claim with any Recorded security defect is landed, released or reported complete only through an Accept and land decision that names each one, even when all its passes are valid. In off, main lists them in its completion report. Either way they go to the Follow-up record under item 7.
4. **Adversarial review timing.** When main identifies a Security-critical claim, it marks whether the Claim's acceptance states a security property, with the reason. Plan review checks each mark and lists every Claim marked as stating none to the user in its result. A Claim marked as stating one gets Adversarial review in the Automatic flow as today, judged against the security invariants its acceptance states. A Claim marked as stating none gets no Adversarial review in this Plan: its Adversarial review is deferred to a later Plan, run at the fixed commit, and in auto its landing or release needs an Accept and land decision naming the missing HELD.
5. **Adversary role.** The installed adversary definition answers BROKEN only for a violation of a security invariant the acceptance states or a promised security fix that still reproduces. Another vulnerability the change introduced is reported as a Recorded security defect, beside pre-existing vulnerabilities, and does not change the verdict. The Adversarial review procedure states that a problem reproduced in a way this Plan's own work would run on this machine is not run and not fixed on the spot, but recorded.
6. **Accept and land for several Claims.** One Accept and land decision may name several Claims, stating for each the commit it accepts, the missing passes, the known vulnerabilities and the remaining risk. Main lists every Claim it would cover for the user's confirmation, and the decision holds only after that confirmation. Main asks once, after every Claim of the Plan has finished its reviews and the final check of item 9 has passed, before landing or release; until then a Claim that needs the decision stays a Pending-acceptance claim and its ticket stays unfinished. Main asks earlier for a Claim only when the user asks to land it earlier.
7. **Follow-up record.** Findings recorded under items 1 to 5 go to one Follow-up record per piece of work, security defects first, together with the Claims whose Adversarial review is deferred. With handoff maintenance active it is a handoff record of its own, kept by that work's handoff writer; otherwise main lists its content in the completion report and, for Recorded security defects, in the Accept and land record. The completion report lists the Claims and defects waiting for a later Plan; nothing starts that Plan automatically, and the user decides when to start it. A later Plan that fixes recorded findings of completed Claims is new work under the existing rules.
8. **Serial within a working tree.** While a code review, outcome verification or Adversarial review call runs, main does not change the working tree it judges, and implementation in that tree waits until the call ends. Main does not create a worktree for a review on its own. Work the user runs in separate worktrees may proceed in parallel, each worktree serial in itself; shared test resources stay governed by each brief's target start and reset.
9. **Final check.** Before landing or release, main runs the Plan's overall acceptance checks at the final commit, within repository safety's Execution rules. It is not a counted step and adds no verdict. A failure reopens the Claims it affects, and landing and release wait for their passes again.
10. **Glossary and ADR.** `CONTEXT.md`'s Recorded security defect and Follow-up record entries state the rules above (already added; checked, not rewritten). Its Blocking finding and Non-blocking finding entries state the criteria of item 1 for every review step; its Adversarial review entry states the timing of item 4 and the BROKEN of item 5; its Acceptance gate entry requires no Recorded security defect besides the passes; its Accept and land entry covers several Claims and Recorded security defects as item 6 states; and its Security-critical claim entry states the security-property mark of item 4. ADR 0013 records the completion criteria, the serial rule and the final check with their rejected options, and states that it amends ADR 0006 and ADR 0009; both are marked as amended by it.
11. **READMEs.** `README.md` and `README.zh-TW.md` explain what holds completion and what is recorded, Recorded security defects with the Accept and land they need, the deferred Adversarial review and the Follow-up record, serial work within a working tree, and the final check; both say the same thing and match the procedures, and the cost explanation states how the deferred Adversarial review affects it.
12. **Tests.** Contract tests pin the new statements and fail on the text before this spec; pins of replaced statements (the old blocking and BROKEN criteria, the old Acceptance gate and Accept and land entries) are updated or become absence pins; the installed reviewer and adversary templates are pinned to the new criteria; the full suite passes in both discovery forms.
13. **Live rehearsal.** With the installed roles of the candidate, main runs a disposable two-ticket Plan in auto: one ticket carries a seeded security defect outside what its acceptance states, and the other is a Security-critical claim whose acceptance states no security property. The record shows plan review listing that mark to the user, the seeded defect reported under an APPROVED as a Recorded security defect and written to the Follow-up record, no Adversarial review run for the marked Claim and its deferral recorded, no working-tree change during a review call, the final check, and main asking for one Accept and land decision naming both Claims, the defect and the missing HELD before landing. The rehearsal, its environment and its result are recorded in the release's validation entry; a deviation from the rules is a finding, not a pass.
14. **Release.** The plugin version is 0.24.0; `claude plugin validate .` passes; `docs/setup-validation.md` gains the release entry with test counts and skips, the rehearsal, the review round and the note that existing installations need the plugin update and then `/cc-feather:setup update`, because installed role definitions changed; README's Updates section says the same; the tag is created after the user's go-ahead, only after checking that it matches `plugin.json` at the tagged commit and does not already exist.

## User Stories

1. As a user, I want work to be complete when it does what its acceptance says without breaking what already worked, so that a review round does not keep widening until it never ends.
2. As a user, I want a claim of broken existing behaviour to need a failing test or a reproduction, so that inference alone does not hold my work.
3. As a user, I want issues that predate the change and problems outside the acceptance recorded for later, so that they are neither lost nor fixed in the middle of unrelated work.
4. As a user, I want every security defect a change introduced named to me before it lands, so that I never ship a known vulnerability without deciding to.
5. As a user, I want a Security-critical claim whose acceptance states no security property to have its Adversarial review in a later Plan, so that the round is not held by edge cases its acceptance never promised.
6. As a user, I want to see which Claims plan review marked as stating no security property, so that I can challenge a mark that would defer an Adversarial review.
7. As a user releasing several Claims, I want one Accept and land decision, asked once at the end of the Plan, to list them all, so that I confirm each once without being stopped after every Claim.
8. As a user, I want deferred findings gathered in one Follow-up record per piece of work, security defects first, so that the next patch starts from a complete list.
9. As a user, I want to decide when the later Plan starts, so that recorded findings never start work on their own.
10. As a user, I want a problem that this round would run on my machine recorded rather than run, so that a review never executes a known defect here.
11. As a user in off mode, I want the same criteria for the reviews I ask for, and the security defects they find listed in the completion report, so that the reviews I request judge the same way.
12. As a user, I want main not to change a working tree while a review of it runs, so that every pass judges exactly the commit it names.
13. As a user of a project with costly setup, I want main not to create worktrees for reviews on its own, so that reviews do not trigger reinstalls or rebuilds.
14. As a user who already works in several worktrees, I want them to proceed in parallel, so that the serial rule does not slow down work I separated myself.
15. As a user, I want one overall acceptance run at the final commit before landing or release, so that a dependency main missed is still caught.
16. As a user, I want that final run not to count toward the Stop threshold, so that it does not stop the flow by itself.
17. As a user reading either README, I want what holds completion and what is recorded explained, so that I know what will stop my work and what will wait.
18. As a maintainer, I want the decision and its rejected options in ADR 0013, so that later readers know why findings outside the acceptance are recorded and why per-Claim review timing was dropped.
19. As a maintainer, I want a live rehearsal with the installed roles, so that the rules are seen being followed, not only stated.
20. As a user with an existing installation, I want the update notes to tell me to run setup update, so that the changed role definitions reach my installation.

## Implementation Decisions

- **Where the rules live.** Review state gains the completion criteria, Recorded security defects, the Follow-up record, the deferred Adversarial review, the serial rule and the final check, beside its existing validity and completion rules. Plan review checks the security-property marks. Code review, outcome verification and Adversarial review judge against the completion criteria. The delegation skill's rule on parallel work gains the serial rule for review calls. The Accept and land rules gain decisions for several Claims and Recorded security defects.
- **Completion criteria in the roles.** The blocking criteria live in the installed reviewer definition, and BROKEN in the installed adversary definition, so the criteria change those two definitions; procedures alone could not stop a reviewer from answering CHANGES_REQUESTED for a problem outside the acceptance. The verifier already stays within the Claim and refutes only on a reproduced failure, so it is unchanged. Existing installations need `/cc-feather:setup update` after the plugin update.
- **A Recorded security defect is not a block but is never silent.** It does not change APPROVED or HELD, so the round can finish; the Acceptance gate instead requires an Accept and land decision that names it, which is how a known vulnerability is shipped today.
- **The security-property mark.** Main marks it when it classifies a Security-critical claim, and plan review checks it, so that a Claim cannot defer its Adversarial review by leaving its security invariants out of its acceptance unseen; every "none" is shown to the user.
- **Serial rule.** It follows from the existing rule that a gated pass judges a workspace equal to the commit its brief names and unchanged during the call; this spec makes main's behaviour explicit. A worktree the user set up for parallel work is its own workspace.
- **Final check.** It is main's own run of the Plan's overall acceptance, such as the full test suite, not a review step, and it does not count. It adds no new verdict: its failure reopens Claims under the existing rules.
- **Unchanged.** Reviews still start once the reviewed Plan is implemented. Reopening stays file-level. The Stop threshold, counts per session, Unknown state, cross-session rules, composed Adversarial review and ticket status rules are unchanged, apart from the Acceptance gate and Accept and land changes above. The installed policy, the verifier, analyst and executor definitions, the handoff skill and the configuration tool are unchanged.
- **ADR 0013** records the completion criteria, the serial rule and the final check, amending ADR 0006 (what holds completion) and ADR 0009 (when Adversarial review runs and what BROKEN means). Rejected: blocking on every correctness or security problem in the change (rounds widen and loop); a separate list of blocking exceptions (its items restate the three conditions and invite reviewers to widen them); a vague exception for findings that endanger this machine (no clear edge); a setting to choose the old criteria (adds configuration for a rule every user benefits from, while Accept and land keeps known vulnerabilities visible); main re-triaging verdicts without changing the roles (the reviewer would still answer CHANGES_REQUESTED, and every Claim would need Accept and land); per-Claim review timing with Review schedules and Review groups (where Claims share files, as nearly all of this project's Plans do, the groups collapse to reviewing after the whole Plan, so the 0.20.0 case that motivated it is not fixed; the chained reopening comes from file-level reopening, and the fix loops these criteria address are the larger cost; deferred until data from other projects shows a need).

## Testing Decisions

- The seam is the existing contract tests on shipped text: key-phrase pins in the procedures, role templates and paired pins in both READMEs, with absence pins for removed wording. Prior art: the Stop threshold procedures, review-state rules and claim-source tests.
- New pins assert: the three completion conditions and the evidence rule; the reviewer's and adversary's new criteria and the Recorded security defects heading; the gate on Recorded security defects; the security-property mark and its plan review; the deferred Adversarial review; Accept and land for several Claims, asked once at the end of the Plan; the Follow-up record; the recorded-not-run rule; the serial rule and its worktree exception; the final check and that it is not counted; and the setup update note. Each fails on the text before this spec.
- The live rehearsal is the second seam, needed because these rules depend on main's conduct: it runs once at the candidate with the installed roles, in a disposable repository outside the project, and is recorded, not automated.
- READMEs, `CONTEXT.md` and the ADR are checked at outcome verification against the procedures.
- Release checks: the full suite in both discovery forms and `claude plugin validate .`.

## Out of Scope

- Per-Claim review timing, Review schedules and Review groups, and the downstream start rule that came with them.
- Worktree-parallel implementation within one Plan, and how passes carry over when branches from separate worktrees are merged; the final check is the only safeguard this spec adds for merged work.
- Reopening by precise dependency instead of by file.
- Wording and test items in the follow-up cleanup record, including the review-state, README Budget, Adversarial review and RETIRED-pattern items.
- The findings deferred from 0.23.0 in the handoff `claims-at-implementation-followups`, which a later patch handles.
- Live rehearsal of other review scenarios, which remain with the handoff `review-live-rehearsal`.
- Claim sizing and what a Claim's reviews read, which the claims-at-implementation spec settles.
- Automatically starting the later Plan that fixes recorded findings or runs deferred Adversarial reviews.

## Further Notes

- Security-critical classification of this spec's Claims happens before its first plan review. It changes the Acceptance gate, when Adversarial review runs and what BROKEN means, so it is expected to be classified as Security-critical, which brings a security analysis before plan review.
- The new `CONTEXT.md` entries were added during the grilling and are committed with this spec; the existing entries item 10 amends are pinned by contract tests, so they change with those tests during implementation. The Review schedule and Review group entries added on 2026-10-13 are removed with this spec.
- The grilling's decisions are recorded in the handoff `review-schedule-per-claim`.
- Rollback: before anything is pushed, the unpushed commits can be dropped with the user's agreement; after the release, a user reinstalls the previous version and runs `/cc-feather:setup update` to restore its role definitions.
