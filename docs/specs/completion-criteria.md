# Only what a Claim's acceptance needs holds its completion, except security

Label: `ready-for-agent`

Vocabulary follows [CONTEXT.md](../../CONTEXT.md), whose Follow-up record entry was added for this spec; its Blocking finding, Non-blocking finding and Accept and land entries are amended as part of this work. It builds on [the claims-at-implementation spec](claims-at-implementation.md), released in 0.23.0. The decisions were settled with the user on 2026-10-14 and are recorded in ADR 0013, written as part of this work, and in the handoff `review-schedule-per-claim`.

This spec replaces the per-Claim review schedule spec of 2026-10-13. On 2026-10-14 the user dropped its per-Claim review timing, Review schedules and Review groups, for the reasons ADR 0013 records, and kept its serial rule and final check, which are stated here. A first version of this spec also let security defects outside a Claim's acceptance land through Accept and land and deferred some Adversarial reviews; the security analysis of that version found that the promise to show every such defect to the user could be broken in many places, mostly through repository content alone, and on 2026-10-14 the user chose to keep security findings blocking as today.

This spec has no Claims table: implementing it makes it one Claim against the Acceptance below, and cutting it into tickets first makes each ticket a Claim.

## Problem Statement

Code review holds completion for more than the Claim promised. Any correctness bug, and any regression a reviewer infers, blocks, whether or not the Claim's acceptance asks for it and whether or not anything shows the regression. Each such finding starts another fix and another review, and each fix can surface the next one; the 0.23.0 round was finished only by deferring findings by hand. Nothing in the product says which non-security findings hold completion and which are recorded for later.

Three smaller gaps sit beside it. Nothing states that main leaves a working tree alone while a review of it runs, although a gated pass judges a workspace equal to the commit its brief names. Nothing runs the Plan's overall acceptance at the final commit before landing or release, so a dependency between Claims that main missed can still slip through. And when several Claims need an Accept and land decision, main may stop the user after each one.

## Solution

A Claim is complete when its acceptance as written is met, existing behaviour is not broken, it introduces no security problem and no data loss, and it has no Deviation. A broken existing behaviour that is neither a security problem nor data loss needs a failing test or a reproduction, judged against the Claim's base revision. Every other finding, including an issue that predates the change, a correctness problem outside what the acceptance states and a regression that is only inferred, is recorded in the work's Follow-up record for a later Plan. Security findings, Adversarial review and BROKEN are unchanged.

Within one working tree, reviews and implementation are serial: while a review call runs, main does not change that working tree, and nothing main started writes to it. Main does not create worktrees for reviews on its own. Work the user already runs in separate worktrees proceeds in parallel, each worktree serial in itself.

Before landing or release, main runs the Plan's overall acceptance at the commit to be landed, and again whenever that commit changes; a failure reopens the Claims it affects, and landing waits for it to pass unless the user's Accept and land decision states its actual state.

When Claims of a Plan need an Accept and land decision, main asks once, at the end of the Plan, with one list built from what it has observed in this session.

## Acceptance

1. **Completion criteria.** Plan review, the review procedures and review state state that a Claim's reviews judge it against these conditions: its acceptance as written is met; existing behaviour is not broken, shown by a failing test or a reproduction; it introduces no security problem and no data loss, as S1 states; and it has no Deviation from the Plan. A Blocking finding shows one of them unmet; a regression that is only inferred and is neither a security problem nor data loss does not block. Every other finding, including an issue that predates the change and a correctness problem outside what the acceptance states, is a Non-blocking finding and is recorded. A Deviation still stops main to ask the user, as today. The criteria apply in both Review modes and to every user; there is no setting.
2. **Reviewer role.** The installed reviewer definition states the Blocking and Non-blocking criteria of item 1, with S1 and S2. The installed verifier and adversary definitions are unchanged.
3. **Follow-up record.** Findings recorded under item 1 go to one Follow-up record per piece of work, as S3 states. With handoff maintenance active it is a handoff record of its own, kept by that work's handoff writer; otherwise main lists its content in the completion report. The completion report names the Follow-up record; nothing starts the later Plan automatically, and the user decides when to start it. A later Plan that fixes recorded findings of completed Claims is new work under the existing rules.
4. **Serial within a working tree.** While a code review, outcome verification or Adversarial review call runs, main does not change the working tree it judges, and implementation in that tree waits until the call ends, as S7 states. This includes main's own handoff records inside the project, which main updates only between calls. Main does not create a worktree for a review on its own. Work the user runs in separate worktrees may proceed in parallel, each worktree serial in itself; shared test resources stay governed by each brief's target start and reset.
5. **Final check.** Before landing or release, main runs the Plan's overall acceptance checks at the final commit, within repository safety's Execution rules and as S8 states. It is not a counted step and adds no verdict. A failure reopens the Claims it affects, with its output supplied to their reviews as evidence, and landing and release wait for their passes again and for the final check to pass at the commit to be landed, unless an Accept and land decision states its actual state; for a landing the Acceptance gate does not cover, S8 states what happens.
6. **Accept and land once at the end.** One Accept and land decision may name several Claims, including a gated Claim whose passes are complete when the final check at the commit to be landed failed or was not run, stating for each the commit it accepts, the missing passes, the known vulnerabilities and the remaining risk, and the final check's state at the commit to be landed (passed, failed with its output, or not run), built and confirmed as S4 states. Main asks once, after every Claim of the Plan has finished its reviews and the final check has run or is recorded as not run, before landing or release; until then a Claim that needs the decision stays under the Acceptance gate as it stands and its ticket stays unfinished. Main asks earlier only when the user asks to land a Claim earlier, as S5 states.
7. **Glossary and ADR.** `CONTEXT.md`'s Follow-up record entry states the rules above (already added; checked, not rewritten). Its Blocking finding and Non-blocking finding entries state the criteria of item 1 for every review step; its Acceptance gate entry, like review state's statement of the gate, adds that landing and release also wait for the final check as S8 states; and its Accept and land entry covers several Claims, a Claim whose passes are complete when the final check failed or was not run, and the timing of item 6. ADR 0013 is written in parts, each by the ticket that implements its rule: the completion criteria, with the rejected options on blocking, the setting, letting security defects land and per-Claim timing, and the note that it amends ADR 0006; the serial rule and the final check; and the single Accept and land decision, with the note that it amends ADR 0008. ADR 0006 and ADR 0008 are each marked as amended by it by the ticket that amends them.
8. **READMEs.** `README.md` and `README.zh-TW.md` explain what holds completion and what is recorded, that security findings still block, the Follow-up record, serial work within a working tree, the final check and the single Accept and land decision; both say the same thing and match the procedures.
9. **Tests.** Contract tests pin the new statements and every security invariant below, and fail on the text at tag `v0.23.0`; pins of replaced statements (the old blocking criteria, the old Accept and land entry) are updated or become absence pins; the installed reviewer template is pinned to the new criteria and the adversary and verifier templates to being unchanged; the full suite passes in both discovery forms.
10. **Live rehearsal.** In the test target T1 below, main runs a disposable two-ticket Plan in auto with the candidate. The record shows the seeded non-security issue outside ticket A's acceptance reported as Non-blocking and written to the Follow-up record; the seeded security defect in ticket B blocking code review until it is fixed; no working-tree change during a review call; the final check refusing to run while the seeded untracked test file is present, then running at the final commit and failing on ticket A's declined acceptance failure; and, after the user tells main not to fix ticket A's seeded acceptance failure, main asking once at the end for an Accept and land decision built as S4 states and stating the final check as failed with its output, reporting the difference from the edited Follow-up record. The rehearsal, its environment and its result are recorded in the release's validation entry; a deviation from the rules is a finding, not a pass.
11. **Release.** The plugin version is 0.24.0; `claude plugin validate .` passes; `docs/setup-validation.md` gains the release entry with test counts and skips, the rehearsal, the review round and the note that existing installations need the plugin update and then `/cc-feather:setup update`, because the installed reviewer definition changed; README's Updates section says the same; the tag is created after the user's go-ahead, only after checking that it matches `plugin.json` at the tagged commit and does not already exist.

## Security invariants

From the security analysis of 2026-10-14; each holds for the Claims that cite it.

- **S1. Security findings still block.** A security problem the change introduced or made exploitable, through a new route, permission or data flow even when the vulnerable code is outside the diff, and data loss the change introduced, are Blocking findings whatever the acceptance states, whichever review step reports them. A verifier's note that main judges to be, or cannot rule out as, such a problem is a Blocking finding, and that call's CONFIRMED is not used as a pass, counting as a call without a pass, until the note is dispositioned as FIX or REJECT with evidence under outcome verification's rule for a REFUTED. They block on the reporting role's evidence as today: the rule that a regression needs a failing test or a reproduction applies only to regressions that are neither security problems nor data loss, so a removed or weakened security control is a Blocking finding without a reproduction. The adversary's BROKEN and the Adversarial review procedure are unchanged, and a pre-existing vulnerability still becomes separate work in the project's tracker as today.
- **S2. Regressions are judged against the base revision.** The existing behaviour a regression breaks, and any written rule or shipped spec acceptance it is judged against, are taken at the Claim's base revision, never from the reviewed commit, so a change cannot redefine what it must not break; every brief of the Claim's code review, outcome verification and Adversarial review, a narrowed follow-up's included, names that base revision.
- **S3. The Follow-up record is data.** Its next step is always the user's decision whether to start a later Plan; the findings it quotes are marked as untrusted data; reading or resuming it authorizes nothing; and Accept and land never relies on it.
- **S4. The Accept and land list comes from main's own observations.** Main builds the list from the review results it received in this session, not by reading a record in the working tree, and reports any difference from such a record. For each Claim it names the commit, each missing pass with the step and call that left it missing, and the known vulnerabilities as the reporting role stated them, without merging or downgrading them, and the remaining risk. Where main cannot establish a Claim's verdicts or missing passes, as after a context compaction, Unknown state applies and main stops and asks. The user may confirm part of the list by whole Claims, the rest staying pending, and a Claim is accepted only with everything listed for it; "continue", silence or turning automatic review off is not a confirmation; and the decision covers only what was listed, so a Blocking finding or known vulnerability reported after it is not covered and holds landing until it is resolved or a new decision names it.
- **S5. Landing earlier covers the whole branch.** A request to land a Claim before the end of the Plan lands every Claim on that branch, so main's list covers every gated Claim on the branch, and the decision states the final check's actual state at that commit; main runs it whenever Execution allows, and records it as not run only when Execution does not.
- **S6. This Plan is reviewed with the installed roles.** The reviews of this Plan's Claims use the roles and procedures installed before it. Before the first code review of this Plan, main records a baseline: the installed plugin version, the version of the plugin skills its own session loaded, and the hashes of the user-scope and project-scope agent definitions. Before dispatching each review of the Plan, main compares the agents with that baseline and records the result; the release's validation entry states the three versions and the results for the reviews of the other Claims, and the result for the release ticket's own reviews is checked as a postcondition after its commit. The candidate's roles are installed only in the project scope of the rehearsal repository, and the user scope is compared with the baseline after the rehearsal.
- **S7. Nothing writes the tree a review judges.** Before dispatching a review call, main confirms that no Assignment or background process it started that may write the working tree is still running. At most one gated call that executes code runs in a working tree at a time. When main's comparison after a call finds a change to a file the Claim depends on, that call's pass is not used: the call counts as a call without a pass, establishes no coverage and resets no count, and the next call for the Claim reviews its full scope from its base revision. The worktree exception extends no trust: each worktree still gets repository safety's preparation and checks.
- **S8. The final check judges the landing commit.** The final check runs only when the workspace equals the commit to be landed or tagged, established as for a gated pass, so an untracked or changed file cannot take part in it. Landing and release wait until it passes at the commit to be landed; otherwise only an Accept and land decision that states its actual state lets them proceed, and such a decision may name a gated Claim whose passes are complete. When Execution does not allow it, it is recorded as not run and that is stated before landing and in any Accept and land decision. It runs again whenever the commit to be landed changes, after a fix or any other commit. After it runs, main compares the workspace as after a review call; a change to a tracked file or a file the check depends on makes that run a failed run, with the change as its output. Once it has failed at a commit, that commit's state is failed, and a later pass at the same commit lets landing proceed only through an Accept and land decision that names the failure. Its state comes only from main's own run in this session at that commit, never from a record or an earlier session, and after a context compaction main runs it again; when main cannot establish from this session that the commit has not failed, it treats the commit as failed, and a record can only make the state failed, never passed. The final-check part of an Accept and land decision covers only the commit and output it states. The final check is a condition of the landings and releases the Acceptance gate covers; for one the gate does not cover, main runs it when Execution allows, reports its state before landing, and the user's instruction decides. Its failure goes with its output to the reopened Claims' reviews as evidence, and a failure that cannot be attributed with evidence reopens every Claim the check covers.

## Test targets

- **T1. Rehearsal repository.** A fresh directory outside the project, under the session scratchpad, holding a bare repository used as `origin` (default branch `main`) and a clone used as the work tree. Synthetic data: tickets A and B and a small Python standard-library module with `unittest` tests. Ticket A's seeds are a non-security off-by-one in a function outside its acceptance, which must be Non-blocking, and an acceptance failure in a function its acceptance names, shown by a failing test, which the user tells main not to fix once code review reports it. Ticket B's seed is a security defect that writes the fixed string `SYNTHETIC-TOKEN-0000` into a log inside the clone, harmless if run, which must block until fixed. Before the final check, an untracked test file is placed in the clone; before main asks for Accept and land, the user edits the Follow-up record to drop one finding. Allowed effects: writes only inside that directory, commits and pushes only to its bare `origin`; the candidate's roles and guidance are installed with the candidate's setup in the clone's project scope; no network and no installation outside the clone. Reachable dependencies: Git, the Python standard library and the bare `origin`. Start: a script outside the project creates the directory, initialises the bare repository, clones it, writes the fixture and commits the base; a separate checkout of the commit under test is made outside the project; a new Claude Code session is opened in the clone with that checkout loaded for the session only through `--plugin-dir`, with the installed cc-feather plugin disabled for that session where Claude Code allows it, automatic review on for the session, the user stating the repository is trusted, and the user asking main to start handoff maintenance for the rehearsal's work so that its Follow-up record is a handoff record in the clone, whose path the rehearsal record states. The user-scope policy still loads; the rehearsal record states the plugin version the session loaded, whether the installed plugin was also loaded, which policy text was in effect and the Stop threshold in effect with its source. Reset: delete the directory and run the start script again, then confirm the user scope's agents are unchanged.

## User Stories

1. As a user, I want work to be complete when it does what its acceptance says without breaking what already worked, so that a review round does not keep widening until it never ends.
2. As a user, I want a claim of broken existing behaviour to need a failing test or a reproduction against the base revision, so that inference alone does not hold my work and a change cannot redefine what it must not break.
3. As a user, I want any security problem or data loss a change introduces still to block, so that relaxing the criteria never ships a known vulnerability.
4. As a user, I want issues that predate the change and non-security problems outside the acceptance recorded for later, so that they are neither lost nor fixed in the middle of unrelated work.
5. As a user, I want deferred findings gathered in one Follow-up record per piece of work, so that the next patch starts from a complete list.
6. As a user, I want to decide when the later Plan starts, and a Follow-up record never to start work, so that recorded findings never act on their own.
7. As a user in off mode, I want the same criteria for the reviews I ask for, so that the reviews I request judge the same way.
8. As a user, I want main not to change a working tree while a review of it runs, and nothing it started to write to it, so that every pass judges the commit it names.
9. As a user of a project with costly setup, I want main not to create worktrees for reviews on its own, so that reviews do not trigger reinstalls or rebuilds.
10. As a user who already works in several worktrees, I want them to proceed in parallel, so that the serial rule does not slow down work I separated myself.
11. As a user, I want an overall acceptance run at the commit that will land, repeated whenever that commit changes, before landing or release, so that a dependency main missed is still caught.
12. As a user, I want that final run not to count toward the Stop threshold, so that it does not stop the flow by itself.
13. As a user, I want one Accept and land decision at the end of the Plan, listing every Claim that needs it, so that I am not stopped after every Claim.
14. As a user, I want that list built from what main observed and not from a file anyone could edit, with nothing merged or downgraded, so that I decide on the real state.
15. As a user, I want to confirm only part of the list, and never to have "continue" taken as a confirmation, so that I accept only what I chose.
16. As a user reading either README, I want what holds completion and what is recorded explained, so that I know what will stop my work and what will wait.
17. As a maintainer, I want the decision and its rejected options in ADR 0013, so that later readers know why non-security findings outside the acceptance are recorded and why security findings and per-Claim timing were left as they are.
18. As a maintainer, I want a live rehearsal with the candidate's roles in a disposable repository, so that the rules are seen being followed without touching my own installation.
19. As a user with an existing installation, I want the update notes to tell me to run setup update, so that the changed reviewer definition reaches my installation.

## Implementation Decisions

- **Where the rules live.** Review state gains the completion criteria, the Follow-up record, the serial rule, the final check and the single Accept and land decision, beside its existing validity and completion rules. Code review and outcome verification judge against the completion criteria. The delegation skill's rule on parallel work gains the serial rule for review calls. The Accept and land rules gain decisions for several Claims, their timing and how the list is built.
- **Completion criteria in the reviewer role.** The blocking criteria live in the installed reviewer definition, so the criteria change that definition; procedures alone could not stop a reviewer from answering CHANGES_REQUESTED for a correctness problem outside the acceptance. The verifier already stays within the Claim and refutes only on a reproduced failure, and the adversary's criteria are security criteria this spec keeps, so both are unchanged. Existing installations need `/cc-feather:setup update` after the plugin update.
- **Security stays as it is.** Security problems and data loss introduced by the change block in code review, BROKEN keeps its meaning and Adversarial review keeps its timing. Rounds that loop on security edge cases are handled by the user's existing triage outside these rules: an edge case that needs the user's own environment is proposed to the user as residual risk, an Adversarial review conjecture the adversary could not reproduce is recorded through the user's existing deferral or waiver decision, and a gap reachable through repository content is fixed; none of this changes what a reviewer's security finding blocks.
- **Serial rule.** It follows from the existing rule that a gated pass judges a workspace equal to the commit its brief names and unchanged during the call; this spec makes main's behaviour explicit and adds S7. A worktree the user set up for parallel work is its own workspace.
- **Final check.** It is main's own run of the Plan's overall acceptance, such as the full test suite, not a review step, and it does not count. It adds no new verdict: its failure reopens Claims under the existing rules.
- **Unchanged.** Reviews still start once the reviewed Plan is implemented. Reopening stays file-level. The Stop threshold, counts per session, Unknown state, cross-session rules, composed Adversarial review, the Acceptance gate's conditions and ticket status rules are unchanged, apart from the final check of item 5 and S8, S7's call whose pass is not used, S1's withheld CONFIRMED, and the Accept and land changes above. The installed policy, the verifier, adversary, analyst and executor definitions, the handoff skill and the configuration tool are unchanged.
- **ADR 0013** records the completion criteria, the serial rule, the final check and the single Accept and land decision, amending ADR 0006 (what holds completion) and ADR 0008 (Accept and land for several Claims and its timing). Each part is written by the ticket that implements its rule, so that its implementation and reviews can check it against the procedures they change. Rejected: blocking on every correctness problem in the change (rounds widen and loop); a separate list of blocking exceptions (its items restate the conditions and invite reviewers to widen them); a setting to choose the old criteria (adds configuration for a rule every user benefits from); letting security defects outside the acceptance land through Accept and land with deferred Adversarial reviews (the 2026-10-14 security analysis found the promise to show every defect could be broken through repository content in many places, and ADR 0009 had already rejected letting a flaw the change introduced land); per-Claim review timing with Review schedules and Review groups (where Claims share files, as nearly all of this project's Plans do, the groups collapse to reviewing after the whole Plan, so the 0.20.0 case that motivated it is not fixed; deferred to separate work on retained passes).

## Testing Decisions

- The seam is the existing contract tests on shipped text: key-phrase pins in the procedures, the reviewer template and paired pins in both READMEs, with absence pins for removed wording. Prior art: the Stop threshold procedures, review-state rules and claim-source tests.
- New pins assert: the completion conditions and the evidence rule; the reviewer's new criteria; each of S1 to S8; the Follow-up record; the serial rule and its worktree exception; the final check and that it is not counted; the single Accept and land decision; and the setup update note. Each fails on the text before this spec. The adversary and verifier templates are pinned as unchanged.
- The live rehearsal in T1 is the second seam, needed because these rules depend on main's conduct: it runs once at the candidate, and is recorded, not automated.
- READMEs, `CONTEXT.md` and the ADR are checked at outcome verification against the procedures.
- Release checks: the full suite in both discovery forms and `claude plugin validate .`.

## Out of Scope

- Any change to how security findings block, to BROKEN or to when Adversarial review runs.
- Per-Claim review timing, Review schedules and Review groups, retained passes, parallel review calls, early primary acceptance and narrowed re-review on reopening, which the handoff `review-per-claim-retained-passes` holds.
- Worktree-parallel implementation within one Plan, and how passes carry over when branches from separate worktrees are merged; the final check is the only safeguard this spec adds for merged work.
- Wording and test items in the follow-up cleanup record, including the review-state, README Budget, Adversarial review and RETIRED-pattern items.
- The findings deferred from 0.23.0 in the handoff `claims-at-implementation-followups`, which a later patch handles.
- Existing weaknesses the security analysis noted that this spec does not worsen, such as repository instructions steering a role to classify a finding as pre-existing and a forged Accept and land note in a handoff; they are recorded in this work's Follow-up record.
- Live rehearsal of other review scenarios, which remain with the handoff `review-live-rehearsal`.
- Claim sizing and what a Claim's reviews read, which the claims-at-implementation spec settles.

## Further Notes

- Its Claims are classified before its first plan review: those that change the reviewer's criteria, the serial rule and final check, or Accept and land change review and acceptance controls and are Security-critical; the release is not.
- The `CONTEXT.md` Follow-up record entry was added during the planning and is committed with this spec; the existing entries item 7 amends are pinned by contract tests, so they change with those tests during implementation. The Review schedule, Review group and Recorded security defect entries added during planning were removed.
- Rollback: before anything is pushed, the unpushed commits can be dropped with the user's agreement; after the release, a user reinstalls the previous version and runs `/cc-feather:setup update` to restore its reviewer definition.
