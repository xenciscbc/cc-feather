# A record that lets test-speedup continue

Label: `ready-for-agent`

Vocabulary follows [CONTEXT.md](../../CONTEXT.md), which defines Plan, Claim, Assignment, User's answer, Working checkout, Handoff store, Checkout lease, Unbounded probe, Unbounded run configuration and Runner; this spec adds Speed-up record and Speed-up item below. The decisions were settled by the user on 2026-11-26 in the conversation that drafted this spec, after a Codex second opinion whose accepted points are folded in. This spec changes the user-invoked `/cc-feather:test-speedup` skill, adds a bundled script to it, and changes the documents describing it; it changes no installed guidance, policy template, role definition or configuration tool, so it is release 0.48.0, after 0.47.0, and needs no setup update.

## Problem Statement

`/cc-feather:test-speedup` only reports: its report stays in the conversation, and it writes no file unless the user asks for one. Each run therefore starts from nothing. On a project where it has already run, the next run cannot tell:

- which tests it already analysed, and in which content, so it analyses the whole scope again even when only a few tests are new or changed;
- which items the user already picked, declined or landed, so it proposes declined items again and cannot say that a picked one has landed;
- how long the tests took when they were last measured, so a test that became slower since then goes unnoticed;
- whether the test runner was upgraded since, so the user does not know to ask what the upgrade means for the tests.

On cc-feather itself the three speed-up batches carried this state by hand, in handoff records and specs (`docs/specs/test-speedup-batch-1.md` to `-batch-3.md`, `.feather/handoffs/test-speedup-batch-2-followups.md`, `.feather/handoffs/test-git-process-reduction.md`). Another project has no such trail, and even here a fresh session has to rebuild it from prose.

## Solution

`/cc-feather:test-speedup` keeps a Speed-up record for the repository and continues from it.

- **Incremental static pass.** A run analyses only the test files whose content changed since the record last analysed them, the new ones, and those analysed under a different set of shared files (shared fixtures, setup files, test runner configuration, test scripts); the rest keep their recorded result. A test file is always analysed whole. The check for Unbounded run configurations runs on the whole scope every time. `--full` analyses the whole scope again and keeps the items' states.
- **Decided items stay decided.** Each Speed-up item has a state. Only the user's answer picks or declines one. A declined item comes back only when its own file's content changed since the decision or the user asks. Main marks an item landed or obsolete only after checking the code; an item that shows up again after being landed or obsolete is reopened as undecided, with its earlier state shown. Tests and settings with resource risk are always listed, whatever their state.
- **Comparable measurements.** Each measurement is kept with a comparison key, and a new one is compared with the last one under the same key: total time, the tests that became slowest and fastest, and the timing change observed around each landed item.
- **Test runner versions.** The record keeps the test runner's version; when it changed, the report says so, and the user can ask main to review what the upgrade changed for the tests.
- **A section of its own.** The report starts with what changed since the last run.
- **Show and prune.** `/cc-feather:test-speedup show` summarises the record and lists the other forms of the command; `/cc-feather:test-speedup prune` removes old measurements and finished items after a dry run the user confirms.

The command still changes no code, test or configuration: the record is cc-feather's own, ignored by Git, written by the bundled script.

## Glossary additions

These two entries go into `CONTEXT.md`, in a section of their own or under Design checks, as the first ticket decides:

- **Speed-up record**: A repository's record of `/cc-feather:test-speedup`: for each test file it analysed, the content and the set of shared files it was last analysed with; its Speed-up items; its analysis runs with the test runner versions they read; and its measurements. It is kept under the main worktree's `.feather/test-speedup/`, or under the project directory of a non-Git project, ignored by Git, and is one of cc-feather's own records, not a change to the checkout. _Avoid_: baseline, speedup log, cache
- **Speed-up item**: One speed-up, removal, test with resource risk or run configuration with resource risk from a `/cc-feather:test-speedup` report, recognised across runs by its file, its kind and the test ids or setting it concerns, with its state: undecided, picked, declined, landed or obsolete. Only the User's answer makes it picked or declined. _Avoid_: finding, suggestion, ticket

## User Stories

2. As a maintainer, I want a new test file analysed on the next run, so that tests added since the last run get checked.
3. As a maintainer, I want a test file whose content changed analysed again, so that a test that became slow through an edit gets checked.
4. As a maintainer, I want change detection to compare content rather than commits, so that an analysis of uncommitted edits, a rebase or a garbage collection never makes a changed file look unchanged.
5. As a maintainer, I want a test file analysed again when the shared fixtures, setup files, test runner configuration or test scripts it was analysed with changed, were added or were removed, so that a change outside the test file is not missed.
6. As a maintainer, I want that rule kept per test file, so that a run on one test after a shared change does not hide the change from the other tests that use it.
7. As a maintainer, I want main to analyse only the tests that use a changed shared file when it can tell, and every test with that shared set when it cannot, so that an unknown dependency never hides a test.
8. As a maintainer, I want a change to the code under test or to a library the tests use not to trigger a new analysis, so that the static pass stays about the tests, and measurement catches what the change made slower.
9. As a maintainer, I want a test file always analysed whole, even when my scope names one test in it, so that the record's "analysed" means the whole file.
10. As a maintainer, I want the run configuration checked on the whole scope every run, so that a changed default or setting is never left to a stale result.
11. As a maintainer, I want the items of a deleted test file marked obsolete, and a renamed file treated as a deletion and an addition, so that the record does not keep proposing work on tests that no longer exist.
12. As a maintainer, I want only files inside the run's scope to count as deleted, so that a run on part of the project never closes items elsewhere.
13. As a maintainer, I want `--full` to analyse the whole scope again while keeping every item's state, so that I can start the analysis over without losing my decisions.

## Implementation Decisions

### The record and its script

- **Script.** A bundled script under the test-speedup skill, launched like the lease tool's `scripts/leases.py`: Python 3.11+, standard library only, bytecode writing suppressed, a version check that prints an error object, and the handoff skill's helpers imported from `../handoff/scripts` for Git top-level and main-worktree discovery. It reuses those discovery helpers, not the lease tool's repository class, which rejects non-Git projects. Each command prints one JSON object; a handled result exits 0 with its `status`, and status `error` exits 2, a usage error included. The script never runs a test, never reads a file beyond hashing it or reading a version from it, and never parses a report, a spec or a handoff record.
- **Location.** In a non-bare Git repository the record lives under the main worktree's `.feather/test-speedup/`, whichever checkout runs the command. In a non-Git project it lives under the project directory's `.feather/test-speedup/`. A bare repository, a main worktree that cannot be established and a directory that cannot be written return an error, and the record is never written anywhere else. There is no tracked mode and no option to choose another root.
- **Ignored by Git.** The directory holds its own `.gitignore` containing `*`, as `.feather/leases/` does; the script never edits the project's `.gitignore`.
- **Contents.** The record is one JSON document with a schema version and these parts:
  - `files`: for each test file analysed, its path relative to the Working checkout's top level, its content hash, the shared-set hash it was analysed with, the commit it was analysed at (shown only; never used to detect change; none outside Git) and the analysis date.
  - `items`: each Speed-up item's key, section (speed-up, removal, test with resource risk, run configuration with resource risk), location, description, expected gain, how correctness is kept, risk and state; the date, reason and the file's content hash of the user's decision; the date it landed and the evidence for landed or obsolete; the date it was first seen and the commit it was last seen at; and the earlier states it had, each with its date and reason, so that a reopened item shows them.
  - `runs`: each analysis run's date, scope, commit, whether it was `--full`, and the test runner and plugin versions it read, each with the file it was read from or unknown.
- **Shared set.** Main names, for each test file it analyses, the shared files it was analysed with: the shared fixtures, setup files, test runner configuration and test scripts within the scope. The script hashes the set as a whole, paths and contents, so a shared file that changed, was added or was removed changes the hash.
- **Versions.** The test runner and its plugins are those whose settings the static pass judges, such as vitest, jest, pytest, pytest-xdist or the Go toolchain; a library the tests import is not one. A version is read without running anything: from the installed package's own metadata, such as its `package.json` or `dist-info`, from `go.mod`'s `go` and `toolchain` lines, or from `.python-version` or `pyvenv.cfg`. One that cannot be read is unknown.
- **Measurements.** Each measurement is a file of its own beside the record: date, commit, comparison key, whether the run succeeded, total time and each test's time. The comparison key holds the command, the tests selected, the concurrency and any override, whether it ran inside the Runner and with which limits, and the tests left out; date and commit are not part of it. Two measurements are comparable only when their keys are equal and both succeeded.
- **Version.** Every read returns the version of the whole store: the record and its list of measurement files. Every write takes the version it read and returns `changed` with the current version, writing nothing, when the store changed since; main then reads it again, merges its own update and writes again. There is no lock: two writes at the same instant can still both pass the check, and the later one wins. This is a residual risk the user accepted, since two sessions rarely run test-speedup at once and the worst outcome is an extra analysis or a decision asked again.
- **Trust.** The record is trusted like other `.feather/` records; no check against forgery is added.

### Script commands

The command names and the full JSON protocol are the first ticket's to define completely: every command's input and output, the absent-record version, the distinction between schema version and store version, the canonical form of an item key (including how test ids are ordered) and what happens when two items found in one run share a key. The behaviour is this spec's.

- **Read.** Return the record and its version, or an absent record with its own version token.
- **Changes.** Given the scope's test files and, for each, the shared files main names, report each file as new, changed, unchanged or deleted by its content hash, and whether its shared-set hash differs from the recorded one. Only recorded files inside the given scope can be reported deleted. Also report the versions read now beside those of the last run.
- **Record a run.** Given the files analysed, the shared set of each, the items found, the run's scope, commit, `--full` flag and versions: update those files' entries only; match each found item to a recorded one by key; add the unmatched ones as undecided; reopen a matched landed or obsolete item as undecided, keeping its earlier state; mark obsolete, with the deletion as evidence, the items of files reported deleted; and return, for each analysed file, the recorded items not found again, with their states. Main then submits its classification of those items, landed or obsolete with evidence, or unchanged, in a second call; the script infers no other state itself.
- **Decide.** Set one or more items to picked or declined, with the date, the reason and the file's current content hash, as main passes them from the user's answer.
- **Measure.** Store a measurement and return the comparison with the last comparable one: total time, the ten tests whose time rose most and the ten whose time fell most, each with seconds and factor (a test with a zero earlier time has no factor), ties broken by test id, and the tests present in only one of the two. For each landed item that names tests, it returns those tests' times in the last comparable measurement before its landing date and the first after, or unavailable. Without a comparable measurement it says so.
- **Show.** Read-only. Without arguments: the last analysis's date and commit, the number of items in each state, the last measurement's date, key and total time, and the number of recorded files whose content changed since they were analysed; followed by the other forms of the command. `items [state]` lists items, of one state or all. `runs` lists analysis runs, with their versions, and measurements. Without a record it says there is none and lists the same forms.
- **Prune.** A dry run lists what a selection would remove and the store's version; the same selection with that version removes exactly that, and returns `changed` when the store changed since. A selection is the union of: measurements before a date, all but the last N measurements by date, obsolete items, and items that landed before a date, by their landing date. Undecided, picked and declined items cannot be selected. A removal that fails part-way reports what it removed and what it did not. There is no reset of the whole record.

### The skill

- **Report-only paragraph.** It changes to: the command changes no code, test or configuration and commits nothing; the only files it writes are those of its Speed-up record, through the bundled script, after every run, without asking. Writing the record is not a change to the checkout and needs no Checkout lease. A failed write is reported, and the report stays in the conversation.
- **Arguments.** The first word `show` or `prune` selects that form; any other argument is the scope, as data. `--full` asks for a full analysis. A scope path that is a reserved word is written with `./`.
- **Whole files.** A scope that names a test inside a file is widened to that file for the static pass and the record.
- **Incremental static pass.** Before the static pass, main gets the scope's changes from the script. The test files to analyse are the new and changed ones, and those whose shared-set hash differs; among the latter, main analyses only those that use a changed shared file when it can tell, and all of them when it cannot. A change to the code under test, or to a library the tests import, does not by itself add a file. Without a record, or with `--full`, the whole scope is analysed.
- **Run configuration every run.** The check for Unbounded run configurations runs on the whole scope every run, with its lookups, and its items are matched against the record like any others.
- **Who analyses.** Unchanged in its split; an analyst Assignment names the files to analyse and does not include the record. Main matches the analyst's items against the record.
- **State rules.** New items are undecided. Main makes an item picked or declined only from the User's answer, passing its date and reason to the script. For a recorded item not found again in an analysed file, main reads the code at the item's location: it marks the item landed when the code shows the item's change, obsolete when the item's test or setting no longer exists or the concern no longer applies, each with its evidence, and leaves the state unchanged when it cannot tell. A declined item found again is proposed again only when its file's content hash differs from the one recorded at the decision; otherwise it is proposed again only when the user asks. A reopened item is shown with its earlier state, date and reason.
- **Report.** A new first section, Since the last run: the last analysis's date and commit; each file analysed again and its reason (new, changed, shared set changed, `--full`); how many files kept their recorded result; each test runner or plugin version that changed, with a sentence that the user can ask for a review of the upgrade; the items found landed, obsolete or reopened, and those proposed again; and the items still undecided or picked. The Speed-ups and Removals sections list only items that are undecided, reopened or proposed again. The two resource-risk sections list every current test and setting with resource risk, those of files not analysed again taken from the record, each with its state; a declined risk stays listed, and only its fix is not proposed again. On the first run without a record, the report ends by saying that items decided before may appear again and that the user can state their states or name the documents where they were decided, which main reads as data and turns into proposed states for the user to confirm.
- **Upgrade review on request.** When the user asks for a review of a test runner or plugin upgrade, main looks up the changes between the two versions in the lookups' order, and reports only those concerning defaults of concurrency, isolation, memory or time, new features that could speed the tests up, fixed bugs the tests or configuration work around, and deprecated or renamed settings the configuration uses, each with its source, the version it applies to and the locations it may affect; the adjustments become Speed-up items. A query sent outside for it may carry the framework's name, both versions and a setting's name, and nothing else. Breaking changes unrelated to these four are outside it.
- **Measurement.** The tests left out by default are the current tests with resource risk, those of files not analysed again taken from the record. After a measurement main stores it through the script and reports the comparison, and says when no comparable measurement exists. The existing rule that timings at a different concurrency are not comparable with the ordinary run is unchanged.
- **Show and prune.** `show` passes its arguments to the script and relays the result. `prune` runs the dry run, shows it, and removes only after the user confirms in the conversation.
- **Not affected.** The scope's definition, the static pass's criteria, the correctness bar, the lookups' order and sources outside the upgrade review, the measurement offer and its Runner rules, the shared test criteria, `test-design`, the delegation skill and its references, the Runner, the role definitions, the policy templates, setup, handoff and leases.

## Testing Decisions

- **Good tests.** Tests check what a user of the script or reader of the skill sees: the JSON a command prints, its exit code and the files it leaves on disk, and the skill's and documents' sentences. They do not check the script's internal functions or the record's field order.
- **Script seam.** The script is tested through its command line as `tests/test_leases_tool.py` tests the lease tool: single calls run in the test process through the entry point with the argument list a subprocess gets, only the JSON result and exit code asserted; the launcher, the unsupported-Python error and the environment it sees run as a subprocess. The fixture is the shared one of `tests/test_handoff_shared_store.py`, a main worktree and linked worktrees, plus a non-Git directory.
- **Covered by the script tests.** The location from the main worktree, from a linked worktree and in a non-Git project; the error and no write elsewhere for a bare repository and an unwritable directory; the directory's own `.gitignore` and an unchanged project `.gitignore`; new, changed, unchanged and deleted files by content hash, including a file analysed with uncommitted content and then restored; a shared file changed, added or removed changing the shared-set hash, and that change still reported for a test file not analysed in the run that saw it; a deletion reported only inside the scope; a partial run leaving other files' entries alone; matching by key, new items undecided, reopening a landed or obsolete item with its earlier state, deleted files' items made obsolete, and unmatched items returned and then classified; decide setting state, date, reason and the decision's content hash; `changed` on a stale version for every writing command, including after a measurement was added or removed; the measurement comparison with equal keys, the refusal to compare unequal keys or a failed run, the top ten each way with ties and a zero earlier time, tests in only one measurement, and a landed item's before and after times or unavailable; version reading from each kind of source and unknown; `show` without a record, with one, `items [state]` and `runs`, and that it changes nothing; `prune`'s dry run, its removal of exactly what the dry run listed, its selection by landing date, its `changed` after a concurrent write, and its refusal to select undecided, picked or declined items; malformed input returning a JSON error with exit code 2.
- **Not covered.** Two writes at the same instant: the residual risk is accepted, not tested.
- **Bounds.** The fixtures use a handful of files and items, and the top-ten check uses eleven tests or more each way; no test generates large records.
- **Skill seam.** The skill is model instructions. Following the project's practice, tests pin each decision-carrying sentence as a whole sentence in the document that states it, reference sentences paired in both languages, in `tests/test_feather_design_checks.py` beside the existing `TestSpeedupCommandTests` pins, which move with the sentences they pin: the changed report-only paragraph, the reference introduction and the README listings replace their old pins.
- **Pinned.** The report-only paragraph's new wording; the reserved words and `./`; `--full`; whole files; the incremental pass's files to analyse, including the fallback and that a change to the code under test or a library adds no file; the run configuration every run; that the analyst's brief does not include the record; the state rules, including the check before landed or obsolete and the reopening; the Since the last run section; the resource-risk sections listing every current risk; the upgrade review and its query rule; the measurement storing and comparison sentence; the first-run sentence; `show` and `prune`'s confirmation; the glossary entries; the reference pairs; the README listings; the 0.48.0 validation entry and Updates notes.
- **Unchanged pins stay.** The scope, who analyses, the static pass's criteria, the never-weaken sentence and the measurement offer's sentences.
- **Packaging.** The skill's packaging test checks, as `PackagingTest` does for the lease tool, that the skill is in the plugin manifest and that `SKILL.md` names its launcher by its relative and its `${CLAUDE_PLUGIN_ROOT}` path.
- **Prior art.** `tests/test_leases_tool.py` and its `LeaseBase` for the script; `TestSpeedupCommandTests` in `tests/test_feather_design_checks.py` and the release tests' version and validation checks for the skill.

## Out of Scope

- An import command. On the first run the user can state earlier decisions in the conversation or name the documents that hold them; a fresh analysis builds the record.
- A record per branch, a tracked record, or an option to place the record elsewhere.
- A lock on the record.
- A review of every test runner upgrade without the user asking; tracking the versions of libraries the tests import.
- A threshold for a regression, or any number cc-feather chooses for the project.
- Analysing again because the code under test changed.
- Analysing part of a test file.

## Further Notes

- **Limits.** The incremental pass, the shared sets main names, the state rules, the check before landed or obsolete and the Since the last run section are instructions to the model; the tests show the script's behaviour and the text, not that a model always applies them. The live run in the validation entry shows one run.
- **Shared files.** Which tests use a changed shared file is main's judgement; the fallback to every test with that shared set keeps a wrong guess from hiding a test only when main says it cannot tell, so the skill states the fallback explicitly.
- **Declared versions.** A version read from `go.mod`, `.python-version` or `pyvenv.cfg` is the one the project declares; the toolchain actually used can differ, for example through `GOTOOLCHAIN`, and the static pass cannot see that, since it runs nothing.
- **Two branches.** Sharing one record across checkouts means a file analysed on two branches keeps the last analysis only, so switching back costs one more analysis; an item seen only on an unmerged branch becomes obsolete the next time main finds its test missing, and is reopened if it shows up again.
- **Tickets.** The first ticket is the script with its complete protocol, its tests and the glossary entries; the skill's text, the reference documents, the README listings and their pins follow; the release with its validation entry is last. Each ticket carries the rules of this spec that apply to it and its own acceptance, since the spec is a checklist and not a ticket's contract. The cut is confirmed with the user before the tickets are written under `.scratch/test-speedup-record/issues/`.
- **Overall acceptance.** This is the Plan's overall acceptance: the full suite, `python -B -m unittest discover -s tests -t .`, passes. The final check runs it for each commit to be landed or tagged, not for each Claim, and it is not part of any Claim's acceptance; each ticket cites it. Each ticket's own acceptance names the test modules related to its change.
