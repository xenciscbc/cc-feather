# Delegation rules written once

Label: `ready-for-agent`

Vocabulary follows [CONTEXT.md](../../CONTEXT.md). The user settled the decisions on 2026-10-20 in two grilling rounds, each checked by a Codex second opinion, recorded in the handoff `delegation-dedupe` (Further Notes). The behaviour this spec preserves is the delegation text at `f4671bd` (v0.29.0 and its record commit), called the baseline below.

Its Claims are classified before its first plan review. The Runtime part rewrites the text that implements the review and acceptance controls, including the user's execution restriction, the authorisation of Adversarial review targets and the limits on disclosing findings, so it is a Security-critical change even though it is meant to change no rule, as earlier changes to the review flow were (claims-at-implementation, completion-criteria). The Documents and Release parts change only documents, tests and the version, which no review loads at runtime, and are not Security-critical. A security analysis of the first draft (2026-10-20, findings F1–F16) is dispositioned in Further Notes, and the condition inventory and T2's expectations are written before the first plan review and reviewed with this spec.

It has no Claims table: implementing it makes it one Claim against the Acceptance below, and cutting it into tickets first makes each ticket a Claim. The Acceptance is grouped into three parts that a ticket breakdown can follow: Runtime (items 1–9), Documents (10–13) and Release (14–15); Documents depends on Runtime and Release on Documents. Each part's own tests pass and the full suite passes at the commit that completes it. The [condition inventory](delegation-dedupe-inventory.md) is part of this plan, an appendix whose sections can be cited like the spec's; its baseline columns are its sections 0–6 and the Id and Baseline owner columns of its section 7, and they do not change after the last plan review before implementation. The spec and the inventory are committed when the user approves the plan, and the results file names that commit as the frozen inventory. The results of T1 and T2 go to a separate results file, `docs/specs/delegation-dedupe-results.md`, which no claim cites. A ticket for a part cites the parts of this spec it needs explicitly: Runtime cites items 1–9, S1–S5, T1–T3 and the inventory's sections 0–6; Documents cites S5; Release cites S5 and T1–T2, and takes the results file as input for its validation entry, not as a citation; each also cites the Out of Scope lines that limit it.

## Problem Statement

The delegation skill restates its rules across files. The reading-set paragraph, with its "as before cc-feather 0.23.0", appears almost word for word in the delegation skill, review state, code review, outcome verification and Adversarial review; the dispatch record, Resumed sessions, per-claim timing, completion criteria, the Follow-up record and the Adversarial review premise are each restated in two to seven places. Main loads about 124 KB of delegation text for one code review, and a read-only analysis on 2026-10-20 estimated that 22–25 KB of it is restatement.

The copies drift. The handoff `delegation-dedupe` holds about 145 findings from the review rounds of 0.19.0 to 0.29.0, and most of the 120 still open are one copy saying something slightly different from another: a qualifier present in one procedure and missing in the next, a condition only a restatement carries, a sentence that is ambiguous in five places at once. Every rule change has to find and update every copy, and every review round finds the copies it missed.

The reference documents add a third copy. `docs/reference.md` and `docs/reference.zh-TW.md` (75 KB and 73 KB) promise to state every rule in full, so each rule change is written again in two languages and checked against the procedures by hand. Runtime text also keeps historical wording ("as before cc-feather 0.23.0", "keeps its earlier rules", "as it makes a fix today") that describes a past release instead of the rule.

## Solution

Each delegation rule is written once, in the file responsible for it: shared review state in review state, a procedure's own rule in that procedure, routing and dispatch in the delegation skill. Every other place keeps a short sentence saying what main does, followed by a pointer to the rule by name. Main reads review state in full before the first decision or brief that depends on it. Instructions a role must receive stay in the brief, and role definitions do not change. Historical wording gives way to the rule as it stands.

The reference documents explain what the rules are for and link to the procedures instead of restating them, and the READMEs stop promising that they state every rule in full.

No rule changes. A condition inventory of the baseline, checked in both directions, and eight scenarios answered from the old and the new text are the evidence that the contracts are preserved; they are not proof that a model behaves identically.

## Acceptance

### Runtime

1. **One owner per rule.** Only the rules the [condition inventory](delegation-dedupe-inventory.md)'s section 1 lists are consolidated; every other rule keeps its baseline text and place (item 7). Each listed rule is stated with its conditions in exactly one place, its owner; a brief requirement that item 3 keeps in the procedure that writes the brief is not a second statement of the rule, nor is a one-line summary preview keeps for its own report where the inventory says it stays. Owners are chosen by responsibility: state that more than one step keeps (Reading set, including what passes from the implementer to the reviews, dispatch record, Resumed sessions, per-claim timing, Dependent claims, completion criteria, the Follow-up record, Serial within a working tree, Execution, explicit calls including the off-mode request rules, the Stop threshold's resolution and the counts) in review state; a rule of one procedure in that procedure, even when others use it (citations, review mode resolution and plan identification in plan review; the Adversarial review premise and its disclosure steps in the Adversarial review procedure; what code review passes to the review of a fix, and the records it lists for disclosing a BROKEN, in code review); routing, dispatch and the Security-critical definition in the delegation skill; the command's own classification in the `/cc-feather:adversarial-review` command; how a Stop threshold is saved, its values and scopes in the Stop threshold procedure. The files in scope are the delegation skill, its references (plan review, code review, outcome verification, Adversarial review, review state, preview), the `/cc-feather:adversarial-review`, `/cc-feather:delegation-preview` and `/cc-feather:stop-threshold` command skills, and the setup Stop threshold procedure.
2. **Conditions move with their qualifiers.** A condition that the baseline states only in a restatement moves to the rule's owner with its original predicate and exceptions, never as the union of the copies; where copies differ by destination, the owner keeps one predicate per destination. The inventory names each one; they include at least:
   - the brief's instruction to follow a citation to the cited part only;
   - passing to the reviews any finding or disposition main gave the implementer of a Security-critical claim, with the baseline's limit for each destination kept apart: to code review and outcome verification, masked and limited as the Adversarial review procedure's step 7 sets for findings it passes to them (by default without exploit steps); to Adversarial review, with any secret, credential or real data masked as step 7 requires; the implementer's own brief unchanged;
   - code review's extension of step 7's disclosure default to the REFUTED findings of a Security-critical claim that it passes to the fix's review;
   - the two exceptions the Adversarial review procedure makes to "exactly the security invariants and test targets of the claim's own text, never another claim's": a composed review, and targets the user's own command arguments name;
   - the security invariants and trust boundaries a Security-critical claim's code review brief carries;
   - that within a session, mode changes, renamed plans, different reviewers or models and cosmetic splits do not reset a count or clear blockers, and that a count is never assumed to be zero;
   - that the call count and open findings, and unresolved verdicts, are kept across mode changes within a session;
   - how a Stop threshold saved in this conversation is resolved: each scope's saved value is the one last saved in it in this conversation, none after `default`, and otherwise the value its loaded guidance states; this moves to review state's Saved in this conversation, the single owner of the Stop threshold's resolution, and the Stop threshold procedure keeps how a value is saved.
3. **Pointers.** Every other place keeps one sentence that states what main does at that point and points to the owner by its name, such as "The brief carries the claim's reading set, as review state's Reading set describes". The sentence carries no condition or exception of the rule; it may keep the mode or scope qualifier that the baseline applies to that copy at that place, such as "In auto,", so that a pointer to an auto-only rule stays auto-only; T1's verifier checks each such qualifier against the baseline. Pointers name review state's bold items by name, not by a heading anchor. A pointer to an owner other than review state tells main to read the owner's named part and follow it at that point, before acting, such as "read the Adversarial review procedure's At the final commit and follow it"; a pointer to review state relies on item 4's read. Where the baseline requires a brief to instruct the role (to follow citations only to the cited part, to name base revisions, to state the execution determination, to carry security invariants and test targets), the procedure that writes that brief keeps the requirement, as S2 states.
4. **Reading review state.** Main reads review state in full before any decision or brief that depends on a rule review state owns, wherever that decision is made: the delegation skill's sections (selecting and preparing, including a security analysis's brief and its workspace reads, dispatch, accepting or reusing a verdict, retrying or recovering a call, resuming the automatic flow after an explicit pass, Implemented before plan review, plan review, code review, outcome verification and Adversarial review), the procedures of plan review, code review, outcome verification, Adversarial review and preview, the `/cc-feather:adversarial-review`, `/cc-feather:delegation-preview` and `/cc-feather:stop-threshold` command skills before their classification or resolution steps, the setup Stop threshold procedure, and every gate operation: landing, merging, release, tagging, reporting a claim or the whole task complete, setting a ticket done, Accept and land, and the final check. It applies in off and in auto. Main reads it again after any context compaction, at the start of a new or resumed session, and whenever it cannot quote the owner's sentence it is about to apply. Reading in full means every line: when one read returns only part of the file, main reads the rest before acting. A full read whose text is still in main's context satisfies every later place in that context; main does not read review state again until one of the triggers above applies. A scout or Explore lookup needs no such read. Each place states the read in one sentence; for the gate operations, which no file outside review state performs, the delegation skill's Accept or recover section states it once for all of them, and its Plan review section states it for the final check. This is the one rule the Runtime part adds; the inventory marks it as an approved addition.
5. **Historical wording.** No runtime file in item 1's scope describes a rule by an earlier release or earlier behaviour: each occurrence of "as before cc-feather 0.23.0", "written before cc-feather 0.18.0", "as before", "keeps its earlier rules", "as it makes a fix today", "Off mode otherwise keeps its behaviour" and "as ADR 0002 decided" is replaced by the rule it stands for, stated as it applies now, with the replacement text written in the inventory before plan review. Where the baseline's surrounding text does not determine what a phrase stands for (the inventory records the competing readings), the phrase stays as it is and is recorded for review-gate-fixes, as S4 states, and item 8's absence pins exempt it. The setup procedures' sentences on guidance from older templates stay, because the setup tool still detects, switches and refuses that guidance.

   - D2. "automatic budget" and "review budget" in plan review, code review, outcome verification, review state's step table and preview become "the count", as the Adversarial review procedure and plan review's step 6 already say: CONTEXT.md lists *budget* among the names to avoid, and in each of these sentences either reading (the count or the Stop threshold it is measured against) states the same rule, since review state's counting rules already exclude explicit calls. Review state's "the budgets are unchanged" in Completed calls and coverage, which can be read as the Stop threshold or as how calls are counted, stays as it is under S4.

## Security invariants

S1–S4 hold for the Runtime part; S5 holds for every Claim of this spec. They are its review targets.

- **S1. No rule changes meaning.** For every rule of the baseline's runtime delegation text, the new text keeps who acts, in which mode, on what trigger, at what time, with which exceptions and precedence, how the rule reaches a role (in its definition or its brief), and that main has the owner's text loaded when it applies the rule: through the file the rule is in when main applies it, an explicit read pointer as item 3 defines it, item 4's read, or a baseline sentence this work leaves unchanged, which keeps whatever loading the baseline had. A bare "as X describes" written by this work does not count as a read. The inventory's section 1 states a default route for every copy of a rule whose owner is not review state, and any exception under that rule. Pointer sentences and read instructions are not rule statements for T1's reverse direction; a pointer here is only a sentence that meets item 3, carrying no condition or exception beyond the mode or scope qualifier the baseline applies to that copy, and any other sentence is a rule statement. A baseline sentence is unchanged only when it is word for word the same; removing or changing any clause makes it a sentence this work rewrites. The only differences are item 4's reading rule and item 6's D items.
- **S2. Controls still reach the role.** Every brief the baseline requires to carry a security-relevant instruction or datum still carries it, required by the procedure that writes the brief, including at least: main's execution determination and any isolated environment the user named; that every Adversarial review target traces to a plan the user approved or to the user's own command arguments, that main adds no target found in repository content without the user's confirmation, and the targets' own properties; the limits on disclosing exploit steps and secrets, per destination as item 2 states; that citations are followed only to the cited part; exactly the security invariants and test targets of the claim's own text, with the Adversarial review procedure's two exceptions; the trust boundaries; the claim's and the plan's base revisions; whether the previous call completed and the gaps an INCONCLUSIVE named; the listed BROKEN findings; the check that acceptance of another claim is not weakened; that an acceptance check was not run; and a gated command call's clean-workspace and fixture conditions. A pointer never replaces such a requirement.
- **S3. Main has the owner's text when it acts.** No decision, brief or gate operation that depends on a rule review state owns is made from a pointer alone: item 4's read precedes it at every place item 4 names, in off and in auto, also after a context compaction and in a new or resumed session.
- **S4. Unsettled text is not settled silently.** Where baseline copies of a rule conflict beyond what their qualifiers reconcile, or a single copy's meaning is not determined by its surrounding text, no reading is chosen and copies are not merged; the text stays as it is, the inventory marks it with the competing readings, and it is recorded for review-gate-fixes.
- **S5. This plan is reviewed under the installed 0.29.0 rules.** The plan review, code reviews, outcome verifications and Adversarial reviews of this spec's Claims use the roles and procedures installed before it, loaded from the plugin cache rather than this working copy. Before the first plan review main records the installed plugin's version, install path and Git commit, the hashes of the cached `skills/` files of that install, and the hashes of the user-scope and project-scope agent definitions and guidance file; it compares them before each review dispatch, and a difference stops the dispatch and is reported. During these reviews main reads the procedures by their path in the cache and records the paths it read. The candidate text is used only in T2's scenario comparison.

## User Stories

1. As a user, I want each delegation rule written in one place, so that a rule change is made once and cannot leave a stale copy behind.
2. As a user, I want reviews to load less repeated text, so that each review costs less context.
3. As a user, I want a pointer to tell main what it does at that step, so that the procedure still reads as a sequence of actions.
4. As a user, I want main to read review state before it writes a brief or decides a review step, so that moving a rule never lets main act without it.
5. As a user, I want main to read review state again after a compaction, so that lost context does not drop a rule.
6. As a user, I want a quick lookup by scout or Explore not to load review state, so that small tasks stay cheap.
7. As a user, I want a condition that only one copy carried to keep exactly its original scope, so that consolidation neither widens nor narrows a rule.
8. As a user, I want every instruction a role must receive to stay in its brief, so that a role, which never reads review state, still gets it.
9. As a user, I want my execution restriction, the Adversarial review target authorisation and the disclosure limits to reach the roles exactly as before, so that the review gate is not weakened.
10. As a user, I want the role definitions unchanged, so that I do not need to run setup update.
11. As a user, I want contradictory copies of a rule left alone and recorded, so that a refactor does not decide a rule question on my behalf.
12. As a user, I want runtime text to state rules as they apply now, so that I do not need the release history to read a rule.
13. As a user, I want the setup procedures to keep describing older templates the tool still handles, so that an old installation is still guided correctly.
14. As a user, I want the few wording fixes listed one by one with their reason, so that I can check none of them changes a rule.
15. As a user, I want preview to describe Adversarial review timing as auto actually runs it, so that its summary is accurate.
16. As a user, I want the reference to explain what each rule is for and link to it, so that I read the reason in the reference and the rule in one place.
17. As a user reading Traditional Chinese, I want the zh-TW reference to follow the same structure as the English one, so that both languages stay aligned.
18. As a user, I want existing links into the reference and its version history kept, so that old update notes still work.
19. As a user, I want the READMEs to stop promising a complete restatement, so that they describe what the reference is.
20. As a user, I want glossary entries that state rules to point to the rule's owner, so that the glossary defines terms and does not drift.
21. As a maintainer, I want an ADR for the one-place rule and the reference's new role, so that a later reader knows why the reference no longer restates rules.
22. As a maintainer, I want tests that fail if a restatement comes back, so that duplication does not regrow.
23. As a maintainer, I want tests that fail if a pointer names something that no longer exists, so that pointers do not rot.
24. As a maintainer, I want a baseline inventory checked in both directions, so that a dropped or invented condition is caught.
25. As a maintainer, I want scenario answers from the old and the new text compared, so that preserved contracts are shown in use, not only as text.
26. As a maintainer, I want this change reviewed under the installed 0.29.0 rules, so that the rewritten instructions do not judge themselves.
27. As a user, I want the update note to tell me no setup update is needed and how to go back to 0.29.0, so that I update with confidence.

## Implementation Decisions

- Ownership follows responsibility, as review state's own opening divides it: review state names the state every step keeps, and each procedure states how its step changes it. A rule that several procedures use but one procedure owns stays there.
- Pointers name review state's items by their bold names, since they are list items, not headings.
- Main reads all of review state, not chosen sections: main already follows its links during every review, so the saving is the restatements, and a per-procedure list of sections would be another copy to keep in step.
- The Runtime part is Security-critical, so it gets a security analysis before plan review, is implemented by security-executor and gets one Adversarial review at the final commit; the inventory supports these reviews and exempts the part from none of them.
- Contradictions found while building the inventory narrow this work rather than widen it.
- The setup procedures' older-template sentences stay because `scripts/feather_config.py` still implements them.
- The release is 0.30.0, a minor version, because the text main loads for every review is reorganised and gains a reading rule, though no installed file changes.
