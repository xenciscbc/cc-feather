# Test speed-ups, third batch

Label: `ready-for-agent`

Vocabulary follows [CONTEXT.md](../../CONTEXT.md), which defines Plan and Claim. This spec applies two speed-ups found while counting the processes cc-feather's own tests start, recorded in `.feather/handoffs/test-git-process-reduction.md`: after the second batch (`docs/specs/test-speedup-batch-2.md`, landed at ba7dc12), the tools' own Git commands are most of the processes left. The user decided on 2026-11-26, after a trial on a scratch copy, that these two test-only changes form this batch, and that merging the tool's two adjacent `rev-parse` calls in `skills/handoff/scripts/feather_handoff/storage.py` is dropped, because the whole suite showed no gain beyond run-to-run variation. This spec changes only files under `tests/`; it changes no shipped file, so it is landed without a version change or tag, as the first two batches were, and the next release carries it. Every speed-up meets the correctness bar of [the shared test criteria](../../skills/test-speedup/references/test-criteria.md).

## Problem Statement

A count on 2026-11-25 at cf1780f found that the suite starts about 10,700 processes, 85% of them started by the tools themselves, and `git rev-parse` is 48% of all of them. Two groups of tests pay for Git work that is not what they verify:

- `tests/test_handoff_header_boundary.py` runs the handoff tool about 167 times on a temporary directory that is not a Git repository, and every run first discovers the root with Git (about 345 of its 512 Git commands). What the module verifies is where a work header ends, in reads and updates, which does not depend on root discovery.
- The leases tests call the lease tool's `list` to read the state of one lease in 21 places, and each listing runs about 17 Git commands and starts the handoff tool for the records next to each checkout; a trial measured about 0.8 s per listing. Of those 21, 18 only check what the lease file holds: that it is gone, or that it holds a given lease. The other three verify the listing itself.

A trial on 2026-11-26 at cf1780f, on an exported copy, three interleaved runs each, measured the five modules these changes touch at about 88.8 s before and 66.3 s after (medians), all passing.

## Solution

Two changes, one per ticket. The header-boundary tests confirm their temporary root with `--exact-root`; the leases tests read the lease file directly where they only check the lease file's content, and keep the listing where the listing's own behaviour is what they verify. Every test keeps its assertions, its inputs and what it verifies, and each change names the tests that keep verifying what it no longer passes through. After both are accepted, main measures the modules before and after and records the gain.

## User Stories

1. As the maintainer, I want the header-boundary tests to skip root discovery, so that about 345 Git commands per run of that module stop.
2. As the maintainer, I want root discovery of a non-Git directory to stay verified elsewhere, so that the header-boundary change hides nothing.
3. As the maintainer, I want the leases tests that only check a lease file's content to read that file, so that 18 listings per run stop.
4. As the maintainer, I want the tests whose subject is the listing to keep calling it, so that the listing's view of a lease, the version it shows and its refusal to reclaim an old lease stay verified.
5. As the maintainer, I want each replaced listing to name the tests that keep verifying what the listing showed there, so that the change can be checked against the correctness bar.
6. As the maintainer, I want the gain measured and recorded, so that I know what the batch saved.
7. As the maintainer, I want no release for this batch, so that users are not asked to update for a change that does not affect them.

## Implementation Decisions

- **Header boundary with an explicit root (ticket 01).** In `tests/test_handoff_header_boundary.py`, the four test classes (`HeaderBoundaryTest`, `HeaderBoundaryControlTest`, `HeaderLineEndingTest`, `HeaderFenceTest`) derive from a module-local base, derived from `tests.test_handoff_local_fixes.InProcessBase`, whose `run_tool` calls `tests.handoff_in_process.run_local` with `--exact-root` before the command's own arguments, so every tool call of these classes, `archive` included, confirms the test's temporary directory as the root. Nothing else in the module changes. The module's assertions never read `root`, and tracking still runs on each successful write. What is no longer exercised here, root discovery of a directory that is not in a Git repository, stays verified by `tests/test_handoff_roots.py`'s `test_git_subdirectory_resolves_root_and_non_git_is_complete`, which lists a non-Git directory and checks `root.state` `non-git`, then the Git root of a subdirectory, then `--exact-root`. `tests/test_handoff_local_fixes.py`, `tests/handoff_in_process.py` and every other module that uses `InProcessBase` are unchanged.
- **A direct read of a lease file (ticket 02).** In `tests/test_leases_tool.py`, `LeaseBase` gains a helper, `lease_state(checkout)`, that reads the lease file of a checkout of the fixture (`main`, whose key is `MAIN_KEY`, `wt1` or `wt2`) from `.feather/leases/` and returns `{"state": "absent"}` when the file does not exist, and otherwise `{"state": "held", "lease": <its JSON>, "version": <the SHA-256 of its bytes>}`; any other checkout fails the test. It reads only, and it does not compute ages.
- **Lease-content checks read the file (ticket 02).** These 18 checks replace `self.entry(self.listing(...), <checkout>)["lease"]` with `self.lease_state(<checkout>)` and keep their assertion as it is:
  - `tests/test_leases_locks.py`: the check after a failed lock in `test_when_locking_fails_the_lease_is_withdrawn_and_the_acquire_fails`, the one in the helper `assert_blocked`, and the one in `test_release_removes_its_own_lock_and_then_the_lease`, each that the lease is absent.
  - `tests/test_leases_park.py`: the helper `assert_released` and `test_the_main_worktree_is_never_parked`, that the lease is absent; `test_parking_with_another_lease_id_changes_nothing`, that the lease is unchanged; `test_continue_in_needs_park_and_a_registered_checkout`, that it is held.
  - `tests/test_leases_takeover.py`: `test_renew_never_acquires`, that it is absent; and six calls of the helper `shown()`, which become calls of a new helper `held(checkout)` that returns `lease_state(checkout)` after asserting its state is `held`: in `test_renew_changes_the_purpose_when_given`, `test_a_concurrent_reader_delays_a_renew_but_does_not_fail_it`, `test_a_takeover_with_a_stale_version_refuses_and_returns_the_current_lease`, `test_a_takeover_of_an_absent_lease_refuses_and_acquires_nothing`, `test_a_takeover_needs_a_version_and_valid_input`, and the second check of `test_no_age_reclaims_a_lease_and_nothing_takes_one_over_automatically`, after the renew with another lease id.
  - `tests/test_leases_tool.py`: `test_release_with_the_holders_lease_id_returns_the_lease`, `test_a_held_critical_section_is_reported_at_once_and_never_broken` and `test_a_concurrent_reader_delays_a_release_but_leaves_nothing_behind`, that the lease is absent; `test_release_meets_a_held_critical_section_and_changes_nothing`, that it is unchanged.
- **Listing checks that stay (ticket 02).** `shown()` keeps calling the listing, and these three calls of it stay: in `test_renew_with_the_holders_lease_id_updates_the_last_reported_activity`, the only check of the ages the listing shows for a held lease (`age_seconds`, `activity_age_seconds`) and of its version after a renew; in `test_a_takeover_with_the_shown_version_writes_a_new_lease_and_moves_the_lock`, whose subject is taking over with the version the listing shows; and the first check of `test_no_age_reclaims_a_lease_and_nothing_takes_one_over_automatically`, that a listing does not reclaim a 400-day-old lease. Every other listing in the leases modules stays as it is: those that check a lock, the work left in a checkout, an unknown lease or an orphan, and the listing tests of `tests/test_leases_listing.py`.
- **What keeps verifying the listing's view (ticket 02).** The 18 replaced checks no longer pass through the listing's reading of the lease file, its re-locking of a held lease without a lock, or its view of a lease. These stay verified by tests this spec does not change: that a free checkout is listed `absent` with "no registered use", by `test_the_listing_never_calls_a_checkout_usable` in `tests/test_leases_listing.py`; that a held lease is listed `held` with its lease, by `test_release_with_another_lease_id_reports_changed_hands_and_changes_nothing` in `tests/test_leases_tool.py`; that the listing's version is the lease's version, by the two listing checks of `test_a_takeover_with_the_shown_version_writes_a_new_lease_and_moves_the_lock` in `tests/test_leases_takeover.py` (`shown()` before the take-over, and the listing after it, of `lease` and `version`, which this spec does not change either) and by the renew test above; that the listing shows a held lease's ages, by the renew test above; that a listing re-locks a held lease without a lock, by `test_listing_locks_a_lockless_held_lease_again_and_reports_it` and `test_a_lease_whose_accepted_session_lock_was_released_is_locked_again_with_its_own_reason` in `tests/test_leases_locks.py`; and that a lease is unknown when its worktree is prunable or missing, by `test_a_prunable_or_missing_worktrees_lease_is_kept_and_listed_unknown` in `tests/test_leases_listing.py`. A listing re-locks only a held lease whose linked worktree has no lock, and at each of the 18 places the lease is absent, or held with the lock its acquire set; the trial on 2026-11-26 passed with the listing removed from all 21 places, so no later assertion depends on a re-locking by these listings.
- **Leases testing decision (ticket 02).** The docstrings of `tests/test_leases_tool.py` and `tests/test_leases_takeover.py` say that a test that only checks a lease file's content reads the file, and that the tests whose subject is the listing call it.
- **Measurement.** After the last ticket is accepted and before the Plan is landed, main measures the five modules the tickets change (`test_handoff_header_boundary`, `test_leases_tool`, `test_leases_takeover`, `test_leases_park`, `test_leases_locks`) and `test_leases_listing`, which imports the changed fixture, at the Plan base and at the final commit in the same session: each module run with `python -B -m unittest tests.<module>` three times, the two trees interleaved, with the median of each reported. Scratch copies of the Plan base live under `J:\gotmp\` and are removed afterwards.
- **Validation record.** Main records the review round and the measurement under a heading of its own in `docs/setup-validation.md`, `## Test speed-ups, third batch (on main after 0.47.0)`, after the Plan's review round, as for the first two batches.
- **Not affected.** Every shipped file: skills, templates, scripts, the plugin manifest, both READMEs, the reference documents, CONTEXT.md, `docs/upstream-manifest.json` and `docs/compatibility.md`. Every test module not named above.

## Testing Decisions

- These are changes to tests, so the evidence is that the same tests pass with the same assertions: each ticket's diff changes no assertion and no input a test verifies, and its modules pass.
- A test id list taken with `unittest`'s discovery before and after each ticket is equal.
- Ticket 01's acceptance is `python -B -m unittest tests.test_handoff_header_boundary tests.test_handoff_roots`; ticket 02's is `python -B -m unittest tests.test_leases_tool tests.test_leases_locks tests.test_leases_park tests.test_leases_takeover tests.test_leases_listing`, with `FEATHER_LINK_TEST_DIR` under `J:\gotmp\`. Those are the modules each ticket changes, those that import what it changes, and the module that keeps verifying what ticket 01 stops exercising.
- The Plan's overall acceptance is the full suite, `python -B -m unittest discover -s tests -t .` with `FEATHER_LINK_TEST_DIR` under `J:\gotmp\`. It is the Plan's overall acceptance, which the final check runs for each commit to be landed, not for each Claim, and it is not part of any Claim's acceptance; each ticket cites it.

## Out of Scope

- Merging the tool's adjacent `rev-parse` calls, or any other change to shipped code.
- Stubs or fakes for Git; whether a given test may use one is decided per test in later batches.
- Caching root discovery across a test's calls.
- The listing checks that verify a lock, the work left in a checkout, an unknown lease or an orphan.
- Process-level parallel runs, and a time limit for the whole run (`.feather/handoffs/test-run-time-limit.md`).
