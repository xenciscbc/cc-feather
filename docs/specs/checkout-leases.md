# Checkout leases

Label: `ready-for-agent`

Vocabulary follows [CONTEXT.md](../../CONTEXT.md), which defines Working checkout, Handoff store, Plan, Claim, Unplanned work and Assignment; this spec adds Checkout lease and Lease holder.

## Problem Statement

Several Claude Code sessions often work in one repository at the same time, each in its own Git worktree: worktrees made with `EnterWorktree`, with `claude --worktree`, for a subagent's isolation, by the desktop app or by hand. Many of them are kept after their work ends and reused later. When a session is about to start work, nothing tells it which of these checkouts is free and which another session is still using. `git worktree list` shows that a worktree exists, not that anyone is in it; `EnterWorktree` with a path enters any registered worktree without checking; cc-feather's history lock only covers a few seconds of history writes; a handoff record's environment says which checkout wrote it, not that the checkout is in use now.

The outcome is two sessions changing one checkout, a commit mixing another session's half-done work, or a session that does not dare reuse or clean a worktree because it cannot tell whether someone is in it. A worktree can also look idle while a dead session's uncommitted changes are still in it, which a careless reuse destroys.

## Solution

cc-feather gains an independent capability that keeps one Checkout lease per checkout of the repository, readable from any checkout. The main Agent takes a lease when it starts changing a checkout and returns it when it stops using it, renews the lease's last reported activity at the same points the handoff maintenance updates its record, and records what the lease is for, such as the ticket being implemented. A listing shows every checkout Git registers with its lease, the work left in it and any Git lock, as facts; the user decides what is usable. A lease is never taken over automatically. When a merged branch's worktree is kept for reuse, it is parked on a detached HEAD so the branch can be deleted.

A held lease on a linked worktree is protected by a Git worktree lock, so that Git, Claude Code's cleanup and tools that do not know the lease also see the worktree as in use and do not prune or remove it. Normally the lock is the lease's own, with a reason naming the lease; in a worktree the session itself just created, Claude Code's own session lock already sits there and is accepted in its place. When a held lease is found without any lock, the tool locks it again. The lease stays the authority and carries the information; the lock only protects it.

The lease is cooperative: it tells sessions that follow the rule who is using a checkout. It does not stop a session that ignores it, and taking over a lease does not stop the old session.

## User Stories

1. As a user running several sessions in one repository, I want to see which checkouts another session is using, so that I do not start work in one of them.
2. As a user, I want a session to take a lease when it starts changing a checkout, so that other sessions can see the checkout is in use.
3. As a user, I want a lease to record what it is for, such as the ticket being implemented, so that I know what the other session is doing.
4. As a user, I want the lease of a serial Plan to cover the whole Plan in that checkout and its purpose to follow the current ticket, so that no other session slips into the checkout between two tickets.
5. As a user, I want a session implementing Claims in parallel to hold one lease per worktree it uses, so that each of those worktrees shows as in use.
6. As a user, I want a session to return the lease of a parallel worktree once its work is merged back and the worktree is no longer used, so that the worktree becomes available again.
7. As a user, I want Unplanned work to take a lease at its first change, so that work without a ticket is also visible.
8. As a user, I want sessions that only read files not to take a lease, so that looking at a checkout does not block it.
9. As a user, I want sessions writing cc-feather's own records in the main worktree not to need its lease, so that sessions in other worktrees never block each other through the main worktree.
10. As a user, I want a merge done inside the main worktree to take the main worktree's lease for the merge, so that no other session changes it at the same time.
11. As a user, I want opening or entering a worktree not to count as using it, so that a lease means work has started.
12. As a user, I want the main Agent, not a subagent, to take and return leases, so that one party decides which checkout each piece of work uses.
13. As a user, I want delegated work to run under the main Agent's lease, so that a subagent never competes with its own session for a checkout.
14. As a user, I want the main Agent to take a lease on a subagent's isolated worktree that was kept with changes, so that the changes waiting to be integrated are visible as in use.
15. As a user, I want a lease's last reported activity renewed at milestones, blockers, before the session waits for me and at completion, so that I can tell a session that recently reported from one that has been silent for hours.
16. As a user, I want the last reported activity labelled as reported, not as liveness, so that I do not read a waiting session as dead or a crashed one as alive.
17. As a user, I want a session that finds its lease taken over to stop and report, so that it never overwrites the new holder's lease or keeps working in a checkout it no longer holds.
18. As a user, I want a session that cannot take a lease to stop and show me the holder, purpose, start time, last reported activity and age, so that I choose what happens next.
19. As a user, I want my choices then to be working in the main worktree, using an idle worktree, opening a new worktree, or taking over a lease I judge left behind, so that work is never blocked by a dead session.
20. As a user, I want a lease never to be taken over automatically, so that two sessions never end up in one checkout because a time limit expired.
21. As a user, I want a takeover to check the lease I was shown is still the one there, so that I never replace a lease that changed while I decided.
22. As a user, I want two sessions taking the same free checkout at the same moment to have exactly one winner, so that a race cannot give the checkout to both.
23. As a user, I want a released or replaced lease to be removable only by its own holder, so that an old session cannot release a new holder's lease.
24. As a user, I want the listing to cover every checkout Git registers, including the main worktree and worktrees outside `.claude/worktrees/`, so that nothing in use is missed.
25. As a user, I want the listing to show uncommitted and untracked changes, commits not on the default branch and handoff records naming the checkout next to each lease, so that I see left-behind work before I reuse a checkout.
26. As a user, I want the listing never to call a checkout usable on its own judgment, so that a feature branch I mean to continue is not hidden or offered as empty.
27. As a user, I want a checkout with no lease shown as having no registered use, not as free, so that a session outside the rule is not mistaken for no session.
28. As a user, I want a lease that cannot be read, or a query that fails, shown as unknown, so that an error never looks like a free checkout.
29. As a user, I want the listing to show a Git worktree lock and its reason as written, so that I see when a Claude Code agent or background session holds a worktree that has no lease.
30. As a user, I want a held lease on a linked worktree to lock that worktree in Git, so that `git worktree prune`, a plain `git worktree remove` and Claude Code's periodic cleanup leave a worktree in use alone.
31. As a user of a tool that does not know about leases, I want a leased worktree to show as locked in `git worktree list`, so that I can see it is in use without cc-feather.
32. As a user, I want cc-feather to remove only a lock whose reason names its own lease, so that a lock Claude Code or I set is never released by it.
33. As a user, I want a session not to take a lease on a worktree that someone else has already locked, and to show me the lock's reason, so that a running Claude Code agent, another session's lock or my own lock is respected.
34. As a user, I want a session to take a lease in a worktree it has just created even though Claude Code locked that worktree for the session, so that the lock Claude Code puts on every worktree it creates does not block its own session.
35. As a user, I want a lock I find on a worktree I merely entered or reused to count as someone else's, so that a lock left by another session is never mistaken for mine.
36. As a user, I want a held lease whose worktree has lost every lock to be locked again by the next listing or acquire, so that a worktree left by a crashed or exited session stays protected from cleanup.
37. As a user, I want a lease whose worktree Git no longer registers to be cleaned up automatically and reported, so that removed worktrees leave no stale leases.
38. As a user, I want a lease whose worktree Git marks prunable to stay and show as unknown, so that I decide what happened to that directory.
39. As a user, I want a kept worktree whose branch is fully merged to be parked on a detached HEAD at the default branch when its holder stops using it, so that I can delete the branch and reuse the worktree.
40. As a user, I want work in a reused parked worktree to start on a new branch from the latest default branch, so that it never builds on a stale commit.
41. As a user running parallel Claims, I want a worktree whose branch was merged into the worktree the work continues in to be parked too when it is returned, so that its branch can be deleted although it has not reached the default branch yet.
42. As a user, I want parking to happen only when the worktree is clean, its branch is fully contained in the default branch or in the branch the work continues in, and it is not the main worktree, so that parking never loses work.
43. As a user, I want parking skipped with the reason reported when a condition fails, so that I know why the worktree was left as it is.
44. As a user, I want parking never to delete a branch or a worktree, so that those decisions stay mine.
45. As a user, I want returning a lease never to reset, clean or switch the checkout, and taking one never to authorise changing what it holds, so that occupancy and the checkout's content stay separate concerns.
46. As a user, I want a handoff completion not to return the lease, so that a session moving on to the next task in the same checkout keeps it.
47. As a user, I want leases stored in one place shared by every checkout and independent of where handoff records are stored, so that every session reads the same state whatever its tracking choice.
48. As a user, I want the persistent rule that tells sessions to take leases to be a setup component I install and remove on its own, off by default, so that I opt in.
49. As a user, I want the capability to work without a handoff record, so that sessions without handoff maintenance are covered too.
50. As a maintainer of codex-feather, I want the lease format and location usable by another tool, so that codex-feather can follow later.
51. As a user, I want the documentation to state what a lease cannot do, so that I do not rely on it to stop a session or a tool that ignores it.

## Implementation Decisions

- **Scope.** Checkouts of one Git repository on one machine: the main worktree and the linked worktrees Git registers. A checkout is not shared between Windows and WSL; cross-environment access to one checkout is out of scope.
- **A new skill and tool.** An independent cc-feather skill for checkout leases, with its own Python tool (standard library only, as the handoff tool), and a user-invocable listing command, `/cc-feather:worktrees`. The command is not read-only: its listing locks a lockless held lease again and removes orphan leases, and its text says so. Low-level file, path and lock helpers may be imported from the handoff tool's package, never moved out of it, so the handoff tool stays unchanged; the lease's lifecycle, location and rules do not depend on handoff records, the Handoff store selection or the review mode.
- **One lease per checkout.** The unit is the whole checkout, the main worktree included. A lease is keyed by Git's per-worktree administration identity (a reserved key for the main worktree), not by a caller-supplied path; the checkout's path is kept for display.
- **Lease content.** A schema version, the checkout key and display path, a lease_id that differs on every acquisition, a session label, the host and runtime, the zoned start time, the purpose and the zoned last reported activity. The tool process's PID is at most a diagnostic hint: the tool is a short-lived subprocess, so no recorded process proves the session is alive.
- **Location.** `.feather/leases/` under the main worktree, beside the Handoff store, used by every checkout of the repository whatever its handoff tracking choice or explicit root. The directory ignores itself with its own `.gitignore` holding `*`, so keeping leases changes no tracked file in any checkout, whatever the project's own ignore rules are, and the leases never show as untracked changes. When the main worktree or that directory cannot be established or written, the tool reports unknown or a failure and never stores the lease elsewhere.
- **Operations.** Acquire, renew (updates last reported activity and, optionally, the purpose), release, take over, list and park.
  - Acquire is an exclusive create; a held lease returns its holder information and acquires nothing. Whether the caller already holds it is decided only by the lease record and the caller's lease_id, never by a lock's reason alone.
  - Renew and release require the caller's own lease_id. A mismatch returns that the lease changed hands and changes nothing; renew never acquires.
  - Take over requires the version of the lease the user was shown and writes a new lease with a new lease_id; a changed lease refuses and returns the current one. A lock that is not the old lease's own, such as an accepted Claude Code session lock, is left as it is, and the result says that it stays.
  - Renew, release and take over replace or remove the lease inside a short metadata critical section, never by holding a lock for a whole session. Acquire's locking step, release's unlocking step, parking and the re-locking of a lockless lease run inside the same critical section, so they never interleave. A critical section already held is reported at once, never waited on or broken, and one left by a crash is reported with its holder and age for the user.
- **States.** A lease that is read is held or absent; an unreadable lease, or a location or query that fails, is unknown. A held lease is never reclaimed automatically, and no time threshold changes that.
- **When the main Agent takes and returns leases.**
  - It takes a lease when it starts implementing the first Claim of a Plan in a checkout, or at the first change of Unplanned work, and before running a writing test or a review that needs a stable checkout there. Reading a checkout takes none. Opening or entering a worktree (`EnterWorktree` by name or path, `claude --worktree`) is not taking it, and neither is starting a session in the main worktree's directory.
  - Writing cc-feather's own records under the main worktree's `.feather/` (leases, handoff records, Dispatch records) is not changing a checkout and needs no lease, so sessions in other worktrees never contend for the main worktree to keep their records.
  - Merging into a branch inside the main worktree changes it, so the main Agent takes the main worktree's lease for the merge and returns it afterwards; landing by a push or a pull request does not touch the main worktree and needs none.
  - For a serial Plan one lease covers the Plan in that checkout, and the purpose follows the ticket being worked on. Parallel Claims use one lease per worktree; once a parallel worktree's work is merged back and it is no longer used, its lease is returned, after parking where parking applies.
  - It renews the lease at the points where handoff maintenance updates its record: milestones, blockers, before stopping to wait for the user, and completion, whether or not a handoff is active.
  - It returns a lease when it stops using the checkout. Completing a handoff record does not return it.
  - Subagents never take, renew or return leases. Delegated work runs under the main Agent's lease; the main Agent decides which checkout each Assignment uses. A subagent's isolated worktree needs no lease while the subagent runs, when Claude Code holds its own agent lock on it; when it is kept with changes, that lock is gone, and the main Agent takes a lease on it, with the lease's own lock, until the changes are integrated.
- **When a lease cannot be taken.** The main Agent stops and shows the holder, purpose, start time, last reported activity and age, and the user chooses: work in the main worktree, use an idle worktree, open a new worktree, or take over a lease the user judges left behind. A session that finds on renew or release that its lease changed hands stops using that checkout and reports.
- **Listing.** Every worktree in `git worktree list`, the main worktree included, with its path and branch or detached HEAD, its lease state and contents, its uncommitted and untracked changes, its commits relative to the default branch, the handoff records that name it, whether its directory still exists, and a Git worktree lock with its reason as written and its parsed process ID, marked as the lease's own lock, an accepted Claude Code session lock, or another holder's lock. The tool does not probe whether a process still exists. A cc-feather lock without its lease is reported as a mismatch; a held lease without any lock is locked again, as below, and reported, and only a held lease that cannot be locked again (its directory missing or Git marking it prunable) is reported as having no lock. Each part that cannot be established is unknown. The listing reports facts and never calls a checkout usable; a checkout without a lease is shown as having no registered use.
  - The default branch is the one `origin/HEAD` names; without it, the one of `main` and `master` that exists when exactly one does; otherwise it is unknown, the commits part shows unknown and parking is skipped with that reason.
  - The handoff records that name a checkout are found by reading the handoff tool's own `list` output, without changing the handoff tool, always starting from the main worktree so the result is the same from any checkout: the main worktree's store through `list`, and each other store that `list` reports under `other_stores` through `list` with that checkout as explicit root, since `other_stores` itself carries no environment field. A record names the checkout when its environment field contains the checkout's path, compared with separators unified and, on Windows, case-insensitively. A store whose `list` is partial or fails makes this part unknown only for the checkouts whose records could be in it, never for the whole listing.
  - The commits part compares a checkout's HEAD with the local default branch when it exists and with the remote default branch otherwise, and names which one it used.
- **Git worktree locks protect leases.** Git keeps one lock per linked worktree and cannot lock the main worktree, so the main worktree has a lease only. Claude Code locks every worktree it creates for a session (reason `claude session <name> (pid N)`) and every isolated subagent's worktree while the subagent runs (reason `claude agent <id> (pid N)`), releases the agent lock when the subagent returns, and leaves a session lock behind after a non-interactive run. For a linked worktree, acquire looks at the lock it finds:
  - No lock: it creates the lease and then locks the worktree with a reason that names cc-feather and the lease_id; when locking fails, the new lease is withdrawn and the acquire fails. A worktree whose directory is missing or that Git marks prunable is not acquired; the result says so.
  - A Claude Code session lock in a worktree this session itself created (with `EnterWorktree` by name, or `claude --worktree` with a new name): the main Agent passes the lock reason it observed right after creating the worktree, and the tool accepts that lock in place of its own only when the current reason is exactly that one. It creates the lease and never changes the lock.
  - Any other lock, including a Claude Code session lock on a worktree the session entered with `EnterWorktree` by path or reused with `claude --worktree` and an existing name, an agent lock, a lock of another tool or the user's: it acquires nothing and returns the reason, and the main Agent stops as when a lease is held. Entering does not establish whose a lock is: Claude Code keeps the existing lock when a session enters a worktree by path.
  - Release, after any parking, removes the lock only when its reason names the releasing lease, and then removes the lease; an accepted Claude Code lock stays. Take over replaces only a lock whose reason names the old lease with one naming the new lease, inside the lease's critical section.
  - The tool never removes or changes a lock whose reason does not name one of its leases.
  - When the tool lists or acquires and finds a held lease on a linked worktree that has no lock at all, for example after Claude Code released its own lock when the session ended, it locks the worktree again with the lease's own reason and reports it. It skips a worktree whose directory is missing or that Git marks prunable: Git can lock such a worktree, and the lock hides that the directory is gone, so that lease stays unknown instead. A crashed holder therefore leaves the lease and a lock, which keeps the worktree from being cleaned up until the user takes the lease over, except in the window before the next listing or acquire.
  - A locked worktree refuses `git worktree remove` without force and `ExitWorktree` removal, so removing a worktree in use first needs its lease returned and its lock released by whoever set it.
- **Orphan leases.** A lease whose checkout Git no longer registers is removed by the tool when it lists or acquires, and the removal is reported. A lease whose worktree Git marks prunable, or whose directory is missing while Git still registers it (a locked worktree is never marked prunable), stays and is shown as unknown. Because a leased linked worktree is locked, this mostly happens after a forced removal or a deleted directory.
- **Parking.** Parking requires the holder's own lease_id; with another one it changes nothing, as release does. When the holder stops using a linked worktree that is clean (no uncommitted or untracked changes) and whose branch is fully contained in the default branch, or in the branch of the checkout the work continues in when the main Agent names one, the tool detaches its HEAD and then the lease is returned. It detaches at the local default branch's commit when the branch is contained there, and otherwise at the named checkout's branch commit; when the default branch exists only on the remote, containment in it counts as a failed condition with that reason. The tool checks the containment itself; a named checkout's branch that does not contain it counts as a failed condition. When a condition fails, the worktree is left as it is, the reason is reported and the lease is returned as usual. Parking never deletes a branch or a worktree and never applies to the main worktree.
  - Example: parallel Claims use worktrees X and Y; Y's branch is merged into X's, and work continues serially in X. Returning Y names X, so Y is parked and its lease and its own lock are returned, while X keeps its lease.
- **Reusing a parked worktree.** A parked commit can be far behind by the time the worktree is reused, so the main Agent starts new work there on a new branch from the latest default branch (the remote's default branch when one exists, as Claude Code's default worktree base does), never from the parked commit itself, unless the user names another base.
- **Setup component.** `cc-feather:setup` gains a third independent component, `leases`, that installs the persistent rule block telling the main Agent to take, renew and return leases as above. It is not installed by default. Existing component selections keep their meaning: `both` still means handoff and delegation and never includes `leases`, and the default component of a mutation stays delegation. `check` and `show` report all three components by default, so the new one shows as not installed.
- **Delegation and handoff pointers.** The delegation skill's dispatch section points at the lease rules where it assigns checkouts to Assignments. Handoff records and the handoff tool are unchanged.
- **Trust.** Lease records are trusted like other `.feather/` records; a forged or hand-edited lease is a documented residual, not a defended case.

## Testing Decisions

- A good test drives the lease tool as a subprocess against a temporary real Git repository with real linked worktrees and asserts only its JSON result and exit status, never internal state.
- **Tool seam.** Acquire on a free checkout succeeds and a second acquire returns the holder; two processes acquiring the same checkout concurrently produce exactly one winner; different checkouts are acquired independently; renew and release with an old lease_id change nothing; a takeover with a stale version refuses; a takeover makes the old holder's renew report a changed lease. The listing covers the main worktree and a worktree outside `.claude/worktrees/`, shows uncommitted, untracked and unmerged work, shows a Git lock reason verbatim, shows an unreadable lease as unknown and an absent one as no registered use. Acquiring a linked worktree locks it with a reason naming the lease and the main worktree gets no lock; a worktree carrying a session lock whose reason matches the one the caller attests is acquired without changing that lock, and one whose reason differs, or that the caller does not attest, is not; a worktree locked by another holder is not acquired and its reason is returned; release leaves an accepted lock in place; a held lease whose worktree has no lock is locked again on listing and on acquire; release removes only its own lock and leaves a foreign one; a takeover moves the lock to the new lease; `git worktree prune` and a plain `git worktree remove` leave a leased worktree; a lease without its lock and a cc-feather lock without its lease are reported as mismatches. An orphan lease is removed and reported; a prunable worktree's lease stays unknown. Parking detaches a clean worktree whose branch the default branch contains at the default branch, and one whose branch a named continuing checkout's branch contains at that branch; it leaves a dirty one, one whose branch neither contains, one naming a checkout whose branch does not contain it, and the main worktree unchanged with the reason. A tracked checkout and an explicit root read the same leases as an untracked one. Acquiring and releasing from a linked worktree, with untracked and with tracked handoff records, leaves the main worktree's `git status --porcelain --untracked-files=all` unchanged. The default branch resolves from `origin/HEAD`, from a lone `main` or `master` without a remote, and is unknown otherwise. A handoff record whose environment names the checkout is listed, one naming another checkout is not, and an unreadable store makes that part unknown. A held lease on a worktree whose directory was deleted stays unknown and is not locked again, and acquiring such a worktree is refused. A tracked linked worktree's record naming itself is listed the same from the main worktree and from that worktree. Parking is skipped with the reason when the default branch is unknown. Parking with another lease_id changes nothing, and a critical section already held is reported at once. Prior art: the handoff tool's tests, which run the tool as a subprocess against temporary repositories with linked worktrees, including its shared store and history lock tests.
- **Rule text seam.** A text-contract test pins the decision-carrying sentences: who takes and returns leases and when, that opening a worktree or starting in the main worktree is not taking one, that writing cc-feather's own records needs no lease, that a merge inside the main worktree takes its lease, renewal points, return on stopping use and not on handoff completion, subagents holding none, the choices on a held lease and that no lease is taken over automatically, that the listing never calls a checkout usable, that a held lease on a linked worktree is protected by its own lock or by the session lock of a worktree the session itself created, that a lock on a worktree only entered counts as another holder's, that a lockless held lease is locked again, parking's conditions, that a reused parked worktree starts a new branch from the latest default branch, that only the lease's own lock is ever removed, that returning a lease never resets, cleans or switches the checkout and taking one never authorises changing it, that last reported activity is reported activity and not liveness, that the listing command locks again and removes orphan leases, and the cooperative limits. It also pins the setup component's rule block and the delegation pointer. Prior art: the existing text-contract test modules for the delegation rules.
- **Setup seam.** The setup tool's existing install, update and remove tests gain the new component, including that installing or removing it leaves the handoff and delegation components untouched, that the default `check` reports it as not installed, that `install --component both` does not install it, and that the default mutation component is still delegation.
- Claude Code's own `EnterWorktree`, its locks and its cleanup are not driven; the tests use Git's lock and prune behaviour directly, setting locks with Claude Code's observed reason formats, and Claude Code's sweep skipping locked worktrees is a documented reliance.

## Out of Scope

- Sharing one checkout between Windows and WSL, or between machines.
- Stopping, detecting or managing the processes of another session; a lease is cooperative.
- Changing Claude Code's worktree creation, its own Git worktree locks or its periodic cleanup, and removing any lock cc-feather did not set.
- Automatic takeover by age, a staleness threshold, a background heartbeat, and renewal through hooks.
- Deleting branches or worktrees, and cleaning or resetting a checkout.
- Making codex-feather follow the protocol; this spec only keeps the format usable by it.
- Leases for non-Git projects.

## Further Notes

- Decided with the user on 2026-11-09 after a two-round discussion with Codex (gpt-6-astra) and a grilling session; the agreed points of that discussion are folded into the decisions above.
- Claude Code facts this design relies on (code.claude.com docs, worktrees and sub-agents pages, read 2026-11-09): worktrees default to `.claude/worktrees/` for `EnterWorktree`, `--worktree` and isolated subagents, and only a `WorktreeCreate` hook moves them; a subagent gets its own worktree only through its frontmatter, the Agent call's isolation or the user's request; Claude Code holds a Git worktree lock while an agent or background session runs, and `-p` runs leave it until a stale-lock sweep; the periodic sweep removes only Claude-created subagent and background-session worktrees older than `cleanupPeriodDays` that hold no work and are not locked, and when it runs is not stated.
- A Git probe on 2026-11-09 showed that a worktree whose directory was deleted is listed as prunable, that `git worktree lock` still succeeds on it, and that the lock then hides the prunable mark and keeps `git worktree prune` from removing it.
- Probes on 2026-11-09 (Claude Code 2.1.319, Windows, headless runs in throwaway repositories): `--worktree` and `EnterWorktree` by name locked the new worktree at creation with `claude session <name> (pid N)`, and the lock stayed after the run; `EnterWorktree` by path into a worktree carrying another session's lock succeeded and kept that lock unchanged; an isolated subagent's worktree carried `claude agent <id> (pid N)` while it ran, the lock was gone after it returned, and the worktree stayed because it held changes; reusing a name with `--worktree` kept an unmerged commit, and in one run replaced the stale lock with the new session's while another worktree's stale lock stayed as it was. Interactive sessions were not probed.
- The decision and its rejected alternatives are recorded in [ADR 0020](../adr/0020-checkout-leases-are-cooperative-records-mirrored-by-git-worktree-locks.md).
- Mirroring leases with Git worktree locks was decided with the user after the discussion, replacing an earlier choice to only show locks: the lock protects a worktree in use from pruning, plain removal and Claude Code's cleanup, which skips locked worktrees and never releases a lock it did not set, and it makes the use visible to tools that do not read leases.
- The installed cc-feather roles set no `isolation` in their frontmatter, so no role runs in its own worktree unless the main Agent asks for it.
- Release: a new minor version, recorded under its version heading in `docs/setup-validation.md`. The release's live rehearsal includes one interactive session that the user runs from steps main gives, recording which lock Claude Code puts on a worktree it creates and whether it stays after exit; if the user does not run it, the validation entry records the interactive behaviour as unverified, a residual, and the release goes ahead.
