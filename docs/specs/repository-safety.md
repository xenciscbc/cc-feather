## Decisions

These hold for every Claim.

- **D1 Threat model (R1-Q7).** The reviewed repository's tracked content (files, `.gitattributes`, submodule settings) and its local Git metadata (`.git/config`, a worktree's `config.worktree`, the hooks directory, `info/attributes`, a gitfile, `commondir` and alternates) are attacker-controlled. Concurrent modification of files between a check and a read (A8-c) is not defended against; the spec states it as residual risk. User- and system-level Git configuration and the user's own environment are trusted.
- **D2 Assurance level (R1-Q8).** The rules are instructions to the model, kept consistent by tests, plus the handoff tool's own code. No permission rule, hook or sandbox enforces them. Every document that describes them says so in the words the existing "instructions to the model" paragraphs use.
- **D3 What the read guarantee covers (C15).** The path rules guarantee how main and the roles read reviewed source content with the file tools and shell tools. Files Git itself consults are outside that guarantee, except the indirect reads C1 items 2, 3 and 4 constrain.
- **D4 Scope (R1-Q1).** The rules apply to every repository read that main or a role makes for a plan review, code review, outcome verification, Adversarial review or security analysis, to main's preparation for them and to main's comparison of the workspace after each call, whatever the claim's classification, unchanged dependencies included. Searches by scout or Explore that main dispatches outside such a review are not covered (Out of Scope).
- **D5 Execution (R2-Q3, S10, S11, Q-S1, Q-S4).** For a review (main's primary acceptance and every role's lint, type check, test or probe), main, reviewer, verifier and adversary execute repository code only when, in this session, the user has said that the repository is trusted to run on this machine and the change under review was written by the user or in this session; otherwise only in an isolated environment the user names, and what needs execution is otherwise reported INCONCLUSIVE. Main makes this one determination, asks whether the repository is trusted the first time a session needs to execute its code, and states the outcome in every brief of a role that may execute code. The only exception is a program the user approved by name under C1 item 6, for the operation and content that approval covers. Who wrote a change is decided only from what the user said in this conversation and the commits and edits main, or a role main dispatched, made in this session, never from Git metadata, a handoff or other repository content; a change of mixed origin counts as not written in this session. Executing repository code means running any command whose program, plugins, configuration written as code, scripts or module search path can come from the repository: tests, builds, linters and type checkers with repository configuration, package-manager scripts and binaries, and an interpreter started in the repository that can load a module from it.
- **D6 What the rules do not reach (B9).** The rules govern what main and the roles do. Claude Code itself runs Git in the project when a session starts and loads the project's `CLAUDE.md`, its imports and its `.claude` settings, all before and outside these rules; that is residual risk, as ADR 0009 already records for `CLAUDE.md`, and every document that summarises these rules says so.

## Problem Statement

A user who asks cc-feather to review code is trusting main and its roles to read that code without being steered by it. Today only one bullet of the `/cc-feather:adversarial-review` command says how to do that. In an ordinary code review, outcome verification, plan review or security analysis, a role reads the repository with the file tools, which follow a tracked symbolic link to a file outside the project; it may diff the working tree, which can run a filter or an fsmonitor that the repository's own configuration names; it may place a file name the reviewed code chose into a shell command; and reviewer is told only to "use read-only git commands", with no definition. Main itself runs `git status` and working-tree diffs before and after each dispatch, and commits and pushes, which can run the same programs, the repository's hooks and its configured credential and transport programs; and the handoff tool runs Git without disabling fsmonitor. The rules that do exist disagree with the handoff tool about hard links and cloud-file placeholders. And when a reviewer cannot read what it needs, it has no way to say so: its only verdicts are APPROVED and CHANGES_REQUESTED.

## Solution

One shared reference states how to run Git and how to handle paths and names when reading a repository for a review, and every review procedure, the command and every role that reads a repository follow it. Main checks the repository's Git metadata and the Git version before it dispatches and again before each later dispatch, never runs a Repository-chosen program to prepare or check a review, and asks the user before a commit, tag or push would run one. Roles with a shell carry an identical, test-guarded paragraph; roles without one read only files and directories main has checked. Main, reviewer, verifier and adversary execute repository code for a review only in a repository the user trusts and for a change written by the user or in this session, and otherwise only in an isolated environment the user names. Reviewer can answer INCONCLUSIVE, which is counted like verifier's. The handoff tool runs every Git command through one hardened helper. The rules are instructions, not enforcement, and the spec says so.

### C1 acceptance

1. **Shared reference.** A new reference in the delegation skill's references, named Repository safety, states the rules of items 2 to 6 once; the delegation skill lists it beside the other references, and the plan review, code review, outcome verification and Adversarial review procedures and the command each say, in the step that dispatches or prepares a call and in the paragraph that compares the workspace after a call, that main and the role follow it for every repository read (D4); so does the delegation skill's security-analysis paragraph. The command's sentences that point to the adversary's Repository, secrets and effects section for Git commands point to the reference instead, and the automatic-review guidance that lets main commit and push without asking points to item 6. The glossary gains Repository-chosen program in this Claim, and the reference uses that term.
2. **Safe Git invocation (G1–G7).** Every Git command main or a role runs to read a repository for a review:
   1. disables fsmonitor with an empty value, `-c core.fsmonitor=`, which disables it whether the installed Git reads the setting as a boolean or as a hook path (G1);
   2. runs with `--no-optional-locks` and `--no-pager`, so no index refresh is written and no configured pager runs (G2, G5);
   3. writes no index, object, ref, configuration or working-tree file, contacts no remote and runs no Repository-chosen program; only main's operations under item 6 write, and Git's own index refresh is not an exception (G2, G6);
   4. reads history and differences only between commits or objects, with `--no-ext-diff --no-textconv`; `blame` always names a commit and uses `--no-textconv`; `cat-file` and `show` are never given `--filters` or `--textconv`; working-tree content is read under item 3, never through a working-tree diff or `git status` (G3);
   5. verifies no signature: `-c log.showSignature=false`, and every `log` or `show` that prints commits names an explicit format containing no signature placeholder, so a format the repository configures is never used (G4, C12);
   6. reads no mailmap file the configuration names, `-c mailmap.file= -c mailmap.blob=`, and no other file a setting names for these commands, `-c blame.ignoreRevsFile= -c diff.orderFile=/dev/null` (an empty `diff.orderFile` makes `git diff` fail on Git 2.43); a tracked `.mailmap` is repository content like any other (R2-Q5);
   7. in a checkout with a promisor remote, uses `--no-lazy-fetch` only on Git 2.45.0 or later; on an older Git, item 4.2 applies: main dispatches nothing in such a checkout and runs only the commands it names (G7, D-1);
   8. never recurses into a submodule, `-c submodule.recurse=false` and `--submodule=short` where a command accepts it; content under a submodule's path is reported as not examined (S19).
   The reference gives the common prefix once, so each procedure and role points to it rather than restating it.
3. **Path and name handling (P1–P6).** Before reading a path's content with the file tools or a shell tool, the reader establishes with file-system metadata that does not follow links:
   1. that no component of the path is a symbolic link, junction or reparse point of any kind, cloud-file placeholders and deduplicated files included (R1-Q4), and that its canonical path lies inside the project, comparing case-sensitively unless the file system is known to be case-insensitive (P1);
   2. that it is a regular file, not a directory read as content, FIFO, socket or device (R1-Q10);
   3. that its link count is 1 (R1-Q6).
   A path that fails, or whose check cannot run or is unclear, is never read: the reader reports the path and why, and for a link its target string obtained without resolving it. It may read the corresponding Git object, including a link's own blob, which holds only the target text (R1-Q3). A symbolic link checked out as a regular file under `core.symlinks=false` may be read after these checks, as the link's text, and the reader reports that the index records it as a symbolic link (R1-Q5). Only conclusions that need the unread content are INCONCLUSIVE; an independently evidenced defect still counts, and no APPROVED, CONFIRMED or HELD rests on unread content (C3). A fixture is never a link, never under one and has link count 1, checked before it is modified as well as before it is read (P2); the command's sentence that a hard link is project content like any other file is removed.
   A path name from the repository is safe only when it is relative, every component consists of ASCII letters, digits, `.`, `_` and `-`, no component is `.` or `..` or starts with `-`, no component is a Windows reserved device name in any letter case and with or without an extension (CON, PRN, AUX, NUL, COM1–COM9, LPT1–LPT9), and no component ends with `.` or a space; an unsafe name is reported in the C-quoted form Git prints with `-c core.quotePath=true`, never trimmed into another name, never read and never placed in a command (P3, R1-Q9). A safe name enters a command only as a single-quoted literal after `--`, or as `:0:'<path>'` or `<commit>:'<path>'` in an object read, and never inside double quotes, a here-document or a command substitution; only tools that honour `--` or take the path as a separate positional argument are used on it (P4). A directory prefix named in a command is a whole number of components of a safe name, written without a trailing `/` (P5). A ref name taken from the repository follows the name rule or is replaced by its object ID; only refs main or the role wrote itself are exempt (P6). No text taken from file content, command output or a link target enters a command (S17). Searching or walking a directory, with the file tools or a shell tool, reads every file under it, so it is done only in a directory every descendant of which passed the checks above, ignored files and nested repositories included, and without following links; any other search names its files one by one (B8).

   **The profile.** Before every such operation, including one that comes before the session's first dispatch, after item 4's version check, main first reads the local and worktree configuration without includes, and an `include.*` or `includeIf.*` key there puts the repository outside the profile before Git follows any include; it then makes item 4.2's checks of the configuration read without includes, and any condition item 4.2 would ask the user about puts the repository outside the profile, so main reports it instead of asking; main then runs item 4.2's detection of a promisor remote, and only then establishes the rest of the profile, the state its answer depends on and what the operation will write. It does all of this with item 2's common prefix and forms and item 3's metadata checks, never with `git status`, a working-tree diff or another command that compares or refreshes the working tree. The repository and the operation are inside the profile only when all of these hold:
   1. *Git and layout.* Item 4's version check has run. Git's top-level directory is the project, and its Git directory is the project's own `.git` directory, not a gitfile, with no `commondir`, no `worktrees` entry, no `objects/info/alternates`, no file under `remotes` or `branches` and no `modules` directory. The index holds no gitlink and the tree `HEAD` names has no `.gitmodules`. No promisor remote is declared, so a partial clone is outside the profile on every Git version. Linked worktrees, alternates, partial clones and submodules are deferred to later work (Codex C13, C14, C16).
   2. *Git-directory entries and operation state.* The top level of the Git directory holds no entry other than these: the regular files `HEAD`, `config`, `description`, `index`, `packed-refs`, `COMMIT_EDITMSG`, `ORIG_HEAD` and `FETCH_HEAD`; the directories `objects`, `refs`, `logs`, `hooks` and `lfs`; the directory `info`, holding no entry other than the regular files `exclude`, `attributes` and `refs`; and the directories `branches` and `remotes`, each with nothing in it. Any other entry puts the repository outside the profile, whoever placed it: an operation state, such as a pseudo-ref `MERGE_HEAD`, `CHERRY_PICK_HEAD` or `REVERT_HEAD` or an entry `SQUASH_MSG`, `sequencer`, `rebase-merge` or `rebase-apply`; other state such as `rr-cache`, `MERGE_RR`, `MERGE_MSG`, `AUTO_MERGE` or `shallow`; a lock file; or a file another tool left there. 8. **Security invariants** (part of this acceptance; the Adversarial review brief carries them): no rule in items 2 to 6 lets main or a role, while preparing, making or checking a review read, run a Repository-chosen program or repository code outside D5, read with the file tools or a shell tool content through a link, reparse point, hard link or non-regular file or at a canonical path outside the project, search or walk a directory with an unchecked descendant, or place an unsafe or attacker-chosen string in a command; and, subject to D1's residual risks and D2's assurance level, main performs an operation under item 6 only in its fixed form and only inside item 6's profile, where every Repository-chosen program the operation can run is either disabled by the fixed form or named in a current answer of the user's, and every push destination is a URL of item 6's two shapes covered by that answer (S18, D-2; Codex consultation C22). A setting, Git-directory entry or state outside the profile, or anything main cannot establish, leaves the operation unperformed; main never treats an answer about configuration it could not identify as an approval of named programs, never lets Git itself, in an operation under item 6, write through a symbolic link, junction or reparse point in the Git directory, write content to a file there with more than one link, or write content to a file on this machine outside the Git directory at a location the repository's content or local metadata chooses, where it sends content is the push destination the previous sentence governs, the timestamps Git refreshes on existing loose objects and pack files excepted; what Git writes where the user's trusted configuration or environment directs it, such as a temporary file for SSH signing in the system's temporary directory, trace output or a cookie file, falls under D1, and what a program the user approved or the trusted configuration runs, such as a hook or a credential helper, writes falls under D5's exception and D1, rather than this sentence; never performs an operation under item 6 in a session after a commit it made there whose recorded tree or parent differed from what the check after a commit compares it with, or whose check it could not establish, never runs a Git command under item 6 without `--no-replace-objects`, never skips hooks without the user's choice, never establishes the profile, what an operation writes or the state its answer depends on outside item 2's forms and item 3's metadata checks, never reads an object or establishes the rest of the profile before promisor detection, the checks before it only ever finding the repository outside the profile, and never relies on an answer after any of item 6's conditions for asking again holds, except that, where the only such condition is one that only the check after a commit can detect, the programs a `git add` or commit attempt runs under the answer before that check, or with no check following it, have already run, which item 6 states as residual risk.

### C2 acceptance

1. **One paragraph for roles with a shell (G6, A4-a).** Reviewer, verifier and adversary each carry a paragraph headed Repository safety, identical in the three templates, that states C1 item 2's common prefix and rules, C1 item 3's checks, name, command and directory-search rules, and that the role reads no path in a review outside what its brief and these rules allow. A test asserts the three paragraphs are byte-identical and that each sentence C1 pins in the shared reference for these rules appears in it.
2. **One read-only Git definition (R1-Q2).** The paragraph defines read-only Git once: no index, object, ref, configuration or working-tree write, no remote contact, no Repository-chosen program. Adversary's Repository, secrets and effects section loses the sentences the paragraph replaces: that Git's own index refresh during status or diff is the only index write tolerated, the sentence defining the read-only Git commands it may run, and the sentence on lazy fetch that names `GIT_NO_LAZY_FETCH=1`; a test asserts the index-refresh sentence no longer appears in any template, and the commit lists each removed pin with the paragraph sentence that now states it. Reviewer's "Use read-only git commands" points to the paragraph. Reviewer obtains the change by comparing commits and reads uncommitted and untracked files the brief lists under C1 item 3, instead of diffing the working tree; it uses log and blame only in C1 item 2's forms.
3. **Execution (D5).** Reviewer runs only the lint and type-check commands its brief names. Reviewer, verifier and adversary execute repository code only when the brief says D5 allows it or in the isolated environment the brief names, and otherwise report INCONCLUSIVE for what needs execution. The code review and outcome verification procedures' step 2 and the Adversarial review procedure's brief say main states D5's outcome in the brief.
4. **Roles without a shell (S14–S16).** Analyst, scout and Explore each carry the paragraph C1 item 4 states for them, word for word, so that in a review assignment they read only listed files and search only listed directories, never follow a link, do not treat an empty search as showing absence, report what that leaves unexamined and report a missing allowlist as a missing requirement; a test asserts the three copies equal the reference's text.
5. **Stale roles (B10).** A new fixture, `tests/role_templates_0_20_0.json`, holds the role templates v0.20.0 shipped for every template this release changes, copied verbatim from `git show v0.20.0:templates/agents/<role>.md`, and a tag-source test asserts that exactly reviewer, verifier, adversary, analyst, scout and Explore differ from v0.20.0 and that the fixture equals the tagged content; a stale-role test shows an installation of those templates reported stale until setup update and current afterwards. The v0.18.0 fixture and its tests are retired in the same commit, with the reason that the stale check that matters is against the previous release and that their exactly-four assertion no longer holds.
6. **READMEs.** Both READMEs' role tables and review sections state items 1, 3 and 4 in summary; paired pins.
7. **Security invariants** (part of this acceptance; the Adversarial review brief carries them, with C1 item 8): no role template lets a role with a shell run a Git command outside C1 item 2's forms, read or search outside C1 item 3, or execute repository code outside D5; no template lets a role without a shell read or search beyond its allowlist or proceed without one in a review; and the three shell roles' paragraphs cannot differ (B4).

### C3 acceptance

1. **Verdict.** Reviewer may answer INCONCLUSIVE when evidence the review needs could not be obtained, safely or at all: it names the missing evidence, lists any non-blocking findings and proves no defect. When it also has a blocking finding, it answers CHANGES_REQUESTED and lists the gaps with it.
2. **Counting and retry (R2-Q4).** Code review counts an automatic INCONCLUSIVE as a call without a pass, like outcome verification; it creates no FIX or REJECT obligation; main makes the next call only after the named missing evidence has changed, and otherwise reports the claim unreviewed. The glossary's Code review and Unreviewed claim say so, in this Claim's commit.
3. **No narrowing past a gap (B3).** The call after an INCONCLUSIVE covers every gap it named, even though that call completed with a verdict; a narrowed follow-up never closes a gap it did not examine, and no APPROVED is given while a named gap is unexamined. Code review's procedure and reviewer's role state this beside the narrowed-review rule; pinned.
4. **Everywhere verdicts are listed.** Every procedure, review-state rule and README sentence that lists reviewer's verdicts lists all three; paired pins.

### C4 acceptance

1. **One helper (H1).** The handoff tool runs every Git command through one function in the module that holds its Git environment, which builds the command as an argument list starting `git --no-pager --no-optional-locks -c core.fsmonitor=`, keeps the existing environment protections, preserves each caller's error handling and can be called before a store exists, so repository discovery, tracking and observations all use it.
2. **Static check.** A test asserts that no other place in the handoff tool's package starts a Git process.
3. **Behaviour check (B6).** A test creates a disposable repository, isolated from the user's global and system Git configuration, whose local configuration names an fsmonitor program that writes a marker file when run. It first shows, as a positive control, that one of the index-reading commands the tool runs, run in that repository without the helper's prefix, writes the marker; when the installed Git or platform does not run it, the test is skipped with that reason, and C5's validation entry records whether it ran. It then runs the tool's list, read, create, update, snapshot and compare operations against the repository and asserts that no marker exists and that the results equal those without the configuration. A clean filter on a tracked path is configured too, as a regression guard named as such, since none of the tool's current commands runs filters.
4. **Test helper.** The shared test helper's scan disables fsmonitor with the empty value, not `false` (C1-e).
5. **Upstream manifest.** The manifest that records the handoff tool's adapted files gets their new hashes and an adaptation note for the helper, as its release test requires.
6. **Security invariants** (part of this acceptance; the Adversarial review brief carries them, with C1 items 2.1 and 2.2): no operation of the handoff tool runs Git without the helper's prefix, runs an fsmonitor, pager or other program the repository's local configuration names, or writes Git's index while reading (B4), including by a lazy fetch in a checkout with a promisor remote (B4, D-1).
7. **Promisor remote (D-1).** Before its first Git command that can read objects in an operation, and before tracking writes anything, the tool reads the effective configuration, includes followed, to find whether it declares a promisor remote (`extensions.partialClone`, or `remote.<name>.promisor` or `remote.<name>.partialclonefilter`). When it does, on Git 2.45.0 or later the helper adds `--no-lazy-fetch` to every command; on an older Git the tool runs no command that can read objects (such as `check-ignore` and `ls-files`), and the operations that need one report tracking as not established with a cause code naming the promisor remote, saving the work as a tracking failure does today, with a recovery that says to upgrade Git or have the user remove the promisor configuration rather than retry; the handoff tool reference's Create section describes this cause code in the same commit. When the configuration cannot be read or the Git version cannot be established, the tool treats tracking as not established in the same way. Observations for snapshot and compare use `rev-parse` and `symbolic-ref`, which read no object, and `show-ref --verify`, which checks that a ref's object exists and can therefore fetch it; that check runs only after the same detection, with `--no-lazy-fetch` on Git 2.45.0 or later, and on an older Git in a promisor checkout the observation reports the Git state as unknown instead of running it. A behaviour test reproduces the refuted case, a blob-less partial clone whose local configuration names a marker program as the remote's upload program, with a positive control showing the plain command runs it (skipped with its reason when the installed Git does not run it, and C5's validation entry records whether it ran), and asserts that no marker appears; another test simulates Git 2.45.0 or later and asserts that every command carries `--no-lazy-fetch`.

## User Stories

1. As a user, I want every code review to read my repository without following a symbolic link out of it, so that a crafted link cannot show a role my private files.
2. As a user, I want outcome verification, plan review and security analysis held to the same rules as Adversarial review, so that safety does not depend on which review runs.
3. As a user, I want unchanged files a review reads to be covered too, so that an attacker does not simply put the link in a file the change does not touch.
4. As a user, I want main never to run a program my repository's configuration names while it prepares or checks a review, so that opening a review does not execute the code under review.
5. As a user, I want main to ask me before a filter must run to compare my workspace, so that I decide whether that program runs.
6. As a user, I want main to tell me when my repository's configuration points outside the project or moves its work tree, so that I can decide before a review starts.
7. As a user, I want main to notice when my repository's Git metadata changes between dispatches, so that a check made at the start does not go stale.
8. As a user, I want main to check my Git version once, so that its safety options are not silently ignored by an old Git.
9. As a user, I want main to name the hooks, filters and signing programs a commit, tag or push would run, and the push destination, so that I choose whether they run.
10. As a user who trusts my own hooks, I want to answer once for the list main named, so that I am not asked at every commit.
11. As a user, I want "skip hooks" to be my explicit choice and to skip every hook it claims to, so that my rule against skipping hooks unasked still holds and nothing runs that I declined.
12. As a user, I want roles never to read a cloud-file placeholder, so that a review does not make my sync provider download files.
13. As a user, I want roles never to read a hard-linked file, so that a review cannot read a file that also lives outside the project.
14. As a user with a pnpm store, I want those files reported as unexamined rather than read, so that I know what the review did not cover.
15. As a user, I want a role to read a link's own Git blob, so that a change to a link's target can still be reviewed.
16. As a user on Windows with `core.symlinks=false`, I want link text files read as text and reported as links, so that the review neither misses nor follows them.
17. As a user, I want names like `aux.txt`, `CON` or `..` rejected, so that a review does not open a device or leave the project.
18. As a user, I want FIFOs and devices never opened, so that a review cannot hang or touch hardware.
19. As a user, I want file names chosen by the reviewed code never placed unquoted in a command, so that a name cannot become an option or a command.
20. As a user, I want the checks themselves to run only tools from outside my repository, so that a planted module is not loaded while checking.
21. As a user, I want history read without signature verification and with an explicit format, so that a configured signing program never runs.
22. As a user, I want blame and diffs read without textconv or an external diff, so that no configured converter runs.
23. As a user, I want mailmap files ignored, so that history output cannot be redirected to a file outside the project.
24. As a user with a partial clone, I want lazy fetch disabled, or on an older Git the review stopped with my choices, so that a review never contacts a remote.
25. As a reviewer role, I want one definition of read-only Git, so that I know exactly which commands I may run.
26. As a maintainer, I want the three shell roles to carry byte-identical safety text, so that the rules cannot drift between them.
27. As an analyst, scout or Explore role, I want main to give me an allowlist of checked files and directories, so that I can read and search safely without a shell.
28. As a user with my own Explore agent, I want the safety paragraph to reach it through the brief, so that replacing a role does not drop the rules.
29. As a user, I want main to ask whether my repository may run on this machine before it runs tests or linters, so that cloning a repository is not consent to execute it.
30. As a user resuming a session, I want code from the earlier session executed only in an isolated environment I name, so that unreviewed code does not run on my machine.
31. As a user, I want reviewer to run only the lint and type checks its brief names, so that it does not run arbitrary repository tooling.
32. As a user, I want a reviewer that could not read what it needed to say INCONCLUSIVE, so that a gap is not reported as approval.
33. As a user, I want an INCONCLUSIVE code review counted like an INCONCLUSIVE verification, so that the Stop threshold behaves the same in both steps.
34. As a user, I want an INCONCLUSIVE not to make main fix an unproved bug, so that work is not changed without evidence.
35. As a user, I want the handoff tool never to run my repository's fsmonitor or filters, or fetch through programs its configuration names in a partial clone, so that saving progress runs no repository code.
36. As a user who installed 0.20.0, I want the changed roles reported stale, so that I know to run setup update.
37. As a user, I want the documentation to say these rules are instructions, not enforcement, so that I do not overestimate the protection.
38. As a user, I want concurrent modification during a review named as residual risk, so that I know what is not defended.
39. As a user, I want main to push only to a remote host named as a host name, never to a path, a drive letter, an IP address, a loopback name, this machine's name or a remote helper, so that a rewritten remote URL cannot run hooks of a tracked directory on my machine except through a name that resolves here, which I am told is residual risk.
40. As a user who approved my hooks, I want main to ask again when content it did not write may have reached what they load, such as after a checkout or a conflicted merge that main can see or is told of, so that my answer does not carry over to hook configuration I never saw.
41. As a user, I want main to decline to commit or push in a repository whose Git configuration or layout it does not recognise, and tell me what it found, rather than ask me to approve configuration it cannot explain, so that my answer always means approving programs I was shown.

## Implementation Decisions

- The shared reference is the single statement of the rules; procedures, the command and the READMEs summarise and point to it, and role templates, which cannot link files, carry the identical paragraph of C2 item 1; roles without a shell receive their paragraph in the brief as well.
- The Git rules are a common prefix plus per-operation forms; the reference names the forms for listing (index and tree listings), object reads, comparing commits, history, blame, attribute checks, configuration reads and content hashing, and names `git status`, working-tree diffs and the `--filters` and `--textconv` options as not used for a review.
- Main's checks of C1 items 4 and 6 read configuration and metadata only; they run nothing the repository chose, and their answers are session state, never handoff content.
- The handoff tool keeps its own link rule (only name-surrogate or unidentified reparse points are links, hard links rejected), because it reads only records Feather writes; the shared reference says so, and makes no claim that every plugin read avoids provider activity.
- Reviewer's INCONCLUSIVE follows verifier's: same meaning, same counting, same retry condition.

## Testing Decisions

- Tests check shipped behaviour through the texts users install and the tool they run, not internal structure: whole-sentence pins in the document and section that state a rule, absence pins for removed wording (the index-refresh tolerance, the hard-link sentence), and a byte-identity check across the three shell roles' paragraphs. Prior art: the pins in the security-review, commands and review-rules test modules.
- Rendered roles are checked through the existing stale-role test and its recorded templates, extended to every template this release changes.
- The handoff helper is checked through the tool's command-line operations against disposable repositories with marker programs, as the tracking-probe and links tests do, plus one static check that no other Git process start remains.
- Text tests show that the shipped contract is consistent; they do not show that a live model follows it (D2). The analysis's inferences about Git (a commit's index refresh running filters for paths it does not commit, content hashing following links, a configured work tree, and D-2's: a drive-letter push URL such as `c:repo` taken as a local path on Windows, a commit's automatic maintenance running `gc.recentObjectsHook`, a commit's rerere step running a configured merge driver for a path `MERGE_RR` lists, a push's negotiation running a program a remote section named by the push URL chooses, a push certificate running the signing program, a credential helper falling back to a local alias, a commit with nothing to commit, including an index whose only change is an intent-to-add entry, running a submodule's filter, and, only on a Git built without expat and so not established with the installed Git, `git http-push` falling back to a local alias, each unless item 6's fixed form or its rules prevent it, a commit writing through a symbolic link planted at `COMMIT_EDITMSG` or `logs/HEAD` to a file outside the project, and its hard-link and junction variants (a hard-linked `COMMIT_EDITMSG` truncated, `logs` a junction), each recorded as skipped or INCONCLUSIVE with its reason when the platform does not let the test create the link, and, for the profile itself, that in a marker repository inside the profile whose trusted configuration supplies a hook, a filter and a signing program, each writing a marker, the fixed forms run only those named kinds, and with skipping chosen only the filter; the outcome verification uses the installed Git, and behaviour of Git versions other than the installed one is not established by it) are reproduced by C1's outcome verification, whose brief names them as acceptance checks run with the installed Git (not repository code) in marker repositories in a scratch directory outside the project, isolated from the user's global and system Git configuration as C4's target is; C1's Adversarial review stays static (B5). For D-3, the same outcome verification shows with the installed Git, in marker repositories, that an entry at the top of the Git directory that profile item 2 does not list puts the repository outside the profile, and that the check after a commit detects a recorded tree that differs from the index entries, also when the repository supplies a replacement ref that would hide it; the brief carries the details privately.

## Out of Scope

- Rules for where sensitive findings may be disclosed (A4-b to A4-f, A5, C3-a, C3-b, C4-a): the second batch.
- Ranges other than two-dot (A8-a), bind mounts and FUSE mounts that link checks cannot see (A8-b), and concurrent modification between a check and a read (A8-c), which stays residual risk (D1).
- Enforcing any rule through permission settings, hooks or a sandbox (D2).
- Files Git itself consults beyond the reads C1 items 2 to 4 constrain (D3).
- Searches by scout or Explore that main dispatches outside a review (D4).
- Live rehearsal of the review scenarios 0.19.0 left unexercised (fix after REFUTED or BROKEN, Adversarial review, command ranges, switching from off to auto).
- Changing the handoff tool's own link rule.
- A trust in a repository that lasts across sessions, which the user asked for on 2026-10-12 and chose to leave to separate work: it changes D5's once-per-session question, ADR 0009's isolation rule for resumed sessions and D1, and needs its own design (a record kept outside the project, bound to the repository's identity, its scope over D5, item 6 and the read rules, and revocation).
- Claude Code's own Git commands at session start and its loading of the project's `CLAUDE.md`, imports and `.claude` settings (D6).
- Main's own Git operations other than `git add`, commit, tag and push, such as fetch, pull, merge, checkout or stash, and opening a pull request with `gh`, which can run hooks or filters; C1 item 6 covers only the four operations the user chose (Q-S3), so these stay residual risk (plan review of D-2, N7). To keep `gh` from pushing on its own, main pushes the branch under C1 item 6 first and opens the pull request naming that branch with `--head`.

## Further Notes

- Git 2.43 is the version this repository is validated on, and this repository has no promisor remote; C1's and C4's outcome verification check the older-Git behaviour in a disposable partial clone.
- This release's review round runs under the installed cc-feather 0.20.0 procedures and roles, never the candidate's own templates. C4's Adversarial review runs the candidate's own handoff tool, code written in this session; in the spirit of D5, main also asks the user before it whether this repository is trusted to run on this machine, and if the review round crosses into a new session, ADR 0009's isolation rule applies, so the user names an isolated environment or the probe is static.
- ADR 0011, committed before C3, already uses the term Repository-chosen program and states D6; the glossary entry arrives with C1, and C1's code review checks that the ADR and the glossary agree.
- C1 item 6's profile leaves outside it, for the user to run themselves, every operation in a repository with linked worktrees, alternates, a partial clone, submodules, an operation in progress, recorded rerere resolutions, or a local configuration key outside its allowlist, such as signing, credential, URL-rewriting or LFS filter settings written to the local configuration, or the keys `git maintenance register` writes, or with an entry at the top of its Git directory that profile item 2 does not list, such as one another tool leaves there, or a link or a non-regular entry anywhere in its Git directory, such as the socket a running fsmonitor daemon creates there when the user's global configuration enables it; that is a usability cost of D-2 the user accepted on 2026-10-12, and later work may widen the profile one reviewed case at a time. When main commits while the index holds an intent-to-add entry, the check after a commit reports it and main performs no further operation under item 6 for the rest of the session; that is a usability cost of D-3.
- Main never pushes to a local path, a UNC path, a `file://` URL, a host given as an IP address, a URL with a port such as `ssh://git@ssh.github.com:443/…`, an scp-like address without `user@` or a host with a label beginning with a digit, such as a backup on a network share, and never signs a push; that is a usability cost of D-2, and main tells the user to run such a push themselves. Likewise, a commit made by anyone but main, including a role main dispatched, moves `HEAD` away from what main recorded, so the next operation under C1 item 6 asks again.
- A repository that uses a filter such as Git LFS makes main ask before every review whose compared paths it covers; that is a usability cost the user accepted with R2-Q1.
- Rollback: before anything is pushed, the Claims' unpushed commits can be dropped with the user's agreement; after the release, a user reinstalls 0.20.0 and runs setup update, which restores the 0.20.0 role templates, and the glossary and procedure changes go with the plugin version.
- The non-security follow-ups of the earlier releases stay in their own work item.
