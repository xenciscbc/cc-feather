# Review each Claim when it is done, and keep its passes

Label: `ready-for-agent`

Vocabulary follows [CONTEXT.md](../../CONTEXT.md), which gains a Dispatch record entry as part of this work. It changes rules that [the completion criteria spec](completion-criteria.md), released in 0.24.0, kept or added: when reviews start, what reopens a pass, how a failed final check is fixed, what a BROKEN holds, the single Accept and land decision and where its list comes from. It builds on [the repo trust default spec](repo-trust-default.md), released in 0.25.0, under which reviews and the final check execute repository code by default. Those specs stay as the record of what they decided. The decisions were settled with the user on 2026-10-14 and 2026-10-15, the second day after a security analysis of this spec, and are recorded in the handoff `review-per-claim-retained-passes`, and in ADR 0015, written as part of this work.

A first version of this spec, written on 2026-10-14 before 0.24.0 was released, kept a pass through a Retention check: an independent narrowed review of the earlier Claim plus a rerun of its primary acceptance. Its security analysis and a second opinion found that in this project nearly every Claim changes the shared test modules, so the check would almost always reopen outcome verification, and that under per-Claim timing the checks grow with the square of the Claims. On 2026-10-14 the user replaced it with the rule below: a pass, once given, stays fixed.

This spec has no Claims table: implementing it makes it one Claim against the Acceptance below, and cutting it into tickets first makes each ticket a Claim.

## Problem Statement

A pass is reopened by any later change to its Claim's files. Most Plans have Claims that share files, so when a later Claim's implementation or fix touches a shared file, every earlier Claim that already passed loses its code review and outcome verification and is reviewed again, even when the change touches nothing it relies on. Each reopened review can surface its own findings, and each fix can reopen the next Claim. In 0.22.0 a change to README Updates alone reopened C1 to C3, and in 0.23.0 T06 reopened T01 to T05. A round that keeps returning to the same Claims also spends the session's context without getting closer to landing.

Because reopening is this costly, reviews wait until the whole Plan is implemented, so a problem in an early Claim is found only after later Claims were built on it.

Adversarial review runs last, but a BROKEN still starts a fix, a code review, an outcome verification and another attack, and a fix there can reopen other Claims, so the costliest step can restart the loop at the end of the Plan.

Work that continues in a new session, or after a context compaction, loses its review state: passing verdicts do not cross sessions, so every Claim that passed earlier is reviewed again before it can land, and the Accept and land list cannot be built from any record.

## Solution

In auto, each Claim is implemented in order and reviewed as soon as it is done: code review, then outcome verification. Once both pass, the Claim's passes are fixed. Another Claim of the same Plan that changes its files does not reopen it, as long as that change is itself covered by a completed, passing review: that Claim's own reviews judge its whole change, and it fixes its own problems. A Claim may change another Claim's acceptance checks only where the Plan says so, and its reviewer then checks that the change does not weaken them.

When every Claim is done, main runs the final check at the final commit: the Plan's overall acceptance and every Claim's primary acceptance. A failure is fixed by the Claim that caused it, through that Claim's reviews, or, when it cannot be attributed, as a fix Claim main adds to the Plan with its own reviews; no Claim whose passes are fixed is reopened, and a final check that keeps failing stops for the user. Then each Security-critical claim gets one Adversarial review at the final commit. Its findings are recorded for the next Plan, not fixed in this one.

Main keeps the Plan's review state in a dispatch record under `.feather/`, so a new session or a compacted context continues from it instead of reviewing everything again.

Finally main asks the user once: land the branch as it stands, or re-review named Claims. The question lists the final check, every Claim's passes, every Adversarial review result, every fix Claim that changed a security control, and what this flow does not check. Off mode keeps today's rules.

## Acceptance

1. **Per-Claim timing in auto.** In the Automatic flow, each Claim's code review and then outcome verification run once that Claim is implemented and committed, replacing the rule that reviews start once the reviewed Plan is implemented. This is the only review timing in auto; there is no setting or Plan statement that selects another. A single-Claim Plan is unchanged. Implementation and reviews in one working tree stay serial as Serial within a working tree states, so a Claim with no dependency still waits for a review call running in the same working tree.
2. **Dependent Claims wait.** A Claim that lists another under Blocked by, or otherwise depends on it as its Plan states, starts only after that Claim has valid APPROVED and CONFIRMED. Claims with no such dependency do not wait for other Claims' passes. Where a Plan states no dependencies between its Claims, main follows the Plan's order and treats each Claim as depending on those before it.
3. **A stopped upstream Claim.** When a Claim's code review or outcome verification stops, its outcome verification cannot be resolved, it has a Deviation, or it would need Accept and land, every Claim that depends on it stops and main asks the user. The user may decide that named dependent Claims proceed; main records it under User decisions as a deferral of the upstream Claim whose scope names the dependent Claims allowed to start, and the upstream Claim stays a Pending-acceptance claim until the decision of item 10 or until its passes become valid.
4. **Passes stay fixed.** In auto, a Claim's valid APPROVED and CONFIRMED are a judgement of the commit they judged and are not reopened by a change to the Claim's files or to what they depend on that lies within the range judged by another Claim's completed code review and outcome verification of the same Plan, both of which passed, as S5 states; a fix Claim counts as another Claim. A Blocking finding in that other Claim's reviews is that Claim's to fix. Any other change, such as an edit outside the Plan's Claims, a rebase, an environment or test target change, a change to the Claim's reading set, or a change whose Claim ends without both passes, keeps today's rules under What a pass covers. A Security-critical claim's HELD is governed by item 8.
5. **Another Claim's acceptance checks.** A Claim may change a file that another Claim's acceptance checks run or read, such as its tests, expected values, fixtures, discovery or runner configuration and their support code, only where the changing Claim's own reading set states that it does; otherwise the change is a Deviation and a Blocking finding. Main decides which files these are from the changing Claim's commit, files it adds included, and counts a file it cannot rule out as one of them. When the changing Claim's diff changes such a file, its code review brief also carries the acceptance of each Claim whose checks the file serves, as a stated exception to the rule that a brief carries only the recorded reading set, and the reviewer checks from the diff that the change does not weaken that acceptance, for example by loosening an assertion, replacing a fixture or turning off discovery; a weakening is a Blocking finding. The installed reviewer definition is unchanged; the code review procedure states this in the brief.
6. **Findings about an earlier Claim.** When a later Claim's review finds a problem in an earlier Claim of the same Plan: a problem that predates the Plan's base revision is a Non-blocking finding, recorded in the Follow-up record, and the later Claim fixes it only when its own acceptance needs it, reviewed in its own reviews; a defect introduced after the Plan's base revision is not a pre-existing issue, as S1 states, and is not only recorded. When the later Claim's acceptance needs it fixed, the later Claim fixes it within its own reviews; otherwise main fixes it as a fix Claim, as item 7 describes, without reopening the earlier Claim, and until it is fixed it is listed under the earlier Claim, as S6 states. A security problem or data loss that the later Claim's change introduces into what an earlier Claim delivers is the later Claim's Blocking finding, as the completion criteria state; when a later Claim changes a security control, main classifies it again as Security-critical by what the change does.
7. **The final check and fix Claims.** Before the final check, main confirms each Claim's reading set as S3 states. The final check runs at the final commit, as today, and also reruns every Claim's primary acceptance there, taken from its recorded reading set, within repository safety's Execution rules. A failure attributed with evidence to a Claim is fixed by that Claim: the fix goes through that Claim's code review and outcome verification, their counts continuing as for a reopened call, and no other Claim is reopened. A failure that cannot be attributed with evidence is fixed as a fix Claim, and no Claim is reopened. A fix Claim is a Claim main adds to the Plan for one fix: its acceptance is that the failing check passes, or for item 6 that the reported defect is fixed; its reading set is the Plan's text with that failure or defect; it gets code review and outcome verification with counts of its own; and it never changes the failing check or another Claim's acceptance checks, as S4 states. Main adds it without asking, as it makes a fix today: it gets no plan review and no ticket, and is kept in the dispatch record; a fix beyond the Plan's scope is a Deviation, as today. A fix Claim that changes a security control is classified as Security-critical by what it does, and main still does not ask: it gets no Adversarial review, and the decision of item 10 discloses it with the problem and a summary of the fix. The final check runs again after each fix. When the final check fails at as many different commits in a row as the Stop threshold in effect, without passing in between, main stops fixing and asks the user.
8. **Adversarial review at the final commit.** Once the final check has passed at the final commit and the workspace equals it, each Security-critical claim of the Plan, other than a fix Claim, gets one Adversarial review there, replacing the requirement of a valid APPROVED and CONFIRMED at the same commit: the Claim's APPROVED and CONFIRMED are a record of the commits they judged, and a HELD judges only the final commit, as S2 states. The brief carries only the Claim's own security invariants and test targets and the Plan's base revision, and the composed review of an already accepted Claim is unchanged. A break of a Claim's invariant at the final commit is reported whichever Claim's change caused it, and a break introduced after the Plan's base revision is not a pre-existing issue. INCONCLUSIVE follows today's rules within the Stop threshold in effect.
9. **Adversarial findings are recorded.** A BROKEN is not fixed in this Plan: it counts as a call without a pass, main does not repeat a call on unchanged code to reach the Stop threshold, and its findings go to the work's Follow-up record, written as Adversarial review step 10 requires, so a tracked record carries only their summary unless the user agrees. The Claim stays a Pending-acceptance claim with its Adversarial review result, and the decision of item 10 lists it.
10. **One decision at the end.** After every Claim's reviews, the final check and the Adversarial reviews have run or are recorded as not run, main confirms each Claim's reading set as S3 states and asks the user once, replacing the trigger of Accept and land at the end of the plan. Main builds the list from the dispatch record and its own observations in this session, never from another record in the working tree such as a handoff, a ticket or the Follow-up record. The list states the final check's state at the commit to be landed; for each Claim, the commit its passes judged, each pass, each missing pass and each unresolved Blocking finding listed under it as S6 states; for each Security-critical claim, its Adversarial review result as S2 states, BROKEN with its findings as the adversary stated them and INCONCLUSIVE with its gaps; each fix Claim that is Security-critical, with its problem, a summary of the fix and that it had no Adversarial review; the Follow-up record; and what this flow does not check, as item 14 states. The user chooses to land as it stands or to re-review named Claims. Landing as it stands is recorded as Accept and land only for the Claims that need it: a Claim with a missing pass or an unresolved Blocking finding, a BROKEN named as a known vulnerability the user lands with, an INCONCLUSIVE or not-run Adversarial review, a Security-critical fix Claim, or a final check that failed or was not run; when nothing listed needs it, the question is only the user's authority to land, which landing needs today. A re-review follows the existing rules; when it changes the code, main runs the final check again, treats each Adversarial review result that no longer judges the commit to be landed as not run, and asks again. Confirming part of the list, what is not a confirmation and what a decision covers stay as today.
11. **The dispatch record.** In auto, main keeps one dispatch record for each Plan of Plan-driven work, at `.feather/dispatch/<name>.md`, named after the Plan: the spec's slug when the Plan is a spec or tickets of it, the ticket's slug for a single ticket, the plan file's name, or for a plan-mode or conversation plan a short name main states to the user. It holds what a later session needs: the Plan, its base revision and its plan-review READY; for each Claim, its classification, its reading set's hash, its base revision, and each review call's judged commit and verdict with a one-line summary; each fix Claim with its problem and a summary of the fix; the branches main created for the work; and the user's decisions with their scope. It holds no counts and no exploit details or secrets, which follow Adversarial review step 10. Main writes it only between review calls, as Serial within a working tree states for handoff records, and keeps it out of Git: when no rule already ignores it, main adds `/.feather/dispatch/` to `.gitignore`, and it never stages or commits the record. In auto it replaces an Active handoff's notes as the place review state crosses sessions; an active handoff records progress and names the dispatch record. Off mode writes none.
12. **Earlier sessions and compaction.** A resumed session, and main after a context compaction, take the Plan's READY, reading sets, passes, Adversarial review results and the user's decisions from the dispatch record, and they count as if received in this session: a Claim is not reviewed again for having passed in an earlier session, and implemented work whose READY the record holds does not ask again under Implemented before plan review. Counts restart in each session, as ADR 0002 decided, and the Stop threshold in effect and the final check's state still come only from this session, so main runs the final check again in the new session before landing. Where the dispatch record lacks what main needs, Unknown state applies as today. For a Plan in auto this replaces the rules that passing verdicts do not cross sessions, that the Accept and land list is never built from a record in the working tree, and that an unresolved verdict reaches a resumed session only through an Active handoff.
13. **Tickets.** In auto, a ticket of a Plan reviewed per Claim is set to a done value only after the decision of item 10. Until then main records each Claim's pass state in the dispatch record.
14. **What this flow does not check.** The procedures and both READMEs state it: a later Claim's reviewer reads only its own reading set and may not know an earlier Claim's design intent; a property of an earlier Claim that no rerun acceptance check covers can be broken without the final check noticing, and acceptance items other than the primary acceptance are not rerun at the final commit; an acceptance check that cannot be rerun, such as a manual check, is not repeated at the final commit; the commit an Adversarial review attacks was not judged as a whole by the Claim's own code review and outcome verification; Adversarial review findings are not fixed in the Plan; a Security-critical fix Claim gets no Adversarial review; and main takes the dispatch record as written, so an edit to it changes what main believes. A re-review chosen under item 10 can recover part of this.
15. **Off mode.** Items 1 to 14 hold in auto. In off, What a pass covers, the final check, Adversarial review, Accept and land and the cross-session rules keep today's rules, as S7 states for a switch during a Plan.
16. **Glossary and ADR.** `CONTEXT.md` gains a Dispatch record entry, and its Automatic flow, Code review, Outcome verification, Adversarial review, Active handoff, Pending-acceptance claim, Acceptance gate and Accept and land entries state the rules above where they mention timing, reopening, BROKEN, sessions or the decision at the end. ADR 0015 records them with their rejected options and states that it amends ADR 0002 (what crosses sessions), ADR 0006 (what a pass covers), ADR 0008 (Accept and land), ADR 0009 (BROKEN holds the Claim) and ADR 0013 (per-Claim timing deferred, the unattributed final check failure, Adversarial review timing, the single decision and its list); each is marked as amended by it.
17. **READMEs.** `README.md` and `README.zh-TW.md` explain per-Claim timing in auto, dependent Claims waiting for their upstream passes, the stopped-upstream decision, fixed passes and their limits, the final check's reruns and fix Claims, Adversarial review at the end with recorded findings, the dispatch record and how work continues in a new session, the decision at the end and item 14; both say the same thing and match the procedures, and the cost explanation states how this changes it.
18. **Tests.** Contract tests pin each statement above and every security invariant below, and fail on the text at tag `v0.25.0`; pins of replaced statements (reviews starting once the Plan is implemented, file-level reopening by another Claim's reviewed change in auto, the unattributed final check failure reopening every Claim, a BROKEN fixed before landing, passes from an earlier session reviewed again before a gated operation, the Accept and land list never built from a record) are updated or become absence pins; the reviewer, verifier and adversary templates and the installed policy are pinned as unchanged; the full suite passes in both discovery forms.
19. **Live rehearsal.** In the test target T1 below, main runs a disposable three-ticket Plan in auto with the candidate. The record shows ticket 01 reviewed before 02 and 03 start; 02's change to 01's file not reopening 01; the dispatch record's path and content after 02 passes; a new session resumed before 03 that takes 01's and 02's passes from the dispatch record without reviewing them again, restarts counts and runs the final check itself; 03's helper change breaking 01's acceptance check found by the final check, attributed to 03 and fixed through 03's reviews without reopening 01; 01's Adversarial review at the final commit, with any BROKEN recorded and not fixed; one decision at the end listing what item 10 requires; and ticket status set to done only after it. The rehearsal, its environment and its result are recorded in the release's validation entry; a deviation from the rules is a finding, not a pass.
20. **Release.** The plugin version is 0.26.0; `claude plugin validate .` passes; `docs/setup-validation.md` gains the release entry with test counts and skips, the rehearsal and the review round; README's Updates section states the change and that no `/cc-feather:setup update` is needed, because no installed definition or policy changed; the tag is created after the user's go-ahead, only after checking that it matches `plugin.json` at the tagged commit and does not already exist.

## Security invariants

From the security analysis of 2026-10-15 and the user's dispositions; each holds for the Claims that cite it.

- **S1. The Plan's base revision bounds what is pre-existing.** Every brief of a Claim's code review, outcome verification and Adversarial review names, besides the Claim's base revision, the Plan's base revision, which main establishes itself from Git in this session or takes from the dispatch record. Main, not the role, judges from Git whether a finding a role reports as pre-existing was introduced after the Plan's base revision; such a finding is a defect of the Plan under item 6 or, for a broken security invariant, a BROKEN of the Claim whose invariant it breaks.
- **S2. An Adversarial review result judges only the commit to be landed.** Only an Adversarial review call made after the final check passed at the commit to be landed, with the workspace equal to it, gives that Claim's result; a result from an earlier or another commit, and an explicit call made before then, counts as not run, so the Claim needs Accept and land or a new call. A BROKEN's findings stay listed until a HELD at the commit to be landed replaces them. The adversarial-review command's rule for when a call counts as the step's pass states the same.
- **S3. Reading sets are confirmed before the final check and the decision.** Before the final check and before the decision of item 10, main confirms that each Claim's reading set is unchanged from its recorded hash; the final check reruns the primary acceptance of the recorded reading set, and a change the user did not authorise is a material Deviation, as today.
- **S4. A fix Claim does not change what it is judged by.** A fix Claim never changes the check whose failure it fixes or another Claim's acceptance checks, the files of item 5; a fix that needs to is a Deviation and stops main to ask the user.
- **S5. A fixed pass needs a passing review of the change.** A Claim's passes stay fixed only for a change inside the range judged by another Claim's completed code review and outcome verification of the same Plan that both passed. When that Claim's review stops, is cancelled, is deferred or ends in Accept and land without both passes, its changes reopen the Claims whose files or dependencies they touch, under today's rules.
- **S6. Unresolved findings stay with their Claim.** A Blocking finding about a Claim, reported after its passes and not yet resolved, is listed under that Claim in the decision of item 10, and that Claim needs Accept and land.
- **S7. Leaving auto during a Plan reopens.** When automatic review is turned off for a Plan before the decision of item 10, every fixed pass whose Claim's files or dependencies another Claim changed after it is reopened under today's rules, and the cross-session rules of off apply from then on.

## Residual risks

Stated in ADR 0015 and both READMEs, as the user decided on 2026-10-15:

- **The dispatch record is trusted.** Main takes the dispatch record as written. Repository code a review or the final check runs, or a person, can edit it and so change which passes and results main believes; cc-feather does not defend against that.
- **Check output.** Repository code that a check runs controls its own output, so it can make a check pass that should fail, hide that a check ran fewer tests, or make a failure point at the wrong Claim; the last only misdirects a fix, after which the final check runs again.
- **Security-critical fix Claims.** A fix Claim that changes a security control gets no plan review, security analysis or Adversarial review; it is disclosed at the end, and the user decides whether to land with it.

## User Stories

1. As a user in auto, I want each Claim reviewed as soon as it is implemented, so that problems in early Claims are found before later Claims build on them.
2. As a user, I want a dependent Claim to wait for its upstream Claim's APPROVED and CONFIRMED, so that it is built on reviewed work.
3. As a user, I want independent Claims not to wait for each other's passes, so that per-Claim timing does not slow down unrelated work.
4. As a user whose Plan states no dependencies, I want main to follow the Plan's order, so that an undeclared dependency is not skipped.
5. As a user, I want to be asked when an upstream Claim stops, and to be able to let named dependent Claims proceed, so that one stuck Claim does not silently block or silently pass the rest.
6. As a user, I want a Claim that passed to stay passed when another Claim touches its files, so that review rounds do not chain through every Claim that shares a file.
7. As a user, I want a pass to stay fixed only when the change that touched it was itself reviewed and passed, so that fixed passes never cover a change no review approved.
8. As a user, I want the Claim that made a change to fix the problems it causes, so that each fix is reviewed once, in the Claim that made it.
9. As a user, I want a Claim to change another Claim's tests only where the Plan says so, and its reviewer to check that it did not weaken them, so that a fixed pass cannot be hollowed out.
10. As a user, I want a defect this Plan introduced never written off as a pre-existing issue, judged against the Plan's base revision, so that fixed passes do not let new defects land unnoticed.
11. As a user, I want the final check to rerun every Claim's primary acceptance as the Plan recorded it, so that a later Claim that broke an earlier one is caught before landing and an edited ticket does not change what is rerun.
12. As a user, I want a final check failure fixed by the Claim that caused it, or by a fix Claim, without reopening every Claim, so that the end of the Plan does not restart every review.
13. As a user, I want a final check that keeps failing at new commits to stop at the Stop threshold, so that fixes that break each other cannot loop without limit.
14. As a user, I want a fix that belongs to no Claim reviewed as a fix Claim with its own acceptance and counts, so that it gets the same reviews without a new kind of work.
15. As a user, I want main to add a fix Claim without asking me, so that the end of the Plan does not stop for every fix, while a fix beyond the Plan still stops as a Deviation.
16. As a user, I want a fix Claim never to change the check it is judged by, so that a failure is fixed rather than hidden.
17. As a user, I want a fix Claim that changes a security control disclosed at the end with the problem and the fix, so that I know what security change I land without being stopped for it.
18. As a user, I want changes outside the Plan's Claims, such as my own edits or a rebase, to reopen passes as today, so that fixed passes never cover a change no review saw.
19. As a user, I want Adversarial review to attack the commit that will land, and a result from any other commit to count as not run, so that its result describes what I would ship.
20. As a user, I want Adversarial review findings recorded for the next Plan instead of restarting this one, so that the costliest step does not loop.
21. As a user, I want those findings kept in the work's Follow-up record, with exploit details only where it is untracked, so that the next Plan starts from one list and nothing public leaks them.
22. As a user, I want one decision at the end that lists the final check, every pass, every unresolved finding under its Claim, every Adversarial review result and what was not checked, so that I decide on the real state once.
23. As a user whose Plan passed cleanly, I want that last question to be only my authority to land, so that Accept and land keeps meaning I accepted something missing.
24. As a user, I want to choose which Claims to re-review at the end, so that I decide how much more review the risk is worth.
25. As a user resuming in a new session, I want the Plan's passes and decisions taken from the dispatch record, so that I do not pay for every review again.
26. As a user whose context was compacted, I want main to continue from the dispatch record, so that compaction does not stop the Plan.
27. As a user, I want counts and the final check still to start fresh in each session, so that a new session still checks the code it would land.
28. As a user, I want the dispatch record kept out of Git and free of exploit details, so that it neither pollutes my commits nor leaks findings.
29. As a user, I want tickets marked done only after that decision, so that ticket status reflects what was accepted.
30. As a user who turns automatic review off during a Plan, I want fixed passes reopened, so that a mode without the final check and the decision at the end does not inherit them.
31. As a user in off mode, I want today's rules unchanged, so that a mode without a final check and a decision at the end keeps file-level reopening.
32. As a user reading either README, I want what this flow does not check and what I trust in the dispatch record stated plainly, so that I know what fixed passes give up.
33. As a maintainer, I want the decision and its rejected options in ADR 0015, so that later readers know why passes stay fixed, why Adversarial findings wait and why the dispatch record is trusted.
34. As a maintainer, I want a live rehearsal with the candidate in a disposable repository, so that the rules are seen being followed without touching my own installation.

## Implementation Decisions

- **Where the rules live.** Review state's What a pass covers gains the fixed-pass rule and its limits; its Final check gains the reruns, the fix rules and the reading-set confirmation; its Accept and land at the end of the plan becomes the decision at the end; its Resumed sessions, Unknown state and Pending acceptance gain the dispatch record; its Ticket status gains the end-of-Plan done value. The code review procedure gains the brief for another Claim's acceptance checks, the Plan's base revision and the findings about an earlier Claim; outcome verification states its timing and the Plan's base revision; the Adversarial review procedure and the adversarial-review command gain the timing at the final commit, the premise and recorded findings. The delegation skill's Automatic flow gains per-Claim timing, the Blocked by wait, the stopped-upstream decision and the dispatch record.
- **Why fixed passes are enough.** Every change that keeps a pass fixed has passed its own Claim's reviews, and the final check reruns every Claim's primary acceptance at the final commit, so a Claim that breaks another Claim's checked behaviour is still caught, and the fix lands in the Claim that caused it. What the reruns cannot see is stated in item 14 and offered back through re-review at the end.
- **Why the brief carries another Claim's acceptance only for item 5.** Carrying every earlier Claim's acceptance into each later review would widen every review; the user rejected that on 2026-10-14. A Claim that changes another Claim's acceptance checks is the one case where the reviewer cannot judge weakening without that acceptance.
- **Why Adversarial review runs once at the end.** Its findings are recorded, not fixed, so attacking earlier gains nothing, and attacking the commit that will land includes every later Claim's and fix's effect; every attack judges the same unchanging commit.
- **Why BROKEN is recorded.** A fix after BROKEN restarts code review, outcome verification and the attack, and can reopen other Claims, at the end of the Plan; the user decides at the end whether to land with the known findings or not land, which keeps ADR 0009's rule that a known flaw is never shipped without the user's explicit choice.
- **Why the dispatch record is trusted.** The user decided on 2026-10-15 that records cc-feather keeps under `.feather/` are taken as written and that guarding them against forgery or hand edits is not cc-feather's job; earlier designs that distrusted records made every new session review everything again. It is kept apart from handoff records because review state is main's own bookkeeping, written in auto whether or not handoff maintenance runs. Counts are left out because ADR 0002 restarts them when the user resumes; the final check's state is left out because rerunning it is cheap and catches a workspace that no longer matches the record.
- **Unchanged.** Plan review, security analysis, the reading set apart from item 5, the completion criteria, the serial rule, the final check's preconditions and fail-closed state, counts per session, the Stop threshold, the composed Adversarial review, repository safety and the Execution rule's session-scoped statements, the installed policy, the reviewer, verifier, adversary, analyst and executor definitions, the handoff skill and the configuration tool.
- **ADR 0015** records fixed passes, per-Claim timing, the final check's reruns and fix Claims, Adversarial review at the final commit with recorded findings, the dispatch record and the decision at the end, amending ADR 0002, ADR 0006, ADR 0008, ADR 0009 and ADR 0013. Rejected: keeping file-level reopening in auto (chains reviews through shared files); the Retention check (in projects whose Claims share test modules it almost always reopens outcome verification, its checks grow with the square of the Claims, and making it safe needed many extra rules); reviewing after the whole Plan, or a setting to choose it (problems are found last, and two timings double the rules and tests); carrying every earlier Claim's acceptance into later reviews (widens every review); Adversarial review after each Claim (attacks a commit that will not land, and its HELD would need its own reopening rules); fixing BROKEN within the Plan (restarts the loop at its costliest step); reviewing every Claim from an earlier session again, or listing earlier passes as only recorded for the user to judge (costly, and pushes main's bookkeeping onto the user); labelling every commit with its Claim to rebuild state in a new session (the dispatch record already holds it); carrying counts across sessions (ADR 0002 restarts them on resume); reopening an earlier Claim for a defect it introduced (restores the chain this spec removes); counting a fix's own review calls to stop fixes that break each other (each fix can pass its own reviews, so the count never reaches the Stop threshold); a new glossary term for a fix outside every Claim (a fix Claim works as any Claim); asking the user before a fix Claim that changes a security control (it stops the Plan for a fix whose purpose is to make it work; disclosed at the end instead); a forced fix round in which every Claim must pass a step before the next (adds a global ordering and ignores stops, INCONCLUSIVE, REJECT and deferral).

## Out of Scope

- Off mode's rules, and a dispatch record in off.
- Any change to the completion criteria, the serial rule, the final check's preconditions and fail-closed state, repository safety or the Execution rule, whose statements about someone else's content and restrictions still last for the session.
- Carrying counts or the Stop threshold's session choice across sessions.
- Guarding the dispatch record or other records under `.feather/` against forgery or hand edits.
- Parallel review calls on one commit, and worktree-parallel implementation within one Plan.
- Fixing the recorded Adversarial review findings, which are the next Plan's work.
- The historical record of the 0.21.0 round, whose kept passes stay as written.
- Live rehearsal of other review scenarios, which remain with the handoff `review-live-rehearsal`.
- The findings deferred in the handoffs `claims-at-implementation-followups`, `completion-criteria-followups` and `repo-trust-default-followups`; those the dispatch record resolves (a Plan main proposed in an earlier session not classified again, a ticket's spec not recognised in a new session, a deleted pending-acceptance note, a base revision taken from a record) are marked resolved once this release lands.
