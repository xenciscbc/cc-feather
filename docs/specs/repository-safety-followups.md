# Repository safety follow-ups

Label: `ready-for-agent`

Vocabulary follows [CONTEXT.md](../../CONTEXT.md). This spec carries out the security follow-ups that the 0.21.0 review round of [the repository safety spec](repository-safety.md) left as separate work, after the user narrowed them under that spec's D-6 threat model on 2026-10-13: it states the review reads' remaining residual risks, defines what happens when a workspace comparison would run a filter, keeps text that may come from the repository off main's Git command lines, and makes the handoff tool find Git without the current directory taking part. Exploit details stay in the untracked records, as the Adversarial review procedure requires; this spec summarises.

The scope was settled in a grilling on 2026-10-13, with an independent Codex opinion (gpt-6-astra, high) on the cost and benefit of each item. Items that only defend against what D-6 accepts as residual risk were dropped and are stated as residual risk instead.

A read-only security analysis on 2026-10-13 reported sixteen findings (S1–S16 below), ten of them essential. Main adopted S2, S4, S5, S7 to S15 and part of S6 and S16, folded into C1 to C5. The release is 0.22.0. No role template changes, so users update the plugin and need no setup update.

C1 to C4 are Security-critical claims: C1 changes the stated security guarantee of review reads; C2 changes when main lets a Repository-chosen program run while it prepares a review; C3 changes how text that may be attacker-controlled reaches main's Git commands; C4 changes code that starts Git on the user's machine. C5 changes no trust boundary or control: it records validation and releases.

## Decisions

These hold for every Claim. D1 to D6 of [the repository safety spec](repository-safety.md) apply unchanged; in particular D1 (with D-6) places the working tree, tracked content and every change neither the user nor main wrote, including refs Git keeps for it, on the attacker's side, and treats the Git directory's own configuration, user- and system-level Git configuration and the user's environment as the user's own.

- **F1 Residual, not control.** A gap reachable only through what D1 treats as the user's own or already states as residual risk is stated as residual risk, and no control is added: a working-tree include the user's configuration names (the user's decision for ticket 01), and a `PATH` entry inside the project (C4). Replacement refs are different: those the user fetches from a repository they do not control are attacker-controlled under D1, and the user accepted them on 2026-10-13 as a new residual risk for their low likelihood (S1); every document says that they are newly accepted, not already covered.
- **F2 One execution rule.** A filter driver that a compared path's attributes select is a Repository-chosen program, so running it while main prepares a review is executing repository code and follows D5 in full, the repository trusted and the change under review written by the user or in this session, with one addition for the content the driver processes: whatever main can find to differ from the reviewed commit without running the driver must be attributable too, while unchanged committed content is covered by the trust answer (S4). A difference in a path whose filter names the driver can only be found by running it; such a difference that is not attributable blocks the call when found, and the driver has then already processed it, which the trust answer covers as D5 covers tests that load the working tree (NB1).
- **F3 No command-line text.** Main never places a commit or tag message on a command line, and every tag, branch, remote or refspec it names in `git add`, commit, tag or push passes the name rule whatever its origin (S8).
- **F4 No search through the current directory.** The handoff tool starts Git by an absolute path it resolved itself, never asks the operating system or Python to search for a bare program name, and passes Git a `PATH` and a working directory that keep the project's current directory out of Git's own program lookups (S14).
- **F5 No claim about the host.** No document claims that Claude Code, Codex or any other host already keeps the current directory out of program lookup; the handoff tool's guarantee holds without any environment variable. How the host starts the tool's own Python interpreter is the host's residual risk (S15).

## Problem Statement

A user relying on cc-feather's reviews and handoffs on a repository whose content may be hostile still has four gaps after 0.21.0. Some Git settings and attributes that come from the working tree are read during review reads without the rules saying so, so the stated guarantee is broader than what holds. When a workspace comparison would run a filter, main stops and asks, but the reference gives no defined answers, so the outcome depends on how a model improvises, and a repository using Git LFS stops at every review even when the user has said the repository is trusted. Main may pass a commit or tag message, or a name taken from file content, on the command line, where text from a reviewed change can reach a shell. And the handoff tool starts Git by a bare name, so on Windows how Git is found can depend on the working directory, which is inside a repository whose working tree is attacker-controlled.

## Solution

The reference and both READMEs state the remaining residual risks of review reads. Main's preparation gives a filter comparison four defined outcomes, one of which runs the driver under D5 when the repository is trusted, the change under review is the user's or the session's, every difference from the reviewed commit that main can establish without running the driver is attributable to the user or the session, and a difference only the driver finds that is not attributable blocks the call, and the comparison after a call never runs a driver. Commit and tag messages always go through a file main writes with its file tool, and names in main's Git operations pass the name rule. The handoff tool resolves Git to an absolute path from fully qualified `PATH` entries only, never falls back to a bare name, and starts Git with a cleaned `PATH` from the Git executable's own directory. The Git 2.45 branch of the handoff tool's promisor handling is checked with a real Git 2.45 or later before release.

### C1 acceptance

1. **Settings and attributes from the working tree (S2).** The reference's Scope and assurance section states as residual risk that settings the user's configuration takes from a file in the working tree, through an include, are not checked: such a file can set any setting the common prefix does not override on the command line, for example `core.attributesFile`, `core.excludesFile`, `core.autocrlf` or a further include, so that Git itself reads paths outside the project, following links, or changes the built-in conversions content hashing applies. It names as affected every review read that consults attributes or ignore rules, for example attribute checks, comparing commits, history, blame, the untracked and ignored listings and content hashing, which main's include-less configuration read does not see. The statement is worded consistently with the reference's existing residual statement for main's `git add`, commit, tag and push and with D3.
2. **Linked leading directories.** The same statement covers attribute and ignore files that Git reads from the working tree through a leading directory that may be a link, as an attribute check without `--cached` does; D3 already places files Git itself consults outside the read guarantee, and the reference now names this case.
3. **Replacement refs (S1).** The reference states that review reads do not carry `--no-replace-objects`, so a replacement ref can make a read, and the blob IDs main compares, return replaced content while main's push sends the original objects; that a replacement ref fetched from a repository the user does not control, for example by a mirror or wide refspec, is attacker-controlled under D1; and that the user accepted this as residual risk on 2026-10-13. The forms under Before add, commit, tag or push keep `--no-replace-objects`.
4. **READMEs.** Both READMEs' residual-risk paragraph of the review section gains the three statements in summary, paired in both languages.
5. **Pins.** Whole-sentence pins in the reference and paired pins in both READMEs.
6. **Security invariants** (part of this acceptance; the Adversarial review brief carries them): no existing rule is weakened or removed; the new statements narrow only what the documents claim; no statement says that a residual gap is defended or that replacement refs were already covered.
7. **Adversarial review:** static, over the reference's Scope and assurance and Safe Git invocation sections, both READMEs' residual paragraph, D1, D3 and F1. C1's outcome verification reproduces, with the installed Git in marker repositories in a scratch directory outside the project and isolated from the user's global and system configuration (`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` an empty file, `HOME` and `XDG_CONFIG_HOME` in the scratch directory), that an included working-tree file setting `core.attributesFile` changes what `check-attr` reports, that a leading directory replaced by a junction or symbolic link is followed for attributes, and that `git replace` changes what `cat-file` returns without `--no-replace-objects`; the scratch directory is removed afterwards.

### C2 acceptance

1. **Outcomes.** The reference's paragraph on comparing paths under main's preparation states that when a compared path's filter names a defined driver, main determines, for that call, one of:
   1. *Run under D5.* Main runs the comparison with the driver as configured only when all of these hold, each established before the driver runs: in this session the user has said the repository is trusted to run on this machine; the change under review was written by the user or in this session, as Execution decides authorship; every difference from the reviewed commit that main can establish without running the driver, among the paths the comparison covers, was written by the user or in this session, using only reads that run no driver (the untracked listing of the paths the comparison covers, the index listing compared with the reviewed commit's tree listing, both forms main's preparation already uses, and, for paths whose filter names no defined driver, the content hash that the reference's Main's preparation defines for its item 3, which applies only built-in conversions such as end-of-line handling, so that a checkout with `core.autocrlf` is not reported as changed), so that untracked or uncommitted content main cannot attribute fails this condition; and no key that defines the driver has its origin in a file inside the working tree, as the `--show-origin` read of the filter-driver keys shows. Content of the reviewed commit that the change leaves unchanged, such as Git LFS files others committed earlier, is covered by the trust answer and does not fail the condition, and a change under review that touches any path someone else wrote, whether or not its filter names a driver, fails it. If the comparison with the driver then finds that a path whose filter names it differs from the reviewed commit and that difference is not attributable, main treats the call as blocked, as outcome 2, offering the remaining choices, does not use the result and reports that the driver has already processed that content, which the trust answer covers (NB1). When the trust question has not yet been asked in this session, main asks it then, as Execution describes; the answer serves both purposes.
   2. *Blocked.* Otherwise, main does not dispatch the call, reports the claim blocked and offers the user the remaining choices.
   3. *Configuration changed.* The user removes or changes the attribute or the driver; main then reads the attributes, the filter-driver keys and item 4's snapshot again before deciding. The reference says that changing `.gitattributes` makes the workspace differ from the reviewed commit, and that disabling a driver in the Git directory's configuration also changes what main's later `git add` stores (S7).
   4. *Isolated environment.* The user names an isolated environment; the comparison, the review it prepares and every driver run happen there, and main runs no driver on this machine for that call (S7).
2. **Comparison after a call (S4, S6).** For a path whose filter names a defined driver, main's comparison after a call (item 5) never runs the driver: before the call main records each such path's raw bytes with a hash it computes from a read under Paths and names, and after the call it compares the raw bytes again. A path whose bytes changed is reported as changed; one whose bytes are unchanged keeps the result of the comparison before the call. A path whose filter names a defined driver only after the call, for example because `.gitattributes` or `info/attributes` changed during it, has no raw-byte record and is reported as changed without hashing (B4).
3. **Exceptions stated (S5).** The reference's Read-only bullet of Safe Git invocation and its sentence that no hash is written to the object database, and both READMEs' "Git commands" bullet, name the one exception on this machine: main's content hashing under outcome 1, which runs the driver and lets it do what it does, including writing into the Git directory, as Git LFS does, and processing an unattributed difference that only the driver can reveal before main blocks the call (NB1).
4. **No other way.** No outcome runs the driver on this machine outside outcome 1; outcome 4 runs it only in the isolated environment the user names. A choice the user has not made is never assumed; the existing stop remains the default.
5. **READMEs.** Both READMEs' "Before a review" bullet states the outcomes in summary, paired.
6. **Spec note superseded.** The repository safety spec's further note that a repository using a filter such as Git LFS asks before every review is not edited; this spec's further notes record that C2 supersedes it.
7. **Pins.** Whole-sentence pins in the reference and paired pins in both READMEs; an absence pin for every replaced sentence; the existing configuration test that pins the README "Git commands" bullet's "runs no program the repository chose" wording is updated with it.
8. **Security invariants:** main never runs a filter driver on this machine during a review's preparation or comparison unless outcome 1's conditions, established before the driver runs, all hold for that call, and a difference only the driver finds that is not attributable blocks the call; it never runs one in the comparison after a call, including for a path whose filter names a driver only after the call; authorship is D5's and never Git metadata, a handoff or repository content; a driver defined from a working-tree file never runs under outcome 1; a configuration change is read again before any decision depends on it; no statement says that a review runs no Repository-chosen program on this machine without naming outcome 1's exception.
9. **Adversarial review:** static, over the reference's Main's preparation, Execution and Safe Git invocation sections and both READMEs, probing a mixed-origin workspace, an untracked file, unchanged LFS content others committed, a change touching a non-filtered file someone else wrote, a driver defined through a working-tree include, the comparison after a call and a path whose filter names a driver only after the call. C2's outcome verification reproduces, in a marker repository set up as in C1 item 7 with `*.bin filter=marker`, a clean driver outside the project that writes a marker, and a second driver defined through an included working-tree file, that `hash-object -- '<path>'` runs the driver, that a raw-byte hash of the file does not, that `check-attr` reports the filter, that the `--show-origin` read of the filter-driver keys shows the working-tree file as the second driver's origin, and, with `core.autocrlf=true` and a CRLF text file without a filter, that the content hash outcome 1 uses equals the file's blob ID; only the scratch directory is written, nothing is fetched, and it is removed afterwards.

### C3 acceptance

1. **Fixed forms.** In the reference's Before add, commit, tag or push table, commit takes its message by `-F` only and an annotated tag by `-F` only; `-m` is removed from both.
2. **Writing the file (S9).** The message file is written with main's file-writing tool, never by a shell command (no `echo`, `printf`, here-document or redirection), even when the host's own instructions show a here-document, as UTF-8 without a byte-order mark, in main's own scratch directory outside the project, under a name that does not start with `-`, passed as a single-quoted literal, and passes the existing checks of that section (link check of each component below the scratch directory, regular file, link count 1, canonical path inside the scratch directory). This applies to every message, not only one carrying text from the repository, so main never decides whether a message is trusted; attribution lines go into the file.
3. **Names (S8).** Every tag, branch and remote that main's `git add`, commit, tag or push names passes the name rule of Paths and names, with `/` allowed between components, whatever its origin, including a name main creates from file content such as a version, and enters only as a single-quoted literal; a refspec is one such name, or two such names joined by a single `:`, never with a leading `+`. The exemption for refs main wrote itself does not cover a name taken from content. When a name fails, including one the user gave, main does not perform the operation and tells the user they may run it themselves, as that section already does when its checks cannot be established (N1, N2).
4. **Other places.** Every other procedure, command or skill text that shows main committing or tagging with `-m` is changed to match, and the README "Before add, commit, tag or push" bullet states both rules in summary, paired.
5. **Pins.** Whole-sentence pins for the new rules, an absence pin that `-m` no longer appears in the fixed forms, and paired README pins.
6. **Security invariants:** no text taken from file content, command output, a link target or a reviewed change reaches a shell command line in main's `git add`, commit, tag or push, except a name that passed the name rule, as a single-quoted literal; the message file is never inside the project and never reached through a link.
7. **Adversarial review:** static, searching the procedures, commands, skills, templates and READMEs for a remaining `-m`, here-document or name taken from content, and probing whether any operation can still place such text on a command line.

### C4 acceptance

1. **Resolution (S11, S12).** The handoff tool's single Git helper starts Git by an absolute path that a resolver in the same module returns. The resolver reads `PATH` from the environment and, when it is absent or empty, finds no candidate; it never uses `shutil.which`, `os.get_exec_path`, `os.defpath` or another lookup that adds a default path or the current directory. It walks the entries in order, removes one pair of surrounding double quotes, and considers only entries that are fully qualified: on Windows a drive letter followed by a separator, or a UNC path, never a drive-relative (`C:foo`), rooted-without-drive (`\foo`), `\\?\` or `\\.\` entry, decided without relying on `ntpath.isabs`; on POSIX a path starting with `/`. Empty, relative and unexpanded entries are skipped. Removing surrounding quotes applies on Windows only. On Windows it accepts only a file named `git.exe` that is a regular file after following any link, never applying `PATHEXT` and never a `.cmd` or `.bat`; on POSIX only a regular file named `git` that is executable, following a symbolic link to its target. The first match wins, and the resolver returns it as found, the entry joined with the file name, not a link's target, so item 3's working directory is that `PATH` entry. App Execution Aliases get no special handling. The resolver keeps no result between calls, so tests can change `PATH` within one process (N5, N6).
2. **No fallback (S10).** The resolver runs only inside the helper, and when no entry yields Git it raises `FileNotFoundError`, as `subprocess.run` does today when Git cannot be found, so every caller's handling is unchanged; the helper never retries with a bare name.
3. **Git's own lookups (S14).** The helper passes Git a `PATH` without the entries item 1 skips, by the same classification, and runs Git with the resolved Git executable's directory as its working directory, so the process's current directory takes part neither in finding Git nor in what Git looks up before it applies `-C`, such as libraries Windows loads; after `-C` Git works in the project, and its own program lookups see only the cleaned `PATH`. The directory Git works on is still given with `-C`, always as an absolute path. When the resolved Git itself lies inside the project, item 4's residual risk, that directory is inside the project too (B2).
4. **Residual statement (S15).** The handoff tool reference states, in a few sentences: how Git is found; that a candidate inside the project is not excluded because `PATH` is the user's environment (F1), with examples such as a virtual environment's scripts directory, `node_modules/.bin` or direnv, and the same holds for an entry outside the project that is a link into it, and because excluding it would need the root that discovery itself finds with Git; that an installation offering only a `git.cmd` gets the same report as when Git is absent, since a batch file re-parses its arguments; and that how the host starts the tool's own Python interpreter is outside the tool's control (F5).
5. **Resolver checks (S12).** A table-driven test runs the resolver over `PATH` values built in a scratch directory and states the expected result of each: on Windows `C:foo`, `\foo`, `.`, an empty entry, `bin`, a quoted entry, `C:/…` with forward slashes, a trailing separator, an unexpanded `%VAR%`, a UNC path, `\\?\` and `\\.\` entries, a directory named `git.exe`, only a `git.cmd`, and a zero-byte file named `git.exe`; on POSIX a non-executable `git`, a symbolic link to a directory, a symbolic link to an executable, and an absent `PATH`.
6. **Behaviour checks (S10, S13).** Through the tool's command-line operations, against disposable repositories in a scratch directory outside the project, with the process's working directory and the directory passed to `-C` always different:
   - on Windows, with a copy of `whoami.exe` from the system directory named `git.exe` in the process's working directory (it only reads, and given Git's arguments it exits with an error instead of `git version …`; N9) and `NoDefaultCurrentDirectoryInExePath` removed from the tool's environment, list and create report `root.state` `git` and the expected results; a positive control first runs, in a child process with the same environment and working directory, a bare-name start of `git version` and shows that the planted file ran (its output is not `git version …`); when it does not, the test is skipped with that reason and C5's validation entry records it;
   - on POSIX, with `PATH` holding an empty entry, `.` and a relative entry before the real Git's directory, and a working directory holding an executable `git` script that writes a marker, a positive control shows that a bare-name start runs the script, and the operations leave no marker and report the expected results;
   - with no Git on `PATH`, and with `PATH` absent, each operation's whole output equals the output it gives today when `subprocess.run` raises `FileNotFoundError`, recorded as a baseline by mocking it to raise the same exception, with the same arguments, that the resolver raises, so the comparison is exact rather than normalised (N4): list and read report the root as uncertain, snapshot and compare report the Git state unknown, and create, update and archive report what they report today, both with and without `--exact-root`;
   - an in-process check records every `subprocess.run` call the tool makes during these operations and asserts that its first argument is the resolver's absolute path, that its working directory is the resolved Git executable's directory, that its `PATH` holds none of the entries item 1 skips, and that no call is made when the resolver finds nothing.
7. **Existing checks.** The static check that only the helper starts a Git process stays and passes; the helper-call tests and the links test that asserts a command's leading arguments assert the resolved absolute path instead of `git`; the compatibility document's description of the helper's command form is updated with it (N3).
8. **Promisor test on a real Git (B3, S16).** The partial-clone test's branch for Git 2.45.0 or later asserts the expected functional results of each operation, not only the absence of the promisor cause codes, so that another Git failure cannot pass it: create and update with either tracking choice exit 0 with status `ok`, and the completed create exits 0 with status `ok` and the work archived (its file removed and its history entry present), since a completed save archives itself when nothing fails; today create and update run but are not asserted there, and the archive retry runs only in the older-Git branch, where it remains. Before C4's outcome verification, main downloads the then-current stable PortableGit release of Git for Windows, at an exact version of 2.45.0 or later and including `sh`, into its own empty directory in the scratch directory, checks it against the SHA-256 the release publishes, and asks the user before running it; C4's outcome verification then runs the three tests of the partial-clone test class with that Git first on `PATH` and requires the positive controls of the two tests that have one, both controls of the second test included, to run. The download is removed after the review round. C4 is not accepted until this branch has run on that Git.
9. **Upstream manifest.** The manifest that records the handoff tool's adapted files gets their new hashes and an adaptation note for the resolver, including why `.cmd` and `.bat` are excluded.
10. **Security invariants:** no process the handoff tool itself starts is found through the current directory, an empty, relative or not fully qualified `PATH` entry, a default path or a bare name; every Git process the tool starts uses the resolver's absolute path, a `PATH` without such entries and the resolved Git executable's directory as working directory, which is outside the project unless the resolved Git itself is inside it (item 4's residual risk); when the resolver finds nothing, no process is started and the error is the one callers already handle; the helper's existing protections (fsmonitor, optional locks, pager, environment, promisor handling) are unchanged. Programs Git itself starts are bounded by those protections and the cleaned `PATH`.
11. **Adversarial review:** dynamic, against a disposable target. Main creates a fresh scratch root outside the project holding `repo` (a new repository with a few text files and one commit) and `cwd` (on Windows a copy of `whoami.exe` named `git.exe`, on POSIX a `git` script that writes a marker into the scratch root). The adversary starts the candidate tool with `python -E -s -S -B <candidate>/skills/handoff/scripts/handoff.py --project <scratch>/repo <operation>` from `cwd`, with `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` an empty file, `HOME` and `XDG_CONFIG_HOME` in the scratch root and `NoDefaultCurrentDirectoryInExePath` removed, over `PATH` variants: planted entries (`""`, `.`, `bin`, a drive-relative entry on the scratch drive, `\foo` only where the scratch drive's root is writable, a quoted entry) before the real Git's directory; planted entries only; `PATH` absent; only a `git.cmd`; and a directory named `git.exe`; each variant with a positive control as in item 6. Reachable dependencies: the installed Git and Python, no network. Allowed effects: creating, changing and deleting inside the scratch root, and running only the real Git, the candidate tool and the planted harmless programs. Reset: the scratch root is removed before the report. This runs the candidate's own code, written in this session, so main asks the user before it whether this repository is trusted to run on this machine (D5).

## User Stories

1. As a user, I want the documentation to say which settings and attributes from my working tree are not checked during a review, so that I do not overestimate the read guarantee.
2. As a user, I want reads through a linked directory named as outside the guarantee, so that I know a hostile layout can still make Git read outside the project.
3. As a user who fetches with a mirror or wide refspec, I want to be told that a replacement ref from that repository can show a review different content from what main pushes, so that I avoid that fetch for repositories I do not control.
4. As a user who never fetches replacement refs, I want no extra Git option or check on every review for that case, so that the rules stay as simple as the risk allows.
5. As a user with a Git LFS repository I have said is trusted, reviewing my own changes on top of LFS files others committed earlier, I want reviews to proceed without asking me again at every call, so that LFS does not make reviews unusable.
6. As a user with an untrusted change or untracked files in an LFS repository, I want main to stop before running the LFS filter whenever it can tell, and to stop and tell me when only the filter could reveal an unattributed difference, so that the filter processes content I did not write only within the trust I gave.
7. As a user, I want a filter defined by a file inside my working tree never to run under the trust answer, so that a hostile include cannot choose the program.
8. As a user, I want the same trust question main already asks before running tests to decide whether a filter may run, so that I answer one question, not two.
9. As a user, I want defined choices when a filter blocks a review, so that I know I can change the configuration, name an isolated environment or leave the claim blocked.
10. As a user who changes my attributes after a stop, I want main to read them again before deciding and to tell me what disabling a driver also changes, so that a stale answer is never used and later commits do not surprise me.
11. As a user, I want the comparison after each call never to run a filter, so that a change made during a call is detected without running repository code.
12. As a user, I want the documentation to name the one case in which main's preparation runs a filter on this machine, so that the "runs no program the repository chose" statement stays true.
13. As a user, I want commit and tag messages never written on a shell command line, so that text from a reviewed change cannot become a command.
14. As a user, I want main to use a message file for every commit, so that safety does not depend on main judging which messages are trusted.
15. As a user, I want the message file kept outside my project and checked for links, so that writing it cannot overwrite a project file.
16. As a user, I want tag and branch names taken from file content checked by the name rule, so that a crafted version string cannot become a command.
17. As a Windows user, I want the handoff tool never to run a `git.exe` that a repository placed in its working tree, so that saving progress cannot run that file.
18. As a user on any platform, I want the handoff tool to ignore empty, relative and drive-relative `PATH` entries, so that the current directory never takes part in finding Git.
19. As a user, I want Git started by the handoff tool to see a cleaned `PATH` and to run from the Git executable's directory, so that Git's own lookups do not search the current directory either.
20. As a user whose Git is installed normally, I want the handoff tool to keep finding it from my `PATH`, so that nothing changes in ordinary use.
21. As a user without Git on `PATH`, or with no `PATH` at all, I want the same report as today, so that the failure is clear and nothing else is tried.
22. As a Codex user sharing the handoff runtime, I want the same lookup protection, so that it does not depend on the host setting an environment variable.
23. As a user, I want the documentation not to claim that my host already protects the lookup, and to say that the host's own start of Python is outside the tool, so that I know where the guarantee ends.
24. As a user whose Git installation offers only `git.cmd`, I want to be told why the tool cannot find Git, so that I can add `git.exe` to `PATH`.
25. As a user with a partial clone and a recent Git, I want the `--no-lazy-fetch` branch checked on a real Git, so that the handoff tool works in my checkout.
26. As a maintainer, I want the partial-clone test to assert real results, and the lookup tests to show their positive controls ran, so that a skipped or unrelated failure cannot pass them.
27. As a user updating from 0.21.0, I want to be told that a plugin update is enough, so that I do not run setup needlessly.
28. As a maintainer, I want every new rule pinned by whole-sentence tests in both languages, so that the documents cannot drift.

## Implementation Decisions

- The shared repository safety reference remains the single statement of the review rules; the READMEs summarise it. C1 to C3 change only the reference's Scope and assurance, Safe Git invocation, Main's preparation and Before add, commit, tag or push sections, the matching README bullets and paragraph, and any procedure or skill text that shows a commit or tag message by `-m`.
- No role template changes: the shared role paragraph keeps its forms, so installed roles stay current and need no setup update.
- C2 reuses D5's existing session determination and authorship rule rather than adding a filter-specific trust record; the answer to the trust question is session state, never handoff content. The raw-byte hashes of C2 item 2 are session state as well.
- The handoff tool keeps one Git helper; the resolver lives in the same module, takes the environment's `PATH`, returns an absolute path or raises `FileNotFoundError`, and starts no process. It keeps no result between calls, as C4 item 1 states.
- The handoff tool does not add `--no-replace-objects` and keeps removing an inherited `GIT_NO_REPLACE_OBJECTS` (see Further Notes).

## Testing Decisions

- Tests check shipped behaviour through the texts users install and the tool they run: whole-sentence pins in the reference and paired pins in both READMEs, absence pins for removed wording, and command-line runs of the handoff tool against disposable repositories in a scratch directory. Prior art: the pins in the repository safety and release test modules, and the tracking-probe, Repository-chosen program and partial-clone tests of the handoff Git helper module.
- The resolver also gets a table-driven test of `PATH` values, because the classification of each entry is the control and the command-line seam cannot reach every entry shape.
- The Windows lookup test uses a copy of `whoami.exe` as the planted `git.exe` and judges by the tool's output, since that executable writes no marker; its positive control runs in a child process with the tool's environment, because the test process may inherit `NoDefaultCurrentDirectoryInExePath` from its host. The POSIX test uses a marker script with its own positive control.
- The no-Git checks compare each operation's output with a baseline recorded by mocking `subprocess.run` to raise `FileNotFoundError`, which is today's behaviour.
- The real Git 2.45 check is part of C4's outcome verification and reuses the existing partial-clone test unchanged apart from C4 item 8, by placing the downloaded Git first on `PATH`; no test-only switch for choosing Git is added.
- The Git behaviours C1 and C2 rely on are reproduced by their outcome verification in marker repositories, not by the test suite; text tests show that the shipped contract is consistent, not that a live model follows it (D2 of the repository safety spec).

## Out of Scope

- `--no-replace-objects` on review reads, a check for replacement refs, or `--no-replace-objects` in the handoff tool (F1; stated as residual risk by C1).
- Asking when an include, `core.attributesFile`, `core.excludesFile` or `core.hooksPath` points inside the working tree (S3; F1).
- Excluding Git candidates inside the project from the handoff tool's lookup (F1; stated as residual risk by C4).
- Comparing an untrusted Git LFS change without running the filter, for example by checking pointer object IDs (S6); such a change stays blocked or goes to an isolated environment.
- Other ways built-in conversions such as `ident` or end-of-line handling can make different bytes hash alike (S6): separate work.
- Reading include-following configuration keys with `-z`.
- Wording that 0.21.0's review round left for item 4.4's hooks snapshot when the hooks directory lies outside the project, and the other non-security wording and test items: the non-security follow-up work.
- A process-only filter driver: already covered by the existing pattern and pins.
- Opening a pull request with `gh`, including its title and body, which stays residual risk as the repository safety spec states.
- Rules for where sensitive findings may be disclosed (A4-b to A4-f, A5, C3-a, C3-b, C4-a): the second disclosure batch, next release.
- Trust in a repository that lasts across sessions, and the pilotfish hygiene items other than the handoff tool's lookup: separate work.
- Ranges other than two-dot and bind or FUSE mounts (A8-a, A8-b): separate work.
- Claude Code's own Git commands at session start (D6 of the repository safety spec).
- Enforcing any rule through permission settings, hooks or a sandbox.

## Further Notes

- C2 supersedes the repository safety spec's note that a repository using a filter such as Git LFS makes main ask before every review whose compared paths it covers: under C2 it asks once, through D5's trust question, when the change under review is the user's or the session's and every difference from the reviewed commit that main can establish without running the driver is attributable to the user or the session, and a difference only the driver finds that is not attributable blocks the call.
- The handoff tool does not carry `--no-replace-objects` and removes an inherited `GIT_NO_REPLACE_OBJECTS` from its environment, as before; its reads use few objects, and the user chose to leave this as it is.
- Git 2.43 is the version this repository is validated on; C4 item 8 is the only check of the Git 2.45 branch on a real Git. If it fails, the fix is part of C4 and C4 goes through its review steps again before C5.
- This release's review round runs under the installed cc-feather procedures and roles (0.20.0 at the time of writing), never the candidate's own templates. C4's Adversarial review runs the candidate's own handoff tool, code written in this session; main asks the user before it whether this repository is trusted to run on this machine, and if the review round crosses into a new session, ADR 0009's isolation rule applies.
- Rollback: before anything is pushed, the Claims' unpushed commits can be dropped with the user's agreement; after the release, a user reinstalls 0.21.0.
