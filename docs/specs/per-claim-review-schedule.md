# Each Claim is reviewed as soon as it is implemented, and only what its acceptance needs holds it

Label: `ready-for-agent`

Vocabulary follows [CONTEXT.md](../../CONTEXT.md), whose Review schedule, Review group, Recorded security defect and Follow-up record entries were added for this spec; its Blocking finding, Non-blocking finding, Adversarial review, Acceptance gate, Accept and land and Security-critical claim entries are amended as part of this work. It builds on [the claims-at-implementation spec](claims-at-implementation.md), released in 0.23.0. The scheduling decisions were settled in a grilling with the user on 2026-10-13, on top of the user's decisions of 2026-10-10, and are recorded in ADR 0013; the completion criteria were settled in a grilling on 2026-10-14 and are recorded in ADR 0014. Both ADRs are written as part of this work, and the decisions are also recorded in the handoff `review-schedule-per-claim`. This is the second stage of that work; the first, the test module split, shipped on main after 0.20.0.

This spec has no Claims table: implementing it makes it one Claim against the Acceptance below, and cutting it into tickets first makes each ticket a Claim.

## Problem Statement

In auto, code review, outcome verification and Adversarial review start once the whole reviewed Plan is implemented. A defect in an early Claim is found only after every later Claim is built on it, and its fix then reopens the later Claims that share its files. In 0.20.0, C3's defect surfaced only after C4 was done, and the fix reopened C1, C2 and C4. Reviewing each Claim as soon as it is done would find such defects early, but because a pass reopens whenever a Claim's files change, reviewing Claims one by one while later Claims keep editing the same files makes passes reopen in a chain. Nothing today tells main which Claims to review together, when a downstream Claim may start, or what to do when the working tree changes while a review runs.

Reviews also hold completion for more than the Claim promised. A correctness bug or security problem anywhere in the change blocks code review, and any vulnerability the change introduced is BROKEN, whether or not the Claim's acceptance states it. Each such finding starts another fix and another review, and each fix can surface the next edge case: the 0.22.0 round looped on Adversarial edge cases of its security claims, and the 0.23.0 round was finished only by deferring findings by hand. Nothing in the product says which findings hold completion and which are recorded for later.

## Solution

In auto, each Claim is reviewed as soon as it is implemented: code review, then outcome verification and, for a Security-critical claim whose acceptance states a security property, Adversarial review. A Claim that depends on another starts only after that one has a currently valid pass.

For a Plan with more than one Claim, main makes a Review schedule when implementation starts. Claims expected to write the same files, or whose acceptance can only be checked with another done, form a Review group: they are implemented together and then each is reviewed on its own at the same commit. Every other Claim follows its `Blocked by` order. Plan review checks the schedule; an active handoff records it; it is never written into the spec or tickets and never changes the Claims. Main may regroup Claims not yet started, stating why and telling the user.

Within one working tree, reviews and implementation are serial: while a review call runs, main does not change that working tree. Main does not create worktrees for reviews on its own. Work the user already runs in separate worktrees proceeds in parallel, each worktree serial in itself.

Before landing or release, main runs the Plan's overall acceptance once at the final commit; a failure reopens the Claims it affects.

A Claim is complete when its acceptance as written is met, existing behaviour is not broken, and it has no Deviation. A finding holds completion only when it shows one of these unmet, and a broken existing behaviour needs a failing test or a reproduction. Everything else found along the way, including issues that predate the change and the change's own security defects outside what the acceptance states, is recorded in the work's Follow-up record for a later Plan. A Recorded security defect never passes silently: in auto, the Claim carrying it is landed or released only through an Accept and land decision that names it. A Security-critical claim whose acceptance states no security property has its Adversarial review deferred to that later Plan.

## Acceptance

1. **Per-Claim timing.** In auto, plan review and the review procedures state that each Claim, or each Review group once all its members are implemented, gets code review, then outcome verification and, for a Security-critical claim marked under item 19 as stating a security property, Adversarial review, as soon as it is implemented and committed, instead of after the whole Plan. Off mode is unchanged.
2. **Downstream start.** A Claim with `Blocked by` dependencies, or placed after a Review group, starts implementation only when every Claim it depends on has a currently valid APPROVED and CONFIRMED, plus HELD for a Security-critical claim whose Adversarial review is not deferred under item 19. An APPROVED that lists Recorded security defects is a valid pass. An accept-and-land decision does not release a downstream Claim. Across sessions, a dependency whose ticket was set to a done value after valid passes, with no relevant change since, releases its downstream Claims; one set to a done value on an accept-and-land decision does not, and its downstream waits for passes in the current session or the user's decision. Independent Claims continue while a dependency is stopped or under review.
3. **Review schedule.** For a Plan with more than one Claim, main makes a Review schedule when implementation starts: its Review groups, each with its members and its reason (expected shared files, or an acceptance that needs another member done), and the order of the other Claims from their `Blocked by` lines. It goes into the plan-review brief, plan review judges it, and an active handoff records it. It is not written into the spec or tickets and never adds, splits or merges Claims. A Plan with one Claim needs none.
4. **Review groups.** Members are implemented in their internal dependency order, committed, and reviewed after the last one is done, each in its own code review, outcome verification and, where required, Adversarial review at the same commit. Each member keeps its own verdicts and counts and the Stop threshold applies to each.
5. **Regrouping.** Main may regroup Claims not yet started, stating the reason, telling the user and updating the handoff, without another plan review. Claims started or already passed keep their state; a change that touches a passed Claim's files reopens it under the existing rules.
6. **Dependency reopened.** When a dependency is reopened while a downstream Claim is being implemented, the downstream Claim may continue, but its reviews wait until the dependency passes again. The downstream Claim's briefs name the dependency commit they rely on, and a later change to what the downstream Claim depends on reopens it under the existing rules. A later Plan that fixes recorded findings of completed Claims is new work and reopens nothing of this Plan.
7. **Serial within a working tree.** While a code review, outcome verification or Adversarial review call runs, main does not change the working tree it judges, and implementation of the next Claim in that tree waits until the call ends. Main does not create a worktree for a review on its own. Work the user runs in separate worktrees may proceed in parallel, each worktree serial in itself; shared test resources stay governed by each brief's target start and reset.
8. **Final check.** Before landing or release, main runs the Plan's overall acceptance checks at the final commit, within repository safety's Execution rules. It is not a counted step. A failure reopens the Claims it affects, and landing and release wait for their passes again.
9. **Already implemented Claims.** When a Review schedule is made for a Plan with some Claims already implemented (Implemented before plan review, or auto turned on mid-Plan), the schedule covers the Claims not yet implemented; the implemented ones are reviewed first, those sharing files as one Review group at the current commit and the rest in `Blocked by` order, and their downstream Claims start under item 2.
10. **Preview.** The Delegation preview lists the Review schedule it expects, marked as a forecast that binds nothing; the binding schedule is the one made when implementation starts.
11. **Glossary and ADRs.** `CONTEXT.md`'s Review schedule, Review group, Recorded security defect and Follow-up record entries state the rules above (already added; checked, not rewritten). Its Blocking finding and Non-blocking finding entries state the criteria of item 16 for every review step; its Adversarial review entry states the timing of item 19 and the BROKEN of item 20; its Acceptance gate entry requires no Recorded security defect besides the passes; its Accept and land entry covers several Claims and Recorded security defects as item 21 states; and its Security-critical claim entry states the security-property mark of item 19. ADR 0013 records per-Claim timing with Review schedules and its rejected options. ADR 0014 records the completion criteria and its rejected options, and states that it amends ADR 0006 and ADR 0009; both are marked as amended by it.
12. **READMEs.** `README.md` and `README.zh-TW.md` explain per-Claim timing, the Review schedule with an example of a Review group and a downstream Claim, serial work within a working tree, the final check, what holds completion and what is recorded, Recorded security defects with the Accept and land they need, and the deferred Adversarial review; both say the same thing and match the procedures, and the cost explanation states how a Review schedule and the deferred Adversarial review affect it.
13. **Tests.** Contract tests pin the new statements and fail on the text before this spec; pins of replaced statements (review after the whole Plan, the old blocking and BROKEN criteria) are updated or become absence pins; the installed reviewer and adversary templates are pinned to the new criteria; the full suite passes in both discovery forms.
14. **Live rehearsal.** With the installed roles of the candidate, main runs a disposable three-ticket Plan in auto: two tickets writing the same file form a Review group and the third is blocked by one of them, and one ticket carries a seeded security defect outside what its acceptance states. The record shows the Review schedule judged by plan review, the group reviewed at one commit with separate calls, the third ticket starting only after its dependency's passes, no working-tree change during a review call, the seeded defect reported under an APPROVED as a Recorded security defect and written to the Follow-up record, main asking for an Accept and land decision naming it before landing, and the final check. The rehearsal, its environment and its result are recorded in the release's validation entry; a deviation from the rules is a finding, not a pass.
15. **Release.** The plugin version is 0.24.0; `claude plugin validate .` passes; `docs/setup-validation.md` gains the release entry with test counts and skips, the rehearsal, the review round and the note that existing installations need the plugin update and then `/cc-feather:setup update`, because installed role definitions changed; README's Updates section says the same; the tag is created after the user's go-ahead, only after checking that it matches `plugin.json` at the tagged commit and does not already exist.
16. **Completion criteria.** Plan review, the review procedures and review state state that a Claim's reviews judge it against three conditions: its acceptance as written is met; existing behaviour is not broken, shown by a failing test or a reproduction that a written rule or a shipped spec's acceptance no longer holds; and it has no Deviation from the Plan. A Blocking finding shows one of them unmet; inference alone does not block. Every other finding, including an issue that predates the change, a correctness or security problem outside what the acceptance states and a regression only inferred, is a Non-blocking finding and is recorded. A Deviation still stops main to ask the user, as today. The criteria apply in both Review modes and to every user; there is no setting.
17. **Reviewer role.** The installed reviewer definition states the Blocking and Non-blocking criteria of item 16, and lists a vulnerability the change introduced outside what the acceptance states under a separate Recorded security defects heading, which does not change an APPROVED. The installed verifier definition is unchanged.
18. **Recorded security defects.** In auto, a gated Claim with any Recorded security defect is landed, released or reported complete only through an Accept and land decision that names each one, even when all its passes are valid. In off, main lists them in its completion report. Either way they go to the Follow-up record under item 22.
19. **Adversarial review timing.** When main identifies a Security-critical claim, it marks whether the Claim's acceptance states a security property, with the reason. Plan review checks each mark and lists every Claim marked as stating none to the user in its result. A Claim marked as stating one gets Adversarial review under item 1, judged against the security invariants its acceptance states. A Claim marked as stating none gets no Adversarial review in this Plan: its Adversarial review is deferred to a later Plan, run at the fixed commit, and in auto its landing or release needs an Accept and land decision naming the missing HELD.
20. **Adversary role.** The installed adversary definition answers BROKEN only for a violation of a security invariant the acceptance states or a promised security fix that still reproduces. Another vulnerability the change introduced is reported as a Recorded security defect, beside pre-existing vulnerabilities, and does not change the verdict. The Adversarial review procedure states that a problem reproduced in a way this Plan's own work would run on this machine is not run and not fixed on the spot, but recorded.
21. **Accept and land for several Claims.** One Accept and land decision may name several Claims, stating for each the commit it accepts, the missing passes, the known vulnerabilities and the remaining risk. Main lists every Claim it would cover for the user's confirmation, and the decision holds only after that confirmation.
22. **Follow-up record.** Findings recorded under items 16 to 20 go to one Follow-up record per piece of work, security defects first, together with the Claims whose Adversarial review is deferred. With handoff maintenance active it is a handoff record of its own, kept by that work's handoff writer; otherwise main lists its content in the completion report and, for Recorded security defects, in the Accept and land record. The completion report lists the Claims and defects waiting for a later Plan; nothing starts that Plan automatically, and the user decides when to start it.

## User Stories

1. As a user, I want each Claim reviewed as soon as it is done, so that a defect is found before later Claims build on it.
2. As a user, I want a downstream Claim to wait for its dependency's valid passes, so that it is not built on code that may still change.
3. As a user, I want independent Claims to continue while another is under review or stopped, so that one stopped Claim does not stall unrelated work.
4. As a user, I want Claims that write the same files reviewed together, so that reviewing one does not reopen another in a chain.
5. As a user, I want each Review group to carry a stated reason, so that I can see why Claims were grouped and challenge it.
6. As a user, I want plan review to check the Review schedule, so that a poor grouping is caught before implementation.
7. As a user, I want the Review schedule kept out of my spec and tickets, so that the documents I agreed to are not edited for scheduling.
8. As a user, I want the Review schedule never to add, split or merge Claims, so that the Claims stay what I named.
9. As a user, I want each member of a Review group to keep its own verdicts and counts, so that grouping does not hide a failing Claim.
10. As a user, I want an accept-and-land decision not to release downstream Claims, so that accepting a risk on one Claim does not let others build on it unreviewed.
11. As a user resuming in a new session, I want a dependency accepted with valid passes to release its downstream ticket, so that finished work is not reviewed again before the next ticket starts.
12. As a user, I want main to regroup Claims not yet started when the schedule proves wrong, and tell me, so that a bad forecast does not force needless reopening.
13. As a user, I want regrouping never to touch started or passed Claims, so that it cannot be used to escape a review.
14. As a user, I want a downstream Claim to keep going when its dependency is reopened, with its reviews waiting, so that work already done is not thrown away.
15. As a user, I want a downstream Claim's briefs to name the dependency commit they rely on, so that a review judges against the right version.
16. As a user, I want main not to change a working tree while a review of it runs, so that every pass judges exactly the commit it names.
17. As a user of a project with costly setup, I want main not to create worktrees for reviews on its own, so that reviews do not trigger reinstalls or rebuilds.
18. As a user who already works in several worktrees, I want them to proceed in parallel, so that the serial rule does not slow down work I separated myself.
19. As a user, I want one overall acceptance run at the final commit before landing or release, so that a dependency main missed is still caught.
20. As a user, I want that final run not to count toward the Stop threshold, so that it does not stop the flow by itself.
21. As a user turning auto on mid-Plan, I want implemented Claims reviewed first with the same grouping rule, so that the schedule covers the whole Plan consistently.
22. As a user, I want the Delegation preview to show the expected Review schedule, so that I can judge the cost before asking for implementation.
23. As a user in off mode, I want reviews still to run only when I ask, so that nothing starts on its own.
24. As a user reading either README, I want the schedule and what holds completion explained with an example, so that I know when reviews will happen and what will stop them.
25. As a maintainer, I want the decisions and their rejected options in ADR 0013 and ADR 0014, so that later readers know why reviews run per Claim and why findings outside the acceptance are recorded.
26. As a maintainer, I want a live rehearsal with the installed roles, so that the rules are seen being followed, not only stated.
27. As a user with an existing installation, I want the update notes to tell me to run setup update, so that the changed role definitions reach my installation.
28. As a user, I want work to be complete when it does what its acceptance says without breaking what already worked, so that a review round does not keep widening until it never ends.
29. As a user, I want a claim of broken existing behaviour to need a failing test or a reproduction, so that inference alone does not hold my work.
30. As a user, I want issues that predate the change and problems outside the acceptance recorded for later, so that they are neither lost nor fixed in the middle of unrelated work.
31. As a user, I want every security defect a change introduced named to me before it lands, so that I never ship a known vulnerability without deciding to.
32. As a user, I want a Security-critical claim whose acceptance states no security property to have its Adversarial review in a later Plan, so that the round is not held by edge cases its acceptance never promised.
33. As a user, I want to see which Claims plan review marked as stating no security property, so that I can challenge a mark that would defer an Adversarial review.
34. As a user releasing several Claims, I want one Accept and land decision to list them all, so that I confirm each once without a separate exchange per Claim.
35. As a user, I want deferred findings gathered in one Follow-up record per piece of work, security defects first, so that the next patch starts from a complete list.
36. As a user, I want a problem that this round would run on my machine recorded rather than run, so that a review never executes a known defect here.

## Implementation Decisions

- **Where the rules live.** Plan review states per-Claim timing, the Review schedule it judges, the downstream start rule and the security-property marks it checks; it replaces the timing that `skills/delegation/SKILL.md` states as plan-driven work needing code review and outcome verification "once implemented" without saying when within a Plan. Review state carries Review groups, regrouping, a reopened dependency, the serial rule, the final check and already implemented Claims beside its existing validity and completion rules, and gains the completion criteria, Recorded security defects, the Follow-up record and the deferred Adversarial review. Code review, outcome verification and Adversarial review state when a Claim or Review group is ready for them, and judge against the completion criteria. The delegation skill's rule on parallel work gains the serial rule for review calls. The preview gains the forecast schedule. The Accept and land rules gain decisions for several Claims and Recorded security defects.
- **Grouping criterion.** A Review group is formed when Claims are expected to write the same files, or one's acceptance can be checked only with another done. A `Blocked by` line alone orders Claims without grouping them. Because reopening stays file-level, a Plan whose Claims all touch a shared file becomes one group, which matches today's behaviour; finer reopening is out of scope.
- **Reviews of a group.** Each member gets its own call with its own brief; installed role report formats keep one Claim per call.
- **Regrouping is not a deviation.** A Review schedule does not change a Plan's outcome, scope or acceptance, so regrouping is not a material deviation and needs no plan review; it must be visible to the user and recorded.
- **Serial rule.** It follows from the existing rule that a gated pass judges a workspace equal to the commit its brief names and unchanged during the call; this spec makes main's behaviour explicit. A worktree the user set up for parallel work is its own workspace.
- **Final check.** It is main's own run of the Plan's overall acceptance, such as the full test suite, not a review step, and it does not count. It adds no new verdict: its failure reopens Claims under the existing rules.
- **Completion criteria in the roles.** The blocking criteria live in the installed reviewer definition, and BROKEN in the installed adversary definition, so the criteria change those two definitions; procedures alone could not stop a reviewer from answering CHANGES_REQUESTED for a problem outside the acceptance. The verifier already stays within the Claim and refutes only on a reproduced failure, so it is unchanged. Existing installations need `/cc-feather:setup update` after the plugin update.
- **A Recorded security defect is not a block but is never silent.** It does not change APPROVED or HELD, so the round can finish; the Acceptance gate instead requires an Accept and land decision that names it, which is how a known vulnerability is shipped today.
- **The security-property mark.** Main marks it when it classifies a Security-critical claim, and plan review checks it, so that a Claim cannot defer its Adversarial review by leaving its security invariants out of its acceptance unseen; every "none" is shown to the user.
- **Unchanged.** Reopening stays file-level. The Stop threshold, counts per session, Unknown state, cross-session rules, composed Adversarial review and ticket status rules are unchanged, apart from the Acceptance gate and Accept and land changes above. The installed policy, the verifier, analyst and executor definitions, the handoff skill and the configuration tool are unchanged.
- **ADR 0013** records per-Claim timing with Review schedules. Rejected: reviewing after the whole Plan (late defects and chained reopening after fixes); writing the schedule into the Plan (main would edit documents the user agreed to); relying on the planning step to merge coupled work into one ticket (tickets are cut for independent verification, not for shared files); one call reviewing a whole group (changes installed roles and breaks per-Claim reading); review worktrees created by main (setup cost in other projects); worktree-parallel implementation and dependency-precise reopening (deferred until needed).
- **ADR 0014** records the completion criteria, amending ADR 0006 (what holds completion) and ADR 0009 (when Adversarial review runs and what BROKEN means). Rejected: blocking on every correctness or security problem in the change (rounds widen and loop); a separate list of blocking exceptions (its items restate the three conditions and invite reviewers to widen them); a vague exception for findings that endanger this machine (no clear edge); a setting to choose the old criteria (adds configuration for a rule every user benefits from, while Accept and land keeps known vulnerabilities visible); main re-triaging verdicts without changing the roles (the reviewer would still answer CHANGES_REQUESTED, and every Claim would need Accept and land).

## Testing Decisions

- The seam is the existing contract tests on shipped text: key-phrase pins in the procedures, role templates and paired pins in both READMEs, with absence pins for removed wording. Prior art: the Stop threshold procedures, review-state rules and claim-source tests.
- New pins assert: per-Claim timing; the Review schedule's content, its plan review and its exclusion from specs and tickets; the grouping criterion; separate calls per member; the downstream start rule, including accept-and-land, a deferred Adversarial review and the cross-session case; regrouping; a reopened dependency; the serial rule and its worktree exception; the final check and that it is not counted; already implemented Claims; the preview's forecast; the three completion conditions and the evidence rule; the reviewer's and adversary's new criteria and the Recorded security defects heading; the gate on Recorded security defects; the security-property mark and its plan review; Accept and land for several Claims; the Follow-up record; the recorded-not-run rule; and the setup update note. Each fails on the text before this spec.
- The live rehearsal is the second seam, needed because these rules depend on main's conduct: it runs once at the candidate with the installed roles, in a disposable repository outside the project, and is recorded, not automated.
- READMEs, `CONTEXT.md` and the ADRs are checked at outcome verification against the procedures.
- Release checks: the full suite in both discovery forms and `claude plugin validate .`.

## Out of Scope

- Worktree-parallel implementation within one Plan, and how passes carry over when branches from separate worktrees are merged; the final check is the only safeguard this spec adds for merged work.
- Reopening by precise dependency instead of by file.
- Wording and test items in the follow-up cleanup record, including the review-state, README Budget, Adversarial review and RETIRED-pattern items.
- The findings deferred from 0.23.0 in the handoff `claims-at-implementation-followups`, which a later patch handles.
- Live rehearsal of other review scenarios, which remain with the handoff `review-live-rehearsal`.
- Claim sizing and what a Claim's reviews read, which the claims-at-implementation spec settles.
- Automatically starting the later Plan that fixes recorded findings or runs deferred Adversarial reviews.

## Further Notes

- Security-critical classification of this spec's Claims happens before its first plan review. It changes the Acceptance gate, when Adversarial review runs, what BROKEN means and what releases downstream work, so it is expected to be classified as Security-critical, which brings a security analysis before plan review.
- The new `CONTEXT.md` entries were added during the two grillings and are committed with this spec; the existing entries item 11 amends are pinned by contract tests, so they change with those tests during implementation.
- The grillings' decisions are recorded in the handoff `review-schedule-per-claim`.
- Rollback: before anything is pushed, the unpushed commits can be dropped with the user's agreement; after the release, a user reinstalls the previous version and runs `/cc-feather:setup update` to restore its role definitions.
