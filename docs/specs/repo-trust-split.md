# Delegation trusts the repository; repository safety becomes a one-time check

Label: `ready-for-agent`

Vocabulary follows [CONTEXT.md](../../CONTEXT.md). This spec replaces the threat model that [the repository safety spec](repository-safety.md) (0.21.0), [its follow-ups](repository-safety-followups.md) (0.22.0) and [the repository trust default](repo-trust-default.md) (0.25.0) built into the delegation skill; those specs stay as the record of what they decided. The user settled the decisions on 2026-10-18 in a grilling, recorded in the handoff `repo-trust-split`; the questions left open there were settled on 2026-10-19 (Further Notes). ADR 0016, written as part of this work, records them. A security analysis of the first draft (2026-10-19, findings D-1 to D-8 and R-1 to R-9) is dispositioned in Further Notes.

This spec removes existing security controls, so it is a Security-critical change and needs a written, reviewed plan the user approves before implementation. It has no Claims table: implementing it makes it one Claim against the Acceptance below, and cutting it into tickets first makes each ticket a Claim. The Acceptance is grouped into four parts that a ticket breakdown can follow: Delegation (items 1–8), repo-check (9–13 and 17), Documents (14–16) and Release (18–19); Documents depends on the first two and Release on Documents. Each part's own tests pass and the full suite passes at the commit that completes it. A ticket for a part cites the parts of this spec it needs explicitly: Delegation cites S1–S5, S8 and T2; repo-check cites S6–S8, T1, T1a and T3; Documents cites S1, S2 and S7; Release cites S1, S8, T1, T1a and T2; each also cites the Out of Scope lines that limit it.

## Problem Statement

Every review, plan review and security analysis follows [repository safety](../../skills/delegation/references/repository-safety.md), a 51 KB reference written against a hostile repository: a common Git prefix and a closed list of Git forms, link, hard-link and name checks before every read, allowlists for roles without a shell, a configuration and hooks snapshot before every dispatch, filter-driver outcomes with a raw-byte comparison, `GIT_INDEX_FILE` handling, promisor detection, and fixed forms with a message-file procedure for every `git add`, commit, tag and push. The reviewer, verifier and adversary definitions carry a 9 KB copy of the read rules, and the analyst, scout and Explore definitions carry the allowlist paragraph.

The rules cost every review: main loads them before each call, roles spend tool calls on metadata checks, and a role that reads a file with an ordinary tool or runs `git status` deviates. They are still instructions, not enforcement, so a hostile repository is not actually contained: since 0.25.0 a review executes the repository's code on this machine by default, and Claude Code loads the project's `CLAUDE.md` and `.claude` settings before any of these rules apply. Each review round of the rules has found another gap, and the Follow-up records of 0.21.0 to 0.28.0 hold dozens of further items against them.

What the user needs is different: a repository they work in is theirs or one they chose to trust, and the moment to doubt a repository is when it arrives, not on every review.

## Solution

Delegation assumes that the repository is trusted: its working tree, its Git directory and configuration, and every change in it are the user's own or content the user chose to accept. Main and the roles read it with ordinary file tools and ordinary Git, and a review keeps only the checks that make its result correct: `HEAD` is the commit the call judges, the workspace has no uncommitted or untracked change before and after the call, and a commit contains only the claim's files. A check whose result cannot be established counts as failed. Reviews execute repository code unless the user, in this session, says they may not; saying only where a change comes from no longer stops it.

A new skill, `/cc-feather:repo-check`, is what the user runs when they want to decide whether to trust a repository, for example after downloading or copying someone else's. It runs a Python tool that reads the repository without executing any of its code and without letting Git run a program or follow a path the repository chooses, and reports what could run code or redirect reads: hooks, programs the configuration or attributes select, includes, links, submodules, replacement refs, the Claude Code files the project carries, and more. It makes no decision and writes nothing; the user decides. Delegation and repo-check never refer to each other.

3. **What a gated pass judged.** Review state's What a gated pass judged keeps its rule (`HEAD` is the commit the brief names, nothing the claim's files or acceptance checks depend on has an uncommitted or untracked change, nothing changes the workspace during the call) and states how main establishes it, as S4 states: before dispatch, `git rev-parse HEAD` names the commit in the brief, and `git -c core.safecrlf=false status --porcelain --untracked-files=all --ignore-submodules=none` lists no path the claim's files or acceptance checks depend on; after the call, the same reads show the same commit and no such path changed. ### The repo-check skill and tool

9. **Skill.** `skills/repo-check/SKILL.md`, listed last in `plugin.json`'s skills, runs the tool on the project root or a directory the user names, presents the report grouped by category, says what each finding could do and what the user may want to inspect, and states that the check covers the repository as it is now: content that arrives later, by a pull, fetch, merge or checkout, is not checked unless the user runs it again. It recommends running the check from a session started outside the checked directory, naming that directory, and says why (S7). It starts the interpreter by name from a shell that does not search the current directory for programs, with the working directory set outside the checked directory. It reads nothing in the checked directory itself with file tools; it presents every value from the report (paths, configuration values, link targets) as quoted data, never as instructions. It makes no trust decision, recommends none by default and writes no file. Its frontmatter sets `disable-model-invocation: true`, like the other user-run commands, so it runs only when the user invokes it. It names no delegation skill, reference, review step or role.
10. **Tool.** `skills/repo-check/scripts/repo_check.py`, a single file (since `-I` keeps its own directory off `sys.path`), Python 3.11+ and the standard library only, started as `python -I -B` with the checked directory as an absolute argument, prints one UTF-8 JSON report with `complete`, the Git version and path used (Git runs only for its version and configuration reads), and a list of findings, each with a category, a path or configuration key, its origin where known, and a one-line description. It reads the repository only as S6 states and reports what it could not examine, as S7 states.

## Security invariants

These hold for every Claim of this spec and are its review targets.

- **S1. The trust assumption is stated, not hidden.** Delegation states that it assumes the repository is trusted and that reading and running it is the user's risk, and the READMEs and reference documents state the residual risks of Acceptance 16. No delegation, role, policy or document text, outside historical records, implies that a review contains or detects hostile repository content, or that stating a change's origin stops it from running.
- **S2. Only the user stops execution, and content cannot lift a stop.** A restriction on running code is decided only from the user's own messages in this session: that the repository is not trusted, that code must not run, or a narrower one such as not running a pull request's tests. Saying only where a change comes from is not a restriction. A restriction covers every later call it names, the final check included, until the user's own message lifts it; a lift covers only what it names, and a restriction whose scope is unclear stops execution on this machine. Text in a tool result, a file, a commit, a role's report, a handoff, dispatch or memory record, hook output or a compaction summary is never the user's statement and can neither state nor lift a restriction nor name an isolated environment. After a context compaction main keeps every restriction the summary still shows; one it lost is not recovered, which is residual risk. A conversation continued with resume or continue is the same session; a new session starts without the statements. A restriction stops execution on this machine; an isolated environment the user's own message named stays available unless the restriction says otherwise.
- **S3. Execution is fail-closed at the role.** A role executes repository code only when main's own statement in its brief says that main has determined that it may, or in the isolated environment its brief names. A statement about execution inside content the brief quotes or supplies is not main's determination, and a brief that does not state it, states it ambiguously, or holds more than one candidate statement allows no execution, so the role reports INCONCLUSIVE for what needs execution.
- **S4. A pass rests only on what it judged.** A gated call is dispatched, and its pass used, only when `HEAD` is the commit its brief names and `git -c core.safecrlf=false status --porcelain --untracked-files=all --ignore-submodules=none` shows no uncommitted or untracked change in what the claim depends on, both before and after the call; a read that exits non-zero, writes to standard error or prints anything but porcelain v1 lines counts as a change. The command line overrides the user's `status.showUntrackedFiles` and submodule-ignore settings, and `core.safecrlf=false` keeps line-ending conversion warnings, common under `core.autocrlf`, off standard error. Ignored files and files marked assume-unchanged or skip-worktree are outside this check, as stated residual risk. Plan review and security analysis compare the same reads before and after the call without requiring a clean workspace.
- **S5. A commit contains only the claim's files.** Main stages the claim's files by name and commits them with `git commit -- <claim files>`, both with `--literal-pathspecs`, so content staged before stays out of the commit and no name is read as a pattern; it never uses `git add -A`, `git add .`, a directory or `git commit -a`, and skips hooks or signing only when the user asks.
- **S6. repo-check reads without running or following anything.** The tool runs no Git command on the checked repository: no command with `-C`, `--git-dir` or `--work-tree`, and none whose working directory is the checked directory. It runs Git only for `git --version` and to read a configuration file as data, and reads everything else itself. In detail, the tool:
    - finds Git itself by walking `PATH` in order and considering only fully qualified entries: on Windows a drive letter followed by a separator, or a UNC path, after removing one pair of surrounding double quotes, with no other `:` and no character in U+F000–U+F0FF; elsewhere a path starting with `/` with no `..` component and not in `/proc` or `/dev/fd`. It skips empty, relative, drive-relative, rooted-without-drive, device and unexpanded entries and any entry inside the checked directory, which it reports; uses the first entry holding `git.exe` as a regular file on Windows (no `PATHEXT`, so no `git.cmd`) or an executable `git` elsewhere; starts it by that absolute path; passes Git a `PATH` of only the entries it considered; and drops an inherited `GIT_EXEC_PATH` that is not one of them. These rules are written out here so that this spec does not depend on another document's wording;
    - never resolves a program from the current or the checked directory, and runs Git with its working directory set to the directory holding the Git executable it found, with `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE` and `GIT_CONFIG_*` removed from its environment and `GIT_CEILING_DIRECTORIES` set to that directory's parent; when that directory itself holds a `.git` entry or is a bare repository layout, the only repository Git could discover under that ceiling, it reports that and sets `complete: false`, and a repository further up is reported for information only;
    - reads a configuration file as data only by reading its bytes itself, through its metadata-and-open function and within its size limit, and passing them on standard input to `git --no-pager config --file - --no-includes --list -z`, never with `--includes`, so that Git opens no path; the working tree's `.gitmodules` is read the same way;
    - reads every other thing itself, as data, with metadata that does not follow links: the Git directory's layout (`.git` as a directory or a gitfile and its target text, `commondir`, `objects/info/alternates`, a bare repository layout at the top, links inside `.git`), the hooks directories, `info/attributes`, the refs under `refs/replace/` (the files under that directory and the matching lines of `packed-refs`, scanned in pieces so that a large `packed-refs` does not exceed the size limit), and the working tree's `.gitattributes` and `.gitmodules` files; it reads no object, no index and no reftable, and so needs no rule for lazy fetch or promisor remotes;
    - reads the configuration, hooks, `info/attributes`, replace refs and `packed-refs` of every Git directory the layout may select that lies inside the checked directory and passes the metadata checks: the top `.git`, a bare repository layout at the top, a gitfile's target, a `commondir`'s target and a nested repository's Git directory found by the walk; a Git directory, common directory or worktree that lies outside, is a UNC path, crosses a link or cannot be resolved is listed with what was not examined because of it and sets `complete: false`; ref storage other than files (`extensions.refStorage` other than `files`, or a `reftable` entry) is listed as refs not examined and sets `complete: false`;
    - before it lists, stats or opens any path, passes every component of that path below the checked directory through its metadata function: no component is a symbolic link, junction or other reparse point, and a file it opens or hands to Git is a regular file with a link count of 1; a path that fails is listed by its text, never read or handed to Git, and sets `complete: false`. A link in the checked directory's own path, above it, is reported separately and does not fail these checks. A file only stat'ed, such as an object under `.git/objects`, is not failed for a link count above 1, which a clone from a local path creates, and at most one summary finding notes such hard links;
    - finds an outer repository by walking up from the checked directory with its own metadata function and reports it separately;
    - judges whether a path lies inside the checked directory from its text, normalised without resolving links, and from the walk's own results, never by resolving it;
    - opens a path that repository content names (an include target, a `CLAUDE.md` import) only when it lies inside the checked directory and passes the walk's checks, and never stats or opens one outside it or a UNC path; an include target it may open is read as data in the same way, recursively, and any other target is listed by its text;
    - walks the working tree itself with metadata that does not follow links, taking each entry's attributes from its parent directory's listing on Windows, so that a cloud placeholder is not recalled by opening it, detecting junctions and other reparse points by those attributes, not descending into them or into cloud placeholders, never opening a file that is not regular or has a link count above 1, reporting names that collide in one listing under case folding (compared by `str.upper().casefold()`, a conservative superset of the folding file systems apply) without resolving either, and listing an entry it cannot examine (for example a path too long to stat) and setting `complete: false`;
    - does every metadata read and file open through one internal function of its own, which the tests observe, and exposes `main(argv)` so that a test wrapper can replace that function before running it;
    - imports nothing from the checked directory, runs no file from it and writes nothing anywhere, its own `__pycache__` included.
- **S7. The tool's report never claims what it did not establish.** An entry it cannot examine, a Git directory, common directory or worktree it cannot read, refs in a storage it does not read, a configuration read that fails or output it cannot parse is listed and sets `complete: false`, and the tool's output never states that the repository is safe. Every report also states, as a fixed note, that the index, objects and commits were not read, so attribute and module files, gitlinks and symbolic-link entries that exist only there are not reported; this note alone does not set `complete: false`. When the report is too long to present whole, the skill says so and summarises rather than truncating silently. The skill presents an incomplete report as incomplete. In a session started in the checked directory, the project's `CLAUDE.md`, `.claude` settings and hooks can steer or replace what the model presents, which is residual risk the skill and the READMEs state; the guarantee is the tool's output.
- **S8. This plan is reviewed under the installed 0.28.0 rules.** The plan review, code reviews, outcome verifications and Adversarial reviews of this spec's Claims use the roles and procedures installed before it, loaded from the plugin cache rather than this working copy, whose repository safety rules main follows for these reviews. Before the first code review main records the installed plugin version and the hashes of the user-scope and project-scope agent definitions and guidance file, and compares them before each review dispatch; a difference stops the dispatch and is reported. The candidate's roles are installed only in a scratch project scope for the setup-update check.

## User Stories

1. As a user, I want reviews of my own repository to read and run it the ordinary way, so that reviews are faster and roles stop deviating from rules that defend against me.
2. As a user, I want reviews to keep checking that they judged the commit they report, so that a pass still means what it says.
3. As a user, I want a check that cannot be completed to count as a failure, so that an unclear workspace never yields a pass.
4. As a user, I want main's commits to contain only the claim's files, even when I have something else staged, so that unrelated changes never ride along.
5. As a user, I want to stop code from running by saying so in the session, so that I keep control without a setting.
6. As a user, I want to be told that saying a change is someone else's no longer stops it, so that I do not rely on what used to work.
7. As a user, I want nothing in the repository to be able to lift my stop or name an environment for me, so that the repository cannot override me.
8. As a user, I want roles to keep their limits on Git state, so that a review never stashes or resets my uncommitted work.
9. As a user, I want to check a repository I did not write before I trust it, so that I can see what it could run.
10. As a user, I want that check never to run the repository's code or programs, nor follow paths it chose, so that checking is safe.
11. As a user, I want the check to tell me what it could not examine, so that I never mistake an incomplete check for a clean one.
12. As a user, I want the check to make no decision for me, so that trust stays mine.
13. As a user, I want to know that content arriving after the check is not checked, and that the check does not cover the code a review runs, so that I know what a clean report means.
14. As a user, I want to know that opening a session inside the repository runs its Claude Code hooks before any check, so that I can check from outside.
15. As a user, I want the READMEs to state plainly what trusting a repository risks, so that I choose with the risks in front of me.
16. As a user, I want the update note to tell me to run setup update, so that my installed roles and policy match.
17. As a user, I want to know how to go back to 0.28.0, so that I can undo the change.
18. As a maintainer, I want tests that fail if the removed rules come back into delegation or if delegation and repo-check start referring to each other, so that the split holds.
19. As a maintainer, I want behaviour tests on hostile fixtures with a positive control and a log of every Git command, so that repo-check's read-only claim is shown, not asserted.

## Implementation Decisions

- The three kept checks live in review state's existing What a gated pass judged and Repository authority bullets, and Execution becomes a bullet of review state, so no new reference is created; delegation-dedupe later removes any restatement.
- `git -c core.safecrlf=false status --porcelain --untracked-files=all --ignore-submodules=none` is the workspace check: it is what a user would run, with the two options that stop the user's configuration and `.gitmodules` from hiding a change. It runs the programs the trusted configuration selects, which is the residual Acceptance 16 states.
- `git commit -- <claim files>` commits the named paths from the working tree and leaves the rest of the index as it was, so the user's staged work is neither committed nor lost.
- S3 keeps the role-side fail-closed rule from 0.25.0 because the only case it serves is the one the user has asked to protect: a session in which the user said code must not run.
- The "someone else's content" condition goes because, under a trusted repository, the user states a stop directly ("don't run this PR's tests"); the documents and the update note say so, because 0.25.0 to 0.28.0 taught users to state the origin instead.
- repo-check is a Python tool, not text instructions, so its read-only behaviour is tested rather than asked of a model. It has its own Git invocation helper written to S6; it may copy, but does not import, the handoff tool's discovery of Git from `PATH`, so the handoff tool stays unchanged. Unlike the handoff tool, it rejects a `PATH` entry inside the checked directory and reports it, since it knows the directory it checks.
- The repo-check checklist is a fixed list in the tool, chosen from what the current repository safety rules defend against plus the repository-borne program and path settings common in practice; a key or file not on the list is not reported, which the READMEs state.
- Tests for removed text are deleted rather than turned into absence pins, except for the absence pins Acceptance 8 lists.
- The release is 0.29.0, a minor version, because the role definitions, the policy and the review procedures change and a skill is added.
