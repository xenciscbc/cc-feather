# Test speed-ups, second batch

Label: `ready-for-agent`

Vocabulary follows [CONTEXT.md](../../CONTEXT.md), which defines Plan, Claim, Unbounded probe and Runner. This spec applies the second batch of speed-ups from the `/cc-feather:test-speedup` report on cc-feather's own tests of 2026-11-25, recorded in `.feather/handoffs/test-speedup-batch-2.md`: the changes to shared fixtures and to how tests start the tools, which the user put after the low-risk first batch (`docs/specs/test-speedup-batch-1.md`, landed at 3617c47). The user decided on 2026-11-25 that the leases tests' in-process calls belong to this batch, and, when this spec was drafted, that the handoff tests' in-process calls cover all four modules the report named, the two upstream ones included. This spec changes only files under `tests/`, `docs/upstream-manifest.json` and `docs/compatibility.md`; it changes no shipped file, so it is landed without a version change or tag, as the first batch was, and the next release carries it.

## Problem Statement

After the first batch the whole suite still takes about 470 s and starts about 16,000 processes. Measurement on 2026-11-25 found that most of the rest is fixture building and tool start-up that the tests do not verify:

- `SharedBase.setUp` in `tests/test_handoff_shared_store.py` builds a fresh repository with two linked worktrees for every test, six Git commands, about 0.21 s per test, for about 237 tests across the handoff and leases modules.
- `StoreFixture.prepare` in `tests/test_handoff_unwritable_store.py` runs the handoff tool four times in a subprocess to build the same records for each of about 25 tests in that module and `tests/test_handoff_history_lock.py`.
- `tests/test_handoff_header_boundary.py` starts the handoff tool about 345 times in a subprocess, about 139 ms each, of which about 100 ms is Python start-up and import; the module takes about 46 s. `tests/test_handoff_local_fixes.py`, `tests/test_handoff_snapshots.py` and `tests/test_handoff_mutations.py` start it about 225 more times.
- The leases tests start the lease tool about 550 times in a subprocess, about 340 ms each (510 ms for a listing), of which about 117 ms is start-up; the leases modules take about 144 s.

## Solution

Four changes, one per ticket. The shared repository fixture is built once per test module and copied for each test; the prepared store is built once per module and written into each test's copy; the handoff tests of four modules and the single-call leases tests call each tool's entry point in the test process instead of starting a process. Every test keeps its assertions, its inputs and what it verifies; tests whose subject is the process boundary, concurrency between processes or the environment a process sees keep starting a process. After all four are accepted, main measures each change's modules before and after and records the gain.

## User Stories

1. As the maintainer, I want the shared repository fixture built once per module and copied per test, so that about 237 tests stop running six Git commands each.
2. As the maintainer, I want each copy to be a real repository with real linked worktrees at its own paths, so that the tests still exercise Git's worktree layout.
3. As the maintainer, I want a test that checks the copied fixture, so that a wrong copy fails loudly instead of letting a worktree point at the template.
4. As the maintainer, I want the prepared store built once per module, so that about 25 tests stop starting the tool four times to make the same records.
5. As the maintainer, I want the first preparation in each module to still run through the tool with its assertions, so that building the records stays verified.
6. As the maintainer, I want the header-boundary, local-fixes, snapshot and history-mutation tests to call the handoff tool in the test process, so that about 570 process starts become function calls.
7. As the maintainer, I want in-process calls to feed the same input bytes and read the same output and exit code, so that input decoding and the JSON contract are still exercised.
8. As the maintainer, I want the single-call leases tests to call the lease tool in the test process, so that about 550 process starts become function calls.
9. As the maintainer, I want the tests of races, concurrent readers, the environment and the launcher to keep starting processes, so that what only a process shows is still verified.
10. As the maintainer, I want the leases tests' new testing decision written down, so that later readers know why most of them no longer start a process.
11. As the maintainer, I want each change's gain measured and recorded, so that I know what the batch saved.
12. As the maintainer, I want no release for this batch, so that users are not asked to update for a change that does not affect them.

## Implementation Decisions

- **Repository template (ticket 01).** In `tests/test_handoff_shared_store.py`, `SharedBase` builds the repository `main` (one commit holding `a.txt`, `core.autocrlf=false`, branch `main`) and its linked worktrees `wt1` and `wt2` once per test module, on the first `setUp` of that module that needs it, in a template directory of its own under `FEATHER_LINK_TEST_DIR` when set and otherwise the system temporary directory, removed by that module's cleanup. It is not built in `setUpModule`, so a skip while building it skips only the tests that use it. Each test's `setUp` keeps building its own base directory, `outside`, `home`, the empty Git configuration and the isolated environment as today, then copies `main`, `wt1` and `wt2` from the template into it and rewrites the four files that hold absolute worktree paths (`wt1/.git` and `wt2/.git`, and `main/.git/worktrees/wt1/gitdir` and `main/.git/worktrees/wt2/gitdir`) to the copy's paths, in the form Git itself writes them (on Windows with `/` separators), without running `git worktree repair`. A template whose building failed part way is never reused. The fixture's commit is built with the same fixed `COMMIT_ENV`, so its commit id is the same as today. `self.main`, `self.wt1`, `self.wt2` and `self.store` keep their meaning. A test that needs another repository keeps building it with `repository()` as today. The template is never written by a test.
- **Template check (ticket 01).** A new test in `tests/test_handoff_shared_store.py` checks, on a copy, that `git worktree list --porcelain` run in the copy's `main` lists exactly `main`, `wt1` and `wt2` at the copy's own paths with their branches, that `git rev-parse --show-toplevel` in each linked worktree names that worktree, that `git rev-parse --absolute-git-dir` in each linked worktree names the copy's own `main/.git/worktrees/<name>`, compared as the same directory, and that no file of the copy names the template's base directory in its native form or with `/` separators, compared without case on Windows.
- **Prepared store (ticket 02).** In `tests/test_handoff_unwritable_store.py`, the first `StoreFixture.prepare` of a test module for a given Working checkout runs through the tool as today, with its `deferred` and `archived` assertions, and records every file and directory it created or changed below the test's base directory, empty directories such as `archive/` included, with each file's bytes and its path relative to the base, and the result it returned. A later `prepare` of the same module and Working checkout creates those directories and writes those files into its own copy, checks before writing that none of their bytes names the first base directory, and returns the recorded result. `CheckoutLocalStoreTest`, whose Working checkout is `main`, gets its own recording. Depends on ticket 01's copies, which make the paths below each base the same.
- **Handoff calls in-process (ticket 03).** A new support module, `tests/handoff_in_process.py`, which holds no tests, calls the handoff tool's `feather_handoff.cli.main()` in the test process: `sys.argv` is the same argument list a subprocess gets, its first item the tool's path as the subprocess helper passes it, standard input is a text stream whose `buffer` holds the same bytes the subprocess would get, so `input_payload` still decodes and checks them, standard output is captured as UTF-8 bytes and decoded as the subprocess helper decodes it, the exit code `main()` returns is compared with `expected` as today, and `storage.reset_roots()` runs before and after each call. It offers the same signature and result as each module's subprocess helper: as `LocalFixesBase.run_tool` (`raw` as given, otherwise the payload's UTF-8 JSON, `null` when there is none) for `tests/test_handoff_header_boundary.py` and `tests/test_handoff_local_fixes.py`, and as `HandoffToolTest.run_tool` (the payload's JSON, or empty input when there is none) for `tests/test_handoff_snapshots.py` and `tests/test_handoff_mutations.py`. These four modules use it for every tool call except the tests whose subject is the process boundary or a second handle on a file, which keep starting the tool: `CliContractTest` and `CliUsageTest` in `tests/test_handoff_local_fixes.py`, and `test_failed_clear_and_seal_retain_sources_then_retry_exact_selection` in `tests/test_handoff_mutations.py`. `LocalFixesBase.run_tool` and `HandoffToolTest.run_tool` themselves keep starting the tool, so `tests/test_handoff_tracking_probe.py`, `tests/test_handoff_tool.py` and every other module that uses them is unchanged. This ticket replaces only the calls that go through `run_tool` or `archive` today, and none of the calls it replaces is made while the test patches anything the tool uses; calls that already run in the test process, such as `invoke()`, stay as they are. Because `tests/test_handoff_snapshots.py` and `tests/test_handoff_mutations.py` are upstream test modules, their hashes in `docs/upstream-manifest.json` are refreshed and their adaptation notes say that they call the tool in-process: `tests/test_handoff_snapshots.py`'s existing note gains it, and `tests/test_handoff_mutations.py`, identical to upstream until now, gains a new adaptation entry whose `source_sha256` is its current hash, and `docs/compatibility.md` gains a note beside the other upstream notes, before the Checkout leases section.
- **Leases calls in-process (ticket 04).** In `tests/test_leases_tool.py`, `LeaseBase.lease` calls `feather_leases.cli.main()` in the test process when it is given no `env`, with the same argument list, its first item the tool's path as a subprocess gets it, standard output captured and decoded as today, the returned exit code compared with `expected` as today, and `storage.reset_roots()` before and after each call; with an `env` it starts the tool as today. A test whose subject is the launcher or a separate process keeps starting the tool: the race of two acquires and the concurrent-reader cases, which already use `Popen`; the cases that replace `PATH` through `env`; and `PackagingTest.test_a_usage_error_is_json`, through a parameter of `lease` that asks for a process. The lease tool's internal start of the handoff tool for a listing is unchanged.
- **Leases testing decision (ticket 04).** The leases test modules' docstrings (`test_leases_tool`, `test_leases_locks`, `test_leases_park`, `test_leases_listing`, `test_leases_takeover`) say that the lease tool runs in the test process through its entry point for single calls, with only its JSON result and exit code asserted and no internal state, and as a subprocess for races, concurrent readers, the environment it sees and the launcher. `docs/specs/checkout-leases.md` is history and is not changed.
- **Measurement.** After the last ticket is accepted and before the Plan is landed, main measures each ticket's modules and the whole suite at the Plan base and at the final commit in the same session, with the same method as the first batch: per-test timing of `python -B -m unittest discover -s tests -t .` inside the Runner, with `FEATHER_LINK_TEST_DIR` under `J:\gotmp\` and the two busy-spin tests (`test_leases_tool.CriticalSectionTest.test_a_concurrent_reader_delays_a_release_but_leaves_nothing_behind`, `test_leases_takeover.RenewTest.test_a_concurrent_reader_delays_a_renew_but_does_not_fail_it`) left out. Scratch copies of the Plan base live under `J:\gotmp\` and are removed afterwards. Main reports each ticket's seconds before and after, and the whole suite's.
- **Validation record.** Main records the review round and the measurement under a heading of its own in `docs/setup-validation.md`, `## Test speed-ups, second batch (on main after 0.45.0)`, after the Plan's review round, as for the first batch.
- **Not affected.** Every shipped file: skills, templates, scripts, the plugin manifest, both READMEs, the reference documents and CONTEXT.md. `tests/feather_support.py`, `tests/test_handoff_tool.py`, the other upstream test modules and every test module not named above.

## Testing Decisions

- These are changes to tests, so the evidence is that the same tests pass with the same assertions: each ticket's diff changes no assertion and no input a test verifies, and its modules pass.
- A test id list taken with `unittest`'s discovery before and after each ticket is equal, except that ticket 01 adds the template check.
- `tests/test_feather_releases.py`'s upstream manifest tests keep passing after ticket 03's refreshed hashes and notes.
- Ticket 01 changes shared test support used across the handoff and leases modules, so its acceptance is the full suite; ticket 02 changes a fixture three modules use; tickets 03 and 04 name the modules that use or import what they change.
- In-process calls are judged by their observable contract only: the same input bytes, the JSON output and the exit code, never internal state.
- The Plan's overall acceptance is the full suite, `python -B -m unittest discover -s tests -t .` with `FEATHER_LINK_TEST_DIR` under `J:\gotmp\`. It is the Plan's overall acceptance, which the final check runs for each commit to be landed, not for each Claim, and it is not part of any Claim's acceptance; each ticket cites it.

## Out of Scope

- In-process calls in `tests/test_handoff_tool.py`, `tests/test_handoff_tracking_probe.py` and the upstream test modules not named above.
- Process-level parallel runs.
- A time limit for the whole run (`.feather/handoffs/test-run-time-limit.md`).
- Speeding up shipped code, such as the configuration tool's `_safe_path` checks.
- Any change to what a test verifies, its inputs or its sizes.
