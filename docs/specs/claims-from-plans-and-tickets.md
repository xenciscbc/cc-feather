# Claims come from the named Plan and its tickets, and a preview binds only its session

Label: `ready-for-agent`

Vocabulary follows [CONTEXT.md](../../CONTEXT.md). The decision is recorded in ADR 0005, written as part of this work.

## Problem Statement

A Claim is "listed in a Plan", but cc-feather never says where a Plan's Claims come from when the Plan is a spec that was split into tickets. The common pair of planning skills in use writes a spec without a Claim list and tickets that are, by construction, independently verifiable slices with their own acceptance criteria and `Blocked by` dependencies; each ticket is sized to be picked up alone in a fresh context. cc-feather's procedures leave it to main to tell reviewers which Claims exist, while the Delegation preview expands only what the Plan's own text lists. So the session that implements the work treats the tickets as Claims, while a preview of the spec treats the spec as one Claim; a session asked to implement a single ticket has no rule for whether its Plan is the ticket or the whole spec. Review counts per Claim, cost estimates and handoff notes that name Claims then disagree. Where specs and tickets live, and whether tickets are committed, is set by the project and the planning skills, not by cc-feather.

A second gap: two sessions previewing the same Plan routed some work differently, both within the rules, but the preview procedure and the glossary call a preview main's dispatch basis without saying whose dispatch.

## Solution

The Plan is what the user names. "Implement this spec", or a set of its tickets, makes the spec with those tickets the Plan: each ticket in scope is one Claim, its `Blocked by` lines are the dependencies, and plan review covers the spec with those tickets once. "Implement ticket 02" makes that ticket the Plan, with its spec supplied as context, unless a Plan in this session already covers that ticket: then the existing Plan continues, with no new plan review and its count, verdicts and blockers kept. A ticket that belongs to no spec is its own Plan, and a spec without tickets keeps its listed Claims or is one Claim. main recognises a spec's tickets by an explicit link, a shared feature directory or the user naming them, asks when that is ambiguous, and states which tickets it used. If a spec lists Claims and also has tickets, they must agree; a mismatch is a plan-review finding for the user to settle. main never edits a spec or ticket to add Claims. The Delegation preview applies the same rules, flags a Plan that refers to tickets or Claims it cannot find, and is the dispatch basis only in the session that made it.

Both READMEs explain this, and the Traditional Chinese README renders protocol failure as 「回覆不合格式」.

## User Stories

1. As a user who says "implement this spec", I want the spec with its tickets to be one Plan reviewed once, so that splitting into tickets does not multiply plan reviews.
2. As a user who says "implement ticket 02", I want that ticket to be the Plan with its spec as context, so that a fresh session reviews only what it will build.
3. As a user who names a ticket in a session that already has a Plan covering it, I want that Plan to continue with its count, verdicts and blockers, so that naming a ticket neither repeats a review nor escapes a stopped one.
4. As a user, I want each ticket in scope to be one Claim and its `Blocked by` lines to be the dependencies, so that the planning skill's output is used as written.
5. As a user, I want a ticket that belongs to no spec to be its own Plan, and a spec without tickets to keep its listed Claims or be one Claim, so that simple plans keep working.
6. As a user, I want main to recognise a spec's tickets by an explicit link, a shared feature directory or my naming them, to ask when unsure, and to tell me which tickets it used, so that I can see and correct its choice.
7. As a user, I want a spec's own Claim list and its tickets to agree, and a mismatch raised in plan review for me to settle, so that no copy wins silently.
8. As a user, I want main never to edit my spec or tickets to add Claims, so that the documents I agreed to change only with my consent.
9. As a user, I want cc-feather not to require where specs live or whether tickets are committed, so that my project and planning skills keep their conventions.
10. As a user, I want the Delegation preview to apply the same rules and flag a Plan that refers to tickets or Claims it cannot find, so that I see the gap before implementation.
11. As a user, I want a preview to guide dispatch only in the session that made it, and the glossary to say so, so that a preview from another session is taken as a reference.
12. As a user, I want how finely Claims are cut to stay with the planning step, so that this change does not reopen ADR 0003.
13. As a user of a ticket workflow, I want the glossary to note that a ticket being "claimed" is unrelated to a cc-feather Claim, so that the two words are not confused.
14. As a user reading either README, I want these rules explained with an example, so that I know what a review will treat as the Plan.
15. As a user reading the Traditional Chinese README, I want protocol failure rendered as 「回覆不合格式」, so that it is not mistaken for a network protocol error.
16. As a maintainer, I want the decision and its rejected options in an ADR, so that later readers know why the named document is the Plan.
17. As a user with an existing installation, I want the change from the plugin update alone, so that I do not need to rerun setup update.

## Implementation Decisions

- **The Plan is what the user names.** A spec or a set of its tickets: the spec with those tickets. A single ticket: that ticket, with its spec supplied as context to plan review and to code review and verification. A ticket that belongs to no spec: its own Plan. This applies the existing rule that telling main to implement a given plan or ticket is agreement. It applies only when no Plan in this session already covers the named work; otherwise that Plan continues with no new plan review, and its count, verdicts and blockers are kept, consistent with the session rules that renamed plans and cosmetic splits never reset a count (ADR 0002, ADR 0004). When the named work only partly overlaps a Plan in this session, the new Plan inherits that Plan's unresolved verdicts and blockers for the overlapping tickets. In a resumed session, an unresolved verdict that an active handoff records for a spec's Plan applies to that spec's tickets when they are named.
- **Claims.** For a spec with tickets in scope, each unfinished ticket in the named scope is one Claim and its `Blocked by` lines are the dependencies. When a single ticket is the Plan, its spec is supplied as context to plan review, code review and outcome verification. For a ticket as the Plan, the Claims it lists, otherwise one. For a spec without tickets, the Claims it lists, otherwise one. A plan-mode or conversation plan's Claims are those in its text; that they are not visible to another session is an accepted limit.
- **Recognising a spec's tickets.** An explicit link in the ticket (such as a `Spec:` line or a parent reference), a shared feature directory with the spec, or the user naming them. When none or several Plans match, main asks. main states the tickets it used in the plan review brief and in the preview.
- **Agreement and ownership.** A spec that lists Claims and also has tickets must agree with them, comparing the spec's whole Claim list with all its tickets (finished or not; a ticket's status line tells which are unfinished); a mismatch is a plan-review finding the user settles. main does not edit a spec or ticket to add Claims.
- **Unchanged.** Claim sizing stays with the planning step (ADR 0003). Counts stay per session (ADR 0002); a fresh session implementing one ticket reviews that ticket's Plan. `skills/delegation/SKILL.md` stays free of preview wording (an existing test asserts it). Installed role definitions, the installed policy, the handoff skill and the configuration tool are unchanged, so existing installations need only the plugin update and a fresh session. cc-feather sets no rule on where specs live or whether tickets are committed.
- **Preview.** It applies the same rules, lists the tickets it used, flags a Plan whose text refers to tickets or Claims of its own that it cannot find (narrowly: references to this Plan's parts, not general mentions of tickets), and says a preview is the dispatch basis only in the session that made it; a preview from another session is a reference and dispatch there may differ without being reported as a difference. The glossary's Delegation preview entry says the same.
- **Glossary.** The Claim entry's `_Avoid_: ticket` becomes a note that a ticket is one place a Claim may be written, not a synonym.
- **ADR 0005** records the decision and the existing-Plan rule's relation to ADR 0002 and ADR 0004. Rejected: requiring every spec to carry a Claims table or having main write one in (duplicates the tickets and edits documents the user agreed to); treating the spec as the Plan even when a single ticket is named (a fresh session per ticket, as the ticket workflow intends, would re-review the whole spec each time because counts and passing verdicts do not cross sessions); treating every ticket as its own Plan even when the whole spec is named (multiplies plan reviews); requiring tickets to be committed or specs to live in a set place (cc-feather does not control project conventions).
- **README.** Also notes that a spec without tickets or its own acceptance (such as a planning skill's spec template, which has no acceptance section) is not yet a Plan.
- **Release** as 0.13.0 under the project rules; once the tag exists it is never moved or reused, and a correction ships as 0.13.1.

## Testing Decisions

- The seam is the existing configuration test module that checks skill text (prior art: the consecutive-failure, explicit-verdict and preview tests).
- New contract tests assert, by key phrase: the named-Plan rule and the ticket-as-Claim rule in plan review; the statement that main does not edit a spec or ticket to add Claims; "as identified for the plan" (or the chosen equivalent) in code review and outcome verification; the preview's new flag and same-session statement. Each fails on the 0.12.1 text. A kept-fallback assertion checks the one-Claim fallback in plan review ("lists none is one claim") and preview ("lists none is one Claim"), each in its own wording, and fails if that sentence is removed. A test asserts the existing-Plan rule.
- READMEs are checked at acceptance by an independent verifier against the procedures.
- Release checks: the full `unittest discover` suite and `claude plugin validate` for the plugin root and the manifest.
- Live model compliance with the new rules is not tested and is recorded as untested.

## Out of Scope

- Changing analyst's installed definition or adding a hard Claim-list requirement.
- Rules on where specs live, whether tickets are committed, or how planning skills write them.
- Recording Claim lists or plan-review verdicts across sessions (handoff changes).
- Changing Claim sizing, the review budget, or the stop rules.
- Rewriting earlier specs.

## Further Notes

- The background analysis is kept outside the shipped files in this machine's scratch directory for the 0.12.1 work; this spec departs from its recommendation by reading tickets as Claims, because the planning skills in use produce them that way and the implementing session has them.
- This spec lists its Claims in a table and also has tracking tickets; under its own rule they must agree, and they do.
