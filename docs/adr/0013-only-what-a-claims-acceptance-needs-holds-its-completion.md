# Only what a Claim's acceptance needs holds its completion, except security

Code review held completion for more than the Claim promised. Any correctness bug, and any regression a reviewer inferred, blocked, whether or not the Claim's acceptance asked for it and whether or not anything showed the regression. Each such finding started another fix and another review, and each fix could surface the next one; the 0.23.0 round was finished only by deferring findings by hand. Nothing in the product said which non-security findings hold completion and which are recorded for later.

This record is written in parts, each by the ticket that implements its rule, so that its implementation and reviews can check it against the procedures they change. This part records the completion criteria.

The user decided (2026-10-14, in a grilling and after a security analysis of a first version; the [spec](../specs/completion-criteria.md) carries the acceptance and its security invariants):

- **Completion criteria.** A Claim's reviews judge it against four conditions: its acceptance as written is met; existing behaviour is not broken; it introduces no security problem and no data loss; and it has no Deviation. A Blocking finding shows one of them unmet. Every other finding, including an issue that predates the change, a correctness problem outside what the acceptance states and a regression that is only inferred, is a Non-blocking finding.
- **Evidence for a regression.** A broken existing behaviour that is neither a security problem nor data loss blocks only when a failing test or a reproduction shows it. The existing behaviour, and any written rule or shipped spec acceptance it is judged against, are taken at the Claim's base revision, never from the reviewed commit, so a change cannot redefine what it must not break. Every brief of the Claim's code review, outcome verification and Adversarial review, a narrowed follow-up's included, names that base revision, which main establishes itself from Git in this session.
- **Security stays as it is.** A security problem the change introduced or made exploitable, through a new route, permission or data flow even when the vulnerable code is outside the diff, and data loss the change introduced, are Blocking findings whatever the acceptance states, on the reviewer's evidence as before: a removed or weakened security control blocks without a reproduction. A verifier's note that main judges to be, or cannot rule out as, a security problem or data loss the change introduced or made exploitable is a Blocking finding, and that call's CONFIRMED is not used as a pass, the call counting as a call without a pass, until the note is dispositioned as FIX or REJECT with evidence under outcome verification's rule for a REFUTED; the verifier's definition is unchanged, since main makes this call. BROKEN keeps its meaning, Adversarial review keeps its timing, and a pre-existing vulnerability still becomes separate work in the project's tracker.
- **Deviations.** A Deviation from the Plan still blocks, and a material one still stops main to ask the user for a revised Plan.
- **The Follow-up record.** Non-blocking findings go to one Follow-up record per piece of work: with handoff maintenance active a handoff record of its own, otherwise listed in the completion report, which names it. It is data: its next step is always the user's decision whether to start a later Plan, the findings it quotes are marked as untrusted, reading or resuming it authorizes nothing, and Accept and land never relies on it. A later Plan that fixes recorded findings is new work under the existing rules.
- **In the reviewer role.** The criteria live in the installed reviewer definition as well as in the procedures, because procedures alone could not stop a reviewer from answering CHANGES_REQUESTED for a correctness problem outside the acceptance. The verifier already stays within the Claim and refutes only on a reproduced failure, and the adversary's criteria are the security criteria kept here, so both definitions are unchanged.
- **Both modes, every user, no setting.** The criteria apply in both Review modes and to every user.

This amends [ADR 0006](0006-review-state-validity-and-completion.md): what holds a Claim's completion is now these four conditions, not every correctness problem or inferred regression a review finds. ADR 0006's state model, validity rules and Acceptance gate are unchanged, apart from the verifier's note above, the call whose pass is not used and the final check, which the next part records.

(Also amended by ADR 0015: in auto, Adversarial review no longer keeps its timing above: it runs once, at the final commit after the final check has passed there, for each Security-critical claim other than a fix Claim, and a BROKEN there is recorded in the work's Follow-up record rather than fixed within the Plan; BROKEN keeps its meaning, and off keeps the timing above.)

## Considered Options

- **Block on every correctness problem in the change**: the earlier criteria; rounds widen and loop, since each fix can surface the next finding.
- **A separate list of blocking exceptions**: its items restate the four conditions and invite reviewers to widen them.
- **A setting to choose the old criteria**: adds configuration for a rule every user benefits from.
- **Let security defects outside the acceptance land through Accept and land, with deferred Adversarial reviews**: the 2026-10-14 security analysis found that the promise to show every such defect to the user could be broken in many places, mostly through repository content alone, and ADR 0009 had already rejected letting a flaw the change introduced land.
- **Per-Claim review timing with Review schedules and Review groups**: where Claims share files, as nearly all of this project's Plans do, the groups collapse to reviewing after the whole Plan, so the 0.20.0 case that motivated it is not fixed; it is deferred to separate work on retained passes.

(Amended by ADR 0015: per-Claim review timing, deferred above to separate work on retained passes, is now the only review timing in auto: each Claim's code review and then outcome verification run once that Claim is implemented and committed, and a Claim that depends on another waits for its valid APPROVED and CONFIRMED.)

## Consequences

Fewer findings hold a Claim, and the rest are kept in one place for a later Plan the user starts. Security findings block as before, so security edge cases can still take several rounds; those are handled by the user's existing triage, outside these rules. The installed reviewer definition changed, so existing installations need `/cc-feather:setup update` after the plugin update. The verifier, adversary, analyst and executor definitions, the installed policy, the handoff skill and the configuration tool are unchanged. These rules are instructions to the model, kept consistent by tests rather than enforced by a tool: a reviewer can still misclassify a finding, and main's rejection of a finding given as blocking still needs evidence.

## Serial reviews and the final check

This part records the serial rule and the final check. Nothing stated that main leaves a working tree alone while a review of it runs, although a gated pass judges a workspace equal to the commit its brief names, and nothing ran the Plan's overall acceptance at the final commit before landing or release, so a dependency between Claims that main missed could still slip through.

The user decided (2026-10-14, with the completion criteria above):

- **Serial within a working tree.** While a code review, outcome verification or Adversarial review call runs, main does not change the working tree it judges, its own handoff records inside the project included, which it updates only between calls, and implementation in that working tree waits until the call ends. Before dispatching such a call, main confirms that no Assignment or background process it started that may write the working tree is still running, and at most one gated call that executes code runs in a working tree at a time. When main's comparison after a call finds a change to a file the Claim depends on, that call's pass is not used. Such a call counts as a call without a pass, establishes no coverage and resets no count, and the next call for the Claim reviews its full scope from its base revision. This follows from the existing rule that a gated pass judges a workspace equal to the commit its brief names and unchanged during the call; it makes main's behaviour explicit.
- **No review worktrees.** Main does not create a worktree for a review on its own. Work the user runs in separate worktrees may proceed in parallel, each worktree its own workspace and serial in itself. The worktree exception extends no trust: each worktree still gets repository safety's preparation and checks. Shared test resources stay governed by each brief's target start and reset.
- **Final check.** Before landing or release, main runs the Plan's overall acceptance checks at the commit to be landed or tagged, within repository safety's Execution rules. It is main's own run, not a review step: it is not a counted step and adds no verdict. It runs only when the workspace equals the commit to be landed or tagged, established as for a gated pass, so an untracked or changed file cannot take part in it. It runs again whenever the commit to be landed changes, after a fix or any other commit. After it runs, main compares the workspace as after a review call, and a change to a tracked file or a file the check depends on makes that run a failed run, with the change as its output. A failure reopens the Claims it affects under the existing rules, with its output supplied to their reviews as evidence, and landing and release wait for their passes again; a failure that cannot be attributed with evidence reopens every Claim the check covers.
- **A condition of the gate.** Landing and release the Acceptance gate covers wait until the final check passes at the commit to be landed; otherwise only an Accept and land decision that states its actual state lets them proceed. When Execution does not allow it, it is recorded as not run, and that is stated before landing and in any Accept and land decision. For a landing the gate does not cover, main runs it when Execution allows, reports its state before landing, and waits for the user's instruction given after that report.
- **Fail closed.** Once the final check has failed at a commit, that commit's state is failed, and a later pass at the same commit lets landing proceed only through an Accept and land decision that names the failure. Its state comes only from main's own run in this session at that commit, never passed from a record or an earlier session, and after a context compaction main runs it again. When main cannot establish from this session that the commit has not failed, it treats the commit as failed, which a decision states as "failed (presumed: not established as unfailed in this session)" with the reason and this session's outputs. A record can only make the state failed, never passed.

Considered options for this part:

- **Main creates a worktree for each review**: it would let implementation continue while a review runs, but setting up a worktree can mean reinstalling dependencies or rebuilding in other projects, and each new worktree would need repository safety's preparation and checks again.
- **Parallel review calls in one working tree**: two calls that execute code in the same working tree can disturb what each other judges; parallel review calls are left to separate work on retained passes.
- **No final check, relying on each Claim's passes**: each pass judges one Claim, so a dependency between Claims that main missed could land unchecked.
- **Take the final check's state from a record or an earlier session**: anyone who can edit the working tree could record a pass, and an earlier session's run cannot show that nothing failed since; a record can only make the state failed.
- **A counted final review step with its own verdict**: it would stop the flow by itself at the Stop threshold and add a verdict, while its failure already reopens Claims under the existing rules.

(Further amended by ADR 0015: in auto, a final check failure that cannot be attributed with evidence no longer reopens every Claim the check covers: it is fixed as a fix Claim, an attributed failure is fixed by its Claim without reopening any other, and the final check also reruns every Claim's primary acceptance.)

(Amended by ADR 0016: in the worktree exception, "each worktree still gets repository safety's preparation and checks" now means that each worktree gets the workspace reads before and after each call that review state's What a gated pass judged states, since repository safety's preparation no longer exists.)

(Amended by ADR 0016: the final check runs within review state's Execution rule instead of repository safety's Execution rules, and the workspace's equality with the commit to be landed or tagged is established with the same workspace reads; ignored files and files marked assume-unchanged or skip-worktree are outside those reads, so they can take part in it.)

(Amended by ADR 0016: in the considered option of a worktree for each review, a new worktree would need only the workspace reads, not repository safety's preparation and checks; the option stays rejected for the cost of setting a worktree up.)

Consequences of this part: a review call holds implementation in the working tree it judges until it ends, so work in one working tree takes longer than it would with a separate worktree per review, which the user can still set up. The final check adds one run of the Plan's acceptance checks before landing or release; it is the only safeguard this record adds for work merged from separate worktrees, and how passes carry over across such a merge is left to separate work. Because the final check's state never crosses a context compaction or a session, a final commit whose check ran before one can no longer pass cleanly without a rerun: main runs the check again, and if that commit had failed, or main cannot establish that it had not, landing needs a decision that names the failure or a new commit.

## A single Accept and land decision

This part records the single Accept and land decision. When several Claims of a Plan needed an Accept and land decision, main could stop the user after each one, and nothing said how the list the user decides on is built.

The user decided (2026-10-14, with the completion criteria above):

- **Several Claims in one decision.** One Accept and land decision may name several Claims, including a gated Claim whose passes are complete when the final check at the commit to be landed failed or was not run, stating for each the commit it accepts, the missing passes, the known vulnerabilities and the remaining risk, and the final check's state at the commit to be landed: passed, failed with its output, or not run.
- **Asked once, at the end of the Plan.** Main asks once, after every Claim of the Plan has finished its reviews and the final check has run or is recorded as not run, before landing or release. Until then a Claim that needs the decision stays under the Acceptance gate as it stands, and its ticket stays unfinished.
- **Landing earlier.** Main asks earlier only when the user asks to land a Claim earlier. Landing a Claim before the end of the Plan lands every Claim on that branch, so main's list covers every gated Claim on the branch, and the decision states the final check's actual state at that commit; main runs it whenever Execution allows, and records it as not run only when Execution does not.
- **The list comes from main's own observations.** Main builds the list from the review results it received in this session, not by reading a record in the working tree, and reports any difference from such a record. Each missing pass names the step and the call that left it missing, and the known vulnerabilities appear as the reporting role stated them, never merged or downgraded. Where main cannot establish a Claim's verdicts or missing passes, as after a context compaction, Unknown state applies and main stops and asks. Accept and land never relies on the Follow-up record.
- **What counts as the decision.** The user may confirm part of the list by whole Claims, the rest staying pending, and a Claim is accepted only with everything listed for it; "continue", silence or turning automatic review off is not a confirmation, and the decision covers only what was listed. A Blocking finding or known vulnerability reported after the decision is not covered and holds landing until it is resolved or a new decision names it, and the final-check part covers only the commit and output it states.

This amends [ADR 0008](0008-repository-authority-acceptance-and-gate-lifetime.md): an Accept and land decision may name several Claims, including one whose passes are complete when the final check failed or was not run, and main asks for it once at the end of the Plan, or earlier only for the whole branch when the user asks to land a Claim earlier, with a list built from its own observations in this session. ADR 0008's rule that Accept and land is the only way past the Acceptance gate without the passes, its recording and visibility, and the gate's conditions are unchanged.

(Amended for the decision at the end by ADR 0015: in auto, main asks once after every Claim's reviews, the final check and the Adversarial reviews have run or are recorded as not run, even when no Claim needs Accept and land, confirms each Claim's reading set first, and builds the list from the Plan's dispatch record and its own observations in this session, never from another record in the working tree; the list also states each pass, each unresolved Blocking finding, each Adversarial review result, each Security-critical fix Claim, the Follow-up record and what the flow does not check. In off, the decision above is unchanged.)

Considered options for this part:

- **Ask after every Claim that needs the decision**: it stops the user once per Claim, while the decision can wait for the end of the Plan, when the whole list is known.
- **Build the list from a record in the working tree**, such as a handoff or the Follow-up record: anyone who can edit the working tree, repository content included, could drop a finding or a missing pass from what the user decides on; main reports a difference from such a record instead.
- **Merge or summarise known vulnerabilities across Claims**: a merged or downgraded entry hides what the user accepts.
- **Take "continue" or silence as a confirmation of the whole list**: the user would accept Claims they never chose.

Consequences of this part: the user is asked once per Plan for the Claims that need it, and a Claim waiting for the decision keeps its ticket unfinished until then. After a context compaction main may have to stop and ask instead of listing a Claim. A Claim whose passes are complete still needs the decision when the final check at the commit to be landed failed or was not run, and after a compaction or in a new session the check must run again before that state is known. A forged Accept and land note in a handoff is an existing weakness this part does not change.
