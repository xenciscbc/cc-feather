# Checkout leases are cooperative records mirrored by Git worktree locks

Several sessions often work in one repository, each in its own worktree, and worktrees are kept and reused; nothing told a session which checkout another session was still using. The user decided (2026-11-09, after a two-round discussion with Codex and a grilling session; the [spec](../specs/checkout-leases.md) carries the acceptance):

- **A lease record is the authority.** One Checkout lease per checkout, keyed by Git's per-worktree identity, kept in a dedicated leases directory under the main worktree's `.feather/`, independent of the Handoff store selection. It holds a per-acquisition lease_id, the session label, host, runtime, purpose, start time and last reported activity. It is taken with an exclusive create and changed only by its own lease_id or, on a takeover the user decides, by the version the user was shown.
- **A Git worktree lock protects it.** A held lease on a linked worktree also locks that worktree with a reason naming the lease. Claude Code locks every worktree it creates for a session, so in a worktree the session itself just created, the Claude Code session lock whose reason the session observed at creation is accepted in place of the lease's own lock. Any other lock, including one found on a worktree the session only entered or reused, blocks acquisition. A held lease found with no lock at all is locked again by the next listing or acquire. cc-feather removes or moves only a lock that names one of its leases.
- **No liveness proof and no automatic takeover.** Start time and last reported activity are shown to the user, who decides a takeover; no time threshold reclaims a lease.

## Considered Options

- **Git worktree lock alone.** It has one free-text reason, cannot lock the main worktree, and Claude Code already uses it for every worktree it creates for a session and for running subagents, leaving session locks behind after `-p` runs (observed 2026-11-09 with Claude Code 2.1.319). Carrying the holder, purpose, start time, last activity and a compare-by-lease_id rule in the reason text would make every other tool's lock look like ours or ours like theirs.
- **Treating every existing lock as blocking.** The first lock rule refused any worktree already locked by someone else; since Claude Code locks the worktree it creates for a session, a session could then never take a lease in a worktree it had just created. Accepting a session lock merely because the session entered the worktree was rejected too: entering by path keeps another session's lock unchanged.
- **Lease record alone, Git locks only shown.** It was the first choice. It leaves a worktree in use exposed to `git worktree prune`, a plain `git worktree remove` and Claude Code's periodic cleanup, which skip locked worktrees, and it is invisible to tools that do not read leases.
- **Liveness by process or heartbeat.** The tool runs as a short-lived subprocess, so no recorded process proves the session alive, and a heartbeat still cannot prove a session stopped; both were dropped in favour of showing time and letting the user decide.
- **The lease inside the Handoff store, or tied to a handoff record.** A tracked checkout and an explicit root select their own store, which would split the state, and many sessions change a checkout without a handoff record.

## Consequences

The lease is cooperative: it neither stops a session that ignores it nor stops the old session on a takeover. The main worktree has only the lease. A crashed holder leaves the lease and a lock: its own, or Claude Code's session lock, which Claude Code may later release, after which the next listing or acquire locks the worktree again with the lease's own lock; until then the worktree is unprotected for that window. A locked worktree refuses `git worktree remove` without force and `ExitWorktree` removal, so a worktree in use is removed only after its lease is returned and its lock released by whoever set it. The design relies on Claude Code's cleanup skipping locked worktrees and never releasing a lock it did not set, as its documentation stated on 2026-11-09, and on the lock reason formats observed then; interactive sessions were not probed.
