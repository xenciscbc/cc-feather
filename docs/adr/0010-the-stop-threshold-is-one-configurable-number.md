# The Stop threshold is one user-configurable number from 2 to 10

ADR 0004 fixed at two the number of consecutive automatic calls without a pass that stops a step of the Automatic flow, and ADR 0009 derived its bounds from that number. A user whose reviews often need a third or fourth round, for example on a large Claim or a Security-critical claim whose Adversarial review is likely to return BROKEN once, had to step in every time, and could not say that the flow should keep trying, either for one session or as a standing preference for a project or for all their projects.

The user decided (2026-10-10, in two grilling rounds and two plan reviews; the [spec](../specs/configurable-stop-threshold.md) carries the claims):

- **One number.** The Stop threshold is one integer K from 2 to 10 that applies to plan review, code review, outcome verification and Adversarial review alike. The default is 2, so an installation where nobody sets it behaves as before.
- **Resolution.** The Stop threshold in effect is the user's task choice, for that task; otherwise the user's session choice; otherwise the value the loaded project guidance states; otherwise the value the loaded user guidance states; otherwise 2. A saved value reaches main only through one sentence the configuration tool writes into the managed delegation guidance; main does not run the tool at each decision. Main never raises or lowers K on its own, states K and its source at each review decision, skips and reports a guidance value outside 2–10, and treats an unknown session choice like an unknown count. A session choice does not cross sessions and is not written into a handoff.
- **One rule for the next automatic call.** A step's next automatic call for a work needs the user's explicit request exactly while that step's count for the work is at or above the Stop threshold in effect, and is made without one while it is below. This replaces each statement that derived the need for a request from a count left where it stopped: after an explicit pass that cleared a stop, for a reopened call, for a review after a Material deviation, for the review of a fix and for work that inherits an overlapping Plan's count and stop. An explicit pass still clears a stop without changing the count, and a valid pass stays valid whatever K is.
- **Changing K.** A change of K never changes a count; the rule above is applied with the new K at once. A stopped step whose count is now below the new K resumes, because the change is the user's own act; a step whose count reaches or exceeds it stops at once, meaning only that its next automatic call needs the user's request, so a step an explicit pass had cleared stays cleared. Main lists the steps the change resumed or stopped. A value the user saves in project or user scope in a conversation replaces any earlier task or session choice in that conversation, and K is resolved again from the saved values, so the session uses what a new session would.
- **Cost.** In one uninterrupted attempt, a Claim makes at most K(K+1) automatic calls: up to K verification calls, between which up to K − 1 fixes each get up to K code reviews, plus up to K code reviews before the first verification. A Security-critical claim makes at most K³ + K² + K: also up to K Adversarial reviews, between which up to K − 1 fixes after BROKEN each get up to K(K+1) code review and verification calls. A Plan with N Claims of which S are Security-critical makes about K + K(K+1)N + K³S, and each reopened Claim or approved Material deviation adds calls, including up to K plan reviews for each deviation. At K = 2 these are 6, 14 and 2 + 6N + 8S; at K = 10 they are 110, 1110 and 10 + 110N + 1000S. The bounds grow faster than K because a fix after REFUTED or BROKEN is code-reviewed with a fresh count while verification's and Adversarial review's counts run across fixes. The user kept the range 2–10 knowing these bounds.

The minimum is 2 because a single non-pass can be a transient interruption or a protocol failure, and stopping on it would interrupt the user for noise. There is no unlimited value because ADR 0004 rejected an unbounded loop: the user is asked at some point. There is one number rather than one per step because no need for separate values is known and four values would turn the cost formula into four variables; a later per-step override could be added without breaking a single saved value.

## Considered Options

- **Keep a fixed two**: the user who wants the flow to keep trying would still have to step in after every second non-pass.
- **One value per step**: no need for it is known, and four values make the cost hard to reason about; it stays possible later.
- **Allow 1, or an unlimited value**: 1 stops a step on one transient failure, and an unlimited value is the unbounded loop ADR 0004 rejected; `off` already exists for no automatic review at all.
- **A smaller maximum**: the user preferred the range 2–10 knowing the bounds at K = 10.
- **A saved value acting as a session choice**: the session would keep a value a new session would not use, and a user value saved in the conversation would beat the project's value against the project-over-user order; a saved value re-resolves instead.
- **Main reading the saved value with the configuration tool at each decision**: an extra tool call before every review decision, when the loaded guidance already carries the value.

## Consequences

This amends ADR 0004, whose two consecutive calls, six calls per Claim, 2 + 6N per Plan and up to two plan reviews per Material deviation are now the values at the default Stop threshold, and ADR 0009, whose two-call stop and fourteen calls per Security-critical claim are likewise the default values; ADR 0002, ADR 0003 and ADR 0006 get amendment notes where they state the fixed number or derive a needed request from it, and ADR 0006's note carries the rule for the next automatic call. Every other counting rule of ADR 0002 and ADR 0004 is unchanged: only an automatic pass resets a count, failed, interrupted and protocol-failure calls count, switching modes, models or reviewers and renaming never reset, verification's count runs across fixes, counts are per session, and Explicit requests sit outside the count. The pre-approval security analysis is not a counted step. A scope without a saved value keeps guidance and state byte-identical to 0.19.0's; a scope with one is rejected by a 0.19.x or older configuration tool. The Stop threshold remains an agent instruction, not a hook-enforced counter.
