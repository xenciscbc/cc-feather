# The Plan is what the user names, and a spec's tickets are its Claims

A Claim was "listed in a Plan", but nothing said where when a spec is split into tickets. The planning skills in common use write a spec without a Claim list and tickets that are, by construction, independently verifiable slices with their own acceptance and `Blocked by` dependencies, each sized to be done alone in a fresh context. The implementing session treated the tickets as Claims while a preview of the spec saw one Claim, and a session asked to implement one ticket had no rule for whether its Plan was the ticket or the spec. We decided that the Plan is what the user names: a spec, or a set of its tickets, makes the spec with those tickets the Plan, each unfinished ticket in scope one Claim and its `Blocked by` lines the dependencies; a single named ticket is the Plan with its spec as context; a ticket that belongs to no spec is its own Plan; a spec without tickets keeps its listed Claims or is one Claim. Main recognises a spec's tickets by an explicit link, a shared feature directory or the user naming them, asks when unsure and states the tickets used, and never edits a spec or ticket to add Claims. A spec's own Claim list and its tickets must agree; a mismatch is a blocker for the user to settle. Where specs live and whether tickets are committed stay the project's choice. A Delegation preview is the dispatch basis only in the session that made it.

The named-Plan rule applies only when no Plan in the session already covers the named work. Otherwise that Plan continues with no new plan review and keeps its count, verdicts and blockers, and a new Plan that partly overlaps one inherits its unresolved verdicts and blockers for the overlapping tickets, so naming a ticket can neither repeat a review nor escape a stopped one; this follows the session rules of ADR 0002 and ADR 0004 that renamed plans and cosmetic splits never reset a count. In a resumed session, an unresolved verdict that an active handoff records for a spec's Plan applies to that spec's tickets when they are named.

## Considered Options

- **Require every spec to carry a Claim list, or have main write one in**: duplicates the tickets, and main would edit documents the user agreed to.
- **Treat the spec as the Plan even when one ticket is named**: a fresh session per ticket, as the ticket workflow intends, would re-review the whole spec each time, because counts and passing verdicts do not cross sessions.
- **Treat every ticket as its own Plan even when the whole spec is named**: multiplies plan reviews for work the user agreed to as one.
- **Require tickets to be committed or specs to live in a set place**: cc-feather does not control project or planning-skill conventions; the implementing session has the files it needs, and the fallbacks cover the rest.
- **Require a Claim list in analyst's installed definition**: needs a setup update, conflicts with the one-Claim fallback, and analyst sees only what main supplies.

## Consequences

The planning skill's tickets are used as written, and how finely they are cut stays with the planning step (ADR 0003). A preview applies the same rules, lists the tickets it used and flags a Plan that refers to its own tickets or Claims it cannot find; a preview from another session is a reference. Another checkout without the tickets falls back to the spec's listed Claims or one Claim, provided the spec has its own acceptance; otherwise it is not yet a Plan. The glossary no longer advises against the word ticket for a Claim; it says a ticket is one place a Claim may be written. Installed role definitions, the policy, the handoff skill and the configuration tool are unchanged.
