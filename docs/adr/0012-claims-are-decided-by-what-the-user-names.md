# Claims are decided when the user asks for implementation, by what the user names

Plan review's "a plan lists its claims" and "main marks each Security-critical claim in a plan it writes" read as instructions for drafting, so main cut each spec it drafted into its own Claims table. The user then cut the same spec into tickets with a planning skill, the two cuts disagreed, and the rule that a spec's listed Claims and its tickets must agree turned the disagreement into a blocker. Separately, a single named ticket had its whole spec supplied as context to plan review, code review and outcome verification, so a review could judge the ticket against parts of the spec it never adopted, and the implementer and the reviewers could each read a different amount of the spec. The planning skills in use write each ticket to be done alone in a fresh context, with its own outcome and acceptance; the spec is where the ticket came from, not part of its contract.

The user decided (2026-10-13, in a grilling; the [spec](../specs/claims-at-implementation.md) carries the acceptance and its security invariants):

- **Claims are decided at implementation by what the user names.** A named spec is the Plan and one Claim, unless it lists its own Claims, which then count as listed. Named tickets of a spec, all or some, are the Plan, each unfinished ticket one Claim with its `Blocked by` lines as dependencies, and plan review runs once over them. A single named ticket is the Plan and its one Claim. A spec without tickets and without a Claims list is one Claim when it has scope and acceptance of its own; main may say in one line that it looks separable into tickets, without stopping the flow.
- **The question for a spec with tickets.** Main first asks whether to implement the spec as it stands or its tickets, only when the named spec has at least one unfinished ticket and no Plan in this session already covers the named work. Answering "the spec" makes the spec one Claim, or its listed Claims; answering "the tickets" makes those unfinished tickets the Plan. A spec that lists Claims and has tickets must still agree with them. The Delegation preview reports the question as open rather than answering it.
- **A ticket's Plan is its own content, and the spec is a checklist for plan review.** When tickets are named, a single ticket included, plan review reads the spec only as a checklist for what the tickets must carry: their scope, their Out of Scope, the decisions and security invariants that apply to them and, when the named tickets with the finished ones are all of the spec's tickets, the spec's outcome. The spec is not part of the Plan's content.
- **Reviews and implementation read the Claim and its citations.** Code review, outcome verification, Adversarial review and the implementing Assignment read the Claim's own text, the spec parts it cites explicitly and, for a Claim a spec lists, the spec parts that state they hold for every Claim. A ticket's `Spec:` line records where it came from and is not a citation of the whole spec.
- **Main does not cut Claims while drafting.** A spec main drafts for the user lists no Claims and is cut into none unless the user asks. It is not a plan main proposes itself, so its Claims are classified before the Plan's first plan review, as for any plan the user wrote.

This amends [ADR 0005](0005-the-named-plan-and-its-tickets.md): the single named ticket's spec is no longer context for its reviews, a named spec with unfinished tickets prompts a question, and when tickets are named the spec is a checklist for plan review rather than part of the Plan's content. ADR 0005's recognition of tickets, its existing-Plan, partial-overlap and resumed-session rules, "nothing left to implement" and the agreement between a spec's listed Claims and its tickets are unchanged.

## Considered Options

- **Ask at drafting time whether to list Claims**: the decision belongs to the moment the user names the work, when the user knows whether tickets will be cut.
- **Main writes a Claims table into specs it drafts**: the cause of the conflict, since the tickets the user cuts later need not match it.
- **Each ticket its own Plan when several are named**: multiplies plan reviews, and no review sees the dependencies between tickets; ADR 0005's rejection of it stands.
- **The whole spec as context for a single ticket**: judges the ticket against parts of the spec it never adopted.
- **Plan review reads only the tickets**: nothing would catch a decision, an Out of Scope line or a security invariant that cutting the tickets lost.
- **Security invariants kept only in briefs and handoffs**: they would be lost across sessions and checkouts; they are written into the Claim's own text or a part it cites.
- **The implementer reads the whole spec while reviewers read the ticket**: the reviews would not judge what the implementer used.

## Consequences

Claim sizing stays with the planning step (ADR 0003), and counts and passing verdicts stay per session (ADR 0002). Security analysis, its timing and its approval step, the Stop threshold, the Acceptance gate and the ticket status rules are unchanged, and so are the installed role definitions, the installed policy, the handoff skill and the configuration tool. Earlier specs keep working: a spec with a Claims table keeps its listed Claims when the user names it and answers "the spec". A ticket with no link to a spec is its own Plan and gets no checklist; the user's naming of it is the agreement. The checklist runs at plan review on the text as it stands then, and these rules are instructions to the model, kept consistent by tests rather than enforced by a tool.
