# Final check passes are recorded, its scope is chosen per Plan, and a clean Plan may land itself

ADR 0015 kept the final check's state inside the session that ran it: a record could make a commit failed but never passed, so a Plan whose final check passed and then waited for the user's decision across a new session ran its whole final check again before landing, at the same commit, with nothing changed. The final check always ran the Plan's overall acceptance, usually the full suite, besides every Claim's primary acceptance, whatever the Plan was; with Related-test acceptance off, each Claim's primary acceptance is often the full suite already. And a Plan that passed everything cleanly still stopped at the end to ask only for the user's authority to land (ADR 0015's decision at the end of the Plan, building on ADR 0008's rule that landing needs the user's authority).

The user decided (2026-11-17, in a grilling session; the [spec](../specs/final-check-reuse-and-auto-land.md) carries the acceptance), for the Automatic flow only:

- **A recorded pass crosses sessions.** Main records each final check run in the Plan's Dispatch record with its commit, scope and result. A resumed session, and main after a context compaction, take a recorded pass as passed while HEAD is that commit and the workspace reads that What a gated pass judged states show no change; a recorded failure keeps that commit failed. A change of environment, such as tool versions or external services, is not detected and is residual risk, as the dispatch record's trust already is (decided 2026-10-15: records under `.feather/` are taken as written).
- **The Final check scope is chosen per Plan.** Plan review recommends `full` (the overall acceptance and every Claim's primary acceptance) or `related` (every Claim's primary acceptance alone) with its reason; the user chooses once, in the ask after READY that resource-risk proposals already use, and main records the choice in the Dispatch record. Without a choice it is `full`; a release always runs `full`. Skipping the final check is not a scope: a final check not run still needs Accept and land.
- **Auto land.** A new delegation setting, off by default and saved like Related-test acceptance, gives the user's standing authority to land a Plan whose decision at the end would need no Accept and land. Main then lands without asking, only by fast-forwarding the remote default branch to the commit the final check and the reviews judged; a pull request main opened is closed as merged by that push. A push that cannot fast-forward, a protected branch or a refused push stops main to ask. Release and tagging stay the user's. After landing, main sets the tickets to their done value, completes an Active handoff and reports the landed commit, the Final check scope and result, and the Follow-up record.

This amends [ADR 0015](0015-each-claim-is-reviewed-when-done-and-keeps-its-passes.md) (a new session: the final check's state no longer comes only from this session; the decision at the end of the Plan: with Auto land on, a clean Plan's question about the authority to land is not asked) and [ADR 0008](0008-repository-authority-acceptance-and-gate-lifetime.md) (landing needs the user's authority: Auto land is that authority, given in advance and saved). It also amends the [Related-test acceptance spec](../specs/related-test-acceptance.md)'s statement that the final check runs the Plan's overall acceptance: it does so at scope `full`. Off mode is unchanged.

## Considered Options

- **Keep the final check per session**: safe against an undetected environment change, but it reruns the slowest check for nothing in the common case of waiting for the user across sessions.
- **Let the last Claim's outcome verification count as the final check**: a verifier runs only its own Claim's checks, not the other Claims' primary acceptance, and its run is a role's, not main's.
- **A `none` scope**: it would let a Plan land with no final check while still counting as clean; a final check not run already has a way through, Accept and land, which keeps it visible.
- **Merge the pull request**: every GitHub merge method creates a commit the final check and the reviews did not judge; a fast-forward push lands exactly the judged commit.
- **Auto land always on in auto**: landing is outward-facing and hard to undo, so it needs the user's own standing choice, not a default.

## Consequences

A Plan that waits across sessions for the user no longer reruns its final check, and a clean Plan with Auto land on finishes without a question. A recorded pass is believed as written, so an edit to the Dispatch record, or an environment change after the run, can let a commit land on a pass that would not hold now. `related` can let a Plan land without the full suite; the user chooses that per Plan, on plan review's recommendation. Auto land never lands anything that needs Accept and land, never rebases or merges to make a push fit, and never releases. Plan review's recommendation is a change to the analyst's role definition, so existing installations need setup update. These rules are instructions to the model, kept consistent by tests rather than enforced by a tool.
