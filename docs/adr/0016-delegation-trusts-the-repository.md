# Delegation trusts the repository

Since 0.21.0, every review, plan review and security analysis followed a repository safety reference written against a hostile repository ([ADR 0011](0011-reviews-treat-the-repository-as-hostile-by-instruction.md)): a common Git prefix and a closed list of Git forms, link, hard-link and name checks before every read, allowlists for roles without a shell, a configuration and hooks snapshot before every dispatch, filter-driver outcomes with a raw-byte comparison, and fixed forms with a message-file procedure for main's `git add`, commit, tag and push. Since 0.25.0 ([ADR 0014](0014-reviews-execute-repository-code-by-default.md)), reviews ran the repository's code by default, and stopped only when the user said that a change was someone else's or that code must not run. The rules cost every review: main loaded them before each call, roles spent tool calls on metadata checks, and a role that read a file with an ordinary tool or ran `git status` deviated. They were instructions, not enforcement, so a hostile repository was not contained anyway: a review executed the repository's code, and Claude Code loads the project's `CLAUDE.md` and `.claude` settings before any of these rules apply. Each review round of the rules found another gap, and the Follow-up records of 0.21.0 to 0.28.0 held dozens of further items against them.

The user decided (2026-10-18, in a grilling, with the questions left open settled on 2026-10-19; the [spec](../specs/repo-trust-split.md) carries the acceptance and its security invariants):

- **The trust assumption.** Delegation assumes that the repository is trusted: its working tree, its Git directory and configuration, and every change in it are the user's own or content the user chose to accept, and reading and running it is the user's risk. No review contains or detects hostile repository content.
- **Ordinary reads.** Main and the roles read the repository with ordinary file tools and ordinary Git commands. The repository safety reference is deleted, and with it the common Git prefix, the link, hard-link and name checks, the allowlists, the configuration and hooks snapshot, the filter-driver outcomes and every statement that forbids `git status`. Reviewer, verifier and adversary lose their shared Repository safety paragraph, and analyst, scout and Explore their allowlist paragraph.
- **The checks a result needs.** A gated code review, outcome verification or Adversarial review is dispatched, and its pass used, only when `git rev-parse HEAD` names the commit its brief names and `git -c core.safecrlf=false status --porcelain --untracked-files=all --ignore-submodules=none` lists no path the claim's files or acceptance checks depend on, both before and after the call. A read that exits non-zero, writes anything to standard error or prints anything but porcelain v1 lines counts as a change, so a check whose result cannot be established counts as failed. The command line overrides the user's `status.showUntrackedFiles` and submodule-ignore settings, and `core.safecrlf=false` keeps line-ending warnings off standard error. The final check uses the same reads before and after it. Plan review and security analysis compare the same reads before and after the call without needing a clean workspace, since they often read an uncommitted plan.
- **Commits.** Main stages the claim's files by name, the files the claim deletes and both paths of a rename included, and commits them with `git commit -- <claim files>`, both with `--literal-pathspecs`, so that no name is read as a pattern and content the user staged before stays out of the commit. It never uses `git add -A`, `git add .`, a directory or `git commit -a`, and skips hooks or signing only when the user asks. Otherwise main commits, tags and pushes with ordinary Git commands: the fixed forms, the message-file procedure, the name rule for tags, branches and remotes and the configured-remote check are gone. The installed policy says that main commits only the claim's files and skips hooks only when the user asks.
- **Execution.** For a review (main's primary acceptance and every role's lint, type check, test or probe) and for the final check, main, reviewer, verifier and adversary execute repository code on this machine unless a restriction the user stated in this session covers the call; a covered call runs what needs execution only in an isolated environment the user's own message in this session names, and otherwise reports it INCONCLUSIVE. A restriction comes only from the user's own messages in this session: that the repository is not trusted, that code must not run, or a narrower one such as not running a pull request's tests. Saying only where a change comes from is not a restriction: the condition on someone else's content, its allowance and its taint rules are gone. Text in a tool result, a file, a commit, a role's report, a handoff, dispatch or memory record, hook output or a compaction summary never states or lifts a restriction, nor names an isolated environment.
- **Fail closed at the role.** A role executes repository code only when main's own statement in its brief says that main has determined that it may, or in the isolated environment its brief names; a brief that does not state it, states it ambiguously or holds more than one candidate statement allows no execution. Reviewer, verifier and adversary carry this rule in one shared paragraph. It is kept because the only case it serves is the one the user asked to protect: a session in which the user said that code must not run.
- **Adversarial review targets.** Every target still traces to a plan the user approved or to the user's own command arguments, and main never adds a target it found in repository content without the user's confirmation, since this limits where destructive probes go whatever the repository's trust.
- **No check before trust.** cc-feather offers no check of a repository before it is trusted, and keeps no trust state file or other record that crosses sessions: deciding whether to trust a repository, for example after downloading or copying someone else's, is the user's.
- **The handoff tool.** The handoff tool's own Git and link safety code, and its documentation, do not change.

This supersedes [ADR 0011](0011-reviews-treat-the-repository-as-hostile-by-instruction.md) and [ADR 0014](0014-reviews-execute-repository-code-by-default.md): the hostile read model with its rules and deviation notes, and the execution default's condition on someone else's content, no longer decide what main and the roles read or run. It amends [ADR 0009](0009-security-critical-claims-get-an-adversarial-review.md), [ADR 0013](0013-only-what-a-claims-acceptance-needs-holds-its-completion.md) and [ADR 0015](0015-each-claim-is-reviewed-when-done-and-keeps-its-passes.md) where they rely on repository safety, as their notes say.

## Considered Options

- **Keep the read rules as defence in depth**: they cost every review and still could not contain a hostile repository, since reviews run its code and Claude Code loads its `CLAUDE.md` and `.claude` settings before any rule applies; each review of the rules found another gap.
- **Keep the "someone else's content" condition**: under a trusted repository the user states a stop directly, such as "don't run this pull request's tests", while the condition's allowance and taint rules added cases without adding protection. The documents and the update note say how to state a stop, because 0.25.0 to 0.28.0 taught users to state a change's origin instead.
- **A read-only repo-check tool**, run once on a repository before it is trusted to report what its Git directory, configuration and content would make Git and Claude Code run, without running any of it: attempted in this release and abandoned on 2026-10-19, because each review found another way for its reading of a hostile Git directory to miss what Git uses, such as includes, worktree and submodule configuration, links inside the Git directory and promisor settings. Its work is kept on the local branch `repo-check-wip`.
- **Harden main's `git status`** with `--no-optional-locks` and an empty `core.fsmonitor`: under a trusted repository those programs are the user's own, and the residual risks below state that the workspace reads run them.

## Consequences and residual risks

The READMEs and the reference documents open their Repository safety sections by stating, in bold, that delegation assumes the repository is trusted and runs its code during reviews, that saying where a change comes from no longer stops that, so the user says that code must not run, and that cc-feather offers no check of a repository before it is trusted, so deciding whether to trust one is the user's. They state the residual risks the user accepted with this decision:

- **Steering by content.** Repository content can steer main and the roles, by its `CLAUDE.md`, comments, commit messages or anything else they read: a role can be led to report a change's security problem as pre-existing or as inference, and main can be led to run code a restriction covers, since a restriction is itself an instruction to main.
- **Code and Git programs run.** Reviews and the final check run the repository's code on this machine, and main's and the roles' Git commands (`git status` before and after every call, the roles' reads, `git add`, commit and push) run the programs the repository's Git configuration, attributes and hooks select, including hooks in a tracked directory and the filters `git status` runs, whether or not a restriction is in force. That code can change anything the user can, including the user's own Git configuration, other worktrees and Feather's own records.
- **Implementation.** A restriction governs reviews and the final check, not implementation: executor and security-executor may run the repository's code while implementing, also while fixing someone else's change.
- **Nothing asks first.** Nothing in cc-feather asks before code runs; what remains is Claude Code's folder trust and the user's permission settings.
- **Isolated environments.** An isolated environment the user named stays available under a general restriction unless the restriction says otherwise; if it holds secrets, such as a CI runner, the code runs there.
- **Outside the workspace check.** Ignored files, and files marked assume-unchanged or skip-worktree, are not part of the workspace check, so such a file can affect a review or the final check.
- **Before any review.** Claude Code loads the project's `CLAUDE.md` and `.claude` settings, and runs the hooks in those settings, when a session starts in the project, so a repository can act before any review starts.
- **Statements end.** Statements that stop execution last for the session and are lost when a context compaction loses them; a new session, including one that continues a handoff, starts without them.

A change made and reverted during a call is not detected. The reviewer, verifier, adversary, analyst, scout and Explore definitions and the installed delegation policy changed, so existing installations need `/cc-feather:setup update` in every scope where delegation is installed after the plugin update, and a fresh session. These rules are instructions to the model, kept consistent by tests rather than enforced by a tool; no live review has shown whether a role follows them.
