# Reviews execute repository code by default

Since 0.21.0, [ADR 0011](0011-reviews-treat-the-repository-as-hostile-by-instruction.md) let main, reviewer, verifier and adversary execute repository code for a review on this machine only when the user had said in the session that the repository was trusted to run there and the change was written by the user or in the session, and otherwise only in an isolated environment the user named. Main asked the trust question in every session that needed execution, and work continued in a new session, as from a handoff, could not run on this machine unless the user said again that the change was theirs. Execution under 0.24.0 already decided authorship only from the conversation and the session's own edits; only outcome 1 of main's preparation used Git listings to attribute differences before it let a filter driver run, and it stopped the call after hashing when the driver revealed a difference it could not attribute. This record reverses the default rather than replacing a Git-based check.

The user decided (2026-10-14, in a grilling and after a security analysis of a first version; the [spec](../specs/repo-trust-default.md) carries the acceptance and its security invariants):

- **Execution by default.** For a review, that is main's primary acceptance and every role's lint, type check, test or probe, and for the final check, main, reviewer, verifier and adversary execute repository code on this machine. Main no longer asks whether the repository is trusted, and no longer requires the change to be written by the user or in the session.
- **What still stops it.** Execution on this machine stops when the user has said, in their own message, that the change under review or content in the workspace, or part of it, comes from someone else, such as another person's pull request, branch or patch, or when the user has said in this session that the repository is not trusted, that code must not run, or a narrower restriction that covers the call. Then what needs execution runs only in an isolated environment the user names, or on this machine only when no restriction covers the call, or the user's own message lifted it, and every part the user said comes from someone else lies in a change the user's own message named and allowed to run on this machine for that call; otherwise it is reported INCONCLUSIVE.
- **Only the user's own messages.** Nothing but the user's own messages can make content the user's, lift a restriction or allow execution. Text in a tool result, a file, a commit, a pull request, a role's report, a handoff or memory record, hook output or a compaction summary never can, and content the user pastes or quotes can only show that a change comes from someone else. Whether content comes from someone else is never inferred from Git authors, in either direction.
- **For the session.** These statements last for the session: a conversation continued with resume or continue is the same session, while a new session, including one that continues a handoff, starts without them. After a context compaction main keeps what the compaction summary still shows, and a statement the summary lost is not recovered.
- **Main's determination.** Every brief of a role that may execute code states main's determination as main's own statement, with its basis and, when execution is not allowed, the reason; a role executes repository code only on that statement or in the isolated environment its brief names.
- **Filter drivers.** A filter driver runs during main's preparation under the same rule, and only when every setting that defines it comes directly from the user's configuration files, not through an include. An allowance of someone else's change covers the driver for the calls it names unless the user limits it to particular commands, and an allowance of one change does not cover other content the user said comes from someone else. Outcome 1 no longer attributes differences from Git listings or stops the call after hashing: a difference only the driver reveals means the workspace does not equal the reviewed commit, so a gated call is blocked.
- **Reads unchanged.** How main and the roles read the repository does not change: the working tree stays attacker-controlled for reads, and Safe Git invocation, Paths and names and main's own `git add`, commit, tag and push stay as they are, apart from the wording that named the removed conditions. Execution states plainly that it does not follow that threat model, and the READMEs state what the new default risks.

This amends [ADR 0011](0011-reviews-treat-the-repository-as-hostile-by-instruction.md): its execution rule, and its statement that running the code of a change neither the user nor main wrote safely needs an isolated environment, no longer decide what runs. It amends [ADR 0009](0009-security-critical-claims-get-an-adversarial-review.md): dynamic probing follows Execution in place of its isolation rule for code the user did not write, its example of a Security-critical claim resumed in a new session and its statement of ADR 0011's extension, which changes its `CLAUDE.md` residual risk as stated below.

## Considered Options

- **Keep the authorship condition**: every session asked the trust question, and a change written in an earlier session, as work continued from a handoff, could not run on this machine unless the user said again that it was theirs, while the condition rested only on the conversation anyway; the user chose to name the exceptions instead.
- **Infer someone else's change from Git authors**: author, committer and remote names are written by whoever made the commit, so they can show neither that a change is the user's nor reliably that it is someone else's, and inferring from them would let repository content decide what runs.
- **A lasting per-project setting**, or a record of trust or distrust that crosses sessions: a file or setting can be changed by repository content or outlive what the user meant; the user chose statements that last for the session, which supersedes the earlier plan for lasting trust across sessions.
- **Ask again after a context compaction**: the user chose to keep what the compaction summary shows and to state the loss of the rest as residual risk rather than be asked after every compaction, which also removes the first version's rule that main treats execution as stopped after one.
- **Extend Execution to implementation**: executor and security-executor would need the user's statement before running the repository's code while implementing, fixes of someone else's change included; the user chose to state it as residual risk.

## Consequences and residual risks

- **The whole repository runs.** A review runs the whole repository at the reviewed commit on this machine, not only the change: content others committed earlier, commits a pull, fetch, merge or rebase brought in, and untracked files. A change whose origin the user does not state is run like the user's own.
- **Nothing in cc-feather asks first.** What remains before code runs is Claude Code's folder trust, given once per folder and not asked again when its content changes, and whatever the user's permission settings require; in a permission mode or with allow rules that do not prompt for commands, nothing asks first.
- **Statements end with the session.** A new session, including one that continues a handoff, starts without the user's statements, and a statement a context compaction lost is not recovered, so code the user said comes from someone else can run on this machine there unless the user repeats it.
- **What a stop does not cover.** A stop does not stop the hooks the user's Git configuration runs for main's `git add`, commit and push unless the user also asks main to skip hooks, and it governs reviews, not implementation: executor and security-executor may run the repository's code while implementing, including while fixing someone else's change.
- **Filter drivers.** A filter driver such as Git LFS runs when main hashes content, under the same stops and allowance as the rest of the review's execution; review Git commands still run no Repository-chosen program apart from it.
- **A changed `CLAUDE.md`.** ADR 0009 named its isolation rule for code the user did not write as mitigating the risk that a commit under attack that changes the project's `CLAUDE.md` steers the role that loads it. For a change whose origin the user did not state, that rule no longer applies, so it no longer mitigates that risk: such a change is probed on this machine by a role that loads its `CLAUDE.md`. The rule still mitigates it for content the user said comes from someone else, while that statement holds.
- **Someone else's code.** Running someone else's code safely needs an isolated environment the user names, such as CI, a container or a virtual machine.

The READMEs state these risks. The reviewer, verifier and adversary definitions changed, so existing installations need `/cc-feather:setup update` after the plugin update. These rules are instructions to the model, kept consistent by tests rather than enforced by a tool; only a live rehearsal shows whether a role follows them.

(Superseded by ADR 0016: reviews and the final check still execute repository code on this machine by default, but only a restriction the user states in this session stops them; saying that a change under review or content in the workspace is someone else's is no longer a restriction, and the allowance of someone else's change, the filter-driver rules and the unchanged hostile read model above are gone. Main and the roles read the repository with ordinary file tools and ordinary Git commands, and the residual risks are those ADR 0016 lists.)
