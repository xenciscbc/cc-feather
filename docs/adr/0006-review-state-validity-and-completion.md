# Review steps share one state model, and a pass holds only for what it judged

Plan review, code review and outcome verification each described their own state, and the descriptions drifted: an explicitly requested pass after a stop had a different effect in each step, nothing said when an APPROVED or CONFIRMED stopped being valid after the work changed, an unverified Claim could be committed although an unreviewed one could not, release Claims had to verify a tag that exists only after the commit, a partly overlapping Plan could restart a stopped count, and lost state after context compaction had no fallback. We now keep one state model for all three steps (work identity, reviewed content, call source, consecutive non-pass count, valid verdict and blockers), cited by each procedure.

An explicitly requested pass clears a stopped step without resetting its count, and in auto the Automatic flow resumes; a later automatic call in that step therefore needs the user's request, and that call is still automatic. An explicit review or verification made before the flow reached that step is not that step's pass. In auto a user's "review" is automatic when the flow is due to run that step and explicit when the step has stopped or the request is outside the flow, and main states which before dispatching. Every attempted call counts, a generic retry included. Unknown state is treated as stopped, compaction is not a new session, and each review result states the count. Work overlapping a stopped Plan keeps that Plan's count and stop. A pass covers only the content it judged: a relevant change reopens Code review and Outcome verification, an environment-only change reopens verification, and updating a ticket's status is not a relevant change. For Plan-driven Claims in the Automatic flow, and for any Claim an active handoff records as unreviewed or unverified, a Claim is never reported complete without a valid APPROVED and CONFIRMED, and without them it is committed only as a work-in-progress commit the user allows, labelled unaccepted. An acceptance item that exists only after an authorised operation, such as a release's tag and version after its commit, is checked by main afterwards as one of its postconditions; outcome verification covers the rest before the operation. Where the project defines a completion value, main sets a ticket to it with the version or commit after its Claim passes and is committed; without a defined value it reports instead, and asks whether a ticket is finished. A ticket is finished by a completion value or the user's word. The user's decisions are recorded as re-review, deferral, cancellation, changed acceptance or waiver, a waiver is never a pass, and saying "continue" or turning auto off does not accept a known defect. Counts and passing verdicts do not cross sessions, while unresolved verdicts recorded in an active handoff restrict related work in both directions. Claim changes a review requires, that is claims added, split or changed because of a REVISE blocker, are decided by the user or the planning step, and main edits a spec or ticket for them only after the user authorises it, keeping the old-to-new mapping and the unresolved blockers each Claim carries. A plan-mode or conversation Plan is used in a new session only from its original text, a record or a version the user confirms.

(Amended in 0.15.0 by the [review follow-ups spec](../specs/review-followups-0-15-0.md): a Claim with postconditions has its ticket set to the completion value only after they hold; a postcondition that does not hold leaves the ticket unfinished.)

(Amended by ADR 0007: the commit gate moved to landing on the remote default branch, release, reporting complete and ticket completion; claims may be committed before their passes, and a claim that passed in an earlier session is reviewed and verified again before a gated operation unless its ticket is finished.)

## Considered Options

- **Fixed totals per Plan or Claim**: rejected again (ADR 0004); a total cannot follow reopened work without either stranding it or hiding its cost.
- **Reset the count on an explicit pass**: the next automatic call would get a fresh budget the user never granted, so one explicit pass could buy unlimited automatic retries.
- **Trust passes across sessions**: a resumed session cannot see what the earlier pass judged or what changed since, and a handoff records unresolved verdicts, not the reviewed content.
- **Treat a generic retry as free**: a failing role could be retried indefinitely under another name, which the consecutive count exists to prevent.
- **Rebuild a conversation Plan from memory**: the rebuilt Plan is not what the user agreed to, and its Claims could silently differ.
- **Widen automatic review to all unplanned work**: the user chose to keep unplanned non-security edits unreviewed regardless of size; a security-boundary change, data migration or irreversible operation still needs a reviewed Plan first.

## Consequences

The bound of six automatic calls per Claim holds for one uninterrupted completion attempt; reopened Claims and Material deviations add calls. This amends ADR 0004's consequence that a Claim makes at most six automatic calls. Main may edit a spec or ticket to change Claims that the user or the planning step decided, only after the user authorises it, and it keeps ticket status current where the project defines a completion value; this amends ADR 0005's statement that main never edits a spec or ticket to add Claims, and ADR 0005's consequence that another checkout without the tickets falls back to listed Claims or one Claim, which the ticket-finding rules have since refined (main looks where the project says tickets live, searches ignored and hidden directories only when the project does not say, and asks when a spec refers to tickets it cannot find). The rest of ADR 0004 and ADR 0005 is unchanged. Installed role definitions, the policy and the setup flow are unchanged; changes to reviewer and analyst templates are separate work that needs a setup update.

(Amended by ADR 0008: a finished ticket counts as accepted only when it was set to a done value after valid passes or an accept-and-land decision, with no relevant change since; a won't-do value never counts as acceptance.)
