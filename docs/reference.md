# cc-feather reference

**English** | [繁體中文](reference.zh-TW.md)

The [README](../README.md) gives the overview and the design trade-offs; this file explains what each delegation rule is for and when it applies, and links to the procedure or review state item that states it. Each rule is written once, in the file responsible for it, and main follows those files, not this one ([ADR 0017](adr/0017-each-delegation-rule-is-written-once.md)). It also states the limits of the flow and the risks that remain yours. Terms are defined in [CONTEXT.md](../CONTEXT.md).

## Automatic review

The review steps, their roles and what each passes with are in the README's [Roles and routing](../README.md#roles-and-routing).

Where the rules are written: routing, dispatch, the definition of a Security-critical change and accepting or recovering a child's result are in the [delegation skill](../skills/delegation/SKILL.md); the state every review step shares, such as counts, the Stop threshold, validity, completion criteria, commits, the final check, your decisions, resumed sessions and the dispatch record, is in [review state](../skills/delegation/references/review-state.md); each step's own rules are in the [plan review](../skills/delegation/references/plan-review.md), [code review](../skills/delegation/references/code-review.md), [outcome verification](../skills/delegation/references/outcome-verification.md) and [Adversarial review](../skills/delegation/references/adversarial-review.md) procedures, and the preview's in the [preview procedure](../skills/delegation/references/preview.md). Below, "review state's Reading set" names the item of review state that starts with that name in bold. Main reads review state in full before any decision or brief that depends on it, as its Reading it says.

- **Unplanned work** gets no automatic review: the flow exists for work done from a plan you agreed to. Work whose mistakes are costly to undo, a Security-critical change, a data migration or an irreversible operation, first needs a written plan that is reviewed and that you approve, so the riskiest work never starts unplanned. The [plan-review procedure](../skills/delegation/references/plan-review.md) states it.
- **Per-claim timing:** in auto, each claim is reviewed and verified as soon as it is implemented and committed, not after the whole plan, so a problem in an early claim is found before later claims build on it. It is the only timing in auto, and reviews still take turns with implementation in the same working tree, as Serial reviews explains. The rule is review state's Per-claim timing.
- **Dependent claims:** in auto, a claim that depends on another, by its `Blocked by` lines or the plan's own order, waits until that claim has passed, so it never builds on work a review may still change; a claim with no such dependency does not wait. When the claim it depends on stops or cannot pass without your decision, it stops too and you decide, and you may let named dependent claims proceed. The rule is review state's Dependent claims.
- **Fixed passes:** in auto, a claim that has passed is not reopened by another claim's change that the other claim's own passing reviews judged, so later claims touching earlier files do not send the plan round the reviews again; a problem the change causes is the changing claim's to fix. A change no passing review judged still reopens, in `off` every change to a claim's files reopens it, and a claim may change another claim's acceptance checks only where its own reading set says so. The rule is review state's What a pass covers. Fixed passes have limits: a later claim's reviewer reads only its own reading set and may not know an earlier claim's design intent, and a property of an earlier claim that no acceptance check the final check runs covers can be broken without the final check noticing.
- **Budget:** each step stops after as many consecutive automatic calls without a pass as the [Stop threshold](#stop-threshold), 2 by default, so a flow that keeps failing waits for you instead of retrying without end; a stop never counts as passing. Counts are kept per plan for plan review and per claim for the other steps, every attempted call counts, and nothing within a session, such as renaming a plan or switching reviewers or models, resets a count; a resumed session starts new counts. The rules are review state's Transitions, What counts as a call and What does not reset a count, and each procedure's counting step says how its own INCONCLUSIVE counts.
- **Re-review during implementation:** a plan is reviewed again when what you agreed to changes, through a material deviation or the discovery of a security control or invariant the plan lacks, so implementation never runs ahead of an agreed plan; dependent work waits for the revised plan's review and your approval. Wording changes and adjustments within the approved outcome, scope and acceptance are not re-reviewed as a plan; the code they touch still goes through code review and verification with its claim. The rule is the [plan-review procedure](../skills/delegation/references/plan-review.md)'s step 5, with review state's Deviations and Deviation scope.
- **Findings:** a review holds a claim back only for what makes it not done: its acceptance as written is unmet, existing behaviour is broken, it introduces a security problem or data loss, or it deviates from the plan. This keeps reviews from growing the work with findings outside the claim's scope, while security problems and data loss block whatever the acceptance says. A broken existing behaviour that is neither needs a failing test or a reproduction, and every other finding is recorded for later. The criteria are the same in both modes and for every user; there is no setting for them. They are review state's Completion criteria; how each step dispositions a finding is in its procedure.
- **Follow-up record:** the non-blocking findings of a piece of work are kept in one record, so they are not lost when the work completes and can feed a later plan you choose to start. It is data: its next step is always your decision whether to start a later plan, the findings it quotes are marked as untrusted, reading or resuming it authorizes nothing, and accept and land never relies on it. Nothing starts the later plan automatically; a later plan that fixes recorded findings is new work under the usual rules. Before main proposes or adopts a requirement or fix derived from any finding, it weighs when the case occurs, its worst credible outcome and whether an existing rule already covers it, so rare edge cases do not add rules; the weighing never changes what blocks. The record is review state's Follow-up record, and the weighing is in the [delegation skill](../skills/delegation/SKILL.md).
- **Not passed:** the gates keep work that has not passed off the default branch and out of releases and completion reports: a claim without APPROVED is unreviewed, one without a valid CONFIRMED is unverified, and a Security-critical claim also needs a valid HELD. While a claim is gated, an active handoff records what it still lacks, so an approval alone, as from an explicit review in `off`, never lets the claim reach the default branch. Your accept-and-land decision is the only exception (see Your decisions). The rules are review state's Commit and completion and Pending acceptance; what follows a REFUTED or a BROKEN is in the [outcome-verification](../skills/delegation/references/outcome-verification.md) and [Adversarial review](../skills/delegation/references/adversarial-review.md) procedures.
- **Validity:** a pass holds only for what it judged, so a later change cannot ride on an earlier pass: a change to a claim's files or what they depend on reopens its code review and verification, an environment change reopens verification, and for a Security-critical claim a change to its test targets or to what shares its security assumptions reopens HELD. A reopened step continues its count rather than starting fresh. The rules are review state's What a pass covers and Reopened calls, and the composed review of changes that share security assumptions is the [Adversarial review procedure](../skills/delegation/references/adversarial-review.md)'s step 9.
- **Commit:** in auto, main may commit a claim before its passes, push it to a branch it created for the work and open a pull request that lists the claims still unaccepted, without asking, so each review judges a named commit and work in progress is not lost. Landing on the default branch, release, reporting complete and marking a ticket done still wait for the passes or your accept-and-land decision. Main asks before pushing to a branch it did not create, a pull request is not permission to merge, and your explicit instruction not to commit or not to push wins. Each commit holds only the claim's files, which main adds and commits by name, so content you staged before stays out of it. The rules are review state's Commits before the passes, Repository authority and Commit and completion.
- **Release checks:** an acceptance item that exists only after an authorised operation, such as a tag after its commit, cannot be verified before it, so main checks and reports it after the operation and verification covers the rest before it. The rule is review state's Postconditions.
- **Serial reviews:** a review judges a working tree that nothing else changes while it runs, so its verdict is about the commit it names; within one working tree, reviews and implementation therefore take turns, and a pass from a call during which a file the claim depends on changed is not used. Main never creates a worktree for a review on its own, since setting one up can mean reinstalling dependencies or rebuilding the project. Work you run in separate worktrees may proceed in parallel. The rule is review state's Serial within a working tree.
- **Final check:** before landing or release, main runs the plan's overall acceptance checks, such as the full test suite, at the commit to be landed, as its own run under the Execution rule of [review state](../skills/delegation/references/review-state.md). Claims that each passed are checked together this way, and in auto each claim's primary acceptance is rerun there. It is not a review step and adds no verdict; a failure is fixed by the claim it is attributed to or by a fix claim main adds, and landing waits for a pass or your accept-and-land decision. When running the repository's code is not allowed, the check is recorded as not run, and main tells you so before landing and in any accept-and-land decision. A fix claim that changes a security control is Security-critical, but main still adds it without asking: it gets no plan review, security analysis or Adversarial review, and main discloses it at the end with its problem and a summary of the fix, so you decide whether to land with it. The rule is review state's Final check. The check does not repeat everything at the final commit: acceptance items other than a claim's primary acceptance are not rerun, and an acceptance check that cannot be rerun, such as a manual check, is not repeated. Repository code a check runs controls its own output, so it can make a check pass that should fail, hide that a check ran fewer tests, or make a failure point at the wrong claim; the last only misdirects a fix, after which the check runs again.
- **Your decisions:** when a step waits for you, main records what you decide as one of re-review, deferral, cancellation, changed acceptance, waiver or accept and land, with its scope, so a decision covers exactly what it names. A waiver stays visible with its remaining risk and never counts as a pass. Accept and land is your explicit acceptance of a named claim without one or both passes, or without its HELD, recorded with the commit it accepts, the missing passes and the remaining risk; a later relevant change ends it. Saying the work is done counts as acceptance only after main confirms it with you and records it as accept and land; saying "continue" or turning auto off does not accept a known defect. The rules are review state's User decisions.
- **Accept and land at the end:** main asks for accept-and-land decisions once, after every claim of the plan has finished its reviews and the final check has run or is recorded as not run, before landing or release, so you decide with the whole plan in view rather than claim by claim. In auto it asks even when no claim needs your decision, and its list states the final check's state, each claim's passes, missing passes and unresolved blocking findings, each Security-critical claim's Adversarial review result, each Security-critical fix claim, the Follow-up record and what this flow does not check. You may confirm part of the list by whole claims; saying "continue", silence or turning automatic review off is not a confirmation, and the decision covers only what was listed. The rules are review state's Accept and land at the end of the plan. What this flow does not check is: a later claim's reviewer reads only its own reading set and may not know an earlier claim's design intent; a property of an earlier claim that no rerun acceptance check covers can be broken without the final check noticing, and acceptance items other than the primary acceptance are not rerun at the final commit; an acceptance check that cannot be rerun, such as a manual check, is not repeated at the final commit; the commit an Adversarial review attacks was not judged as a whole by the claim's own code review and verification; Adversarial review findings are not fixed in the plan; a Security-critical fix claim gets no Adversarial review; and main takes the dispatch record as written, so an edit to it changes what main believes. A re-review you choose at the decision can recover part of this.
- **Authority:** a pass grants no new authority. READY lets already authorized work continue without another routine confirmation. The rules are the [plan-review procedure](../skills/delegation/references/plan-review.md)'s step 5 and review state's Repository authority.
- **Explicit requests** for a plan review, code review, verification or Adversarial review (including `/cc-feather:adversarial-review`) work in either mode, so you can always ask for one; they run only what you asked for, are not counted and never reset a step's count. In auto, when one passes a step the automatic flow had stopped, the flow resumes from there. The rules are review state's What an explicit call runs and Clearing a stop.
- **After a stop:** an explicit pass of a stopped step clears the stop but leaves its count, so a later automatic call in that step for the same work, such as the review of a fix, still needs your request while the count is at or above the Stop threshold; the stop exists to bring you in. The rules are review state's Clearing a stop and Next automatic call.
- **Asking for a review:** in auto, a review you ask for is automatic or explicit depending on whether the flow is due to run that step, and main states which before dispatching, since that decides how it counts. The rule is review state's Classifying a request.
- **Implemented before plan review:** in auto, work that is already implemented but has no plan review in this session, for example because it was implemented in another session, outside Claude or while review was off, makes main ask before any review whether to run plan review first or go straight to code review, so skipping plan review is your choice. Going straight to code review is recorded as a waiver of the missing READY, which does not waive a security analysis. The rule is review state's Implemented before plan review.
- **Retries:** every attempted call counts, including a generic retry after a temporary failure, so retrying cannot get around the Stop threshold; a missing role or fresh context found before dispatch is not a call. The rules are review state's What counts as a call and the [delegation skill](../skills/delegation/SKILL.md)'s Accept or recover.
- **Lost state:** when main cannot establish a count, verdict or blocker in the session, for example after context compaction, which does not start a new session, it treats the step as stopped and asks you rather than guessing. Each review result states the current count. The rule is review state's Unknown state.
- **Dispatch record:** in auto, a plan's review state crosses sessions through one record per plan at `.feather/dispatch/<name>.md`, so a new session, or main after context compaction, does not review passed work again or ask again about implemented work whose READY it holds. It holds no counts, exploit details or secrets, and main keeps it out of Git. Counts still restart in each session, and main runs the final check again before landing. In `off`, main writes none. The rule is review state's Dispatch record. Main takes the dispatch record as written, so an edit to it, by repository code a review or the final check runs or by a person, changes which passes and results main believes; cc-feather does not defend against that.
- **Cost:** in one uninterrupted attempt in a session, with K the Stop threshold, a plan with N claims, S of them Security-critical, makes at least 1 + 2N + S automatic calls and up to about K³ + K(K+1)N + KS, since a claim makes at most K(K+1) (up to K verification calls, between which up to K − 1 fixes each get up to K code reviews, plus up to K code reviews before the first verification), a Security-critical claim at most K(K+1) + K (also up to K Adversarial reviews, once at the end, where a BROKEN is recorded rather than fixed), and the plan reviews and the final check's fixes at most K³ together (up to K plan reviews, and up to K − 1 fixes in a row before the final check stops, each getting up to K(K+1) code review and verification calls in the claim that caused the failure or in a fix claim). At the default K = 2 that is, in one uninterrupted attempt, at most 6 calls per claim, 8 per Security-critical claim and about 8 + 6N + 2S per plan; at K = 10 it is 110, 120 and about 1000 + 110N + 10S. The bounds grow faster than K because each fix is reviewed and verified again. A plan with a Security-critical claim also gets one security analysis per plan or shared trust boundary; each reopened claim, final-check fix or material deviation you approve adds calls; the default roles run on opus/high. A re-review you choose in the decision at the end adds the calls of the reviews you choose, and when it changes the code, the final check runs again. To lower it, keep the Stop threshold low or change a role with `/cc-feather:model`, for example `verifier.effort=medium`; package defaults stay unchanged. How finely a plan is cut into claims is decided where the plan is written, such as a spec, planning or ticket-splitting skill, not by cc-feather. The [preview procedure](../skills/delegation/references/preview.md) states how the preview reports these bounds.
- **Independence:** each review runs in a fresh context and gathers its own evidence, but usually on the same model as main. For model diversity, set a different model for analyst or reviewer with `/cc-feather:model`. cc-feather cannot see or guarantee main's model, and switching a role's model never resets a step's count. A second opinion from another vendor's model, if you have one, is an explicit request outside this flow.

**Which document is the plan.** The plan is what you name when you ask main to implement something; naming it is your agreement to it, and what you name decides its claims. These rules are instructions to main, not enforced by any tool; tests only keep the texts consistent. They are the [plan-review procedure](../skills/delegation/references/plan-review.md)'s plan identification and spec checklist, and review state's Reading set, Ticket status, Claim changes, Deviation scope, Spec updates and Conversation plans.

- **A spec:** a spec you name is the plan, and one claim unless it lists its own claims. When it also has unfinished tickets, main first asks whether you mean the spec as it stands or its tickets, because the answer decides what is reviewed and how many claims there are.
- **Tickets of a spec, all or some:** the tickets you name are one plan, reviewed once, so tickets that belong together are judged together; each unfinished ticket is one claim, and its `Blocked by` lines are its dependencies.
- **A single ticket:** a ticket you name alone is the plan and its one claim, and plan review still checks it against its spec.
- **A ticket that belongs to no spec**, with no `Spec:` line, parent reference or shared directory linking it to one and not named by you as a ticket of a spec, is its own plan and gets no checklist: naming it is your agreement to it. A ticket you name as a ticket of a spec is a ticket of that spec, as Finding the tickets says. **A spec without tickets** keeps the claims it lists or is one claim, provided it has scope and acceptance of its own.
- **Example:** `docs/specs/login.md` has unfinished tickets 01, 02 and 03, and 03 is `Blocked by` 02. "Implement the login spec" makes main ask first: "the tickets" makes one plan with three claims, with one plan review, and 03 waits for 02; "the spec" makes the whole spec one claim. "Implement tickets 02 and 03" makes one plan with two claims. "Implement ticket 02" in a fresh session makes ticket 02 the plan and its one claim, whose reviews read ticket 02 and the parts of `login.md` it cites. `docs/specs/logout.md`, with no tickets and no claims list, is one claim when you name it.
- **The spec as a checklist:** when the plan is tickets of a spec, plan review uses the spec as a checklist rather than as part of the plan, so the tickets stay within the spec's scope, cite the decisions, security invariants and Out of Scope lines that apply to them and, once they are all named or finished, cover the spec's outcome. A missing coverage or citation is a blocker.
- **Citations:** a citation names one part of the spec, such as a section, a numbered item or an identifier like `S2`, so a ticket's reviews read what applies to it and not the whole spec; a `Spec:` line is not a citation, and a citation that does not resolve to exactly one part is a blocker at plan review.
- **What a review reads:** a claim's implementer and its code review, outcome verification and Adversarial review read the same reading set, the text the claim is written in and the spec parts it cites, so that every step judges the claim against the same text and a change to that text is noticed. A Security-critical claim's briefs carry its own security invariants and test targets, not another claim's. When a ticket is implemented or reviewed without a READY for its plan in this session, its reading set is the whole spec. These are instructions to the model: a role can still open the whole spec file, and only its brief keeps it to the cited parts.
- **Checklist limits:** the checklist runs at plan review, on the spec and tickets as written then; its coverage check runs only when the named and finished tickets are all of the spec's tickets; the spec is not a claim's acceptance, so a ticket's reviews after plan review read only the ticket and the spec parts it cites, except that a ticket implemented or reviewed without a READY for its plan in this session reads the whole spec, as What a review reads says; and these rules are instructions to the model, not enforced by any tool.
- **Already covered:** when a plan in this session already covers the work you name, that plan continues with its count, verdicts and blockers, so naming a ticket can neither repeat a review nor escape a stopped one.
- **Partial overlap:** a new plan that overlaps one in this session inherits its unresolved verdicts and blockers, and its count and stop where it had stopped, for the overlapping work, so overlapping work cannot escape a stop. The rule is review state's Overlap.
- **Resumed session:** what crosses into a new session decides what is reviewed again there. Counts never carry over, and finished tickets are not redone. In auto, passes, Adversarial review results, unresolved verdicts and your decisions carry over through the dispatch record; in `off`, passing verdicts do not carry over and only an active handoff carries unresolved verdicts, so a claim that passed in an earlier session is reviewed again before landing unless its ticket shows it was accepted. The rule is review state's Resumed sessions.
- **Nothing left:** when every ticket in the named scope is finished, main reports that nothing is left to implement.
- **Ticket status:** main sets a claim's ticket to the done value your tracker convention defines once the claim has both passes, plus HELD for a Security-critical claim, and is committed, or after your accept-and-land decision, so a finished ticket is not redone; in auto, only after your decision at the end of the plan. Finished only means not redone: a value for work that will not be done, such as `wontfix`, never counts as acceptance. The rule is review state's Ticket status.
- **Finding the tickets:** main recognises a spec's tickets by an explicit link such as a `Spec:` line or parent reference, a shared feature directory, or you naming them, and looks first at your project's instructions for where tickets live. Because a repository-wide search can skip files that version control ignores and hidden directories, an empty result does not count as none. It asks when what you name matches no plan or several, and states which tickets it used.
- **Telling main where tickets live:** add a line to your project's CLAUDE.md or AGENTS.md, or a file it points to, saying where specs and tickets live, for example "Tickets: `.scratch/<feature>/issues/`, linked to specs in `docs/specs/` by a `Spec:` line". A planning tool's setup may write this note for you. If that instructions file is not committed, other checkouts do not have the note, and main falls back to searching.
- **Disagreement:** a spec that lists claims and also has tickets must agree with all of them, finished or not; a mismatch is a blocker for you to settle.
- **Claim changes:** main never edits a spec or ticket to add, split or change claims unless you authorise it, so the plan you agreed to stays yours; it keeps a mapping from old claims to new ones and their unresolved blockers.
- **Deviations in tickets:** after a material deviation in a plan of tickets, the review covers the tickets the change touches rather than the whole plan, and runs the spec checklist again only when the change touches the spec's outcome, scope, decisions or invariants. These are instructions to the model: main judges which tickets a change touches and whether it touches the spec, and the checklist otherwise runs only at plan review, on the text as written then.
- **Spec updates:** once tickets are cut, they govern implementation; when a change you agree to alters the spec's outcome, scope, decisions or invariants, main updates the spec with your authorisation, so later checks and other sessions read the agreed version. An agreed change to a spec part a claim reads reopens that claim's passes.
- **Drafting a spec:** when main drafts a spec for you, it lists no claims and cuts none unless you ask: its claims are decided when you name the spec or its tickets for implementation, and they are classified like those of a spec you wrote; see [Security-critical work](#security-critical-work).
- **Not yet a plan:** a spec with neither tickets nor scope and acceptance of its own, such as a spec template without an acceptance section, is not yet a plan; main completes it and confirms the completed version with you first.
- **Plan-mode and conversation plans:** their claims live in that plan's text, so another session cannot see them; this is an accepted limit. A new session uses such a plan only from its original text, an available record or a version you confirm.
- **Where files live:** cc-feather does not decide where specs live or whether tickets are committed; it uses what the implementing session has.

### Security-critical work

```text
/cc-feather:adversarial-review session token checks in src/auth, against the test server the plan names
/cc-feather:adversarial-review password reset flow HEAD~3..HEAD
```

A Security-critical claim is one whose outcome includes a Security-critical change: a change to a security guarantee at a trust boundary, or to the implementation or configuration of a security control, including where sensitive data goes and how untrusted data is interpreted downstream. Authentication, authorization, sessions and CSRF, credentials, cryptography, input validation and access control are examples, not a closed list; main recognises such a change by what it does, not by keywords. Such a claim gets more care because a mistake in it can expose data or access: security-executor implements it, in `off` too, and main classifies a plan's claims before the work on them starts. The definition, the classification and where the work goes are the [delegation skill](../skills/delegation/SKILL.md)'s Select and prepare and the [plan-review procedure](../skills/delegation/references/plan-review.md).

In `auto`, a plan with a Security-critical claim first gets a read-only security analysis and then plan review of the revised plan, so the security invariants and the disposable test targets the reviews will check are written into the claim before anything is built. You approve the revised plan when the analysis changes it. The analysis is not counted toward the Stop threshold, and a waiver of a missing READY for implemented work does not waive it. The rules are the [plan-review procedure](../skills/delegation/references/plan-review.md)'s security analysis and the [delegation skill](../skills/delegation/SKILL.md).

Adversarial review is the third step: adversary tries to break the claim and answers HELD, BROKEN or INCONCLUSIVE, so a Security-critical claim is attacked, not only reviewed. In `off` it counts only after a valid APPROVED and CONFIRMED at the same commit, and a BROKEN goes back to a fix before completion; in auto it runs once, at the final commit after the final check passes there, and a BROKEN is recorded for your decision at the end of the plan rather than fixed in the plan. A vulnerability that predates the change does not block the claim and becomes separate work in your tracker. Exploit details and secrets stay out of anything public or possibly public, which gets only a summary unless you agree. The rules are the [Adversarial review procedure](../skills/delegation/references/adversarial-review.md), its At the final commit for auto and its step 10 for disclosure. This has limits: the commit an Adversarial review attacks was not judged as a whole by the claim's own code review and verification, and its findings are not fixed in the plan. In `off` no Adversarial review starts automatically and the security analysis before approval is not forced. There is no separate switch for the third step: to land a Security-critical claim without HELD, make an accept-and-land decision for it.

`/cc-feather:adversarial-review` runs an Adversarial review when you ask, in either mode. It takes a required attack scope, which main asks for when you give none, and optional paths or a commit range and disposable targets; the arguments are data and never widen the role's limits. What it reviews, a commit range, your uncommitted change or a claim's commit, and whether its verdict counts toward a claim's gate depend on the claim and its passes, and the result names the reviewed commit or range, what it left out and whether the verdict counts. Targets come only from a plan you approved or from your own arguments; without one, the role analyses statically and reports INCONCLUSIVE for what needs execution. Dynamic probing follows the Execution rule of [review state](../skills/delegation/references/review-state.md): it runs on this machine unless you have stated, in this session, a restriction that covers it, and then only in an isolated environment your own message names; without one the attack stays static. Saying only where a change comes from is not a restriction. See [the adversarial-review procedure](../skills/delegation/references/adversarial-review.md) and [the command](../skills/adversarial-review/SKILL.md).

The adversary's limits are instructions to the model, and only your permission settings (permission mode and allow, ask and deny rules, including managed settings), hooks, the Claude Code sandbox (not available on native Windows) and an external isolated environment such as a container or virtual machine enforce them: in bypassPermissions mode, or with broad allow rules, its Bash commands can run without any prompt or classifier check, and in Claude Code's auto mode a classifier, not you, approves them; see the official [permission modes documentation](https://code.claude.com/docs/en/permission-modes) for how each mode treats commands.

### Repository safety

**Delegation assumes that the repository is trusted, and reviews run its code on this machine. Saying where a change comes from, such as that it is another person's pull request, branch or patch, no longer stops that: to stop it, say in your own message that the code must not run, or name what must not run. cc-feather offers no check of a repository before you trust it, so deciding whether to trust one, for example after downloading or copying someone else's, is yours.**

Main and the roles read the repository with ordinary file tools and ordinary Git commands, and no review contains or detects hostile repository content. A review keeps only the checks that make its result correct, and a check whose result cannot be established counts as failed.

Main reads `HEAD` and the workspace status before and after every code review, verification and Adversarial review, and around the final check, so a pass judges exactly the commit its brief names and a change during the call voids it; plan review and security analysis compare the same reads without needing a clean workspace. Main commits only the claim's files, by name, so content you staged before stays out of the commit, and skips hooks or signing only when you ask. The reads are review state's What a gated pass judged, and the commit forms its Repository authority.

Reviews and the final check run the repository's code on this machine unless a restriction you stated in this session covers the call; a covered call runs it only in an isolated environment your own message names, and otherwise what needs execution is reported INCONCLUSIVE. A restriction comes only from your own messages in this session: that the repository is not trusted, that code must not run, or a narrower one, such as not running a pull request's tests. Saying only where a change comes from is not a restriction. Text in a tool result, a file, a commit, a role's report, a handoff, dispatch or memory record, hook output or a compaction summary can neither state nor lift a restriction, nor name an isolated environment. The rule, including how long a restriction lasts and what lifts it, is review state's Execution.

These rules are instructions to the model, not a sandbox: no permission rule, hook or sandbox enforces them, and tests only keep the texts consistent. What remains is your risk:

- Repository content can steer main and the roles, by its `CLAUDE.md`, comments, commit messages or anything else they read: a role can be led to report a change's security problem as pre-existing or as inference, and main can be led to run code a restriction covers, since a restriction is itself an instruction to main.
- Reviews and the final check run the repository's code on this machine, and main's and the roles' Git commands (`git status` before and after every call, the roles' reads, `git add`, commit and push) run the programs the repository's Git configuration, attributes and hooks select, including hooks in a tracked directory and the filters `git status` runs, whether or not a restriction is in force. That code can change anything you can, including your own Git configuration, other worktrees and Feather's own records.
- A restriction governs reviews and the final check, not implementation: executor and security-executor may run the repository's code while implementing, also while fixing someone else's change.
- Nothing in cc-feather asks before code runs; what remains is Claude Code's folder trust and your permission settings.
- An isolated environment you named stays available under a general restriction unless the restriction says otherwise; if it holds secrets, such as a CI runner, the code runs there.
- Ignored files, and files marked assume-unchanged or skip-worktree, are not part of the workspace check, so such a file can affect a review or the final check.
- Claude Code loads the project's `CLAUDE.md` and `.claude` settings, and runs the hooks in those settings, when a session starts in the project, so a repository can act before any review starts.
- Statements that stop execution last for the session and are lost when a context compaction loses them; a new session, including one that continues a handoff, starts without them.

See [ADR 0016](adr/0016-delegation-trusts-the-repository.md).

### Stop threshold

The Stop threshold is how many consecutive automatic calls without a pass stop a step of the automatic flow: one number from 2 to 10 for plan review, code review, outcome verification and Adversarial review alike, 2 by default. It bounds how long the flow keeps trying without you. Tell main a value for the current task or session, which writes nothing, or save one in project or user scope with the configuration tool's `review --stop-threshold` (see [Stop threshold](setup.md#stop-threshold)). Main never changes it on its own and states it and its source whenever a review decision comes up. How the value in effect is resolved, when it is unknown and what a change does are review state's Resolution, Unknown threshold, Changing it and Saved in this conversation; how a value is saved is the [setup Stop threshold procedure](../skills/setup/references/stop-threshold.md).

```text
/cc-feather:stop-threshold 4
/cc-feather:stop-threshold 4 project
/cc-feather:stop-threshold default user
```

`/cc-feather:stop-threshold` sets it, or asking main in your own words does the same. Without a scope (or with `session`) it applies to this session only and writes nothing; `project` or `user` saves it in an existing delegation installation of that scope, and it never installs delegation. A session choice does not carry into a new or resumed session and is not written into a handoff, and context compaction may drop it. See [the command](../skills/stop-threshold/SKILL.md).

Changing the Stop threshold never changes a count. A step whose count is below the new value can resume and one whose count reaches it stops, and main lists the steps that resumed or stopped. A higher value lets the flow keep trying longer without asking you, at the cost under Cost above, which grows faster than K.

### Delegation preview

```text
/cc-feather:delegation-preview docs/specs/my-feature.md
/cc-feather:delegation-preview TICKET-12 TICKET-13
/cc-feather:delegation-preview
```

Before implementing, see how main would split one or more plans or tickets, or a description of unplanned work: for each claim, every assignment and every part main keeps, with the role, model, effort and where each value comes from (task, session, saved or default), what can run in parallel, the review steps with when each stops, and flags for anything that would hold the work, such as a role that is not installed, an input that is not yet a plan or work that needs exploration first. For a named spec with unfinished tickets, the preview does not answer whether you mean the spec or its tickets: it shows both readings, or marks its counts as depending on your answer. Without an argument it previews the plan under discussion, and asks when there is none or several. What it shows and flags is the [preview procedure](../skills/delegation/references/preview.md)'s Output and Flags.

The preview is read-only: main produces it alone, dispatches no subagent, starts no review, uses no review budget and writes no file. It runs only through this command; asking in conversation does not trigger it. It shows the settings already in effect, including a session `auto-on`/`auto-off`; to try another model or effort, change it with `/cc-feather:model` and preview again. The preview guides dispatch only in the session that made it: when implementation follows there, main dispatches according to it and reports each difference with its reason. A preview from another session is a reference; dispatch there may differ from it without being reported. Model and effort values are configured, not confirmed at execution. The command ships with the plugin, so after a plugin update it needs only a fresh session, not a setup update. See [the preview procedure](../skills/delegation/references/preview.md).
